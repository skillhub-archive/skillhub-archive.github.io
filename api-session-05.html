A. From reading a contract to writing one

Sessions 3 and 4 kept arriving at the same sentence: the API’s documentation is the only authority. NASA reads only X-Api-Key because its documentation says so; jsonplaceholder pages with _page because its documentation says so. That documentation is a contract: a written promise, from the people who run a server to anyone who calls it, naming every URL, every method, every field and every status code. A good one lets a stranger who has never spoken to you write a client that works the first time.

Today you write one. The thing a contract describes is a resource: something the API lets people work with, a noun with fields. jsonplaceholder’s posts are a resource you have read since Session 1, each one an object with userId, id, title and body. The resource you design all session is simpler to picture and has no real version anywhere for you to copy:

Resource
Fields
What staff need to do with it
a library’s books
id, title, author, isbn, publishedYear
list them, look one up, add one, replace one’s details, remove one. No two books may share an isbn, the book-number printed on the back cover that identifies one edition.

Why design before anything exists? Because a contract is a promise, and the cheapest moment to change a promise is before anyone relies on it. While the contract is a page of notes, renaming a field costs you one edit. Once a stranger’s code reads that field, renaming it breaks their code, and section E is about exactly that. Designing first, sometimes called design-first, means you make every decision while it is still free.

The five sections after this one each settle one kind of decision, in the order you have to make them: what the URLs are (B), which method does what (C), which status code answers each outcome (D), how the contract is versioned (E), and how all of it is written down for a stranger (F). Then G puts it in Postman and H has you do the whole thing again, unassisted, for a second resource.

B. URLs that name things, not actions

Every API on this track has been designed in one style, and it is worth naming now that you are about to use it on purpose. REST is a way of designing an API in which the URL names a thing and the method says what to do with it. It is a set of conventions, not a standard with a rulebook, but most public APIs follow it closely enough that a developer who knows the conventions can guess your URLs before reading your contract. That guessability is the whole point. restfulapi.net is the free reference for these conventions, and this section follows it.

A REST API gives each resource two kinds of URL. A collection URL names every member of the resource at once, and an item URL names one member, by its id. jsonplaceholder shows both, plus two ways of reaching things that belong to something else:

four nouns, four answers · jsonplaceholder, verified live
> GET https://jsonplaceholder.typicode.com/posts
200 OK     the collection: an array of all 100 posts

> GET https://jsonplaceholder.typicode.com/posts/1
200 OK     one item: the post whose id is 1

> GET https://jsonplaceholder.typicode.com/posts/1/comments
200 OK     5 comments, ids 1 to 5: the comments that belong to post 1

> GET https://jsonplaceholder.typicode.com/comments?postId=1
200 OK     the same 5 comments, ids 1 to 5, reached by filtering instead

The third and fourth requests return identical data two different ways. /posts/1/comments is a nested URL: the slash reads as “belonging to”, so it says “the comments of post 1”. /comments?postId=1 is the whole comments collection, filtered by a query-string parameter, Session 1’s ?name=value pair. Both are common, and a contract is free to offer either or both. A useful way to choose: nest when the child only makes sense under its parent; filter when people will also want to search the child by other fields.

Not one of those URLs contains a verb. They name things; GET said “read it”. Now look at URLs written the other way round, with the action in the address. These are the shapes people reach for first, and jsonplaceholder has none of them:

action-shaped URLs · all four are 404 on jsonplaceholder
> GET https://jsonplaceholder.typicode.com/getPosts
404 Not Found
{}

> GET https://jsonplaceholder.typicode.com/getPost?id=1
404 Not Found
> POST https://jsonplaceholder.typicode.com/createPost
404 Not Found
> GET https://jsonplaceholder.typicode.com/posts/1/delete
404 Not Found

The 404s only show that this service never made those URLs. The real argument against them is what happens to an API that does. /getPosts says “get” twice, once in the method and once in the address. /createPost, /updatePost and /deletePost give one post three addresses, so the URL stops telling you which thing you are talking about. And the last one, a GET that deletes, is genuinely dangerous for a reason section C makes precise. The REST fix is always the same: the noun goes in the URL and the action goes in the method.

The rest of the naming conventions are smaller, and each one exists so that a stranger never has to guess:

  • Plural nouns for collections: /books, not /book, so /books/7 reads as “book 7 of the books”.
  • Lowercase, with hyphens between words: /book-loans, not /bookLoans or /book_loans. This one has a hard reason behind it. The URL standard, RFC 3986, treats the path as case-sensitive, so a server is entitled to treat /Books and /books as two different addresses. jsonplaceholder happens to forgive it, and answers /POSTS with all hundred posts, but a contract that is lowercase everywhere means nobody ever has to find out what yours does.
  • No trailing slash and no file extension: /books, not /books/ or /books.json. Session 2’s Content-Type already says what format the body is in.
  • Filtering, sorting and paging go in the query string, as in Session 4: /books?author=Tolkien&page=2. They change which members of the collection you get, not which resource you are talking about.

C. One method per operation, and what each method promises

Session 3 taught the methods that change things: PUT replaces the whole thing, PATCH changes part of it, DELETE removes it. Designing an API means pairing each operation a person needs with a method and a URL. For the books, using the two URL kinds from section B:

Method
URL
Operation
GET
/books
List the books.
POST
/books
Add a new book to the collection. The server decides its id.
GET
/books/{id}
Read one book.
PUT
/books/{id}
Replace one book’s details with a complete new set.
DELETE
/books/{id}
Remove one book.

The {id} is a placeholder, not something you type. Session 3 wrote stand-ins as <token>; in a contract, curly braces inside a path are the conventional way to write “an id goes here”, and OpenAPI, the most widely used format for machine-readable API contracts, writes them this way. A real request names a real book, /books/7. Notice that curly braces mean something different again in Postman, where {{page}} is a variable; a single pair is the contract’s placeholder, a double pair is Postman’s variable.

Method names are case-sensitive, and the standard ones are written in capitals. RFC 9110, the specification that defines HTTP’s methods and status codes, says “the method token is case-sensitive”, and that standard methods are uppercase by convention. Put the two together and get is simply not GET. Sent as a lowercase get, the same request for post 1 came back from jsonplaceholder as 400 Bad Request.

Two words from RFC 9110 explain why some pairings are right and others are traps. Each describes a promise a method makes:

  • Safe: a method is safe if it is read-only. The client “does not request, and does not expect, any state change on the origin server”, where the origin server is simply the server that holds the resource. GET is safe. POST, PUT, PATCH and DELETE are not.
  • Idempotent, pronounced eye-dem-POE-tent: a method is idempotent if sending the same request many times has the same effect on the server as sending it once. GET, PUT and DELETE are. Replacing book 7 with the same details twice leaves the same book 7; deleting it twice leaves it just as deleted. POST is not: sending “add this book” twice can add two books. PATCH is not guaranteed to be, because its own specification, RFC 5789, says it is “neither safe nor idempotent”, though a particular PATCH can be designed so that it is.

Now the danger in GET /posts/1/delete is precise. Software all over the internet relies on GET being safe. RFC 9110 says the distinction exists so that automated tools, such as the programs that crawl the web and the ones that fetch links ahead of time to make pages load faster, can work “without fear of causing harm”. A link-preview bot that fetches every URL pasted into a chat would delete the post just by looking at it. A GET must never change anything, so destroying something always gets a method that says so.

And the idempotent ones are why Session 4 said to “retry reads, always with backoff, and never retry writes”. Resending an idempotent request is harmless by definition, which is what makes a retry after a lost answer safe. Resending a POST is not, and making a retried POST safe is Session 8’s subject.

Two design decisions in that table are choices, not rules, and a contract must state them.

  • Create is POST to the collection because the server picks the id. HTTP also allows PUT /books/{id} to create a book at an id the client chose. That suits some designs, but here the library assigns ids, so PUT only ever replaces a book that already exists, and a PUT to an id that does not exist is refused (section D says how).
  • There is no PATCH in version 1. Leaving an operation out is a legitimate decision, and keeping the first version small is a good habit: an operation you add later breaks nobody, while one you ship and then withdraw breaks everyone who used it. What matters is that the contract says it is not supported, and section D shows the status code that says it on the wire.

D. A status code for every outcome, including no

Session 1 taught you to read the status line first. A contract decides what that line will say, for every outcome of every operation. Start with the outcomes where everything works, because RFC 9110 is specific about most of them:

Code
For
What RFC 9110 says, and what this contract chooses
200
GET a list or one book
OK, with the book or books in the body.
201
POST, a book was added
Created. The server “SHOULD send a 201 (Created) response containing a Location header field” identifying the new thing. SHOULD is a word specifications use with care: it means do this unless you have a good reason not to.
200
PUT, a book was replaced
The RFC allows 200 or 204. This contract picks 200 with the stored book in the body, so the client sees exactly what was saved.
204
DELETE, a book was removed
The RFC allows 204, 200 with a description, or 202 if the deletion will happen later. This contract picks 204 No Content, Session 3’s “done, and there is deliberately nothing to tell you”.

Location is the header Session 2 met on a redirect, where it said “go here instead”. On a 201 it says where the new thing now lives, so the client can go and read it without being told its id any other way. jsonplaceholder does exactly what the RFC asks:

a textbook create · jsonplaceholder, verified live
> POST https://jsonplaceholder.typicode.com/posts
> body: { "title": "x", "body": "y", "userId": 1 }
201 Created
location: https://jsonplaceholder.typicode.com/posts/101

{ "title": "x", "body": "y", "userId": 1, "id": 101 }

Its location is a complete URL. Session 2 showed that a Location may also be just a path, and this contract uses the path form, Location: /v1/books/8, so it reads the same whatever address the API is eventually served from. (The /v1 is section E’s.)

Now the outcomes where the answer is no, which is where a contract earns its keep. A client that only ever gets success codes has nothing to code against when things go wrong. These are the refusals the books contract promises:

Code
Name
When this contract sends it
400
Bad Request
The body cannot be read at all: it is not valid JSON. Session 4 met 400 as a request the server “could not make sense of”.
422
Unprocessable Content
The body is valid JSON but breaks one of the contract’s rules: no title, an isbn that is not 13 digits. RFC 9110: the syntax “is correct, but it was unable to process the contained instructions”.
404
Not Found
No book has that id, Session 1’s “nothing at that URL”.
409
Conflict
The request clashes with what is already stored: the isbn belongs to another book. RFC 9110: a conflict “with the current state of the target resource” that the user “might be able to resolve”.
405
Method Not Allowed
The method exists but this URL does not support it: a PATCH, in version 1. RFC 9110 says a 405 MUST carry an Allow header listing the methods that are supported, such as Allow: GET, PUT, DELETE.

Be clear which of those are rules and which are conventions. The Allow header on a 405 is a rule; the RFC says MUST. Using 409 for a duplicate isbn is a widespread convention rather than a rule. And the split between 400 and 422 is this contract’s choice: plenty of real APIs answer 400 for both. The split is worth making because the client fixes the two differently: a 400 means “your code is building broken JSON”, a 422 means “your JSON is fine, one value in it is not”. Where the specification leaves a choice, the contract’s job is to make it and write it down, so nobody has to guess which one you meant.

Every refusal also gets a body, and always the same shape. RFC 9110 says a 409 SHOULD include “enough information for a user to recognize the source of the conflict”, and a client is far easier to write if every error looks alike. This contract uses one small shape for all of them, and a 422 adds one more key, field, naming the field at fault:

the error shape, a design · the same shape on every refusal
409 Conflict
Content-Type: application/json

{ "error": { "code": "isbn_taken", "message": "A book with this isbn already exists." } }

code is a fixed word a program can check; message is a sentence for a person. There is a published standard shape for error bodies, called problem details (RFC 9457), and many APIs invent their own instead. Either is fine, as long as the contract names it.

Now see what an API with no contract for “no” looks like. jsonplaceholder is a practice service, so it was never built to refuse anything, and that makes it the clearest possible picture of what section D is for. Each of these deserved a refusal:

a server that never says no · jsonplaceholder, verified live
> POST https://jsonplaceholder.typicode.com/posts
> body: {}
201 Created                                an empty post, "created"
{ "id": 101 }

> POST https://jsonplaceholder.typicode.com/posts
> body: {"title": oops}
500 Internal Server Error                  not valid JSON, and the server crashed on it
SyntaxError: Unexpected token 'o', "{"title": oops}" is not valid JSON
    at JSON.parse (<anonymous>) ...

> PUT https://jsonplaceholder.typicode.com/posts/101
> body: { "title": "x" }
500 Internal Server Error                  post 101 does not exist
TypeError: Cannot read properties of undefined (reading 'id') ...

> DELETE https://jsonplaceholder.typicode.com/posts/101
200 OK                                     a "successful" delete of nothing
{}

An empty post accepted as created. Two crashes, each pasting the server’s own internals into the response. A deletion of something that was never there, reported as success. None of this is a fault in a practice service, which exists to accept anything. It is what any API looks like when nobody decided in advance what it should refuse, and a client built against it learns nothing about failure until failure happens in production. Under the books contract those four would be 422, 400, 404 and 404.

One more thing the status codes show: idempotent does not mean identical responses. Delete book 8 under the books contract, then send the same request again:

the same DELETE twice, a design · idempotent, and two different status codes
> DELETE /v1/books/8
204 No Content

> DELETE /v1/books/8
404 Not Found
{ "error": { "code": "book_not_found", "message": "No book has the id 8." } }

Different answers, and DELETE is still idempotent, because idempotency is about the effect on the server: after one request or two, book 8 is gone. RFC 9110 says this directly: repeating the request has the same intended effect, “though the response might differ”.

E. Versioning, before anyone depends on it

Once a stranger’s code relies on your contract, some changes become impossible to make quietly. A breaking change is one that can stop a client that worked yesterday from working today, without the client changing anything. A non-breaking change is one that every existing client survives. Sorting changes into the two is the core skill of this section:

Breaking
Why it breaks someone
Rename or remove a field
A client reading author finds nothing there.
Change a field’s type
publishedYear going from the number 1965 to the text "1965" breaks any client doing arithmetic with it.
Make an optional request field required
Every client that never sent it now gets a 422.
Change a URL, or a status code a client checks
A client waiting for 201 does not know what to make of 200.
Non-breaking
Why it is safe
Add a new optional field to responses
A client that has never heard of pages simply does not read it, provided clients ignore fields they do not recognise, which the contract should say they must.
Add a new operation or a new resource
Nobody was calling it, so nobody is affected.
Add a new optional request field or filter
Clients that never send it get exactly what they got before.

That “ignore what you do not recognise” condition is doing real work. Adding a field is only safe if clients were written to skip fields they do not know, so a good contract tells them to, in writing. A non-breaking change is a convention both sides agree to, not a law of nature.

When a breaking change is unavoidable, it goes into a new version, published beside the old one, and the old one keeps running until its clients have moved. That only works if the contract carried a version label from the very first day, which is why you choose one now, while it costs nothing. restfulapi.net lists three places to put it:

in the URL pathGET /v1/books
in a request headerAccept-Version: v1  or  X-API-Version: 1
in the Accept headerAccept: application/vnd.example.v1+json

The last one uses Session 2’s Accept header to ask for a particular version of the format. All three work, and restfulapi.net does not crown one, though it calls the path form the most straightforward and most commonly used. The books contract puts it in the path, for two reasons you can check: every URL then shows its version, in logs and in pasted links alike, so nobody wonders which one a request used; and Session 6’s Mock Server matches requests by their path and, by default, ignores their headers, so a version in the path is a version the mock can always see.

“Before anyone depends on it” also covers decisions that look optional. Take paging. If version 1 returns every book in one response, and later the collection grows and you start paging it, every client that assumed one response held everything now silently gets only page 1, exactly Session 4’s mistyped-variable trap, inflicted on someone else. So the books contract pages from day one, even though a small library could manage without it.

F. The contract, written for a stranger

Here is every decision from sections B to E, written down as the books API contract, version 1. Read it as the stranger would: someone who will build a client from this page alone and cannot ask you a single question. The isbn values on this page are made up for the example.

Shared rules, which apply to every operation below:

  • Every URL starts with /v1. Request and response bodies are JSON, sent with Content-Type: application/json.
  • Any request with a body may be refused with 400 invalid_json if the body is not valid JSON, or 422 if it breaks a rule in the field table. A query parameter that breaks its rule is also 422.
  • On a request to /v1/books/{id}, the id is checked first: if no book has it, the answer is 404 whatever the body says.
  • Every refusal has the body { "error": { "code": ..., "message": ... } }; a 422 adds "field", naming the field at fault.
  • Clients must ignore response fields they do not recognise, so that new optional fields can be added within v1.

The field table. A book, as the API sends and receives it:

Field
Type
Rules
id
integer
Set by the server when the book is added. Never sent by the client; ignored if it is.
title
string
Required. 1 to 200 characters.
author
string
Required. 1 to 200 characters.
isbn
string
Required. Exactly 13 digits. No two books may share one.
publishedYear
integer
Optional. Leave it out if unknown.

A string is text, written in quotes in JSON; an integer is a whole number, written without quotes. isbn is a string even though it is all digits, because it is an identifier, not a quantity: nobody does arithmetic with it.

The operations, each with every status it can answer:

The stranger test. A contract is finished when someone could implement either side of it, the server or a client, without asking you anything. That means it names, for every field, the name, type, whether it is required, who sets it and its rules; and, for every operation, the method, the URL, the request body, and every status it can answer, with that status’s body. If you have to explain something out loud, it belongs on the page.

G. The contract in Postman, as saved examples

A contract on a web page is readable by a person. Postman can hold the same contract in a form a person can read and a tool can act on, and it does it with something you have not used yet: the saved example.

A saved example is a request paired with the response it should get. On the request side it holds the method, URL, parameters, headers and body; on the response side, the status code, headers and body. Usually you make one by sending a request and saving what came back. You can also write one yourself, both halves, without sending anything, which Postman’s documentation calls adding a custom example. That is what designing first means in Postman: there is no server to send to, so you write down what the server will answer.

Why put the contract here rather than leave it as notes? Because Session 6’s Mock Server is built from exactly these examples. When a request reaches a mock, Postman compares its method, then its path and query string, against your saved examples, and answers with the one that fits best. Every example you write today is one answer the mock will be able to give. A contract kept as notes would have to be typed in again.

Your collection syncs to Postman’s servers, as Session 4’s section G explained. Today that is harmless, because a books API about made-up books holds nothing private. It matters for the review activity at the end of the session, if you model something from your own job: keep real customer or company data out of a synced workspace. Invented values are the right choice for a contract anyway.

Step 1, a collection and a stand-in address. One word, two meanings, so to be clear: a Postman collection is Session 4’s saved group of requests, a folder in Postman, and has nothing to do with the REST collection /books from section B. Signed in, create a new Postman collection called Books API v1. Then give the collection a variable called baseUrl with the value https://api.example.com; Postman puts a collection’s variables on a tab of their own, so look for the word “Variables” when the collection is open. example.com is a name reserved for documentation, so nothing real will ever answer there. H. The milestone: a second resource, unassisted

The milestone is to model a small resource and write a contract for it that names every field and status code. You have watched it done once for books. Now do it yourself for a resource you have not seen modelled, from a brief like the ones a real team writes.

Your turn The milestone: a members API, from a blank page

The brief. The same library now wants to keep track of its members. A member has a name and an email address, and may have a phone number. No two members may share an email address. The library assigns member numbers. Staff need to list the members, look one up, sign one up, replace a member’s details, and remove a member.

Do not scroll back up. Write, on paper or in a text file:

  1. The URLs: the collection and the item.
  2. The operations table: a method and URL for each thing staff need, and every status each one can answer, refusals included.
  3. The field table: every field, its type, whether it is required, who sets it, and its rules.
  4. The error shape, plus the full response for signing up a member whose email is already taken.
  5. The version label, and where it goes.
  6. Then create a second collection, Members API v1, and put your contract in its description. Adding examples is optional today.
