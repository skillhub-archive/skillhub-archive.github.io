A. The lost answer: why a retry can create something twice

Every request you send can end three ways: an answer comes back, an error comes back, or nothing comes back at all. The third is the dangerous one, and it is worth slowing down on. Say the library’s desk app sends POST /v1/loans to lend book 8 to member 31, and waits, and no answer arrives. From the desk app’s side there is just silence. From the server’s side, any of three things may have happened:

1
It never arrived. The connection broke on the way. No loan exists.
2
It arrived and worked, and the answer was lost. Loan 501 exists. The 201 never made it back.
3
It arrived and is still working. Loan 501 is being made right now, slowly.

The desk app cannot tell these apart, because silence looks the same in all three. So it has two choices, and both are bad. If it gives up, the member in case 1 leaves without a book that the system says they never borrowed. If it sends the same POST again, the member in cases 2 and 3 now has two loans for one book:

a blind retry after a lost answer · an illustration of a real server
> POST /v1/loans  {"bookId": 8, "memberId": 31}     10:00:00
  the server makes loan 501; the 201 is lost on the way back
> POST /v1/loans  {"bookId": 8, "memberId": 31}     10:00:12, a retry
201 Created
Location: /v1/loans/502                         a second loan for the same book

Session 5 named the reason: POST is not idempotent. Sending it twice can have twice the effect, where a PUT or a DELETE sent twice leaves things just as one would. RFC 9110 turns that into a rule for clients: “A client SHOULD NOT automatically retry a request with a non-idempotent method unless it has some means to know that the request semantics are actually idempotent, regardless of the method, or some means to detect that the original request was never applied.” That is Session 4’s “never retry a write”, and its last clause is the way out. Give the server a means to recognise a retry, and a retried write becomes safe. That means is the subject of the next two sections.

B. The idempotency key: the client’s half

An idempotency key is a value the client makes up and sends with a write, so that the server can recognise the same request arriving again. The proposed standard for it, an IETF draft called “The Idempotency-Key HTTP Header Field”, defines it as “a unique value generated by the client which the resource uses to recognize subsequent retries of the same request”, carried in a request header named Idempotency-Key. It is still a draft: version 7, from October 2025, has expired without becoming an RFC. But real APIs, Stripe’s among them, already use the same header, and it is the pattern you will meet.

The whole pattern is in one sentence: one key per operation, not per attempt. The client makes the key once, before the first attempt, for “lend book 8 to member 31, this time”. It sends that key with the first attempt and the very same key with every retry of it. A different operation, even lending the same book again next month, gets a new key. If every attempt carries a fresh key, the server sees strangers, and you are back in section A.

What a key looks like. The draft says it is “RECOMMENDED that a UUID [RFC4122] or a similar random identifier be used”, and Stripe suggests the same. A UUID (universally unique identifier) is 128 bits, nearly all of them random, written as 32 hex digits, the digits 0 to 9 and the letters a to f from Session 7, in five groups joined by hyphens:

this session’s practice key · a version 4 UUID, the random kind
Idempotency-Key: 7c4f2a9e-3b1d-4e8a-9f60-2d5c8b1a4e73

Random is what makes it work: two clients making keys at the same moment will, in practice, never make the same one, so nobody has to hand them out. One detail varies between APIs. The draft writes the value in double quotes, "8e03978e-...", while Stripe’s own example sends it bare. Follow the documentation of the API you are calling; the library’s contract sends it bare, as above.

Now the trap, which catches people in Postman specifically. Postman has dynamic variables: built-in names that start with a $, whose values, in its documentation’s words, “are generated when the request runs”. One of them, {{$guid}}, is listed as “A uuid-v4 style guid” (GUID is another name for a UUID). It looks perfect for a key, and it is exactly wrong for one, because it makes a new value on every send. postman-echo shows you, since it echoes your headers back:

the same request sent twice, a key from {{$guid}} and a key from a variable · captured live with newman, Postman’s command-line runner
> POST https://postman-echo.com/post
> Idempotency-Key: {{$guid}}                       sent twice
"idempotency-key": "88ab6e25-ce76-4ef6-bf5a-709c85341c68"
"idempotency-key": "f16a2990-f648-4ad7-8be3-e3278017d546"   a stranger

> Idempotency-Key: {{loanKey}}                      sent twice
"idempotency-key": "7c4f2a9e-3b1d-4e8a-9f60-2d5c8b1a4e73"
"idempotency-key": "7c4f2a9e-3b1d-4e8a-9f60-2d5c8b1a4e73"   the same operation

The second form is right: the key is made once, kept in a collection variable, and every send of that operation reads the same value. echo prints header names in lower case, which, as Session 2 showed, changes nothing.

C. The server’s half: a memory of keys

A key only helps if the server remembers it. A server that honours keys keeps a table of every key it has seen. For each one it keeps a fingerprint of the request body, a hash of it, the idea from Session 7, so it can tell whether a retry really is the same request; a state, in progress or done; and, once done, the answer it gave. The draft’s rules come down to five cases, and Stripe’s documentation describes the same remembering, though it names no status codes for the refusals and never requires a key:

The key is
The server
Answers
new
records it as in progress, does the work, stores the answer against it
the normal answer: 201 with loan 501
seen, done, same body
does not do the work again; looks up the stored answer
the stored answer again, the same 201 with loan 501
seen, still in progress
does nothing; the first attempt is still working
409 Conflict: try again shortly
seen, different body
does nothing; this is a client bug, one key on two operations
422 Unprocessable Content
missing, where required
does nothing
400 Bad Request

The second row is the point of everything. In the draft’s words, for a retry after the first attempt completed, the server “SHOULD respond with the result of the previously completed operation, success or an error”. Stripe’s documentation says it saves “the resulting status code and body of the first request made for any given idempotency key, regardless of whether it succeeds or fails”, so a retry gets the same result, “including 500 errors”. A retry is answered from memory, never by doing the work twice. The two refusals are Session 5’s codes in a new job. 422 was a body that is valid JSON but breaks a rule, and a key reused for a different body breaks the key’s one rule. 409 was a conflict with the state of the server, and a first attempt still running is exactly that.

Two more promises belong in a contract, because a client cannot guess them. How long keys are remembered: the draft says the server “SHOULD define such expiration policy and publish it in the documentation”, and Stripe’s says keys can be removed “after they’re at least 24 hours old”. The library remembers them for 24 hours, so a retry later than that is a new request. And whether a failure was stored: the library’s 503 means it never started, so nothing was stored and a retry with the same key will do the work. Finally, the library adds a header to a replayed answer, Idempotent-Replayed: true, so a client can tell “made just now” from “made earlier, here it is again”. That header is the library’s own choice; the draft does not define one.

What a mock can and cannot do with this. The server’s whole job here is remembering, and Session 6 showed that a mock stores nothing. So a mock can show the contract of a key, every answer a client must be ready for, and it can never show the remembering. On the lending mock built for this session, a loan request that carried a perfectly good key, with no example asked for, came back 400 with idempotency_key_missing, three times running. The mock never reads the key: five of the six loan examples share one body, none is a 200, and the tie went the way Session 6 section D said ties go. So in this session every loan request asks for its answer by name, and you play the memory, on paper.

D. The receiver’s half: remembering events

Session 7’s webhook receiver has the same problem from the other side. A sender retries, so a receiver gets duplicates, and Session 7 gave every delivery attempt of one event the same id. That id is an idempotency key the sender chose for you. So the receiver keeps the same kind of memory, a table of processed event ids, and before acting on a delivery it checks the table.

One thing is different, and it is easy to get wrong. A client calling the loans API wants the stored answer back, so the server replays it. A sender only wants to know whether to stop retrying. So a receiver answers a duplicate with a 2xx, and does nothing else. Answering 409 or 422 would count as a failed attempt, which Session 7’s contract says is retried, so the sender would keep sending the very event the receiver is trying to ignore. Put together with Session 7’s order, a receiver handles a delivery like this:

1
Verify the signature on the raw body and the timestamp, as in Session 7. A failure is 401, and nothing is recorded.
2
Look the event’s id up in the processed table. Already there: answer 200 and stop.
3
Not there: store the event and record its id, in one step that refuses an id already present, so two attempts arriving together cannot both get in.
4
Answer 200, then do the slow work, as Session 7 advised.

Step 3’s “one step” matters because a receiver can be busy with two attempts at once, if its first attempt stalls for over a minute and the retry arrives. Check first, then add the id as a separate step, and both can slip through:

check, then add, as two steps · an illustration
a1  checks: evt_1001 not in the table
a2  checks: evt_1001 not in the table     a1 has not added it yet
a1  adds evt_1001, acts, answers 200
a2  adds evt_1001, acts, answers 200      acted on twice

Done as one step that refuses an id already present, the second attempt is refused at the moment it tries to record, and only one gets in. Databases offer exactly this, a rule that a column’s values must be unique; how to set one up belongs to whoever builds the receiver, and the contract’s job is to say it is needed.

How long to remember. At least as long as the sender keeps retrying. The library’s last attempt comes an hour after its first, so an hour is the bare minimum; receivers usually keep ids for days, because remembering a short string is cheap and forgetting too early brings the double-count back.

Now watch the duplicate get made. Session 7 said a slow receiver causes retries. A mock can show you that moment for real, because Postman lets a mock wait before it answers. When you edit a mock’s configuration there is a setting, Simulate a fixed network delay, whose choices are No delay, 3G (100 ms), 2G (300 ms) and Custom, in milliseconds. A delay longer than the sender waits turns your receiver mock into a slow receiver. On Postman’s web app, this is what the sender saw:

E. Chaining calls into one workflow

Real integrations rarely make one call. Lending a book from the desk app is four, and each later call needs something an earlier one answered. A sequence like this is a workflow:

Call
Does
Needs, and gives
1 Read the member
GET /v1/members/31, a read
gives: the member exists and is active
2 Read the book
GET /v1/books/8, a read
gives: the book exists
3 Lend the book
POST /v1/loans, a write, with a key
needs: 1 and 2 to have passed; gives: the loan’s id
4 Notify the member
POST /v1/notifications, a write
needs: the loan’s id from 3

Session 4’s Collection Runner sends a collection’s requests in order, which is half a workflow. The other half is carrying a value from one answer into a later request, and that takes a post-response script: the JavaScript Postman runs after a response arrives, which Session 4 used for its status check. Three pieces of it are all you need today, each one line:

  • pm.response.code is the status code of the answer, as a number, such as 201.
  • pm.response.json().id reads the answer’s body as JSON and takes its id field, the way you would read "id": 501 by eye.
  • pm.collectionVariables.set("loanId", ...) stores a value in the collection variable loanId, so a later request can write {{loanId}}, exactly as it reads {{baseUrl}}.

On call 3, that becomes the script below, which keeps the loan’s id for call 4. Three more pieces of JavaScript hold it together. if (test) { ... } runs the lines inside the braces only when the test is true, and skips them otherwise. === asks “is exactly equal to”; a single = would set a value instead. And a line starting // is a note for people, which Postman ignores:

// Lend the book, post-response: keep the new loan's id for call 4
if (pm.response.code === 201) {
  pm.collectionVariables.set("loanId", pm.response.json().id);
}

Call 4’s body then reads {"memberId": 31, "loanId": {{loanId}}, "template": "loan.created"}. {{loanId}} has no quotes round it, because the loan’s id is a number, and Postman puts the value in before it sends. To choose call 3’s answer on a mock, its x-mock-response-name header reads {{loanAnswer}}, a collection variable, so you can change the mock’s answer for a whole run in one place. On a real server you would leave that header out.

F. When call three of four fails

Now make call 3 fail: set loanAnswer to 503 unavailable and run again. Session 4 taught that a 503 is worth retrying after a wait. But look first at what the Runner did:

a run where call 3 answers 503 · captured live with newman, Postman’s command-line runner
1 Read the member     200
2 Read the book       200
3 Lend the book       503    No loan was made.
4 Notify the member   sent anyway
  if loanId still holds 501 from the last run:
    201 sent                a notice about a loan this run never made
  if loanId holds nothing:
    400 badRequest          the body is no longer valid JSON

A failed request does not stop a run. The Runner sends every request in the collection, so call 4 went out about a loan that does not exist: either it told member 31 about the last run’s loan, which is worse than an error because nothing looks wrong, or it sent a broken body. Which of the two you see depends on what loanId holds when the run starts. This is a partial failure: some calls of a workflow happened, some did not, and the ones after the failure acted on a state that was never reached. The fix in the run is to stop on the first answer you cannot continue past. Session 4’s optional cursor script used pm.execution.setNextRequest to choose the request the Runner sends next; giving it null, which means “no request”, ends the run. And if gets a partner: else { ... }, straight after the if’s braces, runs its lines only when the test was false:

// Lend the book, post-response, replacing the script from section E
if (pm.response.code === 201) {
  // the loan exists: keep its id for the next call
  pm.collectionVariables.set("loanId", pm.response.json().id);
} else {
  // no confirmed loan: stop, so nothing is sent about a loan that may not exist
  pm.execution.setNextRequest(null);
}

With that in place, the same run sends three requests and stops. Calls 1 and 2 need the same guard, or a member who does not exist still gets a loan. Their success is a 200, and !== asks “is not exactly equal to”:

// Read the member and Read the book, post-response
// anything but 200: stop the run here, nothing after this is sent
if (pm.response.code !== 200) {
  pm.execution.setNextRequest(null);
}

That is the run fixed: it stops at the first call it cannot continue past. Designing for partial failure is the bigger job: for every call in a workflow, decide in advance what a failure means. Four questions do it:

  • Did it change anything? Calls 1 and 2 are reads, so a failure there leaves nothing behind: stop, and start again later.
  • If it failed, do we know whether it changed something? The library’s 503 says “No loan was made”: known. No answer at all, section A’s silence, is unknown.
  • Is it safe to send again? For call 3, yes in both cases, because it carries a key: if the loan was made, the retry gets it back from memory; if not, the retry makes it. Without a key, the unknown case has no safe move. This is the pattern Session 4 promised, the one that makes a retried write safe.
  • What about the calls that already worked? If call 4 fails after call 3 made the loan, there are two honest ways forward. Retry forward: send the notice again later, because the loan is what matters and a late notice is fine. Or compensate: undo the earlier write with a request of its own, such as cancelling loan 501, which is called a compensating action. Nothing undoes a write for you; if undoing is the plan, the API needs a way to do it, and the workflow has to call it.

Three habits fall out of those questions. Put the reads first, so most failures happen before anything is written. Give every write its own key, made once for that run. And keep how far a run got, the key and the loan’s id, so that running it again resumes with the same key instead of starting a new operation.

G. Tracing a retry end to end, on paper

Everything in this session can go wrong at a moment no test happens to hit. A trace is how you find those moments before anyone builds anything: you walk one scenario through every party, one row per moment, and at the end you count what exists. It needs no tools, and it is how a double-charge gets caught at a whiteboard instead of in a customer’s bank statement. A trace has five columns:

Column
Holds
Why
time
when, to the second where it matters
timeouts and retry schedules are about time
sent
who sends what, with its key or event id
a key that changes between rows is a bug you can see
receiving side
what it does, and its memory afterwards
the memory is what makes a retry safe
answer
what comes back, or “nothing”
every “nothing” is a place a retry starts
sender knows
