$enc = New-Object System.Text.UTF8Encoding($false)
function Add-LabFile($rel, $lines, $when) {
  $path = Join-Path $lab $rel
  $dir = Split-Path $path -Parent
  if (-not (Test-Path $dir)) { New-Item -ItemType Directory -Path $dir | Out-Null }

  [System.IO.File]::WriteAllText($path, $text, $enc)
  (Get-Item $path).LastWriteTime = [datetime]$when
}

A. A function: a command of your own

A function is a block of code with a name. You make it once, then run it whenever you like by typing its name, exactly like a cmdlet. The form is function NAME { CODE }: the word function, the name you choose, then the code in braces, a script block as in Session 2. NAME and CODE in capitals are placeholders for your own. Making a function prints nothing; it only remembers the code under that name.

A function is usually several lines long. Type its first line, ending in {, and press Enter: PowerShell sees the command is not finished and shows >>, as it did in Session 2 after a |, waiting for the rest. Type each line and press Enter after it. When you type the closing } and press Enter, the function is made. Indenting the lines inside the braces by two spaces is not needed, but it shows at a glance where the function ends. Here is a function that outputs the open tickets, and three ways to use it:

make a function, then run it · captured live
PS C:\Users\you\ps-lab> function Get-OpenTicket {
>>   Import-Csv "$HOME/ps-lab/data/tickets.csv" | Where-Object State -eq 'open'
>> }
PS C:\Users\you\ps-lab> Get-OpenTicket | Select-Object TicketId, Customer, Priority

TicketId Customer Priority
-------- -------- --------
T-103    Gus Lind high
T-104    Ana Ruiz medium
T-105    Eli Moss low

PS C:\Users\you\ps-lab> $open = Get-OpenTicket
PS C:\Users\you\ps-lab> $open.Count
3
PS C:\Users\you\ps-lab> get-openticket | Select-Object -ExpandProperty Customer
Gus Lind
Ana Ruiz
Eli Moss

Whatever a function outputs goes down the pipe like any command’s output, or into a variable, as in Session 5. Its name, like a cmdlet’s, can be typed in any case. Inside it, the path is built from $HOME, for Session 5’s reason: a relative path is found from the folder you are in, so a full path works from anywhere.

Name it Verb-Noun, like every cmdlet (Session 1). PowerShell keeps a list of approved verbs, the ones its own commands use, and Get-Verb shows it; give it verbs to check them. Choosing from the list makes your command read like the rest: Get fetches, Show displays. A noun is usually singular, such as Ticket. Shout is not on the list:

is a verb approved? · captured live
PS C:\Users\you\ps-lab> Get-Verb Get, Show, Shout | Select-Object Verb, Group

Verb Group
---- -----
Get  Common
Show Common

A function with an unapproved verb still works, and typed at the prompt it gets no warning. The warning comes when a command with one arrives as part of a module, a package of commands, which is Session 9. A function lives in this window only, like a variable: close the window and it is gone. Typing function again with the same name replaces it, without asking.

B. Parameters: param() and types

Get-OpenTicket always does the same thing. A parameter lets whoever runs the function hand it a value, just as -Path and -Filter hand values to Get-ChildItem. You list a function’s parameters in a param() block, which must be the first thing inside the braces (only help and [CmdletBinding()], both later today, may come before it). Each parameter is a variable, such as $Status, and the type in square brackets in front of it, [string] here, is the same type name Session 5 used with -is. Inside the function, use the parameter like any variable. The value someone gives it when they run the function is called an argument.

a function with a parameter · captured live
PS C:\Users\you\ps-lab> function Get-Order {
>>   param([string]$Status)
>>   Import-Csv "$HOME/ps-lab/data/orders.csv" | Where-Object Status -eq $Status
>> }
PS C:\Users\you\ps-lab> Get-Order -Status pending | Select-Object OrderId, Customer, Total

OrderId Customer Total
------- -------- -----
5006    Ana Ruiz 29.00
5008    Gus Lind 82.00

PS C:\Users\you\ps-lab> Get-Order refunded | Select-Object OrderId, Customer, Total

OrderId Customer   Total
------- --------   -----
5004    Dara Singh 34.00

PS C:\Users\you\ps-lab> Get-Order

The parameter’s name becomes the function’s -Status. The second run leaves the name out: an argument with no name is positional, and fills the parameters in the order param() lists them, first to first, second to second. The third run gives no argument at all. $Status then holds nothing, no order’s Status equals nothing, and nothing prints, with no error. Section C fixes that.

Read your own SYNTAX. Get-Command NAME -Syntax prints just the SYNTAX line of any command, yours included, and Session 1’s table reads it. Whole thing in brackets: you can leave it out. Name in brackets: you can leave the name out, so it is positional.

your function’s SYNTAX · captured live
PS C:\Users\you\ps-lab> Get-Command Get-Order -Syntax

Get-Order [[-Status] <string>]

Why a type. When the function runs, PowerShell converts each argument to its parameter’s type before any of your code runs, the way Session 4’s [int] converted text, and it rounds the same way. A value it cannot convert stops the function with an error that names the parameter, so a mistake is caught at the door instead of quietly giving a wrong answer. Here [int]$Over is a whole number, and the filter is Session 2’s script block, comparing each Total, converted as in Session 4:

a whole-number parameter · captured live
PS C:\Users\you\ps-lab> function Get-BigOrder {
>>   param([int]$Over)
>>   Import-Csv "$HOME/ps-lab/data/orders.csv" | Where-Object { [double]$_.Total -gt $Over }
>> }
PS C:\Users\you\ps-lab> Get-BigOrder -Over 50 | Select-Object OrderId, Customer, Total

OrderId Customer   Total
------- --------   -----
5002    Ben Okafor 58.00
5008    Gus Lind   82.00

Get-BigOrder: Cannot process argument transformation on parameter 'Over'.    one line, wrapped here
Cannot convert value "fifty" to type "System.Int32". Error: "The input       one line, wrapped here
string 'fifty' was not in a correct format."

Read the error from the start: argument transformation is the conversion, and System.Int32 is Session 5’s Int32, the type [int] makes. The SYNTAX now says <int>, one of Session 1’s kinds of whole number, so anyone reading it knows to give a number.

C. Defaults, switches, and parameters you must give

A default is the value a parameter takes when nobody gives one: write = VALUE after it in param(). Now Get-Order on its own means the pending orders. A default that is a path is built from $HOME, so it works from any folder. SYNTAX does not show defaults; section G shows where they appear.

------- --------

A switch. Session 1’s table said a parameter in SYNTAX with no angle brackets after it, such as [-Recurse], is a switch: it takes no value, it is either there or not. Make one with the type [switch]. Inside the function, the switch is True when the caller added it, so an if from Session 5 can test it:

a switch · captured live
PS C:\Users\you\ps-lab> function Get-ShopName {
>>   param([switch]$Full)
>>   if ($Full) { 'Fernhill Goods Ltd' } else { 'Fernhill' }
>> }
PS C:\Users\you\ps-lab> Get-ShopName

PS C:\Users\you\ps-lab> Get-ShopName -Full
Fernhill Goods Ltd
PS C:\Users\you\ps-lab> Get-Command Get-ShopName -Syntax

Get-ShopName [-Full]

A value that must be given. Some values have no sensible default, such as a person’s name. Write [Parameter(Mandatory)] just before the parameter’s type, and the function cannot run without it. Run at the prompt without one, PowerShell asks for it: type the value after Name: and press Enter. Press Enter with nothing typed, and it stops with an error instead. In the transcript, the value typed at the question is in olive:

Read the SYNTAX with Session 1’s table: only the name is in brackets, [-Name] <string>, so the value is required and the name is optional. (The [<CommonParameters>] on the end is section D.) A program that runs PowerShell with nobody there to answer, such as pwsh -NonInteractive, cannot ask: on this workbook’s computer that run stopped with Cannot process command because of one or more missing mandatory parameters: Name. and carried on to its next line. So which to use? A default whenever there is a sensible one, so the command runs with nothing typed; Mandatory only when no one but the caller can know the value.

D. Messages and output: [CmdletBinding()], -Verbose, Write-Host and return

Every cmdlet takes a set of extra parameters that SYNTAX does not list one by one; it shows them as [<CommonParameters>]. They are the common parameters: -Verbose is one, and -ErrorAction, which Session 7 uses, is another. Your function gets them when you write [CmdletBinding()] on the line just before param(). That makes it an advanced function, one that behaves like a cmdlet. A [Parameter()] line does the same, which is why Get-Greeting’s SYNTAX already showed them.

With the common parameters comes Write-Verbose "TEXT", which prints TEXT with VERBOSE: in front, but only when the caller adds -Verbose. Use it for messages about what the function is doing: they stay out of the way until someone asks to see them.

an advanced function, quiet, then with -Verbose · captured live
PS C:\Users\you\ps-lab> function Get-OrderCount {
>>   [CmdletBinding()]
>>   param([string]$Status = 'pending')
>>   Write-Verbose "Counting $Status orders"
>>   $rows = Import-Csv "$HOME/ps-lab/data/orders.csv" | Where-Object Status -eq $Status
>>   $rows.Count
>> }
PS C:\Users\you\ps-lab> Get-OrderCount
2
PS C:\Users\you\ps-lab> Get-OrderCount -Verbose
VERBOSE: Counting pending orders
2
PS C:\Users\you\ps-lab> Get-OrderCount -Status shipped -Verbose
VERBOSE: Counting shipped orders
5
PS C:\Users\you\ps-lab> Get-Command Get-OrderCount -Syntax

Get-OrderCount [[-Status] <string>] [<CommonParameters>]

The trap: no [CmdletBinding()], no message, and no error. Here is the same function without that line. -Verbose is accepted and quietly does nothing, because a plain function takes extra arguments without complaint. What counts as output. Everything a function produces and does not store in a variable is its output: the $rows.Count line on its own is output, and so is a message in quotes on its own line, as in Session 5’s scripts. You will also see Write-Output VALUE, the long way to write the same thing. Output goes down the pipe, or into a variable. E. Taking input from the pipeline: process

Cmdlets take objects from the pipe, one at a time. Your function can too. Mark a parameter [Parameter(ValueFromPipeline)], and each object piped in fills that parameter. But try it with code like the functions so far, and only one of three arrives:

piped in, without a process block · captured live
PS C:\Users\you\ps-lab> function Show-Order {
>>   param([Parameter(ValueFromPipeline)][string]$Id)
>>   "Order $Id"
>> }
PS C:\Users\you\ps-lab> '5001', '5002', '5003' | Show-Order
Order 5003

No error, and two orders gone. Code written straight into a function runs once, after everything has been piped in, by which time the parameter holds only the last object. The fix is a process { } block: the code inside it runs once for each object that comes down the pipe, with the parameter holding that object. Called with -Id instead, it runs once, for that value:

the same function, with process · captured live
PS C:\Users\you\ps-lab> function Show-Order {
>>   param([Parameter(ValueFromPipeline)][string]$Id)
>>   process { "Order $Id" }
>> }
PS C:\Users\you\ps-lab> '5001', '5002', '5003' | Show-Order
Order 5001
Order 5002
Order 5003
PS C:\Users\you\ps-lab> Import-Csv data/orders.csv | Where-Object Status -eq 'pending' |
  Select-Object -ExpandProperty OrderId | Show-Order                         one line, wrapped here
Order 5006
Order 5008
PS C:\Users\you\ps-lab> Show-Order -Id 5004
Order 5004

Before and after: begin and end. Two more blocks go with process. begin { } runs once, before the first object arrives, and end { } runs once, after the last. Together they make Session 5’s running total into a function: begin starts the total at 0, process adds each object, and end outputs the total. The [int] converts each Qty from CSV text as it arrives:

begin, process and end · captured live
PS C:\Users\you\ps-lab> function Get-ItemTotal {
>>   param([Parameter(ValueFromPipeline)][int]$Qty)
>>   begin { $total = 0 }
>>   process { $total = $total + $Qty }
>>   end { "Items: $total" }
>> }
PS C:\Users\you\ps-lab> Import-Csv data/orders.csv | Select-Object -ExpandProperty Qty |
  Get-ItemTotal                                                              one line, wrapped here
Items: 12

The rule: a function that takes pipeline input puts its work in process.

G. Help for your own command: comment-based help

The cmdlets’ help comes from files Microsoft writes. Yours comes from a comment-based help block: a comment that spans several lines, opened with <# and closed with #>, holding keywords, each a word in capitals after a dot, on a line of its own, with its text on the lines below. Four keywords cover what a stranger needs:

Keyword
What its text says
Shown by
.SYNOPSIS
one line: what the command does
Get-Help
.DESCRIPTION
a few lines: how it does it, and what comes out
Get-Help
.PARAMETER NAME
what one parameter means, and its default; one for each parameter
-Parameter NAME, -Full
.EXAMPLE
a command someone can copy and run
-Examples, -Full

In a script, the help block goes at the very top of the file, before param(). Here is order-report.ps1 again, with help in place of its first comment; the code under it is unchanged. Save it over the old one:

In a script, [CmdletBinding()] goes just above param(), after the help, exactly as in a function. The second run gives both values by position. The Verbose messages show $HOME joined to the rest of the path exactly as written, with both kinds of slash; Windows accepts either. The rows come out last, after the CSV is saved and the second Verbose message, so the messages print above the table. Because the rows are objects, not printed text, Measure-Object can add up their Count column: Sum : 5 is Session 5’s “5 ERROR lines in all”, with no loop to write. And the help shows a default as you typed it, $HOME and all.

In Windows PowerShell 5.1, use -NoTypeInformation -Encoding utf8 in place of -Encoding utf8BOM, as in Sessions 4 and 5; 5.1’s Measure-Object also prints no StandardDeviation line.
