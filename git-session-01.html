A. What Git is, and getting it running

Version control means keeping a recorded history of a set of files: what changed, when, by whom, and why. Git is the version control tool almost everyone uses.

Here is the problem it replaced. Without version control you save copies: report.docx, then report-v2.docx, then report-final.docx, then report-final-ACTUAL.docx. You cannot tell what changed between any two of them, you cannot tell why, you cannot get back a version you overwrote, and two people editing at once simply overwrite each other. Git replaces that whole pile with one folder that remembers every version you deliberately recorded, each one labelled with a message explaining the point of it.

Git is not GitHub. This is the single most common beginner confusion, so lock it in now:

  • Git is a program that runs on your own computer. It works with no internet connection at all. Everything in Sessions 1 through 4 happens entirely on your machine.
  • GitHub is a website that stores copies of Git repositories so other people can get at them. It is one of several such sites (GitLab and Bitbucket do the same job). You will not need an account until Session 5.

A repository (almost always shortened to repo) is a folder that Git is tracking, plus the complete recorded history of that folder. You will make one in section C.

Where you type Git commands. Git has no window and no buttons. You drive it from a terminal, which is a program that gives you a text prompt where you type one command, press enter, and read what it prints back. Every operating system ships one:

  • Windows: press the Start button, type PowerShell, and open Windows PowerShell. This session uses PowerShell as its default.
  • Windows, alternative: installing Git also installs Git Bash, a terminal that behaves like the macOS and Linux one. Useful later if you follow a tutorial written for Mac.
  • macOS: open Terminal (in Applications, Utilities).
  • Linux: open your terminal application, often Terminal or Konsole.
  • Inside VS Code, on any system: press Ctrl+` (Cmd+` on Mac) to open a terminal in the bottom panel, already sitting in your project folder. This is the most convenient option once you are working on real files.

One promise that makes this whole track portable: every command that starts with the word git is identical on Windows, macOS and Linux, and in every shell. Only the surrounding housekeeping commands differ (making a folder, creating a file, listing what is in a folder), and wherever one of those appears, both versions are shown side by side.

First, find out whether you already have Git. git --version asks Git to print its own version number and nothing else, which makes it the safest possible first command:

checking the install · what it looks like when it runs
> git --version
git version 2.54.0.windows.1

Any version number means Git is installed and you can move on; yours will differ. One honest caveat about that: Git reworks the little (use "git add ..." to ...) hint lines inside its own output every few releases, so on an older or newer Git a hint may be worded slightly differently from the transcripts here. The commands and their behaviour are stable. If a hint reads differently, that is a version difference, not a mistake on your part.

If instead you get an error along the lines of git: command not found or 'git' is not recognized, Git is not installed yet. Install it:

  • Windows: go to git-scm.com/downloads, download the Windows installer, and run it. Accept every default, they are all sensible. Then close and reopen your terminal (a terminal only learns about newly installed programs when it starts) and run git --version again.
  • macOS: run git --version and macOS will offer to install the developer command line tools; accept. Alternatively, if you have Homebrew, brew install git.
  • Linux (Debian or Ubuntu): sudo apt install git. On Fedora, sudo dnf install git.

Open a terminal now (PowerShell if you are on Windows), run git --version, and install Git from the matching bullet above if it is not there yet. Section B finishes the setup, and the two together are your first tracked task.

B. Tell Git who you are

Every commit Git records is stamped with an author name and email address, permanently. So before your first commit you have to tell Git what to stamp. This is a one-time setup for your whole computer, not something you redo per project.

The command is git config. The --global part is a flag: a word starting with two dashes that you attach to a command to change how it behaves. (Flags are sometimes called options, and single-letter ones take one dash, like the -m you will meet in section E.) This particular flag means "for my user account on this machine, in every repository", as opposed to just the repository you happen to be standing in. Repository-specific settings, which matter when you work under two different identities, are Session 9.

one-time setup · substitute your own name and email
> git config --global user.name "Ada Lovelace"
> git config --global user.email "ada@example.com"

Neither command prints anything when it works. Silence from a Git command usually means success, which takes some getting used to. (Git does sometimes print a warning and carry on anyway; you will meet one in section E, and the difference between a warning and an error is spelled out there.)

Use a real name and a real email. The email is what services like GitHub match commits against later, and the name is what teammates see next to every line you write. Nothing is verified here, Git records whatever string you give it, which is exactly why it is worth typing carefully.

Set one more thing while you are here. Every repository has a default branch, the name of the first line of history in it. Git historically called it master; the wider world has moved to main, and Git itself now warns that its own default will change to main in Git 3.0. Setting it yourself gives you main and settles the question:

choose the default branch name once, for all future repositories
> git config --global init.defaultBranch main

Do not skip this one, and do not count on Git to nag you about it. What you see if you leave it unset depends on your platform. On a stock macOS or Linux install, Git prints a block of hint: lines every time you create a repository until you choose a name, so it is hard to miss. On Windows it says nothing at all, because the Git for Windows installer already answered the question for you in a machine-wide setting, and the answer it wrote was master. So skipping this step on Windows is completely silent: you would quietly end up on master while every transcript in this sprint says main. That is why step 3 of the task below has you confirm the setting with --list rather than assume it.

Branches themselves are Session 3. For now, main is simply the name of the only line of history you have.

Now check that all three settings landed. --list prints every global setting Git currently holds for you:

confirming the setup · what it looks like when it runs
> git config --global --list
user.name=Ada Lovelace
user.email=ada@example.com
init.defaultbranch=main

Two things to notice, because both surprise people. Git prints the setting name back in lower case (init.defaultbranch, not init.defaultBranch): setting names are case-insensitive and this is just how Git displays them, nothing went wrong. And if you have used Git on this machine before, you will see extra lines here that you did not just add; that is fine, leave them alone.

Your turn Get Git working and tell it who you are

This one task covers sections A and B, so you set the whole environment up in one sitting.

  1. Open a terminal and run git --version. If Git is missing, install it from the list in section A, then close and reopen the terminal and run it again.
  2. Run all three git config --global commands above, using your own name and email.
  3. Run git config --global --list and confirm your name, your email, and init.defaultbranch=main all appear.
What if I skip the identity step?

Depending on your system Git either refuses to commit at all, or guesses a name and email from your computer account and warns you about it. The guess is usually wrong, and it gets stamped permanently onto every commit you make until you notice. Sixty seconds now saves that.

C. Turn a folder into a repository: the practice sandbox

Now build the repository you will use for the rest of the sprint. Call it the sandbox. Its whole job is to be disposable: every risky command in this track gets tried here first, so that you never learn reset or rebase on work you care about.

Three housekeeping commands, and this is one of the few places the shells differ. cd means "change directory", that is, move to a different folder; ~ is shorthand for your home folder (C:\Users\YourName on Windows). mkdir means "make directory".

Both shellscd ~
Both shellsmkdir git-sandbox
Both shellscd git-sandbox

You are now standing inside an ordinary empty folder. One command converts it:

git init · what it looks like when it runs
> git init
Initialized empty Git repository in C:/Users/you/git-sandbox/.git/

Read that message closely, because it says exactly what happened: Git created a folder called .git inside git-sandbox. That .git folder is the repository. Every commit, every message, every stored version lives inside it. Everything outside it is just your ordinary files.

This has a liberating consequence: delete .git and the folder is a plain folder again, with your files untouched but the history gone. Nothing about git init is magical or irreversible.

The . at the front of .git marks it as hidden, so a plain folder listing will not show it. To see it you have to ask for hidden entries, and here the two shells genuinely differ:

PowerShellGet-ChildItem -Force
Git Bash / macOS / Linuxls -a

Either one lists .git. Do not edit anything inside it by hand, ever. Every command in this track is a safe, supported way of asking Git to change it for you.

Finally, the command you will run more than any other. git status answers "what is the state of this repository right now":

git status in a brand-new, empty repository
> git status
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

Three facts, spread over five lines because Git separates them with blanks. On branch main: the default branch name you configured took effect. No commits yet: the history is genuinely empty. And a suggestion of what to do next, which git status gives you constantly. Get in the habit of reading those hint lines instead of skipping them; they are the best documentation Git has.

Your turn Create the sandbox
  1. Make and enter the git-sandbox folder using the three housekeeping commands above.
  2. Run git init and read the path it prints back.
  3. List the hidden entries with your shell version of that command and confirm .git is there.
  4. Run git status and confirm it says On branch main and No commits yet.

Keep this folder. Sessions 2 through 10 all reuse it.

D. The three areas

This is the model that makes Git predictable, and the reason most copy-pasters stay stuck: they picture one place where files live, when Git has three. A file you are working on exists in up to three states at once.

Working tree
The folder as you see it in your editor. Where you actually make changes.
→git add
Staging area
A shortlist of the changes you want in your next commit. Also called the index.
→git commit
Repository
The .git folder. Permanent recorded snapshots, and everything Git remembers.

A change travels left to right, and it only moves when you tell it to. git add puts a change on the shortlist. git commit records everything on the shortlist as one permanent snapshot and empties the shortlist.

Why have a middle area at all? Because it separates "I changed this" from "this belongs together in one recorded step". Suppose you fix a typo and, while you are in there, also start a half-finished new feature. Those are not one change. The staging area lets you commit the typo fix on its own and leave the unfinished work sitting in your working tree, uncommitted. Tools that snapshot everything automatically, like a Dropbox version history, cannot do that: they record what happened to the folder, whereas Git records what you decided was a change worth keeping. That authorship is the whole point, and it is why the staging area is a feature rather than an annoying extra step.

Every git status you run is really a report on these three areas, and it uses a fixed vocabulary for them:

  • Untracked: a file sitting in your working tree that Git has never been told about. It is in no commit and no shortlist, and Git will not record it until you add it.
  • Changes to be committed: what is on the shortlist right now, waiting in the staging area. Also called staged.
  • Changes not staged for commit: a file Git already tracks, which you have edited without adding the edit to the shortlist. Also called modified.
  • Working tree clean: nothing untracked, nothing staged, nothing modified. This exact phrase appears only when all three areas agree, which makes it a genuinely useful thing to check for.

Now make that concrete. Put a file in the working tree. You can create it in your editor, which is the normal way, or straight from the terminal:

Any editorCreate a file called notes.md in the git-sandbox folder, type a line into it, and save.
PowerShellSet-Content notes.md "Git sandbox"
Git Bash / macOS / Linuxecho "Git sandbox" > notes.md

Both terminal versions write the file from scratch, replacing anything already in it. That is what you want right now, since the file does not exist yet, but keep it in mind: Set-Content and a single > overwrite. The commands for adding a line to an existing file come up in section F.

The .md ending is just a convention for a plain-text notes file. Git does not care about file extensions at all, and a file with no extension is as valid to Git as any other. Here is what git status reports now:

git status with one untracked file
> git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	notes.md

nothing added to commit but untracked files present (use "git add" to track)

Note the last line: Git does not say "working tree clean" here, because an untracked file is unfinished business. Note also that <file> in that hint is a placeholder, not something you type literally; Git means "put a real file name here". Placeholders in angle brackets appear throughout Git output and this track, and they are never typed as written.

Create notes.md in your sandbox now, by either route above, and run git status to see it listed as untracked. Section E moves it the rest of the way, and the task at the end of E covers the whole journey.

E. status, add, commit: your first commit

git add moves a change onto the shortlist. Its most important property is the one nobody mentions: git add copies the file exactly as it is at that moment. It is a snapshot of the file, not a subscription to it. Edit the file afterwards and that later edit is not staged, and will not be in your commit unless you add it again. That single fact explains most beginner confusion about Git, and you will predict it in Part 2.

Three forms, all taught here because you need all three:

  • git add notes.md stages one named file.
  • git add alpha beta stages several named files in one go, separated by spaces.
  • git add . stages everything in the current folder and below: new files and edits to tracked files alike. Convenient, and worth a moment of suspicion each time, because it is also how people accidentally commit a password file. Session 2 covers .gitignore, which is the real fix.

Stage the file and look at the difference in git status:

git add, then git status · the file has moved to the shortlist
> git add notes.md
> git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   notes.md

git add printed nothing, which as ever means it worked. The heading changed from Untracked files to Changes to be committed, and Git labelled the change new file: because this file has never been in a commit before. Once a file has been committed, later stagings of it read modified: instead.

Two harmless surprises in that output, both worth naming so they do not worry you.

First, you may see a warning from git add rather than silence, reading warning: in the working copy of 'notes.md', LF will be replaced by CRLF the next time Git touches it. Windows ends its lines with two invisible characters (carriage return plus line feed, CRLF); macOS and Linux use one (LF). The Git for Windows installer turns on a setting that converts between them for you, and this warning is Git narrating that conversion. It is a warning, not an error: Git did the thing and carried on, the file staged fine, and nothing is broken. That is the general distinction to hold on to. A warning means "done, but you should know this"; fatal, which you will meet in section G, means "not done".

Second, the hint in brackets changes depending on the state of your repository. Above it reads (use "git rm --cached <file>..." to unstage) because there are no commits yet. Once your repository has at least one commit, the same line reads (use "git restore --staged <file>..." to unstage), which you will see later in this session. Both undo the same staging; Git simply picks the one that works from where you are. Different hint text for a different state is normal.

Now record it. git commit takes everything on the shortlist and writes it into the repository as one permanent snapshot. The -m part supplies the message, in quotes:

git commit · what it looks like when it runs
> git commit -m "Add notes.md"
[main (root-commit) b12d1b7] Add notes.md
 1 file changed, 1 insertion(+)
 create mode 100644 notes.md

Unpacking that output, since every part of it means something:

  • main is the branch the commit landed on.
  • (root-commit) appears only on the very first commit in a repository. Section F explains why.
  • b12d1b7 is the start of the commit identifier. Yours will be different, always.
  • 1 file changed, 1 insertion(+) is a summary Git calculated for you by comparing this snapshot against the one before it. It is not what the commit stores, which matters in section F. If you typed more than one line into notes.md, your insertion count is higher, and that is the only part of this output that depends on your file.
  • create mode 100644 is the file permission Git recorded. You can ignore it; 100644 just means an ordinary non-executable file.

Write the message like a professional from day one, because you cannot easily fix it later and other people read it. Two conventions do most of the work: keep the summary short, and write it as a command describing what applying the commit does, so Add notes.md and Fix date parsing on empty rows rather than added stuff or changes. Say why where it is not obvious. Never write update, which is what a message says when the author did not want to think about it.

Confirm the state afterwards:

git status after committing · all three areas now agree
> git status
On branch main
nothing to commit, working tree clean

There is the exact phrase from section D. No commits yet is gone, the shortlist is empty, and the working tree matches the last commit.

One more behaviour worth knowing before you can predict Git confidently: committing with an empty shortlist does nothing at all. Git will not invent a commit for you out of edits you never staged:

git commit with an edited file that was never added
> git commit -m "Attempt with unstaged change"
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   notes.md

no changes added to commit (use "git add" and/or "git commit -a")

No commit was created. Git printed the status instead and stopped. This is the behaviour that makes the staging area safe: it never guesses at your intent.

F. What a commit really is: a snapshot with a parent

Almost everyone starts out believing a commit stores the changes you made. It does not, and that single wrong belief is what makes branching and merging feel like magic later. Here is the truth:

A commit stores a complete snapshot of every tracked file at that moment, plus the author name and email, the date, your message, and a pointer to the commit that came before it, called its parent. That is the whole object.

So a commit records unchanged files too. If a commit touches one file out of fifty, the commit still contains all fifty; the forty-nine unchanged ones simply point at content Git already has stored, which is why this costs almost no disk space. Nothing is ever reconstructed by stacking changes on top of each other, which means any commit can be recovered on its own without replaying history.

Then what about the 1 file changed, 1 insertion(+) line, and the whole idea of a diff? A diff is a comparison, and Git computes diffs on demand by comparing two snapshots. It never stores one. So the old mental model, the tracked-changes-in-a-document one where a version is a pile of edits, is the wrong picture: Git keeps whole photographs and works out the differences between them whenever you ask. (Session 2 is entirely about asking.)

The parent pointer is what makes history a chain. Each commit knows the one before it, so Git can always walk backwards. Note the direction: the arrows point back in time, from newer to older, because a commit cannot know what will come after it.

b12d1b7
Add notes.md
parent: none (root commit)
← parent
8dea82d
Add a second line of notes
parent: b12d1b7
← parent
your next
Add alpha
parent: 8dea82d

That is the chain you will have built by the end of this session: the commit you just made, the one you are about to make in the task below, and the milestone commit at the end of section G.

The very first commit has nothing before it, so it has no parent at all. Git calls that one the root commit, and that is what (root-commit) was telling you in section E. Every later commit has exactly one parent, until Session 4, where merging produces the one kind of commit with two.

About that identifier. The full name of a commit is a 40-character hash, a string of hexadecimal digits like 223e773141200119b9e709e46653da1c515f3815. Git calculates it from the commit contents: the snapshot, the message, the author, the date, and the parent. So the hash is not a serial number handed out in order, it is a fingerprint of that exact commit. Change any detail and you get a completely different hash, which is why Git can guarantee history has not been quietly altered. In practice you use the first 7 characters, which is what git log --oneline prints and is plenty to be unique in a repository this size.

G. Reading history with git log

git log walks backwards from your newest commit along those parent pointers and prints each one. Newest first, always:

git log · the full form, after the two commits you have made
> git log
commit 8dea82df95b250ea9cbccdd40dc2cf7e2b9c38c7 (HEAD -> main)
Author: Ada Lovelace <ada@example.com>
Date:   Tue Jul 28 13:17:54 2026 -0500

    Add a second line of notes

commit b12d1b7c076f4ce41924aea202d1e4c0c10d09d2
Author: Ada Lovelace <ada@example.com>
Date:   Tue Jul 28 13:17:54 2026 -0500

    Add notes.md

There is your identity from section B, permanently attached to both, and the full 40-character hash from section F. The newest commit is on top.

What is that (HEAD -> main)? It appears on the newest commit only, and it is Git telling you where you are standing: HEAD is Git shorthand for "the commit you are currently on", and here HEAD is reached through the branch main. Nothing is wrong and there is nothing to fix. Session 2 takes HEAD apart properly, and Session 3 does the same for branches. One quirk worth knowing so it does not confuse you: Git only prints that label when it is writing to a terminal, so if you ever pipe git log into another command or a file, the label disappears.

The full form gets unreadable fast at four commits per screen, so the form you will actually live in is --oneline, which compresses each commit to its short hash and its summary line:

git log --oneline · the same two commits
> git log --oneline
8dea82d (HEAD -> main) Add a second line of notes
b12d1b7 Add notes.md

Compare each short hash to the long one above it: the short form really is just the first 7 characters, exactly as section F said.

The reverse ordering is easier to see with three commits. In this different repository, the commits were made in the order alpha, then beta, then gamma:

git log --oneline in a repository with three commits
> git log --oneline
94d46df (HEAD -> main) Add gamma
22f89ae Add beta
8c9ec6c Add alpha

The output is the reverse of the order they were made in, because log starts at the newest commit and follows parent pointers backwards. Reading top to bottom is reading back in time. That also explains what your commit messages are really for: this list is the only description of your project history that anyone, including future you, will ever read.

Session 2 is largely about the other flags that shape log output.

One thing that trips people up on a brand-new repository: git log before any commit exists is an error, not an empty list.

git log in a repository with no commits yet
> git log
fatal: your current branch 'main' does not have any commits yet

Nothing is broken. fatal is simply the word Git uses for "I stopped, I did not do the thing", and here it stopped because there is no history to walk yet.

Try both forms in your own sandbox before going on. Run git log and find your name, your email, both hashes and both messages. Then run git log --oneline and check two things: your newest commit is at the top, and the short hash really is the first 7 characters of the long one above it. You will use --oneline again as the last step of the milestone below.
