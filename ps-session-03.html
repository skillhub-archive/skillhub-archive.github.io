A. A place to write: New-Item and Test-Path

Before you write anything, make a folder for it. New-Item makes a new item, which is PowerShell’s word for anything that lives at a path: a file or a folder. Its -ItemType parameter says which: Directory makes a folder (directory is the older word for a folder), and when you leave -ItemType out, it makes an empty file. Either way, it prints the new item the way Get-ChildItem would:

a folder, then an empty file inside it · captured live
PS C:\Users\you\ps-lab> New-Item -ItemType Directory out

    Directory: C:\Users\you\ps-lab

Mode                 LastWriteTime         Length Name
----                 -------------         ------ ----
d----           10/7/2026  9:53 AM                out                       your date

PS C:\Users\you\ps-lab> New-Item out/todo.txt

    Directory: C:\Users\you\ps-lab\out

Mode                 LastWriteTime         Length Name
----                 -------------         ------ ----
-a---           10/7/2026  9:53 AM              0 todo.txt                  your date

The file is 0 bytes long, an empty file, ready to be written to. To ask whether something exists without listing anything, use Test-Path: it answers True or False, the same two answers a comparison gives.

does it exist? · captured live
PS C:\Users\you\ps-lab> Test-Path out
True
PS C:\Users\you\ps-lab> Test-Path out/nothing.txt
False

Making something that is already there is an error: PowerShell stops that command and prints a message in red saying what went wrong. Read the message before anything else; it usually names the problem exactly.

the folder is already there · captured live
PS C:\Users\you\ps-lab> New-Item -ItemType Directory out
New-Item: An item with the specified name C:\Users\you\ps-lab\out already exists.
Windows PowerShell 5.15.1 prints the same message in its longer error form, with At line:1 char:1, a row of ~ marks under your command, and two indented lines starting with +. Session 1 showed the same shape for a typo.
In BashThe mkdir command makes a folder (mkdir out), and touch out/todo.txt makes an empty file. Neither prints anything when it works, where New-Item shows you what it made.

B. Searching inside files: Select-String

In Session 2 you found the ERROR lines of a log with Where-Object { $_ -like '*ERROR*' }. PowerShell has a command built for that job: Select-String, which searches inside files for a piece of text and prints every line that contains it. The first thing after it is the pattern, the text to look for, and the second is the file to look in. (Its SYNTAX starts Select-String [-Pattern] <string[]> [-Path] <string[]>: both names are optional, as Session 1 taught, so the pattern and the path can simply come in that order.)

one log, one pattern · captured live
PS C:\Users\you\ps-lab> Select-String ERROR logs/web-2026-03-03.log

logs\web-2026-03-03.log:3:2026-03-03 14:21:05 ERROR POST /checkout 500 payment timeout
logs\web-2026-03-03.log:4:2026-03-03 14:21:30 ERROR POST /checkout 500 payment timeout

Each line it prints has three parts, separated by colons: the file it was found in, the line number in that file (the first line is 1), and the line itself. In PowerShell 7 the matching text is also highlighted on your screen. The path is written from the folder you are standing in, so from your home folder the same search prints paths that start ps-lab\logs\ instead. A wildcard in the path searches several files at once, which is where the file part earns its place:

every web log, then from your home folder · captured live
PS C:\Users\you\ps-lab> Select-String ERROR logs/*.log

logs\web-2026-03-01.log:5:2026-03-01 09:06:03 ERROR POST /checkout 500 payment timeout
logs\web-2026-03-02.log:3:2026-03-02 10:12:02 ERROR GET /products/9999 404 not found
logs\web-2026-03-03.log:3:2026-03-03 14:21:05 ERROR POST /checkout 500 payment timeout
logs\web-2026-03-03.log:4:2026-03-03 14:21:30 ERROR POST /checkout 500 payment timeout

ps-lab\logs\web-2026-03-02.log:3:2026-03-02 10:12:02 ERROR GET /products/9999 404 not found

capitals, ignored and then not · captured live

The second one printed nothing: no line has error in small letters. Select-String also searches whatever is piped into it. Lines that arrive from Get-Content did not come from a file it opened, so it prints them without the file and line number:

searching piped lines · captured live

Two ways a search goes wrong. A file that is not there is an error. A folder given as the path is worse: PowerShell 7 searches nothing and says nothing, so it looks like a search that found no matches:

a missing file, then a folder · captured live

because it does not exist.
PS C:\Users\you\ps-lab> Select-String ERROR logs

So when a search prints nothing and you expected something, check the path first: logs/*.log, the files, not logs, the folder.

D. When the pattern is not plain text

So far every pattern has been letters and digits, and those simply mean themselves. But Select-String reads its pattern as a regular expression, a small language for describing text, used by search tools everywhere, in which some punctuation has a special meaning. You do not need that language today; you need to know the two characters that trip people up. The first is *. In Session 2’s -like, '*ERROR*' meant “ERROR anywhere”. Here it is an error:

a -like pattern given to Select-String · captured live
PS C:\Users\you\ps-lab> Select-String '*ERROR*' logs/*.log
Select-String: The string *ERROR* is not a valid regular expression:         one line, wrapped here
Invalid pattern '*ERROR*' at offset 1. Quantifier '*' following nothing.

You do not need the stars: Select-String already finds the pattern anywhere in the line, so ERROR alone does what '*ERROR*' did with -like. The second character is the dot, ., which in a regular expression means “any one character”. Looking for the text .50, as in a price like 22.50, finds lines that contain no dot at all:

the dot matches anything · captured live
PS C:\Users\you\ps-lab> Select-String '.50' logs/*.log

logs\web-2026-03-01.log:5:2026-03-01 09:06:03 ERROR POST /checkout 500 payment timeout
logs\web-2026-03-03.log:3:2026-03-03 14:21:05 ERROR POST /checkout 500 payment timeout
logs\web-2026-03-03.log:4:2026-03-03 14:21:30 ERROR POST /checkout 500 payment timeout
logs\web-2026-03-03.log:6:2026-03-03 14:25:00 INFO  GET /orders/5003 200

PS C:\Users\you\ps-lab> Select-String '.50' logs/*.log -SimpleMatch

The dot matched the space before 500 and the / before 5003. The switch -SimpleMatch tells Select-String to take your pattern literally, character for character, so the second search looks for a real dot followed by 50, and the logs have none. Patterns with punctuation or spaces in them go in single quotes, as text values did in Session 2. The rule for today: letters, digits and spaces are safe; when your pattern has any other punctuation, add -SimpleMatch. (With -SimpleMatch, '*ERROR*' is no longer an error, but it looks for real stars, and finds nothing.)

In Bashgrep reads a regular expression too, and the dot behaves the same way: grep '.50' logs/*.log prints the same four lines, each starting logs/. Its -F, for fixed text, is the counterpart of -SimpleMatch, and with it the search finds nothing.

E. Writing files: >, >>, Out-File, Set-Content and Add-Content

Anything that would print on your screen can go into a file instead. The redirection operator > sends a command’s output into the file named after it, creating the file, or replacing everything in it without asking if it already exists. >> appends: it adds to the end of the file and keeps what was there. Out-File is the same thing as a cmdlet: | Out-File FILE does what > FILE does, and | Out-File FILE -Append what >> does. (FILE in capitals is a placeholder: you type a real path in its place.) Text in single quotes, typed on its own, is output like anything else: 'first' alone just prints first, so 'first' > out/two.txt writes it to the file instead.

replace, then append · captured live
PS C:\Users\you\ps-lab> 'first' > out/two.txt
PS C:\Users\you\ps-lab> 'second' >> out/two.txt
PS C:\Users\you\ps-lab> Get-Content out/two.txt
first
second
PS C:\Users\you\ps-lab> 'only' > out/two.txt
PS C:\Users\you\ps-lab> Get-Content out/two.txt
only

A redirect prints nothing on screen: the output went into the file. Notice what the last > did to first and second. And do not use > to mean “greater than”: Microsoft’s about_Redirection page warns that 36 > 42 does not compare anything, it writes 36 into a new file called 42. Comparisons are -gt and -lt, as in Session 2.

What > writes is what the screen would show. Here is a search sent to a file and read back:

a search, redirected · captured live
PS C:\Users\you\ps-lab> Select-String ERROR logs/*.log > out/errors-raw.txt
PS C:\Users\you\ps-lab> Get-Content out/errors-raw.txt

F. Bytes, encodings and line endings

A file on disk is a row of bytes, small numbers from 0 to 255, and a file’s Length is how many there are. Text has to be turned into bytes to be saved, and the rule for doing that is the file’s encoding. PowerShell 7 uses UTF-8, the most common encoding today, in which each plain English letter, digit or space is one byte. So hello should be five bytes. It is seven:

one word, two ways · captured live
PS C:\Users\you\ps-lab> 'hello' | Out-File out/hello.txt
PS C:\Users\you\ps-lab> Set-Content out/hello2.txt 'hello'
PS C:\Users\you\ps-lab> Get-ChildItem out/hello*.txt | Select-Object Name, Length

Name       Length
----       ------
hello.txt       7
hello2.txt      7

The other two bytes mark the end of the line. On Windows, PowerShell ends every line it writes with two invisible characters: a carriage return, called CR, and a line feed, LF. Together they are CRLF, the Windows line ending. The lab’s own files were written with LF alone, the line ending of Linux and macOS, which is why copying README.txt’s four lines makes a file four bytes longer:

the same four lines, two line endings · captured live
PS C:\Users\you\ps-lab> Get-Content README.txt | Set-Content out/readme-copy.txt
PS C:\Users\you\ps-lab> Get-ChildItem README.txt, out/readme-copy.txt | Select-Object Name, Length

Name            Length
----            ------
README.txt         183
readme-copy.txt    187

Every byte count in this session was taken on Windows. Microsoft’s .NET documentation gives LF alone as the line ending on Unix systems such as Linux and macOS, so there expect one byte less per line; this workbook did not run them there.

Letters beyond plain English take more bytes. In UTF-8, é is two bytes, so café on one line is seven: three, two, and the line ending. (Copy the command from this page if your keyboard has no é.)

an accented letter · captured live
PS C:\Users\you\ps-lab> Set-Content out/cafe.txt 'café'
PS C:\Users\you\ps-lab> Get-ChildItem out/cafe.txt | Select-Object -ExpandProperty Length
7
PS C:\Users\you\ps-lab> Get-Content out/cafe.txt
café

Why the same command can write two different files. Windows PowerShell’s defaults were set before UTF-8 became the norm on Windows, and its file-writing commands do not even agree with each other. Out-File, > and >> write UTF-16, an encoding with two bytes for every plain letter, and start the file with a BOM, a byte order mark: a few bytes at the very start that announce which encoding follows. Set-Content and Add-Content use the older Windows encoding Microsoft calls ANSI, one byte per letter, whose letters beyond plain English depend on the computer’s language settings. Microsoft’s about_Character_Encoding page lists every default, and in 5.1 this machine gave:

Command
5.1 writes
hello took
Out-File, >, >>
UTF-16, with a BOM
16 bytes: 2 for the BOM, 2 per letter, 4 for CRLF
Set-Content, Add-Content

7 bytes

Plain English text survives all of this: every version reads every one of these hello files back as hello. The trouble comes with letters beyond plain English, when one version writes and the other reads. A UTF-8 file with no BOM gives 5.1 no hint, so it assumes ANSI and reads each two-byte letter as two wrong ones. Telling it the encoding with -Encoding fixes it:

PowerShell 7’s cafe.txt, read in Windows PowerShell 5.1 · captured live
PS C:\Users\you\ps-lab> Get-Content out/cafe.txt
cafÃ©
PS C:\Users\you\ps-lab> Get-Content out/cafe.txt -Encoding utf8
café

The habit to take away: when a file is going to another program, another computer or the other version, say which encoding to use, with -Encoding utf8, when you write it and when you read it. Out-File, Set-Content, Add-Content, Get-Content and Select-String all take it. One catch: in 5.1, -Encoding utf8 writes a BOM, and in 7 it does not (7 calls the BOM version utf8BOM). Given -Encoding utf8, both versions read either kind correctly. And if you ever need UTF-16 itself, its -Encoding name is unicode, for historical reasons: 'hello' | Out-File FILE -Encoding unicode makes the same kind of file 5.1’s Out-File does. The 5.1 trap from section E is one direction only: >> onto a file Set-Content made adds UTF-16 to an ANSI file, because, as the about_Character_Encoding page warns, >> makes no attempt to match the file’s existing encoding. Add-Content does match it, which makes it the safe way to append in either version.

Look under the hood: the bytes themselves (optional, not graded, PowerShell 7)

When two files look the same on screen but one of them breaks the program that reads it, the difference is in the bytes, and Format-Hex shows them. It prints each byte as two characters from 00 to FF (a counting system called hexadecimal, which you do not need to learn to read this). Ignore the long Offset numbers on the left and the column on the right; read only the Bytes in the middle, and look for three landmarks:

  • 0D 0A at the end of a line is CRLF, the Windows line ending. 0A on its own is LF.
  • FF FE at the very start is the BOM of a UTF-16 file.
  • 00 after every letter means UTF-16: the second byte of each two-byte letter.

With -Encoding unicode from above you can make 5.1’s kind of file in 7, and compare:
