A. One integration, three owners

An integration is a piece of work that makes two or more systems act as one: it takes something from one, maybe changes it, and hands it to another. Today’s is small and complete. The library wants each book in its catalogue to carry a one-line description, and Wikipedia already has one for most books. So the integration reads a book from the library’s API, asks Wikipedia about that book, and saves the answer back to the library. Every integration, however big, has the same three parts, and the useful question about each is who owns it:

Your API
The library’s Books API v1, which you designed in Session 5 and mocked in Session 6. You own it: you can change its contract, and its mock answers what you tell it to.
Their API
Wikipedia. You own nothing here. You read its documentation, you follow its rules, and you cope with what it sends back, whether you like it or not.
The glue
The requests and scripts that carry values from one to the other. You own it completely, and, as section E shows, it is where most integrations quietly go wrong.

The integration is three calls, run in order by Session 4’s Collection Runner, each needing something the one before it found:

Before the first request: say who you are. Every request carries a User-Agent header, which names the program sending it; Postman fills one in for you, PostmanRuntime/ and a version number. Wikipedia’s rate-limit rules, which are new in 2026 and say they may change, allow a request with “no identifying characteristics other than IP address” 10 requests a minute, and one whose User-Agent names the program and gives a way to contact its owner 200. In the test below, sent from one home internet connection, Postman’s own User-Agent got the 10. Their documentation asks for exactly that: “a meaningful User-Agent header that includes contact information such as an email or full URL”, written as the program’s name, a /, its version, then the contact in brackets. This is how it went building this session:

Which agent sends it matters. Session 8 showed that Postman sends every request through an agent, named at the bottom right of the window. On the web app checked for this session, Auto-select chose the Cloud Agent, and it sent the User-Agent set below, as the task’s echo step proves. newman sent it too; the desktop app was not checked. The Browser Agent sends from your web browser, and browsers may refuse to let a page change this header, so do not pick it today; it was not checked either. This is Session 3’s idea from the other side. An API that needs no key still wants to know who is calling, and a User-Agent with a contact is how you tell it: not a secret, just a name and a way to reach you if your program misbehaves. Session 4’s rules for a 429 still hold: wait the number of seconds Retry-After gives, then send again. Wikipedia’s page adds “limit the number of concurrent requests to 3 or fewer”, where concurrent means at the same time, and the Runner sends one at a time anyway.

> GET ...&titles=A Wizard of Earthsee

A 200 for a page that is not there. No 404, no error object: the request was fine, and the honest answer to it is “that page is missing”, so Wikipedia gives it inside the body as "missing": true. You saw the same habit in Session 4, where a forged cursor came back as a 200 wrapping an error. Wikipedia’s documentation says it plainly: “If something goes wrong in an API request, an error or a warning will be thrown (although the HTTP response will usually still be 200 OK).” A real error, as opposed to a missing page, also sets a response header, MediaWiki-API-Error, whose value is the error’s code; a missing page sets none. So with this API, the status code alone tells you almost nothing. Read the body every time.

Two more things a title can do. Wikipedia keeps redirects: titles that are another name for a page, and lead to it. And it capitalises only the first letter of a title for you, so a wizard of earthsea becomes A wizard of earthsea, a different title, which happens to be a redirect. With redirects=1 you land on the real page, and the answer tells you every step it took:

a title in the wrong case · captured live
> GET ...&redirects=1&titles=a wizard of earthsea
"normalized": [ { ..., "from": "a wizard of earthsea", "to": "A wizard of earthsea" } ],
"redirects":  [ { "from": "A wizard of earthsea", "to": "A Wizard of Earthsea" } ],
"pages": [ { "pageid": 2890, "title": "A Wizard of Earthsea",
             "description": "1968 fantasy novel by Ursula K. Le Guin", ... } ]

So the page you get back can have a different title from the one you asked for. Keep the title Wikipedia answers with, not the one you sent: it is the page the description actually came from.

C. Your side: one more operation, designed first

The library has nowhere to keep a description. A book in Session 5’s field table has a title, an author, an isbn and a year, and that is all. You could add a field to the book, but the description is not the library’s own fact about the book, it is Wikipedia’s, fetched by an integration that may run again next month. So it gets a place of its own: the book’s about, at /v1/books/{id}/about, a resource that belongs to one book. Session 5 called this a nested URL: the slash reads as “belonging to”, as in jsonplaceholder’s /posts/1/comments.

Session 5 section E sorted changes into breaking and non-breaking, and “add a new operation or a new resource” was non-breaking: “Nobody was calling it, so nobody is affected.” So this goes into Books API v1 itself, with no new version. Here is the contract row, in Session 5’s shape:

Request
Success
Refusals, with their error code
PUT /v1/books/{id}/about
200, the about as stored, with the book’s id as bookId
404 book_not_found · 400 invalid_json · 422 field_required or field_invalid · 503 unavailable, nothing saved
Field
Type
Rules
description
string
Required. 1 to 200 characters. A one-line summary.
wikipediaTitle
string
Required. The title of the page the description came from.

The 400 is Session 5’s shared rule for any body that is not valid JSON. It gets no example of its own today: Session 7 showed that a mock answers broken JSON with its own 400 before it matches anything, so an example could only ever be reached by name. The other four statuses each get one, and, as in Session 5, one 422 example stands for both of its codes.

Why PUT, not POST. A book has one about, at one address, and saving it replaces whatever was there, which is exactly what Session 5 said PUT means. The contract makes that literally true: every book has an about from the moment the book exists, empty until something is saved, so a save always replaces one and always answers 200. (Had the first save created the about instead, RFC 9110 would want 201 for that save, and the mock would need a second success example.) And PUT is idempotent: save the same about twice and the book still has one about, the same one. So, unlike Session 8’s loans, this write needs no idempotency key. If a save gets no answer, sending it again is safe by the method itself. Choosing the method well removed a whole problem before it existed.

D. The glue: carrying a value from one API to the other

Session 8 carried a loan’s id from call 3 to call 4 with a post-response script and a collection variable. The integration does the same twice: the title from call 1 into call 2’s URL, and the description from call 2 into call 3’s body. But there is a catch Session 8 never met. A loan id is a number, like 501, and goes anywhere unchanged. A title is text written by somebody else, and text can hold characters that mean something where you put it.

Into a URL. Session 1 showed that a query string’s pairs are joined by &. So a book called Pride & Prejudice put straight into titles= ends the title at the &, and Wikipedia reads the rest as a separate parameter, called Prejudice, which it does not recognise. A # is worse: everything after it is cut off before it is sent. The cure is percent-encoding: each such character is replaced by % and its number in hex, Session 7’s digits 0 to 9 and a to f, so & becomes %26 and a space %20, and a server reads them back as the characters they stand for. Postman encodes the spaces in a URL you type for you, which is why section B’s titles worked; it cannot know that an & inside a value was meant as part of a title rather than as a separator. JavaScript has a function that does it, encodeURIComponent(text): give it text, and it gives back the same text made safe to put inside one part of a URL.

a title with an ampersand, sent both ways · captured live
> titles=Pride & Prejudice                        put in as it is
"warnings": { "main": { "warnings": "Unrecognized parameter: Prejudice." } }
"title": "Pride", "description": "Positive effect from the perceived
  value of a person"                                  the wrong page

> titles=Pride%20%26%20Prejudice                  encodeURIComponent
"redirects": [ { "from": "Pride & Prejudice", "to": "Pride and Prejudice" } ]
"title": "Pride and Prejudice", "description": "1813 novel by Jane Austen"

Into a JSON body. Inside a JSON string, a " ends the string. Session 1 showed a JSON string holding an escaped line break, \n; a quote mark is escaped the same way, as \". Wikipedia has a page called "Repent, Harlequin!" Said the Ticktockman, quote marks and all, and pasting that title between quotes in a body produces JSON that is broken. The cure is JSON.stringify(value): give it a value, and it gives back that value written as JSON, so a piece of text comes back with its quote marks round it and every quote inside escaped. Because it adds the quotes itself, the variable goes into the body with no quotes of its own, just as Session 8’s {{loanId}} did:

a title with quote marks, sent both ways · captured live, against your mock
> {"description": "{{aboutDescription}}", "wikipediaTitle": "{{wikiTitle}}"}
  sent as: {..., "wikipediaTitle": ""Repent, Harlequin!" Said the Ticktockman"}
400 Bad Request          the mock's own badRequest: not valid JSON

> {"description": {{aboutDescription}}, "wikipediaTitle": {{wikiTitle}}}
  sent as: {..., "wikipediaTitle": "\"Repent, Harlequin!\" Said the Ticktockman"}
200 OK                   JSON.stringify made both values

The rule, which holds for any integration: a value going into a URL gets encodeURIComponent; a value going into a JSON body gets JSON.stringify; and neither is ever pasted in as it is.

Reading Wikipedia’s answer takes four more pieces of JavaScript, each one line:

  • var page = ...; keeps a value under a name, page, for the next few lines of the same script. Unlike a collection variable, it is gone when the script ends.
  • pages[0] takes the first item of the array pages. Positions in JavaScript count from 0, so [0] is the first, [1] the second.
  • undefined is what JavaScript gives you when you ask for a field that is not there: a page with no description has page.description === undefined.
  • || means “or” between two tests: the whole test is true if either side is. JavaScript checks the left side first, and if that is already true it never looks at the right. Section E shows why that order matters here.

Now the three scripts. One case first: a mistake in your request, such as a parameter name typed wrongly, gets a 200 with no query in the body at all, which is what call 2’s first test looks for; section E shows one. Call 1 keeps the title, already encoded for a URL. Call 2 stops the run unless it got a real description, and keeps the description and the page’s title, already written as JSON. Call 3 stops if the save failed. Every if, else, !== and setNextRequest(null) is Session 8’s.

// Read the book, post-response: keep the title, ready for a URL
if (pm.response.code !== 200) {
  pm.execution.setNextRequest(null);
} else {
  pm.collectionVariables.set("titleParam", encodeURIComponent(pm.response.json().title));
}
// Ask Wikipedia, post-response: keep the description, ready for a JSON body
if (pm.response.code !== 200 || pm.response.json().query === undefined) {
  pm.execution.setNextRequest(null);
} else {
  var page = pm.response.json().query.pages[0];
  if (page.missing === true || page.description === undefined) {
    pm.execution.setNextRequest(null);
  } else {
    pm.collectionVariables.set("aboutDescription", JSON.stringify(page.description));
    pm.collectionVariables.set("wikiTitle", JSON.stringify(page.title));
  }
}
// Save the about, post-response
if (pm.response.code !== 200) {
  pm.execution.setNextRequest(null);
}

Call 3 is the last call, so its stop changes nothing today. It is there so that if a call is ever added after the save, it cannot run after a failed one. Two collection variables choose the mock’s answers, the way loanAnswer did in Session 8: call 1 sends x-mock-response-name: {{bookAnswer}} and call 3 sends x-mock-response-name: {{saveAnswer}}. On a real server you would leave both headers out.

E. When it breaks: your side, their side, and the glue

An integration can fail in three places, one for each owner from section A, and each looks different when it does. The first job when a run goes wrong is to say where it showed up and who caused it, because that decides what you can do about it. The two are not always the same: Wikipedia reports a missing page, but the title it could not find came from your own API.

Side
What you see
What you can do
your API
your contract’s own refusals: 404 book_not_found, 422, 503 unavailable
everything: you own the data and the contract. A 503 means try the run again later.
their API
a 429 with Retry-After; or a 200 whose body says "missing": true: no page has the title you sent
only what their rules allow: wait and resend. For a missing page, check the title in your own data first; their data is not yours to fix.
the glue
a 200 with no query, because your request asked wrongly; or, worse, nothing at all: every call says 200 and the wrong thing is saved
fix your own requests and scripts

Look at what happens after the 503. Nothing was saved, and the whole run is safe to repeat later: calls 1 and 2 are reads, and call 3 is a PUT, which section C chose so that repeating it is harmless. Now look at the || in call 2’s first test. A 429’s body is plain text, and pm.response.json() on plain text stops the script with an error. Because the status test comes first, and || stops at the first true side, a 429 never reaches the part that reads JSON.

The glue fails differently: it does not stop. Here are the same scripts written the way a first draft usually is, with the title put into the URL as it is, the description pasted between quotes, and no checks:

Every status is 200, and the mock said 200 saved both times, because a mock checks nothing. On a real server those would have been a wrong description and the word null, stored against a real book, found weeks later by a reader. The glue’s failures are the dangerous ones precisely because nothing fails. (The null is how Postman fills in a variable that a script set to undefined.)

One more, which catches careful people: a script that stops with an error. On a run whose call 2 URL had a typing slip, Titles= with a capital T, Wikipedia answered 200 with a warning and no query, and a script without the query === undefined test stopped with an error. In the web app, the run’s results list call 2 as a 200, and the error appears under the results’ Errors tab, marked as coming from the post-response script:

a script error, in the Runner’s results · as Postman’s web app showed it
SCRIPT  Post-response: TypeError: can't access property "pages",
        pm.response.json().query is undefined

What happens next depends on one Runner setting, Stop run if an error occurs, which is ticked when you open the Runner. Ticked, the run ends at that call, and Postman reports that the run did not finish. Unticked, the run carries on, and so does newman, Postman’s command-line runner, unless it is told otherwise. Carrying on, call 3 went out anyway: with the variables empty, it sent broken JSON and got the mock’s 400; with values still sitting there from an earlier run, it got 200 saved, for the previous run’s description. A request that gets an error status, such as a 503, does not count as an error for that setting: it is still an answer, and the run goes on past it, as Session 8 found. So do not rely on the setting. Anyone can untick it, and newman, for one, carries on unless told otherwise. The query === undefined test in section D’s script stops this run at call 2 whatever the setting says.

F. Writing it down, so someone else can pick it up cold

Session 5 called it the stranger test: a contract is finished when someone could build against it without asking you anything. An integration has the same test with a harder stranger: the person who has to run it, and fix it at nine on a Monday morning, when you are away. They need different things from a contract’s reader. Not every field’s rules, but what this thing does, what it touches, what to set before running it, and, above all, what each failure looks like and what to do about it. That document is usually called a README, the file people are expected to read first, and in Postman it goes in the collection’s description, where Session 5 put the contract. Six headings cover it:
