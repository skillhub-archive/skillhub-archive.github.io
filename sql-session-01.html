A. What a relational database is, and getting SQLite running

A database is an organized collection of data. A relational database keeps that data in tables. A table is rows and columns, like a spreadsheet tab but with rules:

  • A row (also called a record) is one thing: one customer, one order.
  • A column (also called a field) is one attribute: a name, a city. Every value in a column is the same kind of data.
  • A primary key is a column whose value is unique for each row (here, id), so you can point at exactly one row. Keys get real depth in Level 2 and Level 4; for now, just know id is what makes each row unique.

SQL is Structured Query Language, the language you use to ask a relational database questions (and later, to change it). A query is just a question you ask the database. "SQL" is said either "sequel" or "S-Q-L", both are fine.

We use SQLite: a tiny relational database that ships with Python, so the database engine itself needs nothing installed. A whole SQLite database is just a single file on your computer (for example shop.db). What you do need is a tool to type SQL into and see the results. You have not used one before, so let's set one up now, it is a one-time step for the whole sprint.

Recommended: DB Browser for SQLite. It is a free desktop app that gives you a window into a database file, with a box to type SQL and a grid to show what comes back. It is the friendliest way to start:

  • Go to sqlitebrowser.org and click Download. On Windows, take the 64-bit standard installer (an .msi) unless you know you need the ARM64 one. On macOS, take the single Universal .dmg, which covers both Intel and Apple Silicon (brew install --cask db-browser-for-sqlite also works if you use Homebrew). On Linux, use your package manager (apt, dnf, pacman or zypper) or grab the AppImage from that page. Install it, then open DB Browser for SQLite.
  • Click New Database, give it a name like shop.db, and save it somewhere you will find again. If an "Edit table definition" pop-up appears, click Cancel, we will create our table with SQL instead.
  • Click the Execute SQL tab. That is where you type or paste SQL. Run it with the blue ▶ play button (or press Ctrl+Enter). Results from a SELECT show in a grid at the bottom.
  • One gotcha: DB Browser does not save changes to the file until you click Write Changes in the top toolbar. Do that after you add or change data. Just reading with SELECT never needs it.

Two other options, named so you recognize them if you see them: the sqlite3 shell is a command-line program (you type sqlite3 shop.db in a terminal to get a sqlite> prompt); and if you have VS Code with Python set up, you can run SQL from a short Python script using the built-in sqlite3 module, which is exactly what Level 5 covers. For now, DB Browser is the simplest, stick with it.

SQL is a standard, but each database (SQLite, PostgreSQL, MySQL) has small differences. We use SQLite, and I'll flag where Postgres or MySQL do it differently. One thing you'll see below: -- starts a comment in SQL (the rest of that line is a note for humans, ignored by the database).

B. SELECT ... FROM: asking for columns

The core read query is SELECT <columns> FROM <table>;. SELECT lists what you want back; FROM says which table to read. The semicolon ; ends the statement (the shell needs it; get in the habit everywhere).

The * is a shortcut meaning every column. Handy for a quick look, but in real queries you usually name the columns you actually want, comma-separated, in any order:

SELECT * FROM customers;          -- every column of every row
SELECT name, city FROM customers; -- just those two columns, in that order

Keywords like SELECT and FROM are written in UPPERCASE by convention. They are not case-sensitive (select works too), but uppercase keywords with lowercase table and column names is the readable norm. The result of a SELECT is itself a little table of rows and columns, called a result set. Selecting only reads, it never changes the stored data.

Here is what asking for two columns gives back:

SELECT name, plan FROM customers; · result
name   plan
Amara  Pro
Ben    Basic
Chen   Pro
Diego  Basic
Esi    Pro
Your turn Pick your columns

C. Aliases and computed columns

You can rename a column in the result with AS. This is called an alias. The stored column keeps its real name; only the result's header changes:

SELECT name AS customer FROM customers;  -- header reads "customer", data unchanged

The SELECT list can hold expressions, not just plain columns. SQL does math with + - * /, and it computes the expression once per row, producing a new output column:

SELECT name, monthly_fee * 12 AS yearly_fee FROM customers;
result
name   yearly_fee
Amara  480
Ben    240
Chen   480
Diego  240
Esi    480

You can even SELECT with no table at all, as a calculator. Normal math precedence applies (* and / before + and -):

SELECT 40 * 12;      -- one value: 480
SELECT 20 + 5 * 2;   -- 5*2 first, then +20: 30

One trap to lock in now: when both sides of / are whole numbers, SQLite divides as whole numbers and throws away the remainder. So SELECT 7 / 2; gives 3, not 3.5. To get a decimal, make one side a decimal: SELECT 7.0 / 2; gives 3.5. (This is the same idea as Python's // floor division from the Python track.)

Expressions can build text too. The || operator glues strings together (concatenation): SELECT name || ' from ' || city FROM customers; produces values like Amara from Austin. (In MySQL you'd use CONCAT(...) instead; || is standard SQL and works in SQLite and Postgres.)

Your turn Compute a column

Run SELECT name, monthly_fee * 12 AS yearly_fee FROM customers;. Then try SELECT 100 / 8; and predict its value before you run it (remember the integer-division trap).

Show the answer to the second one 
SELECT 100 / 8;   -- both whole numbers, remainder dropped: 12
SELECT 100.0 / 8; -- one decimal side: 12.5

D. DISTINCT: each unique value once

A column usually repeats values (several customers live in Austin). Put DISTINCT right after SELECT and the database collapses duplicate rows, returning each distinct value just once. Compare the two:

SELECT city FROM customers;           -- 5 rows, one per customer (Austin and Denver repeat)
SELECT DISTINCT city FROM customers;  -- 3 rows: Austin, Denver, Boston
SELECT DISTINCT city FROM customers; · result
city
Austin
Denver
Boston

DISTINCT looks at the whole selected row, not just one column. So SELECT DISTINCT city, plan FROM customers; keeps each unique combination of city and plan. (This is SQL's version of finding the unique values in a set, like the dedupe you did with a Python set.)

Your turn Dedupe a column

Run SELECT plan FROM customers; and count the rows, then run SELECT DISTINCT plan FROM customers; and count again. Confirm the second returns fewer rows.

E. LIMIT: capping how many rows come back

Real tables can have millions of rows. LIMIT n returns at most the first n rows, which is perfect for a quick peek without dumping everything:

SELECT * FROM customers LIMIT 3;   -- at most 3 rows come back

An honest caveat: without an ORDER BY (that's next session), the database may return rows in any order it likes. So "the first 3" is not guaranteed to be any particular 3 rows, only that you get at most 3. For a quick look that's fine; when order matters, you'll add ORDER BY in Session 2. (In SQL Server the keyword is TOP instead: SELECT TOP 3 * FROM ...; SQLite, Postgres and MySQL all use LIMIT.)

Now put the whole session together. The milestone query names its columns, computes one of them, gives it an alias, and caps the rows, everything from A to E in one statement:
