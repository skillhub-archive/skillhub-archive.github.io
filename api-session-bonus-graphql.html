GraphQL: one endpoint, the shape you ask for

Every API in the ten sessions gave you a URL per thing and decided for you what came back. GraphQL turns both round: one address for the whole API, and the client writes down exactly which fields it wants, nested as deep as it likes, and gets back that shape and nothing else. This workbook sends it, reads its schema, breaks it, writes to it, weighs what it costs against everything Sessions 1 to 10 relied on, and then designs a schema of its own, Level 3’s habit in a new language.

Milestone Answer a screen with one GraphQL query and count what REST would have cost, then write a schema as the contract for an API you designed.
{ }

Open Postman before you start, signed in with the free account from Session 4. Everything today is an ordinary HTTP request, so the web app works as it is, through the Cloud Agent. Postman also has a separate GraphQL request type; section A says why this workbook does not use it.

No signup, no key, and nothing you send is kept. Both services today are public practice APIs. One of them, GraphQLZero, is built on Session 1’s jsonplaceholder, so the posts and people are ones you have met.

A. One request, the shape you asked for

Picture a screen that shows one blog post as a card: its title, the name of the person who wrote it, and its comments. With Session 1’s tools you could fill it from jsonplaceholder, and it takes three requests, one of which has to wait for another:

one post card, the REST way · captured live
> GET https://jsonplaceholder.typicode.com/posts/1
{ "userId": 1, "id": 1, "title": "sunt aut facere repellat ...",
  "body": "quia et suscipit ..." }               the author is only a number

> GET https://jsonplaceholder.typicode.com/users/1   needs the 1 from above
{ "id": 1, "name": "Leanne Graham", "username": "Bret",
  "email": ..., "address": {...}, "phone": ..., "website": ...,
  "company": {...} }                             eight fields; you wanted one

> GET https://jsonplaceholder.typicode.com/posts/1/comments
[ { "postId": 1, "id": 1, "name": ..., "email": ..., "body": ... },
  ... ]                                          five comments, five fields each

Two problems, each with a name. Over-fetching is getting fields you did not want: the card needs one field of the user, and the answer carried eight, address and company included. Under-fetching is the opposite: no single answer had everything, so the client had to make more requests, and the second could not even start until the first said who wrote the post. On a phone with a slow connection, each extra round trip is time the screen sits empty.

To be fair to REST: an API can offer a way round this, and jsonplaceholder does. GET /posts/1?_expand=user&_embed=comments returns the post with the user and all five comments inside it, in one request. But it returns every field of each, and the parameters are this one server’s own invention, which another API may not have. The server still decides the shape.

GraphQL is a query language for APIs: a small language in which the CLIENT writes down the shape of the answer it wants. Three ideas carry all of it:

  • One endpoint. The whole API lives at one URL. Today’s first is https://graphqlzero.almansi.me/api. There is no /posts/1 and no /users/1: what you want is said in the request body instead.
  • A query. The body carries text written in GraphQL’s own language, called a query. A pair of braces { } holds a selection set: the list of fields you want, written as bare names, one per line or separated by spaces. A field can take an argument in round brackets, post(id: 1), which works like a REST path or query parameter: it says which post.
  • Nesting. When a field is an object rather than a single value, as a post’s user is, you give it braces of its own and name the fields you want from inside it. So one query can walk from a post to its author in a single request.

Here is the card’s first two parts, as one query, and the answer:

the same card, the GraphQL way · captured live
> POST https://graphqlzero.almansi.me/api
> {
>   post(id: 1) {
>     id
>     title
>     user {
>       name
>     }
>   }
> }
200 OK
{ "data": { "post": { "id": "1",
                      "title": "sunt aut facere repellat ...",
                      "user": { "name": "Leanne Graham" } } } }

Read the answer against the query. It sits inside a top-level field called data, and below that it has exactly the query’s shape: a post holding id, title and a user holding only name. No body, no userId, no email. The fields also come back in the order you asked for them: the GraphQL specification says a server “should preserve the order of requested fields”, and this one does. One more detail: "id": "1" is in quotes, a string, where jsonplaceholder sent the number 1. Section B explains why.

How it travels. On the wire this is still Session 1’s HTTP: a POST with a JSON body. Postman takes the query text you type and sends it as one JSON field called query, with Content-Type: application/json. Sent to postman-echo, which echoes a request back as in Session 1, a query arrives like this:

what Postman actually sends · captured live, with newman
content-type: application/json
{"query":"{ post(id: 1) { title } }"}           the query text, as one JSON string

Postman offers two ways to send this, and you want the ordinary one. Postman has a dedicated GraphQL request type, but its own documentation says that in the web app it needs the Postman Desktop Agent, a separate program you install, and that such requests “can’t be saved to collections that contain HTTP requests”. The ordinary HTTP request does everything this workbook needs, in the same collections as every earlier session: set the method to POST, open Body, and pick GraphQL in the row of body types. Two boxes appear, QUERY and GRAPHQL VARIABLES, and you type the query into the first. That was checked in the web app through the Cloud Agent.

B. The schema is the contract

Session 5 wrote a contract as tables in a collection’s description: every field, its type, and whether it is required. Every GraphQL API has the same thing built in, called its schema: a typed list of everything a client can ask for. It is written in GraphQL’s schema definition language, SDL for short, and the server enforces it, which a table in a description never could. Here is part of GraphQLZero’s:

part of GraphQLZero’s schema · read from the server
type Query {
  post(id: ID!): Post                one post, by its id
  user(id: ID!): User
  ...
}

type Post {
  id: ID
  title: String
  body: String
  user: User                         an object: give it braces
  comments(options: PageQueryOptions): CommentsPage
}

Read it a line at a time. type Post { ... } defines a type, a kind of object, and lists its fields, each as name: Type. type Query is special: its fields are the places a query can start, which is why your query opened with post(id: 1). The types a field can have come in two kinds:

Type
Holds
Notes
String
text
as in JSON
Int
a whole number
Float is the one with a decimal point
Boolean
true or false
as in JSON
ID
an identifier
always comes back as a string, whatever it looks like: Session 5’s isbn reasoning, made a rule. In a query, 1 and "1" both work
Post, User, ...
an object, defined by its own type
a field of this kind needs braces and a selection

The first four rows, plus Float, are the five built-in scalars: single values, with nothing inside them to select. That is why "id": "1" came back in quotes: the schema says ID, and an ID always comes back as a string. Two marks change a type:

  • ! means non-null: the value is never null. On an argument, post(id: ID!), it means the argument is required. On a field, it is the server’s promise that the field always has a value.
  • Square brackets mean a list: [Language] is a list of languages. The marks combine, and position matters: [Language!]! is a list that is never null, holding items that are never null. It can still be empty.

GraphQLZero puts ! on almost nothing it sends back, so any field might be null. Today’s second service is stricter. The Countries API, at https://countries.trevorblades.com/graphql, describes every country, and its schema says:

part of the Countries API’s schema · read from the server
type Query {
  country(code: ID!): Country
}

type Country {
  name: String!                      always there
  capital: String                    may be null
  currency: String
  languages: [Language!]!
  ...
}

Every country has a name, but not every country has a capital, and the schema tells you so before you ask. Antarctica, whose code is AQ, has neither a capital nor a currency:

a field the schema allowed to be null · captured live
> { country(code: "AQ") { capital currency } }
200 OK
{ "data": { "country": { "capital": null, "currency": null } } }

Asking the server for its own schema. A GraphQL server answers questions about its schema through the same endpoint, in the same language, which is called introspection. The fields for it start with two underscores. The smallest is __typename, which any selection may include and which names the type you are looking at. __type(name: "Post") describes one type:

introspection · captured live
> { __typename }
{ "data": { "__typename": "Query" } }

> { __type(name: "Post") { fields { name } } }
{ "data": { "__type": { "fields": [ { "name": "id" }, { "name": "title" },
  { "name": "body" }, { "name": "user" }, { "name": "comments" } ] } } }

Postman uses introspection for you. When you type a GraphQL URL into a request with a GraphQL body, it fetches the schema, says Schema Fetched in green beside the body types (with an Auto Fetch menu next to it), and then suggests field names as you type: inside post(id: 1) { }, typing t offered title and __typename. That is the schema acting as a contract in the most practical way: the editor will not even suggest a field the API does not have.

C. Arguments anywhere, and variables

Any field can take arguments, not only the first. The card also wants the post’s comments, and comments takes one argument, options, whose value is an input object: braces holding named values, like a JSON object whose keys have no quote marks. GraphQLZero wraps every list in a page object, with the items under data and a count under meta:

an argument on a nested field · captured live
> { post(id: 1) {
>     comments(options: {paginate: {limit: 2}}) {
>       data { id }
>       meta { totalCount } } } }
{ "data": { "post": { "comments": {
    "data": [ { "id": "1" }, { "id": "2" } ],
    "meta": { "totalCount": 5 } } } } }

limit: 2 is Session 4’s page size: two comments came back. totalCount still says 5, because it counts every comment the post has, not the ones on this page, the same job x-total-count did in Session 4.

One thing this server does that its schema does not tell you. Ask for the count without any options, and it answers null:

the same count, with no options · captured live
> { post(id: 1) { comments { meta { totalCount } } } }
{ "data": { "post": { "comments": { "meta": null } } } }

> { post(id: 1) { comments(options: {}) { meta { totalCount } } } }
{ "data": { "post": { "comments": { "meta": { "totalCount": 5 } } } } }

Empty options, {}, are enough. The schema allows it, because meta has no !, but no schema can say when a nullable field will be null, and only trying it does. Note that null here does not mean “no comments”: zero would be 0. Read the value itself, as Session 9 read "missing": true, not just whether the field came back.

Variables. Every query so far had its values typed straight into the text: id: 1, code: "BR". Session 9 showed where that leads: a value pasted into text written in another language breaks the moment it contains a character that means something there, which is why you met encodeURIComponent and JSON.stringify. GraphQL has its own answer, built in. You declare a variable at the top, use it where the value goes, and send the value separately:

a query with a variable · captured live
> query Card($id: ID!) {          QUERY box
>   post(id: $id) {
>     title
>     user { name }
>   }
> }
> { "id": "2" }                    GRAPHQL VARIABLES box
{ "data": { "post": { "title": "qui est esse",
                      "user": { "name": "Leanne Graham" } } } }

The first line now has three parts. query is the keyword for an operation that reads; until now it was left out, which GraphQL allows for a query with no name and no variables. Card is the operation name, a label you choose, so that a person reading a server’s records can tell one kind of request from another. ($id: ID!) declares one variable: its name always starts with $, and it has a type, here a required ID, exactly as the schema’s post(id: ID!) wants. In the body, $id stands where the value goes. The values themselves are JSON, typed into the GRAPHQL VARIABLES box with the names written without the $, and Postman sends them alongside the query:

what Postman sends · captured live, with newman
{"query":"query Card($id: ID!) {\n  post(id: $id) { title }\n}",
 "variables":{"id":"1"}}

An operation can declare several variables at once, separated by commas, as in query Two($first: ID!, $second: ID!), and the variables box then holds a value for each. So the query text never changes, and only the variables do. A value with a quote mark or an & in it is just JSON in the variables, never GraphQL text. Leave the variables box empty and Postman sends no variables at all, and this server says so, in a body you have to read, because the status is 200:

a required variable left out · captured live
200 OK
{ "errors": [ { "message": "Variable \"$id\" of required type \"ID!\" was not provided.",
    "locations": [ { "line": 1, "column": 12 } ],
    "extensions": { "code": "BAD_USER_INPUT" } } ] }

D. When it goes wrong: read the body

A GraphQL answer holds data, errors, or both. To see why there are three possibilities, follow what a GraphQL server does with a request, in an order nothing can skip, because each step needs the one before it:

Step
What happens
If it fails
1 Read the JSON
take query and variables out of the request body
nothing to run: an error, no data
2 Parse
turn the query text into a structure: fields, arguments, braces
broken text, like a missing brace: an error, no data
3 Check
check that structure against the schema (does every field exist on its type, does every argument fit?), then check the variables against the types the query declared
a misspelt field, or a missing variable: an error, no data
4 Execute
fetch the value of every field you asked for
a field that fails is null, with an error beside the rest of the data
5 Respond
send data, and errors if there were any

So a request that fails before step 4 never runs at all, and its answer has errors and no data: nothing was fetched, so nothing can come back. Only step 4 can produce some data and some errors together. Misspell a field and step 3 stops it, with a message that helps:

the same mistake, two servers · captured live
> POST https://graphqlzero.almansi.me/api
> { post(id: 1) { titel } }
400 Bad Request
{ "errors": [ { "message": "Cannot query field \"titel\" on type \"Post\".
    Did you mean \"title\"?", "locations": [ { "line": 3, "column": 5 } ],
    "extensions": { "code": "GRAPHQL_VALIDATION_FAILED" } } ] }

> POST https://countries.trevorblades.com/graphql
> { country(code: "BR") { nam } }
200 OK
{ "errors": [ { "message": "Cannot query field \"nam\" on type \"Country\".
    Did you mean \"name\"?", "locations": [ { "line": 3, "column": 5 } ],
    "extensions": { "code": "GRAPHQL_VALIDATION_FAILED" } } ] }

The same failure, two different status codes. Both bodies are the same error, with the same code under extensions, the place a GraphQL error keeps machine-readable details. locations points at a line and column. On GraphQLZero they are in the query you sent (both queries here were sent spread over five lines, as you would type them); the Countries API counts them in its own re-formatted copy of your query, so even a one-line query there reports line 3. But one server says 400 and the other 200. GraphQL itself says nothing about HTTP status codes; how GraphQL should use HTTP is being written down separately, and that document is still a working draft. Some servers answer 200 to any request they could read, and others use 4xx codes for one they could not run.

The Accept header can change it, too. Session 2 taught Accept as a request about the format of the answer. GraphQL’s draft adds a media type of its own, application/graphql-response+json, and a server that knows it may use more precise status codes for a client that asks for it. Postman sends Accept: */*, anything at all, by default. Send the Countries mistake again with the header set:

the Countries mistake, asking for the GraphQL media type · captured live
> Accept: application/graphql-response+json
400 Bad Request
Content-Type: application/graphql-response+json; charset=utf-8
{ "errors": [ { "message": "Cannot query field \"nam\" on type \"Country\". ..." } ] }

Same body, now 400. And on GraphQLZero, a missing variable (section C) was 200 while a misspelt field was 400: one server, two habits. So the rule is Session 9’s: read the body every time. If it has errors, something went wrong, whatever the status says.

Field names are case-sensitive. Title is not title: GraphQLZero answers it 400 with Cannot query field "Title" on type "Post". Did you mean "title"?

“Not found” is not an error. In REST, a post that does not exist is a 404. In GraphQL the request was perfectly valid, so it runs, and the honest answer is a null:

things that are not there · captured live
> { post(id: 9999) { id title } }              GraphQLZero
200 OK
{ "data": { "post": { "id": null, "title": null } } }

> { country(code: "ZZ") { capital } }          Countries: no such code
200 OK
{ "data": { "country": null } }

> { country(code: "br") { capital } }          lower case
200 OK
{ "data": { "country": null } }

Countries answers the clean way: the whole country is null, which its schema allows (country(code: ID!): Country, no !). GraphQLZero hands back a post whose every field is null, a post-shaped nothing, so a client that checks only whether post is there would be fooled; check a field you know every real post has, like id. And the third shows that values are case-sensitive as well as names: country codes are capitals, and br matches nothing. Session 9’s "missing": true was the same idea in another API’s words.

One quirk to know about, not to learn from. The Countries API breaks the order rule from section A in one place: it always puts name last. Ask for name capital currency and you get capital, currency, name; every other field keeps your order. The specification says “should”, not “must”, so a server is allowed to, and nothing you do here depends on order.

E. Writing: mutations, and why it is all POST

Reading is a query. Changing something is a mutation: an operation whose fields make a change and then answer with what changed. The schema lists them under type Mutation, as it listed reads under type Query:

part of GraphQLZero’s schema · read from the server
type Mutation {
  createPost(input: CreatePostInput!): Post
  updatePost(id: ID!, input: UpdatePostInput!): Post
  deletePost(id: ID!): Boolean
  ...
}

input CreatePostInput {          input, not type: a shape you send
  title: String!
  body: String!
}

An input is a type for values you send rather than values you get back. It is declared with the keyword input instead of type, and it can never contain an object type like Post or User, so nothing in it needs a selection. A mutation starts with the keyword mutation, and since a mutation’s field answers with an object, you select what you want back, as with any other field:

a mutation, then a look for what it made · captured live
> mutation AddPost($input: CreatePostInput!) {
>   createPost(input: $input) { id title }
> }
> { "input": { "title": "Hello", "body": "First post" } }
200 OK
{ "data": { "createPost": { "id": "101", "title": "Hello" } } }

> { post(id: 101) { id title } }
200 OK
{ "data": { "post": { "id": null, "title": null } } }

If that feels familiar, it should. GraphQLZero is built on jsonplaceholder, and it behaves the same way Session 1 told you about: a write is answered convincingly, new id and all, and never kept. Post 101 does not exist a moment later. It is a safe place to practise exactly because nothing sticks.

Why everything is POST. A query reads and a mutation writes, but you sent both as POST. Session 5 taught that the method says what a request does: GET only reads and can be repeated and cached, POST may change something. GraphQL moves that meaning into the body: the keyword query or mutation says it, and the HTTP method mostly does not. graphql.org’s guide to serving GraphQL over HTTP says a server “must handle the HTTP POST method for query and mutation operations, and may also accept the GET method for query operations”, with the query in the URL’s query string; a mutation is never sent as GET. So POST is the one method every server takes, and GET is optional. GraphQLZero refuses a plain one:

the card query as a GET · captured live
> GET https://graphqlzero.almansi.me/api?query={ post(id: 1) { title } }
400 Bad Request
{ "errors": [ { "message": "This operation has been blocked as a potential
    Cross-Site Request Forgery (CSRF). Please either specify a 'content-type'
    header ... or provide a non-empty value for one of the following headers:
    x-apollo-operation-name, apollo-require-preflight", ... } ] }

Cross-Site Request Forgery, CSRF, is an attack in which a web page you are visiting quietly sends a request to another site, and your browser attaches your cookies for that site as it does for any request to it. A plain GET is the easiest such request for a hostile page to make, so this server refuses one unless it carries a header a hostile page cannot easily add. Between that and the simplicity of one method, most GraphQL traffic is POST.

Session 8 still applies. Send the same createPost twice and a real server makes two posts: a mutation is no more idempotent than a POST was, and GraphQL has no idempotency key built in. If a mutation can be retried, its design has to handle that, with Session 8’s key or by making the mutation safe to repeat.

Caching. Session 2 taught the headers that let a cache keep an answer: Cache-Control says for how long, and ETag lets it check later whether the answer changed. What a cache files its copy under is the request’s URL: a browser, or a shared cache sitting between many clients and the server, stores the answer to a GET under that URL, so the next GET of the same URL can be answered without asking the server. Answers to POST are, in practice, not kept: RFC 9110 says “Responses to POST requests are only cacheable when they include explicit freshness information ... and a Content-Location header field that has the same value as the POST’s target URI”, and GraphQLZero’s answers carry neither. graphql.org’s own caching page states the problem plainly: “In GraphQL, there’s no URL-like primitive that provides this globally unique identifier for a given object.” Compare the headers on the same post fetched both ways:

the same post, two caching stories · captured live
> GET https://jsonplaceholder.typicode.com/posts/1
Cache-Control: max-age=43200                     keep it for 12 hours
etag: W/"124-yiKdLzqO5gfBrJFrcdJ8Yq0LGnU"
cf-cache-status: HIT                             a shared cache answered

> POST https://graphqlzero.almansi.me/api
> { post(id: 1) { id title } }
cache-control: no-store                          keep nothing
x-cache: Miss from cloudfront                    the shared cache passed it on

GraphQL clients make up for it inside the app instead: a client library keeps each object it has seen, keyed by its type and id, which is why graphql.org recommends every object have an id field. Some servers also accept queries as GET, which graphql.org notes can “facilitate HTTP caching or edge caching in a content delivery network”. Both are extra work the REST version got for free.

Cost to the server, and the N+1 problem. A GraphQL server finds each field’s value with a small piece of code of its own, called a resolver. That keeps the server’s code tidy, and it has a trap that graphql.org names: ask for 20 posts and each one’s author, and a naive server runs one lookup for the list of posts and then one more for each post’s author, 20 more. graphql.org calls this “the N+1 problem, where an initial request to an underlying data source ... leads to N subsequent requests to resolve the data for all of the requested fields”. The usual fix is batching, collecting those 20 author lookups and sending them as one, with a tool like DataLoader. You will not write a server in this workbook, but the client-side lesson is real: a short query is not necessarily a cheap one. The GraphQL-over-HTTP draft lets a server add checks of its own, and names a “depth limit, complexity limit” as examples: a limit on how deep or how costly a query may be, the way Session 4’s APIs limited how often.

Optional: could Session 6’s mock play a GraphQL server? Postman’s documentation says a mock can answer GraphQL by matching the request body saved in an example. Tried on a real mock with two examples, book 8 and book 9: book 8’s saved query got book 8, even written on one line, because the mock ignores spacing. But anything else fell to Session 6’s tie-break, which happened to pick book 9 every time: book 8 with fewer fields (it sent book 9, with all its fields), with its fields in another order, with an operation name, or with a field misspelt (200 and the canned data, no error). With x-mock-match-request-body: true, the ones tried that way became the mock’s own 404. A mock never validates a query and never returns only the fields asked for, which is the whole idea of GraphQL, so this workbook designs its schema on paper instead.

G. Designing: a schema as the contract

Level 3 designed before it built: Session 5 wrote the contract first, as tables, and everything after followed it. In GraphQL the schema IS that contract, written in a language a server can enforce and a tool like Postman can read. So designing a GraphQL API starts by writing SDL. Take the brief from Session 5’s milestone, the library’s members: “A member has a name and an email address, and may have a phone number. No two members may share an email address. The library assigns member numbers. Staff need to list the members, look one up, sign one up”. Here it is as a schema, a decision per line:

Members, as a GraphQL schema · checked with graphql-js
"""A library member. Email addresses are unique."""
type Member {
  id: ID!               the member number: the library assigns it
  name: String!         required in the brief, so never null
  email: String!
  phone: String         "may have": no !, so it can be null
}

input NewMember {       what staff send to sign one up
  name: String!
  email: String!
  phone: String         no id: the library sets it
}

type Query {
  member(id: ID!): Member                    null if there is none
  members(page: Int, limit: Int): [Member!]!
}

type Mutation {
  """Errors: email_taken."""
  signUpMember(input: NewMember!): Member!
}

Each line is one of Session 5’s decisions in a new notation:

  • Required or optional becomes ! or not. Session 5’s “Required” is !; “may have” is a type without one.
  • Who sets a field decides where it appears. Session 5 said the server sets the id and ignores one sent by a client. So id is in Member, which comes back, and not in NewMember, which is sent: a client cannot even try.
  • “Not found” is a nullable return type. member(id: ID!): Member, without !, is how the schema says a lookup may find nothing, exactly as Countries’ country did in section D. Session 5’s 404 becomes a null.
  • A list that may be empty is [Member!]!. The list itself is always there, possibly empty, and holds no null members. page and limit are Session 4’s paging, as optional arguments.
  • Rules SDL cannot say go in descriptions. “No two members may share an email” is not a type, so the schema cannot enforce it. Text in triple quotes """...""" just before a type or field is its description, which introspection hands to anyone who asks, so the rule is at least written where a client’s tools can find it. A line starting # is a comment, for the schema’s authors only.

Where Session 5’s refusals go. Some disappear: a signUpMember with no name, or a name that is a number, is refused at step 3 before anything runs (section D), with no code of yours involved. The rest, like an email that is already taken, come back in errors, and the contract names a code for each in extensions, the way GraphQLZero named BAD_USER_INPUT. So the description says it: email_taken, Session 5’s error-code habit with a new home.

Changing it later, Session 5 section E again. Adding a field is not breaking: no query asked for it, so no query changes. Removing or renaming one is breaking, because a query that names it now fails validation. Instead of a /v2, GraphQL marks the old field and keeps it working while clients move: phone: String @deprecated(reason: "Use phones."). Introspection reports the field as deprecated, with the reason, to a client that asks for deprecated fields too (they are left out unless it does), so clients can find it before it goes.
