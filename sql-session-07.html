A. From querying to building: DDL vs DML

Back in Session 1 you pasted a setup script full of CREATE TABLE and INSERT lines and were told to just run it, that it would be explained later. This is later. Those CREATE TABLE statements are DDL, Data Definition Language: the commands that define and change the structure of your database (CREATE to build a table, ALTER to change one, DROP to delete one). Everything else you have done since (SELECT, INSERT, and later UPDATE and DELETE) is DML, Data Manipulation Language: commands that read and change the data inside those tables. DDL builds the container; DML fills and reads it.

Before you build a table, you model it: decide its shape. The guiding idea is one fact in one place. That is why back in Session 4 the shop was split into two tables: customer facts (name, city, plan) live once in customers, and each order lives in orders with a customer_id pointing back, rather than copying the customer name onto every order. Part of modeling is choosing a primary key: one column that uniquely and stably identifies each row. A plain integer id is the usual choice because it never changes and is guaranteed unique. Decide the shape before you build, then the CREATE TABLE just writes it down.

First, make sure you still have both tables from earlier. If shop.db is open with customers and orders, you are set. If you lost it, run the full setup below once, then Write Changes.

B. Storage classes and type affinity

When you write price REAL or id INTEGER in a CREATE TABLE, you are declaring a type. But SQLite handles types differently from most databases, and this trips people up, so it is worth meeting head-on. Under the hood SQLite has just five storage classes a value can actually be stored as: NULL, INTEGER, REAL (a decimal number), TEXT, and BLOB (raw bytes). The type you declare on a column is treated as an affinity: a preference for how to store values, not a strict rule that rejects mismatches.

To see what a value was actually stored as, use the typeof() function: you pass it a value or column and it returns the storage-class name ('integer', 'text', and so on) as text. Watch what an INTEGER column does with four different inserts. Create a scratch table, put a value in, and ask typeof:

-- a throwaway table with one INTEGER column, to watch affinity in action
DROP TABLE IF EXISTS demo;   -- clear any earlier demo so this runs cleanly
CREATE TABLE demo (label TEXT, q INTEGER);
INSERT INTO demo VALUES ('the text 123',  '123');
INSERT INTO demo VALUES ('the text hello','hello');
INSERT INTO demo VALUES ('the number 4.0', 4.0);
INSERT INTO demo VALUES ('the number 4.9', 4.9);
SELECT label, q, typeof(q) FROM demo;
result · what an INTEGER column actually stored (rows in insert order; the label names each)
label           q      typeof(q)
the text 123    123    integer
the text hello  hello  text
the number 4.0  4      integer
the number 4.9  4.9    real

Read those rows carefully, because they are the whole lesson. The text '123' could be read as a whole number, so the INTEGER affinity converted it and stored the integer 123. The text 'hello' could not be converted, so SQLite gave up and stored it as text anyway. The value 4.0 was a clean whole number, so it was narrowed to the integer 4; 4.9 was not, so it stayed a real. That third and fourth rows are the classic trap: two very similar numbers land in two different storage classes. This is the answer to the puzzled question "why did my number come back as text?" or "why did my decimal lose its point?": affinity converted what it could and stored the rest as-is.

Cross-database note. This store-anything behavior is specific to SQLite. PostgreSQL, MySQL and SQL Server are strictly typed: putting 'hello' into an integer column raises an error instead of quietly storing text. If you want that strictness in SQLite, declare the table STRICT (write CREATE TABLE ... STRICT, available since SQLite 3.37), and it will reject any value it cannot store as the declared type. For this session we use ordinary (non-strict) tables, so keep typeof() in your back pocket.

C. Constraints: making a table defend itself

Now the heart of the session. A CREATE TABLE takes a name and then, in parentheses, a column-definition list: one entry per column, separated by commas. In the general form CREATE TABLE name (col TYPE, col TYPE, ...), the word name is a placeholder for the table name you choose, and each col TYPE is a placeholder for a real column name and its type (you do not literally type the words name, col or TYPE). After a column's type you can add constraints: rules the table will enforce on every row, refusing any insert that breaks them. Here are the five you need, each introduced before we use it:

  • NOT NULL means the column can never be empty; an insert that leaves it out (and gives no default) is refused.
  • UNIQUE means no two rows may share that column's value.
  • DEFAULT value supplies a value to use when the insert omits the column; here value is a placeholder for whatever default you want, such as DEFAULT 1.
  • CHECK (expr) refuses any row where the condition is false; expr is a placeholder for any boolean condition, such as CHECK (price > 0) or a range check like CHECK (rating BETWEEN 1 AND 5) (BETWEEN is from Session 2).
  • PRIMARY KEY marks the row's unique identifier; on an INTEGER PRIMARY KEY column SQLite also auto-assigns an id if you do not supply one.

Put them together and you can model the shop's products catalog so the table itself guarantees the data stays clean. Read the definition top to bottom: an integer primary key, a required and unique sku, a required name, a required price that must be positive, and an in_stock flag that defaults to 1 (in stock) when an insert does not mention it:

-- model the products catalog: every column carries the rules it should obey
CREATE TABLE products (
  id        INTEGER PRIMARY KEY,
  sku       TEXT    NOT NULL UNIQUE,
  name      TEXT    NOT NULL,
  price     REAL    NOT NULL CHECK (price > 0),
  in_stock  INTEGER NOT NULL DEFAULT 1
);

Now seed it with five products. Notice the insert lists only four columns and leaves in_stock out on purpose, to watch the DEFAULT fill in:

-- five starter products; in_stock is omitted so DEFAULT 1 fills it
INSERT INTO products (id, sku, name, price) VALUES
  (1, 'BOX-S', 'Small box',    2.50),
  (2, 'BOX-L', 'Large box',    4.00),
  (3, 'TAPE',  'Packing tape', 3.25),
  (4, 'WRAP',  'Bubble wrap',  6.75),
  (5, 'LABEL', 'Label sheet',  1.20);

Run SELECT * FROM products ORDER BY id; and here is what you get. Two things to notice: in_stock is 1 on every row even though you never typed it (the DEFAULT did that), and the prices you wrote as 2.50 and 4.00 print as 2.5 and 4.0 because they are stored as real numbers, not as the text you typed:

result · SELECT * FROM products ORDER BY id
id  sku    name          price  in_stock
1   BOX-S  Small box     2.5    1
2   BOX-L  Large box     4.0    1
3   TAPE   Packing tape  3.25   1
4   WRAP   Bubble wrap   6.75   1
5   LABEL  Label sheet   1.2    1

The table now defends itself. Try to insert a second product that reuses an existing sku and the UNIQUE rule refuses it, naming the column and table that failed:

-- BOX-S already exists, so the UNIQUE rule on sku rejects this
INSERT INTO products (id, sku, name, price)
VALUES (6, 'BOX-S', 'Another small box', 5.00);
Error: UNIQUE constraint failed: products.sku

Aside: auto-assigned ids. Because id is INTEGER PRIMARY KEY, SQLite will hand out an id for you if you omit it, so you can insert with just (sku, name, price) and let the id fill itself. There is a stricter variant, INTEGER PRIMARY KEY AUTOINCREMENT, that guarantees an id is never reused even after deletes; it is slower and rarely needed, so plain INTEGER PRIMARY KEY is the everyday choice. Other databases spell auto-numbering differently: MySQL uses AUTO_INCREMENT, PostgreSQL uses SERIAL or IDENTITY, and SQL Server uses IDENTITY. The constraints themselves (NOT NULL, UNIQUE, DEFAULT, CHECK, PRIMARY KEY) are standard across all four.

D. Foreign keys in DDL, and turning them on

Back in Session 4 you learned that orders.customer_id is a foreign key: it holds a value that must match an id in customers, linking each order to the customer who placed it. In DDL you declare that link right on the column with REFERENCES, as the setup script has done all along: customer_id INTEGER REFERENCES customers(id). That one clause says "the value here should be an existing customers.id."

Here is the gotcha, first flagged in Session 4 and worth proving now: SQLite does not enforce foreign keys unless you turn them on. The enforcement is off by default for each new connection, so an insert with a nonexistent customer slips in silently. You switch it on per connection with a PRAGMA (a SQLite setting command):

-- turn on foreign-key enforcement for this connection (off by default)
PRAGMA foreign_keys = ON;

-- customers only go up to id 10, so customer 999 does not exist
INSERT INTO orders (id, customer_id, amount, order_year)
VALUES (14, 999, 50, 2024);
Error: FOREIGN KEY constraint failed

With the pragma on, that orphan insert is refused. With it off (the sqlite3 command-line default), the exact same insert succeeds and you end up with an order pointing at a customer who does not exist, which is how bad data quietly creeps in. The good news: DB Browser for SQLite turns foreign keys on for you, so if that is your tool you are already protected; in the sqlite3 shell or from code, run the pragma yourself once per connection.

Aside: what happens to children when a parent is deleted. You can extend a foreign key with an action, for example REFERENCES customers(id) ON DELETE CASCADE (delete a customer and their orders go too) or ON DELETE SET NULL (the orders stay but their customer_id becomes NULL). These are handy but a topic of their own, so just know the phrases for now.

Cross-database note. The REFERENCES syntax is standard, but the foreign-keys-off-by-default quirk is SQLite-only. PostgreSQL, MySQL (InnoDB) and SQL Server enforce declared foreign keys automatically; there is no pragma to remember.

Your turn Turn foreign keys on and watch an orphan fail

Run PRAGMA foreign_keys = ON;, then try the orphan insert above (customer_id 999). Confirm it fails with FOREIGN KEY constraint failed. If you are curious, run PRAGMA foreign_keys = OFF; and try again to see it slip through, then turn it back ON and delete the stray row so orders stays at 13.

E. The milestone: build it and prove it defends itself

Put the whole session together. From a blank editor, model and build the products table with every constraint, seed the five rows, then deliberately attack it three ways and watch each attack bounce off a different rule. A table you can trust is one that refuses bad data on its own, and this proves yours does.

The three attacks: a duplicate sku (blocked by UNIQUE), a zero price (blocked by CHECK), and a missing name (blocked by NOT NULL). Each fails with its own specific message, telling you exactly which rule caught it. Try the whole thing yourself before peeking.
