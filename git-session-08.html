Recovery & rewriting history

Git almost never deletes a commit. It stops pointing at it. There is a log of everywhere you have been, it is on your disk right now, and it is the reason "I lost it" is nearly always false. Once you believe that, rewriting history stops being frightening, which is exactly the moment you need the one rule that keeps rewriting safe.

Milestone Recover a lost commit and tidy a messy branch before sharing it.
git

You do not need undo-lab or any other folder from an earlier session. Step one below builds a small new repository called rewrite-lab from nothing. It gets its own folder because this session rewrites history on purpose, over and over, and a lab you can throw away is what makes that comfortable rather than nerve-racking. Session 7 already told you that undo-lab was finished with, so delete it whenever you like.

No account and no network. Everything here is local, including the part about pushing to a shared copy, which uses a second repository on your own disk exactly as Session 5 did.

One thing is different about this session: a text editor is going to open, on purpose, and it is part of the interface rather than an accident. Section F tells you what will open on your machine, how to drive it, and how to back out of it before you meet it. Read that section rather than skipping it.

Learn & Do

Short concept, then immediately your turn. Run each task in your own terminal before moving on, and tick the box once you have seen the result with your own eyes.

How to read the transcripts below. A line that starts with > in blue is what you type. Everything underneath it is what Git printed back. Do not type the > itself. Three things will legitimately differ on your machine: commit hashes (short strings like 98fe89a), dates, and paths. Everything else should match.

Hashes matter more in this session than in any before it. Every section from E onward creates commits with new hashes, so yours will diverge from the printed ones almost immediately and will keep diverging. That is correct and expected. Read the printed hashes as shapes rather than as values: what matters is whether a hash changed, not what it changed to. Nothing in this session is graded on a hash.

A. The question Session 7 left you with, twice

Session 7 asked you the same question two different ways, and then stopped. The first time was after you threw a commit away with git reset --hard HEAD~1 and got it back with git reset --hard and the hash. It worked only because you had written the hash down, and Session 7 said so plainly:

"If you had not, the commit would still be sitting in the repository, unreachable and invisible to git log, and you would have no name to call it by. There is a command that gives you that name back, and it is the first thing in Session 8."

The second time was sharper. You stood on a detached HEAD, made a commit, and Git printed its hash on the way out so you could rescue it with git branch rescued <hash>. Session 7 closed the section by pointing at the obvious weakness of that:

"That worked because Git printed the hash and you were still looking at the terminal. Close the window, and you have no name for that commit and no way to list it."

Both are the same question: where do you get the name from when nobody wrote it down? The answer is a command called git reflog, and you are going to run it in about two minutes. It is worth naming what it fixes first, because the fix is bigger than the command.

Session 7 established that reset never changes the repository. It moves a branch pointer, and the commit carries on existing with nothing aimed at it. That fact is only useful if you can find the commit again, and until now finding it has depended on you having copied a hash somewhere. The reflog removes that dependency, and once it is gone, the sentence "almost nothing in Git is truly unrecoverable" stops being reassurance and starts being something you can act on.

And that is the hinge of this session. The first half is recovery, so that you believe the safety net is real. The second half is rewriting history on purpose, which is the thing the net makes safe to attempt: fixing a commit message, folding a forgotten file into the commit it belonged in, and squashing six scrappy commits into one before anybody else sees them. Recovery first, rewriting second, deliberately. Nobody should be asked to jump before they have looked at the net.

Out of scope today, named so you know they exist: git rebase --onto, which is a more surgical rebase; rerere, which memorises how you resolved a conflict so it can redo it for you; and submodules. Two more, git filter-repo and BFG, come up properly in section J, where they matter.

PowerShell writes files the way Git wants already and prints none of them.

C. git reflog: every position HEAD has held

git log answers "what is the history of this branch". git reflog answers a completely different question: "where has HEAD been". Every time HEAD moves, for any reason, Git writes a line into a local file recording where it moved to and why. Committing moves it. So does checking out, switching, resetting, merging, reverting, rebasing and cherry-picking. Run it:

run in rewrite-lab · the whole build block, played back
> git reflog
98fe89a HEAD@{0}: reset: moving to HEAD~1
5d12590 HEAD@{1}: revert: Revert "c3 add c"
98fe89a HEAD@{2}: checkout: moving from a20293697f10e2c3629cfd48e5a3190d2737a500 to main
a202936 HEAD@{3}: checkout: moving from main to HEAD~1
98fe89a HEAD@{4}: commit: c3 add c
a202936 HEAD@{5}: commit: c2 add b
3500f9d HEAD@{6}: commit (initial): c1 add a

Read that from the bottom up and it is the build block, in order. Three commits, a checkout out to an old commit, a checkout back to main, a revert, and a reset. Seven lines for seven moves, each labelled with the kind of operation that caused it. Nothing here was configured or turned on; Git has been keeping this record since Session 1 and simply never mentioned it.

Every line has the same three parts, and reading them is a skill worth slowing down for:

98fe89aThe hash of the commit HEAD was pointing at after that move. Not the commit that was made, necessarily: the position HEAD landed on.
HEAD@{0}How many moves ago. Zero is where you are now, one is the position before that, and the numbers renumber every time HEAD moves again.
reset: moving toThe kind of operation, then its own description of what it did. The label before the colon is the command that caused the move.

HEAD@{0} is not a special name for the reflog. It is a name for a commit, and it works anywhere Git wants one, exactly as Session 2 said of HEAD~1 and a raw hash. git show HEAD@{4}, git log HEAD@{2} and git reset --hard HEAD@{1} are all ordinary commands with an ordinary commit name in them. That is why the reflog rescues you: it hands you a name for a commit that has no other name left.

Do not confuse HEAD@{1} with HEAD~1. They look alike and they mean unrelated things. HEAD~1 walks one step back along the parent link, which is a fact about history. HEAD@{1} means where HEAD was standing one move ago, which is a fact about you. In a repository you have just cloned and never touched they can point at wildly different commits, or HEAD@{1} may not exist at all.

Now the two caveats, and neither is optional. The reflog is a safety net, not an archive, and it is a net with two specific holes:

it is local onlyThe reflog lives in your .git folder and is never pushed, pulled or cloned. Nobody else can see yours and you cannot see theirs.
it expiresEntries are cleaned up eventually: Git defaults to 90 days for entries still reachable from a branch and 30 days for unreachable ones. A commit you orphaned two months ago may already be gone.

The locality one is easy to prove and worth proving, because it is the half people get wrong. A fresh clone of a repository with a long and eventful history has a reflog exactly one line long:

a brand new clone of a repository that has been rewritten repeatedly
> git reflog
8d7ee70 HEAD@{0}: clone: from ../origin.git

One entry, because from this clone the only thing that has ever happened is the clone itself. Every commit, reset, amend and force push that produced the history it just downloaded happened in somebody else's folder and stayed there. So the reflog will save you from your own mistakes and never from anyone else's, and "it is in the reflog" is only ever a claim about the machine you are sitting at.

D. Getting a commit back when nobody wrote the hash down

Now the situation Session 7 set up. Make a commit that matters, then throw it away carelessly, without noting anything:

PowerShellSet-Content d.txt "important work"
Git Bash / macOS / Linuxecho "important work" > d.txt
run in rewrite-lab · commit it, then lose it
> git add d.txt

> git commit -m "d4 important work"
[main f3f21a7] d4 important work
 1 file changed, 1 insertion(+)
 create mode 100644 d.txt

> git reset --hard HEAD~1
HEAD is now at 98fe89a c3 add c

> git log --oneline --decorate=short
98fe89a (HEAD -> main) c3 add c
a202936 c2 add b
3500f9d c1 add a

Three commits again, and d.txt is no longer in the folder. As far as git log is concerned that work never happened. Session 7 would have left you stuck here unless you had copied the hash somewhere. Ask the other question instead:

run in rewrite-lab · where has HEAD been
> git reflog
98fe89a HEAD@{0}: reset: moving to HEAD~1
f3f21a7 HEAD@{1}: commit: d4 important work
98fe89a HEAD@{2}: reset: moving to HEAD~1
5d12590 HEAD@{3}: revert: Revert "c3 add c"
98fe89a HEAD@{4}: checkout: moving from a20293697f10e2c3629cfd48e5a3190d2737a500 to main
a202936 HEAD@{5}: checkout: moving from main to HEAD~1
98fe89a HEAD@{6}: commit: c3 add c
a202936 HEAD@{7}: commit: c2 add b
3500f9d HEAD@{8}: commit (initial): c1 add a

There it is, on the second line. Read the top two lines together and they tell the whole story: HEAD@{0} is the reset you just ran, and HEAD@{1} is the position HEAD held immediately before it, which is the commit the reset stepped off. The commit you lost is almost always the entry directly below the operation that lost it, and f3f21a7 is a name you can now use even though you never wrote it down.

Having found it, there are two different things you might want, and they are genuinely different rather than two spellings of one idea. Decide which before you type:

git branch <name> <hash>Put it beside your current work. Creates a name pointing at that commit and does not move you. Use this when you are unsure, because it changes nothing you already have.
git reset --hard <hash>Go back to it. Moves your current branch onto that commit and makes your files match. Use this when you know the commit is what you want to be on.

Try the cautious one first. git branch <name> <hash> is the command Session 7 met on the way out of a detached HEAD, and it behaves the same here:

run in rewrite-lab · give the lost commit a name, without moving
> git branch rescued f3f21a7

> git log --oneline --decorate=short rescued
f3f21a7 (rescued) d4 important work
98fe89a (HEAD -> main) c3 add c
a202936 c2 add b
3500f9d c1 add a

> git log --oneline --decorate=short
98fe89a (HEAD -> main) c3 add c
a202936 c2 add b
3500f9d c1 add a

Silence, and then two logs that disagree, which is the point. Reading rescued shows four commits with the recovered one on top. Reading your own branch still shows three, because main has not moved and neither have you. The commit is safe and nothing about your working situation changed, which is exactly what you want from a first move when you are not yet sure what happened.

Now the committing one. You have decided you do want to be back on that commit, so move main onto it:

run in rewrite-lab · go back to it, and tidy the rescue name away
> git reset --hard f3f21a7
HEAD is now at f3f21a7 d4 important work

> git log --oneline --decorate=short
f3f21a7 (HEAD -> main, rescued) d4 important work
98fe89a c3 add c
a202936 c2 add b
3500f9d c1 add a

> git branch -d rescued
Deleted branch rescued (was f3f21a7).

(HEAD -> main, rescued) on one line means two names now point at the same commit, which is Session 3's definition doing its ordinary work. Having got main back where you want it, the rescue name has no job left, and git branch -d removes it. d.txt is back in your folder. Four commits, nothing lost, and you never knew the hash.

A third route exists and you have already used it without noticing. Because HEAD@{n} is an ordinary commit name, git reset --hard HEAD@{1} would have worked in place of the hash, straight off the reflog with no copying at all. It is convenient and it is also slightly treacherous, because the numbers shift every time HEAD moves: run one other command in between and HEAD@{1} means something else. Read the reflog, then use the hash, which never changes meaning.

E. git commit --amend, the gentlest rewrite

Everything from here on rewrites history, and this is the smallest possible version of it. You commit, and immediately notice the message has a typo, or that you left a file out. git commit --amend replaces the commit you just made with a better one.

Read that sentence again, because "replaces" is literal. Git does not edit a commit. A commit cannot be edited: Session 1 established that a commit is a snapshot plus a parent plus the message and the author details, and its hash is computed from all of that. Change any part and it is a different commit with a different hash. --amend builds a new commit and points your branch at it, leaving the old one behind exactly the way reset did. Make a commit with a deliberate typo in the message:

PowerShellSet-Content notes.md "the notes" Set-Content extra.md "extra detail"
Git Bash / macOS / Linuxecho "the notes" > notes.md echo "extra detail" > extra.md
run in rewrite-lab · commit only notes.md, with a typo in the message
> git add notes.md

> git commit -m "Add the notse"
[main ec66f8e] Add the notse
 1 file changed, 1 insertion(+)
 create mode 100644 notes.md

> git commit --amend -m "Add the notes"
[main b963def] Add the notes
 Date: Thu Aug 13 21:43:51 2026 -0500
 1 file changed, 1 insertion(+)
 create mode 100644 notes.md

> git log --oneline --decorate=short -1
b963def (HEAD -> main) Add the notes

ec66f8e became b963def. One commit, two hashes, and the first one is now unreachable in exactly the sense section D taught: still stored, nothing pointing at it, findable in your reflog. That single transcript is the entire reason the golden rule in section J exists, and it is worth sitting with for a moment. You did not change a commit. You made a second commit and abandoned the first.

The Date: line is Session 7's, arriving for the same reason. It appears when a commit's author date and its committer date differ. --amend keeps the original author date and stamps a new committer date, so they differ from now on. Nothing is wrong.

The second use is more common than the message fix. You committed, then realised a file that belonged in that commit was never staged. Stage it and amend with --no-edit, which means "keep the message exactly as it is":

run in rewrite-lab · fold a forgotten file into the commit it belonged in
> git add extra.md

> git commit --amend --no-edit
[main 821d00d] Add the notes
 Date: Thu Aug 13 21:43:51 2026 -0500
 2 files changed, 2 insertions(+)
 create mode 100644 extra.md
 create mode 100644 notes.md

> git show --stat --oneline HEAD
821d00d Add the notes
 extra.md | 1 +
 notes.md | 1 +
 2 files changed, 2 insertions(+)

One commit holding both files, and a third hash. Compare this against Session 7's answer to the same problem, which was git reset --soft HEAD~1 followed by git add and a fresh git commit. Both work. --amend is the one-step version, and it is what you will actually reach for when the mistake is seconds old.

Where this fits in Session 7's table. Session 7 mapped every undo command onto four things: the working tree, the staging area, the branch pointer and the repository. --amend fits without any new vocabulary. It leaves your files alone, it leaves the staging area alone, it adds a commit to the repository, and it moves the branch pointer forward onto that new commit. Every rewriting command in this session does the same shape of thing, which is why the frame still holds:

commandworking treestaging areabranch pointerrepository
git commit --amendnonoforward, onto a new commitadds one
git rebase -inonoforward, onto new commitsadds them
git cherry-pickyesyesforward, onto a new commitadds one

Notice what is missing from that table: a "removes" column. There is not one, because none of these commands remove anything. Rewriting history in Git means building replacement commits and pointing at those instead, and the originals sit exactly where they were until the reflog forgets them. That is why every rewrite in this session is recoverable.

--no-edit and -m both keep an editor closed. A bare git commit --amend, with neither, opens your text editor so you can rewrite the message by hand. That is often exactly what you want, and section F is about being ready for it. Until you have read that section, use -m "new message" to replace the message or --no-edit to keep it.

F. Before the todo list opens: the editor, and how to back out

The next command opens a text editor, and there is no version of it that does not. The editor is not a side effect to be avoided here; it is the interface. You edit a list of instructions, save it, and Git carries them out. So it is worth knowing three things before you meet it: what will open, how to change one line, and how to leave without doing any damage.

Find out what will open, on your machine, right now:

run anywhere · ask Git which editor it will use
> git var GIT_EDITOR
vim

Session 4 taught you this command and the escapes that go with it. On a standard Git for Windows install, as here, the answer is vim, which opens inside your terminal window rather than in a separate program. That is why it looks like the terminal has frozen when it has not. If your machine prints something else, use that program instead; the Git side of this section is identical either way.

The three vim keystrokes you need, and nothing more:

iStart typing. Vim opens in a mode where letters are commands rather than text. Pressing i switches to inserting, and now the keyboard behaves normally.
EscStop typing. Back to command mode, where the next two work.
:wq then EnterSave and close. Write, then quit. This is what hands your edited list back to Git.

To change a line, that is the whole procedure: move the cursor to it with the arrow keys, press i, edit the text, press Esc, then type :wq and Enter. You will be changing one word at the start of a line, which is about as small as an edit gets.

Now the important half: getting out without breaking anything. There are two moments you might want to escape from, and they need different commands.

Moment one, the editor is open and you have changed your mind. Delete every line in the list, save and close. Git reads an empty list as "do nothing" and stops:

what an emptied todo list produces
> git rebase -i HEAD~3
error: nothing to do

Nothing was changed and no rebase started. The word error looks alarming and means only that Git had no instructions to carry out. In vim, deleting all the lines is dG from the top of the file, then :wq. If that feels like too much to remember, quitting without saving works too: :q! leaves the list exactly as Git wrote it, which says "keep all three commits as they are", and the result is a rebase that reports success and changes none of your hashes.

Moment two, the rebase has already started and something is going wrong. This is the one to memorise:

the escape hatch, from anywhere inside a rebase
> git rebase --abort

It prints nothing and puts your branch back exactly as it was, hashes included. It is this session's git merge --abort, and it deserves the same treatment Session 4 gave that one: learn it before you need it, because you will want it at the exact moment you are least inclined to go looking. Its opposite number, git rebase --continue, tells Git to carry on once you have dealt with whatever it stopped for.

Lost in the middle and not sure which state you are in? git status knows. During a rebase it opens with interactive rebase in progress and then lists the commands already done and the ones still to come, which is usually enough to tell you whether to continue or abort.

G. git rebase -i and the todo list

An interactive rebase replays a stretch of your recent commits, one at a time, doing whatever you told it to do with each. You choose the stretch, Git opens a list of those commits, you mark each line with a verb, and Git rebuilds them. Give the lab something worth tidying first, three scrappy commits of the kind everyone actually produces:

#         message (or the oneline, if no original merge commit was
#         specified); use -c <commit> to reword the commit message
# u, update-ref <ref> = track a placeholder for the <ref> to be updated
#                       to this position in the new commits. The <ref> is
#                       updated at the end of the rebase
#
# These lines can be re-ordered; they are executed from top to bottom.
#
# If you remove a line here THAT COMMIT WILL BE LOST.
#
# However, if you remove everything, the rebase will be aborted.
#

That is the whole thing, unabridged, because an abridged version would not match what you see. It is long and most of it is a reference card you can ignore. Only the first three lines are the list. Everything from # Rebase down is a comment: lines starting with # are notes to you and Git ignores them.

The oldest commit is at the TOP. This is the reverse of git log, which you have read newest-first since Session 2, and it is the single most common way beginners squash the wrong commits. In the list above, wip 1 is the oldest of the three and it is on line one. Git applies the lines from top to bottom, oldest first, which is the order the commits were originally made. Before you edit a single line, find the oldest commit and confirm it is at the top.

Four of those verbs are worth learning now. The list is longer, as you can see, and the rest can wait until you have a reason for them:

pickKeep this commit as it is. The default on every line, so a list you do not edit changes nothing.
rewordKeep the commit, change its message. Git stops and opens the editor on that message when it reaches the line.
squashMerge this commit into the one above it, keeping both messages so you can combine them into one.
fixupMerge this commit into the one above it and throw its message away. Section H is about when to prefer this.

drop is worth recognising too: it removes a commit from the stretch entirely, and it is the polite spelling of what the legend warns about in capital letters. Deleting a line does the same thing as writing drop in front of it, which is why If you remove a line here THAT COMMIT WILL BE LOST. is there. Since you now know about the reflog, "lost" means "orphaned and findable for a few weeks", not "destroyed". The verbs this session is not teaching are edit, exec, break, label, reset, merge and update-ref. They exist, they solve real but narrower problems, and none of them is needed to tidy a branch.

H. squash against fixup, which is the distinction that matters

The two verbs do the same thing to the commits and different things to the messages. That is the whole difference and it decides which one you want:

squashKeeps both messages and opens an editor so you can write one message out of them. Use it when the second commit says something worth keeping.
fixupDiscards the second message entirely and opens no editor at all. Use it when the second commit was only ever a correction.

fixup is the right answer far more often than beginners expect, because most of the commits people want to squash are called things like "fix typo", "oops", "actually fix it" and "lint". Those messages have no value, and squash would make you sit in an editor deleting them by hand. Prove it on a pair of commits of exactly that shape:

PowerShellAdd-Content w.txt "a second paragraph" git add w.txt git commit -m "Add a second paragraph" Add-Content w.txt "teh -> the" git add w.txt git commit -m "fix typo"
Git Bash / macOS / Linuxecho "a second paragraph" >> w.txt git add w.txt git commit -m "Add a second paragraph" echo "teh -> the" >> w.txt git add w.txt git commit -m "fix typo"
run in rewrite-lab · a real commit and a correction to it

No second editor opened. That is the practical difference you will feel: squash stops and asks, fixup does not. The message fix typo no longer exists anywhere, the change it carried is folded into the commit above it, and w.txt holds every line you wrote. The surviving commit has a new hash, 597aec6, for the reason section E gave: it is a different commit that happens to contain the same work.

 Date: Thu Aug 13 21:44:16 2026 -0500

98a392a Add the first w.txt draft
821d00d Add the notes

Both hashes changed, not just the reworded one. That is worth pausing on, and it is the deepest idea in the session. A commit's hash is computed from its content and its parent, so rewriting a commit changes every commit built on top of it, all the way to the tip. You cannot rewrite one commit in the middle and leave the ones above it alone, because they name it as their parent. Rewriting is always "and everything after it too".

  1. From main, run git switch -c rebase-practice.

Stuck getting out of the editor?

In vim: arrow keys to move, i to start typing, Esc when you have finished typing, then :wq and Enter to save and close. To abandon the whole thing instead, press Esc and type :q! then Enter, which changes nothing. If a rebase has already started and you want out, git rebase --abort.

I. git cherry-pick: one commit, copied somewhere else

git cherry-pick <hash> takes the change from one commit and applies it to the branch you are standing on. It is what you want when a fix landed on the wrong branch, or when one commit out of a long feature branch is needed on main today. Set up the situation, a side branch with one commit on it, and a main that has moved on since:

PowerShellgit switch -c side Set-Content s.txt "work done on the side branch" git add s.txt git commit -m "Add s.txt on side" git switch main Set-Content m.txt "main carried on" git add m.txt git commit -m "Add m.txt on main"
Git Bash / macOS / Linuxgit switch -c side echo "work done on the side branch" > s.txt git add s.txt git commit -m "Add s.txt on side" git switch main echo "main carried on" > m.txt git add m.txt git commit -m "Add m.txt on main"
run in rewrite-lab · two branches that have diverged
> git log --oneline --decorate=short -3

2fd81b5 Add a second paragraph
98a392a Add the first w.txt draft

> git log --oneline --decorate=short side -3

2fd81b5 Add a second paragraph
98a392a Add the first w.txt draft

Both branches share everything up to 2fd81b5 and then disagree. You want that one commit from side on main, without merging the branch. Standing on main:

run in rewrite-lab · copy one commit across
> git cherry-pick 26a48e3
[main 994b351] Add s.txt on side
 Date: Thu Aug 13 21:46:16 2026 -0500
 1 file changed, 1 insertion(+)
 create mode 100644 s.txt

> git log --oneline --decorate=short -3
994b351 (HEAD -> main) Add s.txt on side
5ce57fc Add m.txt on main
2fd81b5 Add a second paragraph

> git log --oneline --decorate=short side -2
26a48e3 (side) Add s.txt on side
2fd81b5 Add a second paragraph

Look at the two hashes: 26a48e3 on side, 994b351 on main. Same message, same file, same change, different commit. And the original is untouched, still sitting on side where it always was. You now have two commits carrying the same change, which is what "copy" means here.

Why the hash differs is the one sentence to take from this section, and it explains rebasing too. Session 1 established that a commit is a snapshot plus a parent. The snapshot is identical. The parent is not: on side the commit sits on top of 2fd81b5, and the copy on main sits on top of 5ce57fc. Different parent means different commit means different hash. That is also exactly what an interactive rebase does to every commit it touches, and why section H saw two hashes change when only one commit was reworded.

The same reasoning covers something you might otherwise wonder about. A commit's hash is computed from the whole commit, so the parent is not the only thing that can force a new one: the time the copy was made is in there too. That is why cherry-picking a commit onto a branch produces a new hash even in the odd case where the parent happens to be the same commit. The rule to carry forward is the simple one: a copy of a commit is a new commit, and the reason you will meet in practice is the parent.

J. The golden rule, stated as a question

Everything since section E has replaced commits with different commits. That is harmless while the commits are yours alone and it is a genuine problem the moment they are not. The rule that covers this is usually written as a commandment, never rewrite public history, which is easy to remember and slightly useless, because it does not tell you where the line is. Ask a question instead:

Has anybody else got this commit?

If no: rewrite it freely. Amend it, squash it, reword it, drop it. This is normal, safe and good practice.
If yes: do not rewrite it. Undo its effect with git revert, which Session 7 taught, because that adds a commit rather than replacing one.

That is a decision rather than a taboo, and the honest version has a wide "yes, go ahead" side. The commits on a branch only you have worked on, that you have never pushed, or that you pushed to your own feature branch that nobody has pulled, are yours. Tidying them before you open a pull request is not a dangerous exception to the rule; it is the single most common legitimate use of everything in this session.

Why it matters when the answer is yes. Your teammate has commit abc123. You replace it with def456 holding the same work. Their Git has no idea these are related: it sees a commit that has vanished and a stranger in its place. When they next pull, Git tries to reconcile two histories that genuinely disagree, and the usual outcome is that they end up with both copies of your work and a merge nobody wanted. Nothing is destroyed and everything is confusing, which in practice costs more time than losing the work would have.

This is also the other half of Session 6. Session 6 offered rebase-and-merge as one of the ways to land a pull request and said the tidying belonged before the review, not after. This session is that tidying: squash your own scrappy commits into a reviewable shape while the branch is still yours, then push, then open the pull request. Once review has started, other people have those commits, and the answer to the question flips.

The secret you committed in Session 2

Session 2 left you with a promise, and this is where it comes due. It asked whether an API key committed yesterday and deleted today is safe, and answered: no, it is still in yesterday's snapshot, and getting it out for real means rewriting history, which Session 8 would cover. So, plainly:

  • Rewriting history can remove a secret from your local history. --amend handles it if the commit is the most recent one and nothing else has happened since.
  • For anything older, the real tools are git filter-repo and BFG Repo-Cleaner. Both rewrite every affected commit in the whole repository. Neither is built into Git, both need installing, and this session is not going to teach them: they are the correct tools and they deserve more room than a footnote.
  • It is disruptive for everyone who has the repository. Rewriting every commit means every clone in existence now disagrees with the shared copy, and every one of your colleagues has to be told what to do about it.
  • None of it un-leaks a secret that was ever pushed. Anybody who cloned, fetched, or read a notification still has it. Automated scrapers watch public repositories for exactly this.

So the conclusion is the one Session 2 already gave you, and it does not soften with more knowledge: rotate the secret. Change the key, revoke the old one, and treat the history rewrite as tidying up afterwards rather than as the fix. A rewrite is not a remedy for a leak. It is worth doing, and it is worth doing second.

K. Pushing a rewrite: --force-with-lease

Rewriting a commit you have already pushed leaves your branch and the shared copy disagreeing, and Git will not quietly resolve that for you. This section builds a second lab to show it, using Session 5's trick: a bare repository on your own disk standing in for GitHub, and two clones standing in for two people. No account, no network.

work-a is you and work-b is a colleague, with her own name set so her commits are visibly hers. Session 5 built the same shape. The first clone prints warning: You appear to have cloned an empty repository., which is true at that moment and stops being true one line later. You end up standing in work-a, which is where the rest of this section runs.

Your paths will be longer than the ones printed below. Git reports the full path of the shared repository in its push and fetch output. The transcripts here shorten that to ../origin.git for readability, exactly as Sessions 5 and 6 did. Everything else matches.

Rewrite the commit you already pushed, then push normally:

run in work-a · the wall you hit first
> git commit --amend -m "Add a second line, reworded"
[main 552cbba] Add a second line, reworded
 Date: Thu Aug 13 22:24:51 2026 -0500
 1 file changed, 1 insertion(+)

> git push
To ../origin.git
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to '../origin.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

Session 5's rejected push, with a new cause. There it happened because a colleague had pushed and you were behind; here it happens because you replaced a commit the shared copy still has. Git cannot tell those two situations apart, which is why the hint it prints is, in this case, actively bad advice: git pull would merge the old commit back into your branch and leave you holding both copies of the same work, which is the opposite of what a deliberate rewrite is for.

What you want is to tell the shared copy to take your version instead. There are two flags for that and the difference between them is the whole section:

run in work-a · the safe one, when nothing has moved
> git push --force-with-lease
To ../origin.git
 + bb4a33f...552cbba main -> main (forced update)

The report looks different from an ordinary push and it is worth learning to spot. A normal push shows something like 552cbba..d0cb1e9, with two dots and no marker, and you will see exactly that shape a few steps below when Rae pushes. A forced one shows a leading +, three dots, and (forced update) on the end. Three dots mean the old commit is not an ancestor of the new one, which is the machine-readable version of "history was rewritten here".

Now the case the flag exists for. Rae picks up your rewrite, does her own work on top of it and pushes, all perfectly reasonably. Run this in a second terminal, or cd ../work-b and back again:

PowerShellcd ../work-b git fetch git reset --hard origin/main Set-Content r.txt "raes note" git add r.txt git commit -m "Rae adds r.txt" git push
Git Bash / macOS / Linuxcd ../work-b git fetch git reset --hard origin/main echo "raes note" > r.txt git add r.txt git commit -m "Rae adds r.txt" git push

Why Rae fetches and resets rather than simply pulling. Her clone still holds the commit you replaced, so a git pull would try to merge your rewritten history with her copy of the old one and hand her a merge commit she never asked for, which is precisely the mess section J describes. git fetch followed by git reset --hard origin/main is her saying "throw my copy away and take the shared one", using Session 7's reset and Session 5's origin/main. Her fetch reports (forced update), which is the shared copy telling her that history was rewritten under her.

Meanwhile you, back in work-a, rewrite your commit again, knowing nothing about Rae's push, and try the same safe flag:

run in work-a · the refusal this whole section exists for
> git commit --amend -m "Add a second line, reworded again"
[main 8d7ee70] Add a second line, reworded again
 Date: Thu Aug 13 22:24:51 2026 -0500
 1 file changed, 1 insertion(+)
 create mode 100644 extra.txt

> git push --force-with-lease
To ../origin.git
 ! [rejected]        main -> main (stale info)
error: failed to push some refs to '../origin.git'

(stale info) is the entire lesson, and it is not self-explanatory, so translate it once and remember the translation: "somebody moved this and you have not looked recently." Notice what the message does not say. There is no mention of a lease, no mention of force, no hint text, and no suggestion of what to do. Two words in brackets are the whole warning, so learn to recognise them.

What the flag actually checks is narrower than it sounds, and this is the part most explanations get wrong. --force-with-lease compares the shared copy against your own remote-tracking branch, the origin/main that Session 5 explained as your local record of where the shared branch was when you last looked. If those match, it pushes. If they do not, it refuses. So the honest description is:

--force-with-lease refuses if the remote moved since you last fetched.

Say it that way rather than the way most tutorials do. The common claim is that the flag makes it impossible to destroy someone else's work, and that is false.

There are two ways past that refusal, and the point of this section is that they end in exactly the same place. Run one of them, not both: whichever you pick, the shared copy finishes identically, and the block after them is what Rae sees either way.

way one · run in work-a · no check at all
> git push --force
To ../origin.git
 + d0cb1e9...8d7ee70 main -> main (forced update)

That one is unsurprising: you asked for no check and you got none. The second way is the one worth knowing about, because it looks careful and is not. Anything that updates origin/main renews the lease, including a bare git fetch whose output you never read. From the same refused state, fetch and do nothing else, then run the identical safe push again:

way two · run in work-a · the footgun, verified
> git fetch
From ../origin
   552cbba..d0cb1e9  main       -> origin/main

> git push --force-with-lease
To ../origin.git
 + d0cb1e9...8d7ee70 main -> main (forced update)

It succeeded, and Rae's commit is gone from the shared copy just as surely as the plain --force would have taken it. The fetch updated the very thing the lease was measured against, so the check had nothing left to object to. The flag protects you from pushing on stale information, not from pushing on information you never read. Notice too that the fetch printed 552cbba..d0cb1e9 with two dots, Rae's commit arriving on top of yours, and you pushed straight over it without looking.

A success message is not evidence of harm, so go and look at the harm. In work-b, Rae fetches:

run in work-b · the other side of that push
> git fetch
From ../origin
 + d0cb1e9...8d7ee70 main       -> origin/main  (forced update)

> git log --oneline --decorate=short origin/main
8d7ee70 (origin/main, origin/HEAD) Add a second line, reworded again
9a0cd71 Add n.txt

> git status
On branch main
Your branch and 'origin/main' have diverged,
and have 2 and 1 different commits each, respectively.
  (use "git pull" if you want to integrate the remote branch with yours)

nothing to commit, working tree clean

Rae adds r.txt is not in that list. It was on the shared copy and now it is not. Her own clone still has it, so nothing has been destroyed on her disk, but the shared copy no longer agrees with her and Git is telling her the two histories have diverged. Untangling that is her problem now, caused by your push, and she got no warning of any kind.

So the habit is two-sided and neither half is optional. Look at what you fetched before you force, because the flag cannot do that part for you. And prefer --force-with-lease over --force anyway, because it catches the case where you forgot to look at all. It is a seatbelt, not a self-driving car.

L. The milestone: destroy a branch, bring it back, and tidy one

Two halves, and the first is the shortest recovery in Git. Section K left you standing in share-lab/work-a, so the first thing to do is go back to the lab this section uses:

PowerShellcd ~/rewrite-lab
Git Bash / macOS / Linuxcd ~/rewrite-lab

Confirm with git log --oneline --decorate=short that you are back on nine commits with Add s.txt on side on top. Now make a branch with work on it and delete it on purpose:

PowerShellgit switch -c doomed Set-Content p.txt "work I care about" git add p.txt git commit -m "Precious work" git switch main
Git Bash / macOS / Linuxgit switch -c doomed echo "work I care about" > p.txt git add p.txt git commit -m "Precious work" git switch main
run in rewrite-lab · Git protects you, then hands you the key
> git branch -d doomed
error: the branch 'doomed' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D doomed'
hint: Disable this message with "git config set advice.forceDeleteBranch false"

> git branch -D doomed
Deleted branch doomed (was 250d182).

Read those two in order, because the order is the teaching. git branch -d refused, and it refused for a good reason: doomed holds a commit that exists nowhere else, so deleting the name would leave that commit with nothing pointing at it. Session 3 taught that deleting a branch removes 41 bytes and no commits, and that is still true; what Git is objecting to is that those 41 bytes are the only way you have of finding this particular commit.

And then look at what -D printed as it did the thing you insisted on. Deleted branch doomed (was 250d182). That hash is the recovery key, handed to you unasked, and it is the same generosity Session 7 saw when Git printed the hash of an orphaned commit on the way out of a detached HEAD. Putting the branch back is one command, the one from section D:

run in rewrite-lab · back, in one command
> git branch doomed 250d182

> git log --oneline --decorate=short doomed -2
250d182 (doomed) Precious work
994b351 (HEAD -> main) Add s.txt on side

And if you had closed the terminal and lost that hash, the reflog has it too, because making the commit moved HEAD and everything that moves HEAD is recorded. Run git reflog and you will find commit: Precious work one line down, at HEAD@{1}, directly below the checkout that carried you back to main. That is section D rule again: the commit sits underneath the operation that moved you off it. Two independent routes to the same commit, which is a fair summary of why this level claims that almost nothing is unrecoverable.

The second half is the one you will use every week. Tidying a messy branch before anybody sees it is the whole of sections G and H put to work, and it is the reason to have learned them.

Your turn The milestone: recover a deleted branch, then tidy a messy one

Do not scroll back up. Work in rewrite-lab. Both halves are graded on what you can say, not on which hashes you get.

Half one: destroy and recover.

  1. Make a branch called scrap, put one commit on it holding a file only it has, and switch back to main.
  2. Try to delete it with git branch -d scrap. Read the refusal out loud and say why Git is refusing, in terms of what would be left with nothing pointing at it.
  3. Delete it for real with -D. Do not copy the hash it prints.
  4. Get the branch back, with its commit, using the reflog rather than the printed hash. Prove it worked with git log --oneline --decorate=short scrap.

Half two: tidy a branch for sharing.

  1. Make a branch called feature and put three commits on it, all touching one file, with messages as scrappy as the ones you really write: something like wip, more wip, fix typo.
  2. Before touching anything, answer the golden rule question out loud: has anybody else got these commits? Say what that answer permits.
  3. Turn the three into one commit with a message that describes the finished work, using git rebase -i HEAD~3. Use fixup rather than squash for the two throwaway messages. Since fixup opens no editor at all, you get the message right in one of two ways: mark the first line reword in the same list, or run a second git rebase -i HEAD~1 afterwards and reword it there.
  4. Confirm the result three ways: git log --oneline shows one commit on top of main, the file contains all three of your changes, and git status is clean.
  5. Say which command you would use to publish this if the branch had already been pushed, and say what it would refuse to do and when.

You have hit the milestone when scrap is back without the printed hash, feature is one clean commit holding all three changes, and you can state the golden rule as a question with both of its branches.

Part 2

Predict the Output

This is the whole track in miniature: work out what the command will do before you run it, type your answer, then check. Do not run it first, committing to a guess is what builds the model. Each drill tells you the shape of answer it wants, a single value, a count, or a list. They get harder toward the end, and after you check you can reproduce any of them in rewrite-lab.

Where a drill names the four things, it means Session 7's four: working tree, staging area, branch pointer, repository. No drill grades a hash, a date or a path, since all three differ per machine.
