A. Why APIs require authentication, and the three common shapes

Session 7's APIs were open: anyone could read a ZIP code or a public profile. Most real APIs are not, because they guard private data, cost money per call, or limit how much any one user can pull. So before they answer, they need to know who is asking. Authentication is proving your identity to the server so it can decide what you are allowed to do, and you do it by attaching a credential (a secret that identifies you) to each request. A credential rides along in one of three common shapes, and it helps to name all three because you will meet each in the wild:

  • An API key in a query parameter. The key goes on the URL as a ?api_key=... query parameter, the same params= dict you used in Session 7. Simplest to send, but the weakest: the key sits in the URL, which gets logged and shows up in browser history.
  • An API key in a custom header. A header is a piece of metadata sent alongside the request (not part of the URL or the body). Here the key travels in a header the API names, often something like X-API-Key, keeping it out of the visible URL.
  • A bearer token in the Authorization header. The most common shape today, and what GitHub uses. You send a header named Authorization whose value is the word Bearer, a space, then your token: Authorization: Bearer <token>. "Bearer" means exactly what it says, whoever bears (holds) this token is treated as authorized, which is also why leaking one is dangerous.

When your credential is missing or wrong, the server refuses, and it tells you with a status code you already know how to read from Session 7. Two 4xx codes matter here: 401 Unauthorized means "I do not know who you are, your credential is missing or invalid," and 403 Forbidden means "I know who you are, but you are not allowed to do this." Both are 4xx, so both are your side to fix (a bad key for 401, insufficient permissions for 403). Checking for them is just the Session 7 discipline, look at the status before you trust the body, applied to auth.

B. Headers, secrets, and never hardcoding a key

Sending a header from Python mirrors the params= dict exactly: you pass a headers= dict, and requests attaches each key/value to the request. So a bearer token looks like requests.get(url, headers={"Authorization": "Bearer ghp_xxx"}). Now the important part, where the token comes from.

The tempting move is to paste the token straight into your script as a string. Do not:

token = "ghp_abc123realtoken"    # DON'T: a live secret, now sitting in your source code

A secret is any value that would let someone act as you, and a token is exactly that. The moment that file is committed to git and pushed, especially to a public repo, your secret is public: anyone can read it in the code or the git history and use it as you. This is a real security incident, not a hypothetical. GitHub actively scans public commits and will auto-revoke a token it detects, and by then it may already have been used. The fix is to keep the secret out of the file entirely and read it in at runtime from an environment variable, a named value that lives in your terminal or operating system rather than in your code. That happens in two steps: first you set the variable in your terminal, then your code reads it back.

Step 1, set it in your terminal. Set it in the same terminal you will then run Python from, so the Python process inherits it. On Windows PowerShell (your setup):

# in PowerShell, this is a terminal transcript, not a Python file
PS C:\work> $env:GITHUB_TOKEN = "ghp_xxxxxxxx"   # set it for THIS terminal session
PS C:\work> python check_token.py                # now run python from that SAME terminal so it inherits the value

setx GITHUB_TOKEN "ghp_xxxxxxxx" saves it permanently for future terminals instead (it takes effect in new windows, not the current one), and on Mac or Linux the equivalent is export GITHUB_TOKEN=ghp_xxxxxxxx.

Step 2, read it in your code. With the variable set, Python reaches it through the built-in os module:

import os                            # the os module lets Python talk to the operating system

token = os.getenv("GITHUB_TOKEN")    # read the env var named GITHUB_TOKEN, or None if it isn't set

os.getenv("NAME") returns the value of the environment variable NAME, or None if that variable does not exist. None is Python's built-in "nothing here" value, and it counts as False in an if test (the truthiness idea from Session 2), which is how you will check whether a token actually loaded. There is also os.environ, a dictionary of every environment variable: you can read one with os.environ["NAME"] or set one for the current program with os.environ["NAME"] = "...". Because the secret now lives in the environment and never in the file, committing your code leaks nothing.

C. Making the authenticated call

Now put the pieces together: read the token, build the Authorization header, and send the GET. GitHub's https://api.github.com/user/repos endpoint lists the repositories of the authenticated user, and unlike Session 7's open /users/<name>, it requires a token. That makes it the perfect place to watch auth both succeed and fail. (Note you can import several modules on one line, comma-separated: import requests, os.)

import requests, os

token = os.getenv("GITHUB_TOKEN")
headers = {"Authorization": f"Bearer {token}"}    # the bearer shape from Concept A, token filled in by the f-string
response = requests.get("https://api.github.com/user/repos", headers=headers)
print(response.status_code)    # 200 if the token is good; 401 if it is missing or wrong

The f"Bearer {token}" is the f-string from Session 1, dropping the token's value into the header string. If the token is valid you get 200 and a JSON list of repos; if it is missing or wrong you get 401, and you handle that the Session 7 way, check the status before trusting the body:

if response.status_code == 401:
    print("check your token, GitHub says 401 Unauthorized")    # a clear message beats a confusing crash later
elif response.ok:
    data = response.json()     # safe to parse now (2xx)

D. Sending data with POST

Every call so far has been a GET, which reads. To create or send data you use POST (named in Session 7's methods list). With requests that is requests.post(url, json={...}). The json= keyword takes a Python dict and does two chores for you: it serializes the dict into a JSON string (the json.dumps step from Session 7) and it sets the request's content-type header to say "this body is JSON," so the server parses it correctly.

It is worth contrasting json= with its neighbor data=, because mixing them up is a classic first bug. json={"a": 1} sends a JSON body (what modern APIs expect), while data={"a": 1} sends the dict as old-style HTML-form fields, encoded like a=1&b=2, the format an HTML form submit uses. Rule of thumb: a JSON API wants json=. And the reply to a successful create is usually 201 Created rather than 200, still a 2xx (so response.ok is True), which you read exactly as before.

To practice safely we will POST to https://httpbin.org/post, a free testing endpoint that simply echoes your request back so you can confirm what you sent. It returns 200 and puts your parsed body under the "json" key:

import requests

payload = {"title": "Buy dowels", "done": False}       # the data we want to send
response = requests.post("https://httpbin.org/post", json=payload)   # send it as a JSON body
print(response.status_code)          # httpbin echoes back with -> 200
print(response.json()["json"])       # httpbin returns what we sent under "json" -> {'title': 'Buy dowels', 'done': False}

Be honest about what you are seeing: httpbin is an echo service for testing, so it answers 200 and reflects your payload. A real create endpoint would answer 201 and return the record it created, but the mechanic you are practicing, json= sends a body and you read the result, is identical.

E. Pagination, rate limits, then your milestone

Here is the trap that quietly costs people real data. Most endpoints that return a list do not hand you everything at once. To stay fast they paginate, splitting a big result into pages and capping how many items come back per request (GitHub returns 30 by default, up to 100 with per_page). So a single call gives you page 1, and if you stop there you have silently pulled only the first 30 (or 100) items while believing you got them all. Compare the naive call with the loop. Both reuse two names your milestone script sets up first: url (the endpoint string, "https://api.github.com/user/repos") and headers (the bearer dict you built in Concept C), so only params is new here:

# NAIVE: one call, assumes it is everything. You silently get only the first page.
repos = requests.get(url, headers=headers).json()   # just page 1
print(len(repos))                                    # maybe 100, even if you actually have 250 repos
# CAREFUL: keep asking for the next page until one comes back short
all_repos = []
page = 1
while True:                                       # loop forever until we choose to break (Session 2)
    params = {"per_page": 100, "page": page}      # ask for up to 100 items, one page at a time
    resp = requests.get(url, headers=headers, params=params)
    batch = resp.json()                           # this page's list of repos
    all_repos.extend(batch)                       # add all of this page's items to the running list
    if len(batch) < 100:                          # a short (or empty) page means there is no more
        break                                     # so stop the loop
    page = page + 1                               # otherwise, go get the next page
print(len(all_repos))                             # now this is the FULL count

Two things to name here. .extend(other) is a list method that adds every item of another list onto this one, unlike .append from Session 3 which adds a single item. And the stop condition is the whole game: you keep going while each page arrives full (its length equals per_page, suggesting more may follow), and you stop the first time a page comes back with fewer items than you asked for, because a short or empty page is the last one. Get that wrong and you either miss data or loop forever.

Not every API counts pages this way. Some return a cursor or a next URL you follow until there is no "next", and GitHub also sends a Link header carrying the next page's URL. The signal differs but the idea is identical: keep going until the API tells you to stop. One more courtesy: if you request too fast, an API protects itself by replying 429 Too Many Requests (a 4xx), often with a Retry-After header saying how many seconds to wait. A polite client slows down or waits that long instead of hammering in a tight loop.

Your turn The milestone: authenticate and pull every page

This is your Session 8 milestone, run for real in VS Code with your own token. Write a script that: (1) reads GITHUB_TOKEN with os.getenv and builds the bearer headers; (2) pages through https://api.github.com/user/repos with params={"per_page": 100, "page": n}, climbing the page number and collecting every repo; (3) stops when a page returns fewer than 100 items; (4) wraps the loop in try/except requests.RequestException (Sessions 6 and 7) so a dropped connection fails gracefully; (5) handles a 401 with a clear "check your token" message; and (6) prints the total repo count and the first few names. Build it before you peek, this is the full real-world pull.

Show reference solution 
import requests, os

token = os.getenv("GITHUB_TOKEN")
if not token:                                    # None is falsy, so this catches a missing token early
    print("set GITHUB_TOKEN in your terminal first")
else:
    headers = {"Authorization": f"Bearer {token}"}
    url = "https://api.github.com/user/repos"
    all_repos = []
    page = 1
    try:
        while True:
            params = {"per_page": 100, "page": page}
            response = requests.get(url, headers=headers, params=params)
            if response.status_code == 401:
                print("check your token, GitHub returned 401")
                break
            response.raise_for_status()          # any other bad status becomes an exception
            batch = response.json()              # this page as a list of repo dicts
            all_repos.extend(batch)              # collect this page
            if len(batch) < 100:                 # short page means no more pages
                break
            page = page + 1                      # otherwise ask for the next page
    except requests.RequestException as e:       # a network failure lands here instead of crashing
        print("network problem:", e)

    print("pulled", len(all_repos), "repos")
    for repo in all_repos[:5]:                   # the first few names to eyeball (slice from Session 3)
        print("-", repo["name"])
