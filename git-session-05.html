Remotes, demystified

There is no such thing as the repository. There are several complete copies, and origin/main is your copy's written note of where somebody else's main was the last time you asked. Every confusing thing about remotes follows from that one fact, including the push that gets refused. This session has you break sync on purpose and put it back.

Milestone Explain what push and pull each change, and recover from a rejected push.
git

You do not need merge-lab from Session 4. Step one below builds a brand new folder called remote-lab, and this one holds three repositories rather than one. It has to be new, because the whole point of this session is watching two copies of the same project drift apart, and that needs a setup no earlier session built. No account and no internet are needed for any of this.

This is a workbook, not a reading. You will predict what a command does to your repository, reassemble command sequences, fill blanks, and write from scratch, and each part hands you less scaffolding than the last. The goal is the one this whole track is built on: read a Git command and know what it will do before you press enter.

How to read the transcripts below. A line that starts with > in blue is what you type. Everything underneath it is what Git printed back. Do not type the > itself. Four things will legitimately differ on your machine: commit hashes (short strings like 99a877c, and one full 40-character one), dates, full paths (anywhere you see ... at the start of a path, that stands for wherever your home folder lives, and it is different on every machine), and the name and email on the teammate's commits, in the one transcript that prints them, if you skip the identity lines in the section D setup block. A. Three copies, one project

Start with the idea, because the commands only make sense underneath it. Until now you have had one folder with one .git in it, and that was the whole world. Working with other people does not change that folder. It just means there is more than one of them.

Each copy is complete. Each has its own commits, its own branches, its own .git. None of them is in charge, and none of them knows anything about the others except what somebody deliberately went and asked for. That last clause is the whole session.

The usual arrangement has three, and you are about to build all three on your own disk:

origin-repo.git
The shared copy everybody agrees to send work to. On a real team this lives on GitHub. Here it is a folder next door, and it behaves identically.
work-a
Your copy. You will spend the session standing in this one.
work-b
A teammate's copy. Same project, different person, and it is how you will make somebody else push.

The shared copy is a little different, and it has a name: a bare repository. It has the history in it but no working files, because nobody edits in it. They only send work to it and take work from it. You make one by adding --bare, and the .git on the end of the folder name is a convention that says "this one is bare", not something Git enforces.

Now build the lab. This is the longest setup block in the track, and every line in it is either a command you already know, one this section just explained, or the single new one that section B is entirely about:

PowerShell (Windows default) · build remote-lab
cd ~
mkdir remote-lab
cd remote-lab
git init --bare origin-repo.git
git init -b main work-a
cd work-a
git remote add origin ../origin-repo.git
Git Bash / macOS / Linux · build remote-lab
cd ~
mkdir remote-lab
cd remote-lab
git init --bare origin-repo.git
git init -b main work-a
cd work-a
git remote add origin ../origin-repo.git

The two blocks are identical, which is worth a moment: nothing here writes a file, so there is no Set-Content or echo to differ over. The two shells only part company when files are involved.

Already have a folder called remote-lab? Read this first

The mkdir line fails if the folder exists, and the cd after it then succeeds anyway and takes you into the folder you already had, so the rest of the block runs against whatever is in there. This is the same trap Session 4 flagged, and it has the same two ways out.

The safe one: use another name. Replace remote-lab with remote-lab-2 in the mkdir and cd lines. Everything else in the session is identical.

The other one: delete the old folder first. This permanently removes that folder and everything inside it, so only run it if you are certain you do not need what is in there.

PowerShellcd ~ Remove-Item -Recurse -Force remote-lab
Git Bash / macOS / Linuxcd ~ rm -rf remote-lab

Two of those lines printed something. Here is what, and the paths are the only machine-specific thing on this page:

run in remote-lab · the two repositories being created
> git init --bare origin-repo.git
Initialized empty Git repository in .../remote-lab/origin-repo.git/

> git init -b main work-a
Initialized empty Git repository in .../remote-lab/work-a/.git/

Notice the difference in those two lines, because it is the whole of what --bare means. The bare one lives directly in origin-repo.git/. The ordinary one lives in a .git/ tucked inside work-a/, with room beside it for your actual files.

git init -b main is the same line Sessions 3 and 4 used, with one addition: giving it a folder name makes the folder as well, so you do not need a separate mkdir.

B. What origin actually is

That last setup line was the new one. git remote add origin ../origin-repo.git saves a URL under a nickname. That is genuinely all it does. It writes two lines into your repository's config and stops.

A remote is a nickname for a URL, and origin is a nickname like any other. There is nothing special about the word. It is simply the name Git picks by default, so everybody has one called origin and it came to feel like a keyword. You could have called it shared or upstairs and every later command would work the same with that word in it.

Ask Git what nicknames it has:

run in work-a · git remote -v
> git remote -v
origin	../origin-repo.git (fetch)
origin	../origin-repo.git (push)

Two lines, not one, and it is not a display bug. Git lets a remote have a different address for reading than for writing, so it always prints both. They are the same here, and on a normal GitHub setup they are the same too. Worth knowing the day you see two that differ.

Why ../origin-repo.git and not a long path? The .. means "the folder above this one", so read from inside work-a it points at its sibling. Git stores whatever you type, so a short relative address stays short, and every path you see for the rest of this session will be this same short string on your machine as well as on this page. A real remote would be a URL like https://github.com/someone/project.git instead, and nothing else would change.

One sentence on the thing you will meet eventually and can safely park: a repository can have several remotes, each with its own nickname, and you name the one you mean in the command. Session 9 is where a second one earns its place.

C. Your first push, and what -u sets up

You have a remote but nothing to send, so make a commit first. Only this part differs by shell:

PowerShellSet-Content notes.md "line one"
Git Bash / macOS / Linuxecho "line one" > notes.md
run in work-a · the first commit
> git add notes.md

> git commit -m "Add notes.md"
[main (root-commit) 99a877c] Add notes.md
 1 file changed, 1 insertion(+)
 create mode 100644 notes.md

Now look carefully at the state of things before you push, because the difference afterwards is the lesson. Session 4 gave you git status --short, the two-letter form. Adding b to that flag adds one line at the top about the branch, and -sb is how it is nearly always typed:

run in work-a · before the first push
> git status -sb
## main

> git branch -vv
* main 99a877c Add notes.md

> git branch -a
* main

Three commands, one message: there is a branch called main and it is alone in the world. git status -sb names it and says nothing else about it. git branch -vv is git branch -v from Session 3 with a second v, and that second v asks for one extra thing, the branch on the other side that this one is paired with. There is no such pairing yet, so nothing appears. And git branch -a, the "all branches" form from Session 3, finds only your own.

Send it:

run in work-a · git push -u origin main
> git push -u origin main
To ../origin-repo.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
  • To ../origin-repo.git is where the work went, echoed back so you can see you sent it where you thought.
  • * [new branch] main -> main reads left to right: your branch main became a branch called main over there. It says new branch because the shared copy was empty and had none.
  • branch 'main' set up to track 'origin/main'. is the -u reporting for duty. That is the flag's whole effect and the next block proves it.

Run the same three commands again:

run in work-a · after the first push
> git status -sb
## main...origin/main

> git branch -vv
* main 99a877c [origin/main] Add notes.md

> git branch -a
* main
  remotes/origin/main

All three changed, and -u is why. -u is short for --set-upstream, and an upstream is the branch on the other side that yours is paired with. Once that pairing exists, Git can answer "how do I compare to them" without being told which branch to compare against, which is what the ...origin/main and the [origin/main] are announcing.

You only need -u once per branch. The pairing is saved, so from now on plain git push is enough in this repository. Push without -u and the work still arrives, it just leaves you with no pairing and none of those three readouts.

And the one thing to fix in your head about push before anything else: pushing does not merge, and it does not ask. It either adds your commits on top of what is already there, or it is refused outright. Section J is that refusal, and it is the most useful thing in this session.

  2. Run git remote -v and confirm you get two lines, one (fetch) and one (push).
  3. Run git status -sb, git branch -vv and git branch -a, and read all three before you push.
  4. Run git push -u origin main.
  5. Run those same three commands again and find what changed in each one.

D. git clone, and the three kinds of branch name

Time to make the teammate. git clone takes a copy of a repository, and it is the command most people meet first, usually by pasting it off a GitHub page without knowing what it did. It does four things:

  • Copies the whole repository, every commit and every branch, not just the latest files.
  • Creates a remote called origin pointing at wherever you cloned from. So git remote add is the manual version of something clone does for you.
  • Checks out the default branch, so you get working files to look at.
  • Sets up tracking on that branch, which is the -u pairing you just made by hand.

Go up one folder and clone. The three commands after the clone are explained right below, so run all six lines:

PowerShell · make the teammate copy
cd ..
git clone ./origin-repo.git work-b
cd work-b
git remote set-url origin ../origin-repo.git
git config user.name "Rae Okafor"
git config user.email "rae@example.com"
Git Bash / macOS / Linux · make the teammate copy
cd ..
git clone ./origin-repo.git work-b
cd work-b
git remote set-url origin ../origin-repo.git
git config user.name "Rae Okafor"
git config user.email "rae@example.com"
run in remote-lab · git clone
> git clone ./origin-repo.git work-b
Cloning into 'work-b'...
done.

git remote set-url changes the address behind a nickname, leaving the nickname alone. Clone always writes down the full path it cloned from, which would be long and different on your machine, so this swaps it for the same short ../origin-repo.git that work-a uses. It is a real command worth knowing, since a project that moves house is exactly when you need it.

And git config user.name without --global sets the name for this repository only, rather than for everything you do. Session 1 set your identity globally; dropping --global overrides it in one place. That is what makes work-b genuinely somebody else rather than you in a different folder.

An aside worth thirty seconds. You cloned a repository that already had a commit in it. Clone an empty one and it tells you so: warning: You appear to have cloned an empty repository. That is a warning, not an error, and Session 1 drew that distinction: a warning means it worked and you should know something. It is only saying there was nothing to copy yet.

Now the reason this session exists. You are about to see three different names that all look like they mean "main", and telling them apart is the whole skill.

main
Yours. A branch in your copy, on your disk. It moves when you commit, and nothing anybody else does can move it.
origin/main
Your note about theirs. Also on your disk. It records where the shared copy's main was the last time you asked. It moves only when you ask again.
(the branch on the server)
Theirs. It has no name you can type, because you never see it directly. Everything you know about it is the note in the middle box.

The middle box is a cache, and almost every confusing thing about remotes is somebody treating it as live. origin/main is not a window onto the server. It is a sticky note you wrote, and it goes stale the moment somebody else pushes. Git has a name for that middle kind: a remote-tracking branch, meaning a branch that tracks what a remote had.

Look at all of it inside the fresh clone:

run in work-b · all the branch names, and one commit wearing three of them
> git branch
* main

> git branch -a
* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/main

> git branch -vv
* main 99a877c [origin/main] Add notes.md

> git log --oneline --decorate=short
99a877c (HEAD -> main, origin/main, origin/HEAD) Add notes.md
  • git branch shows only your own, which is why it looked so quiet in Session 3.
  • git branch -a adds the remote-tracking ones, spelled out in full as remotes/origin/main. The short way to write that same thing is origin/main, and that is what you will see everywhere else.
  • origin/HEAD -> origin/main is the remote's idea of its own default branch, the one you land on when you clone. It is a pointer at another pointer, and it is the reason you get main rather than being asked. You will almost never need to think about it, but it turns up in decorations, so it should not be a mystery.

That last line is the one to sit with. One commit, 99a877c, wearing three names at once: HEAD -> main (you are standing here), origin/main (your note says they are here too), and origin/HEAD (and this is their default branch). Three names, one commit, because right now everybody agrees. The rest of the session is what happens when they stop agreeing.

  3. Run git branch, then git branch -a, and say out loud what the extra lines are.

E. Somebody else pushes

Stay in work-b. You are Rae now. Add a line to notes.md and send it:

PowerShellSet-Content notes.md "line one" Add-Content notes.md "a line from B"
Git Bash / macOS / Linuxecho "line one" > notes.md echo "a line from B" >> notes.md
run in work-b · the teammate commits and pushes
> git add notes.md

> git commit -m "B adds a line"
[main 8b55c64] B adds a line
 1 file changed, 1 insertion(+)

> git push origin main
To ../origin-repo.git
   99a877c..8b55c64  main -> main

The push line has a different shape this time. Instead of * [new branch] it reads 99a877c..8b55c64, which is Git saying "the branch over there moved from this commit to that one". Two dots between two hashes is Git's way of writing a range, and you will see it again in a moment.

And this is where those two git config lines pay off. Ask plain git log for the last commit, in the full form Session 1 introduced rather than --oneline, and somebody else is genuinely on it:

run in work-b · the commit has a different author
> git log -1
commit 8b55c64905e8815b8e533c4655b0a88298f363a5
Author: Rae Okafor <rae@example.com>
Date:   Thu Aug 6 17:48:27 2026 -0500

    B adds a line

Your own commits in work-a still carry your name, because work-a never had its identity overridden. Two names in one project is what a shared repository looks like, and it is worth seeing once so that "somebody else pushed" is a fact about a person rather than a phrase in a workbook. If you skipped those config lines, this prints your own name instead and nothing else in the session changes.

The shared copy has now moved, and nothing told work-a. Nothing ever will, on its own. That is the next section, and it is the best demonstration on this whole track.

F. The proof that origin/main is only a note

Go back to your own copy and ask it how things are. Predict the answer before you read it. Rae has pushed. Your copy has not been told:

Both shellscd ../work-a
run in work-a · AFTER the teammate has already pushed
> git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

> git status -sb
## main...origin/main

> git log --oneline --decorate=short
99a877c (HEAD -> main, origin/main) Add notes.md

Read that second line again: Your branch is up to date with 'origin/main'.

It is perfectly true and completely useless. You are up to date with origin/main, because origin/main is your own note and your note has not changed. It says nothing whatsoever about the shared copy, which has moved on without you. Git is not lying and it is not broken. It is answering the question you asked, which was about a sticky note.

This single output is why the three-box picture matters, and once you have seen it, most remote confusion stops being confusing. Nothing in Git contacts the network unless you run a command that contacts the network. git status is not one of them, and neither is git log, or git diff, or anything else you have learned so far.

git fetch is the command that goes and asks. It contacts the remote, brings back anything new, and updates your origin/main to match what it found. That is all it does. It does not touch your branch. It does not touch a single file in your folder. If you fetch and then look at your files, nothing has changed, and that is the point rather than a disappointment:

run in work-a · git fetch
> git fetch
From ../origin-repo
   99a877c..8b55c64  main       -> origin/main

One line of report, and it is the same range shape from the push: the thing that moved from 99a877c to 8b55c64 was main over there, and what it updated here was origin/main. Git writes down which of your names it moved. (The address loses its .git ending on this line, purely because fetch prints the repository rather than the folder. Nothing has changed.)

Now ask the same questions as before:

run in work-a · the same three commands, after fetching
> git status -sb
## main...origin/main [behind 1]

> git status
On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)

nothing to commit, working tree clean

> git log --oneline --all --decorate=short --graph
* 8b55c64 (origin/main, origin/HEAD) B adds a line
* 99a877c (HEAD -> main) Add notes.md

Nothing happened to your work between those two blocks. The only thing that changed is what you know. The commits were sitting in the shared copy the whole time; you had simply never asked. [behind 1] means there is one commit they have that you do not.

And the graph makes it visible: origin/main has climbed one commit above HEAD -> main. Your two names are no longer on the same commit, which is the picture of being out of sync. (Your copy picked up an origin/HEAD of its own during that first fetch, which is why it appears here and did not in section C.)

G. Look at it before you take it

You have fetched, so the commits are already on your disk. They are just not in your branch. That gap is a genuinely useful place to stand, and it is the reason to know fetch as its own command rather than only ever using the shortcut in the next section.

You can read what is coming with a command you have had since Session 2. git diff HEAD origin/main compares where you are standing against your note of where they are, and Session 2's diff reading applies unchanged:

run in work-a · what is about to arrive
> git diff HEAD origin/main
diff --git a/notes.md b/notes.md
index 2d00bd5..62d3631 100644
--- a/notes.md
+++ b/notes.md
@@ -1 +1,2 @@
 line one
+a line from B

One line added to one file. Get in the habit: fetch, then diff, then decide. It costs seconds and it means nothing ever arrives in your folder unannounced.

Now take it, with a command you already know. origin/main is a branch name like any other, so you merge it exactly as you merged topic in Session 4:

run in work-a · git merge origin/main
> git merge origin/main
Updating 99a877c..8b55c64
Fast-forward
 notes.md | 1 +
 1 file changed, 1 insertion(+)

> git status -sb
## main...origin/main

Fast-forward, and that word should mean something to you now. Session 3 taught it: your branch had not moved since theirs went ahead, so there was nothing to combine and Git slid your pointer forward. Nothing about remotes changed that rule. An update that only arrives from somebody else, while you have added nothing, is always a fast-forward, and that is why most days of working with other people involve no merge commits at all.

The two names are back on the same commit, and [behind 1] is gone.

Your turn Break sync, prove it, then close it
  1. In work-b, add the line to notes.md, commit it, and push.
  2. Move to work-a and run git status before fetching. Read the "up to date" line and say why it is true and useless.
  3. Run git fetch. Read the one line it prints and name which of your branch names it moved.
  4. Run git status -sb and find [behind 1], then draw the graph and see the two names on different commits.
  5. Run git diff HEAD origin/main and read what is about to arrive.
  6. Run git merge origin/main and confirm it says Fast-forward.

H. git pull is those two in one command

Now that you have done it the long way, the shortcut cannot mislead you. git pull is git fetch followed by a merge into the branch you are on. Two commands, one word, nothing else hiding in it.

Prove it. Back in work-b, have Rae add a file and push it:

PowerShellcd ../work-b Set-Content summary.md "summary: not written yet"
Git Bash / macOS / Linuxcd ../work-b echo "summary: not written yet" > summary.md
run in work-b · a second change from the teammate
> git add summary.md

> git commit -m "Add summary.md"
[main 25fb465] Add summary.md
 1 file changed, 1 insertion(+)
 create mode 100644 summary.md

> git push
To ../origin-repo.git
   8b55c64..25fb465  main -> main

Plain git push with nothing after it, because work-b was cloned and clone set up the tracking. Now go back to work-a and pull:

run in work-a · git pull, with the two halves labelled
> git pull
From ../origin-repo
   8b55c64..25fb465  main       -> origin/main
Updating 8b55c64..25fb465
Fast-forward
 summary.md | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 summary.md

Read that output as two blocks, because it literally is two commands. The first two lines are the fetch, word for word what section F printed. The rest is the merge, word for word what section G printed. git pull did not do anything new; it ran both and printed both.

So when should you use which? Use pull when you just want the latest and you have nothing of your own in flight, which is most of the time. Use fetch then diff then merge when you want to see what is coming first, or when you already have commits of your own and want to know what you are walking into. Both are correct. The only bad option is not knowing which one you ran.

One name to file away and not act on: there is a setting called pull.rebase that makes git pull combine the two sides a different way, by rewriting your commits rather than merging them. It is off unless somebody turns it on, so your pull merges. Rebasing is Session 8, and until then a merge is the right mental model.

I. Reading ahead and behind

You have seen [behind 1]. There are four states that line can be in, and reading them at a glance is worth more than any single command in this session:

## main...origin/mainLevel. Neither side has anything the other lacks. Nothing to do.
[ahead 1]You have 1 they do not, as far as your note knows. You committed and have not pushed. If the note is current, a push will be accepted; if it is stale, this is the reading that lies to you.
[behind 1]They have 1 you do not. A pull will fast-forward you.
[ahead 1, behind 1]Diverged. Both sides moved since you last agreed. This is where a push gets refused, and it is the interesting case.

Every one of those numbers is measured against your note, not against the server, so all four can be out of date. A stale [ahead 1] is exactly how people get surprised by a rejected push, which is section J.

There is a command that prints the two numbers on their own, and it is worth meeting because its output is so blunt it is hard to misread:

run in work-a · the two numbers, once you are diverged (section J builds this state)
> git rev-list --left-right --count origin/main...HEAD
1	1

Left number is the thing named on the left of the three dots, right number is the thing on the right. So 1 commit in origin/main that HEAD cannot reach, and 1 commit in HEAD that origin/main cannot reach. One each: diverged. Swap the two names around and the two numbers swap with them, which is the only thing about this command that catches people out.

The three dots are the same range notation as the two dots you saw in the push and fetch lines, asking a slightly different question. You do not need to memorise the distinction; you need to remember left is the left name.

J. The rejected push, and both of its labels

Set it up deliberately. Rae pushes something, and then, without asking the server anything, you commit something of your own. Crucially the two of you touch different files, so there is nothing to argue about; this is purely about push and pull, not about conflicts.

PowerShell · both sides move, on different files
cd ../work-b
Set-Content todo.md "todo: pick a chart"
git add todo.md
git commit -m "Add todo.md"
git push
cd ../work-a
Set-Content ideas.md "idea: add a glossary"
git add ideas.md
git commit -m "Add ideas.md"
Git Bash / macOS / Linux · both sides move, on different files
cd ../work-b
echo "todo: pick a chart" > todo.md
git add todo.md
git commit -m "Add todo.md"
git push
cd ../work-a
echo "idea: add a glossary" > ideas.md
git add ideas.md
git commit -m "Add ideas.md"

You are now in work-a, one commit ahead as far as you know, and quietly one behind as well. Ask your own copy and it will confirm the half it can see:

run in work-a · what you believe
> git status -sb
## main...origin/main [ahead 1]

Push it:

run in work-a · the refusal
> git push
To ../origin-repo.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '../origin-repo.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

Nothing has gone wrong. Read it as the safety feature it is. Git was asked to move the shared branch to your commit, and it noticed that doing so would leave Rae's work with nothing pointing at it. Rather than lose somebody's commits, it refused and handed the decision back to you. Push is the one command in Git that can affect other people, and this refusal is why it cannot hurt them by accident.

  • ! [rejected] names the branch that was turned away.
  • error: completes a set you have been collecting. Session 1 gave you warning (it worked, but know this) and fatal (it could not even start), and Session 3 showed you one error: in passing, when git branch -d refused to delete an unmerged branch. error sits between the other two: the command started, and this part of it did not succeed. Like Session 4's conflict, it also finishes with a nonzero exit code, the invisible number that lets scripts notice.
  • The hint: lines are the answer, and they tell you to integrate the remote changes before pushing again. That is exactly what you will do.
  • The last hint is honest but unhelpful. git push --help opens the full manual page for push, usually in your browser, and it is thousands of words about every flag the command has. Everything you actually need is in the four lines above it.

Now do the first half of what it asked, and watch the message change:

run in work-a · fetch, then try the same push again
> git fetch
From ../origin-repo
   25fb465..283d6ff  main       -> origin/main

> git push
To ../origin-repo.git
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to '../origin-repo.git'
hint: Updates were rejected because the tip of your current branch is behind

Same refusal, different label, and the difference is worth having.

(fetch first)Your origin/main is stale. Git can tell the shared copy holds something you have not got, but your own note is too old for it to say more. The label is an instruction: go and ask.
(non-fast-forward)Now your note is current, and Git can be precise. Your branch is not a straight continuation of theirs, so the move it was asked to make is not a fast-forward, and it will not do it.

K. Recovering: fetch, integrate, push again

Three steps, and you already know all three. Get their work, join it to yours, then send the result. You have fetched, so step one is done. Step two is the merge.

Read this before you run the pull, because something will open. Both sides have moved, so joining them is a real merge, exactly the kind Session 4 taught, and a real merge builds a commit. A commit needs a message, so Git writes one and opens your editor to let you change it. This is not a problem and it is not a conflict. You have two choices, both fine: let it open and get out of it the way Session 4 showed (in vim: Esc, then :wq, then Enter), or add --no-edit to accept the prepared message and open nothing. If you are not sure which editor you have, run git var GIT_EDITOR first, exactly as in Session 4.

The transcript below leaves --no-edit off, so you meet it once and see what it says. Brace yourself for a screen that goes quiet, because this pull prints nothing at all before the editor appears:

run in work-a · git pull, and the editor opens straight away
> git pull

No output, and that is correct rather than alarming. Section H's pull printed a fetch report first because it had something new to collect. This one does not: you already fetched in section J, so origin/main is current and the fetch half has nothing left to say. Straight past it to the merge, and the merge opens the editor.

L. The milestone: what push and pull each change

This is the table the whole session was built to let you fill in. Three commands, and three things each one might move: your branch, your note of theirs, and the branch on the shared copy. Nine boxes, and if you can fill them in and prove two of them at the terminal, you have the model.

Here is the answer, so that the task below is a check rather than a guess. Cover it and try first.

Commandyour mainyour origin/mainthe branch on the shared copy
git fetchnoyesno
git pullyesyesno
git pushnoyesyes
  • fetch moves one thing. It updates your note and touches nothing else, which is why it is always safe to run.
  • pull moves two, because it is a fetch plus a merge, and the merge is what moves your branch. It never touches the shared copy.
  • push moves two as well, and it is the only one of the three that changes anything anybody else can see. It also updates your note on the way, which is why git status -sb reads level immediately after a successful push rather than still claiming you are ahead.
  • Nothing moves your main except you, by committing or by pulling. No one else can reach it.

Work in remote-lab for the milestone. Do not scroll back up; if you get stuck, git status tells you where you are, which is the habit this whole track is really teaching.

Proving the fetch row. The point is that the first line of each pair is identical before and after, and the second line is not:

Your main did not move at the push step because pushing sends commits you already made. The commit was the thing that moved it, one step earlier.
