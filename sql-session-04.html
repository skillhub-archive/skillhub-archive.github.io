A. Keys, and a second table to join to

Until now everything lived in one table. Real databases spread data across many tables so a fact is stored once, not repeated on every row, then recombined when you query. Two ideas make that work:

  • A primary key is the column that uniquely identifies each row of a table. Your customers.id has been the primary key since Session 1 (you declared it INTEGER PRIMARY KEY): no two customers share an id.
  • A foreign key is a column in one table that points at another table's primary key. It is how a row here says "I belong to that row over there."

So instead of jamming order details onto the customer row, you keep a separate orders table where each order carries a customer_id foreign key naming which customer placed it. Paste and run this in the Execute SQL tab, then click Write Changes. (You will write CREATE and INSERT yourself in Level 4; for now, just run it.)

add-orders.sql · run once against your shop.db
-- a second table; customer_id is a foreign key pointing at customers.id
CREATE TABLE orders (
  id           INTEGER PRIMARY KEY,
  customer_id  INTEGER REFERENCES customers(id),
  amount       INTEGER,
  order_year   INTEGER
);

A SQLite gotcha worth knowing now. Declaring customer_id INTEGER REFERENCES customers(id) documents the foreign key, but SQLite does not actually enforce it unless you first run PRAGMA foreign_keys = ON; in your session. Without that, SQLite would happily let you insert an order pointing at a customer that does not exist. Most other databases (PostgreSQL, MySQL, SQL Server) enforce foreign keys by default. Our data is already consistent, so nothing breaks either way here.

B. INNER JOIN: combine rows that match

An order on its own only tells you customer_id 6, not who that is. To pull the name from customers and the amount from orders into one result, you join the tables on the key that links them, with JOIN ... ON. Before the first join query, meet the two bits of notation it leans on, so nothing in it is a surprise.

Table aliases and qualified columns. In a join you give each table a short alias with AS: customers AS c and orders AS o (this is the same AS you used to rename result columns in Session 1, now naming a table). Here c and o are names we chose; you could spell the tables out in full or pick other letters. You then refer to a column as alias.column: c.name means "the name column of the table aliased c," and o.amount means the amount column of o. The general form is table.column. Why bother? Once two tables are in play, both might have a column with the same name (both could have an id), and a bare id would be ambiguous: the database would not know which table you meant. Qualifying every column with its table removes all doubt, and it makes a long query readable.

Now the join itself. JOIN names the second table and ON gives the condition to match rows on, here c.id = o.customer_id (a customer's primary key equals the order's foreign key):

SELECT c.name, o.amount, o.order_year
FROM customers AS c
JOIN orders AS o ON c.id = o.customer_id
WHERE c.name = 'Amara'
ORDER BY o.amount;
result · Amara's rows, name joined to each of her orders
name   amount  order_year
Amara  100     2023
Amara  200     2024

Read the whole FROM/JOIN/ON as one thought: start from customers, attach orders, and keep every pair of rows where the keys match. Each matching pair becomes one combined row, so Amara's two orders come back with her name filled in on both. Because every column is qualified, there is never any doubt which table a value came from.

Plain JOIN is short for INNER JOIN: the two words mean exactly the same thing. An inner join keeps only rows that find a match on both sides. Join the whole tables and count the result:

SELECT COUNT(*) FROM customers AS c
JOIN orders AS o ON c.id = o.customer_id;   -- 13: one row per matched order

Thirteen, exactly the number of orders, because every order matches exactly one customer. But Diego and Jae, who placed no orders, do not appear at all in an inner join: with nothing to match, an inner join drops them. Often that is what you want; sometimes it is not, which is the next concept.

One convenience across databases: if the joining columns had the same name in both tables (say both were called customer_id), you could shorten ON c.customer_id = o.customer_id to USING (customer_id). Our key names differ (id vs customer_id), so we use the explicit ON. USING works the same in SQLite, PostgreSQL and MySQL.

C. LEFT JOIN: keep the unmatched rows too

Sometimes the rows with no match are exactly the ones you care about, for example "which customers have never ordered?" An inner join can never answer that, because it already threw those customers away. A LEFT JOIN (full name LEFT OUTER JOIN) fixes this: it keeps every row from the left table (the one in FROM), matched or not. When a left row has no match, the right-side columns come back as NULL, the "missing value" marker you met in Session 2.

SELECT c.name, o.id AS order_id, o.amount
FROM customers AS c
LEFT JOIN orders AS o ON c.id = o.customer_id
WHERE c.city = 'Boston'
ORDER BY c.name, o.amount;
result · Diego is kept, with NULLs where an order would be
name   order_id  amount
Diego  NULL      NULL
Gita   10        150

Diego stays in the result even though he has no order; his order_id and amount are NULL because there was nothing on the right to fill them. With a plain JOIN, Diego's row would be gone entirely. That is the whole difference: INNER JOIN keeps only matches; LEFT JOIN keeps every left row and pads the misses with NULL. Count the two joins over the full tables and you can see it directly:

  • JOIN (inner): 13 rows, one per order.
  • LEFT JOIN: 15 rows, the same 13 plus one NULL-padded row each for Diego and Jae.

Because the misses are exactly the rows where the right side is NULL, you find the non-matches by testing the right table's key with IS NULL (recall from Session 2 that you test for a missing value with IS NULL, never = NULL):

SELECT c.name
FROM customers AS c
LEFT JOIN orders AS o ON c.id = o.customer_id
WHERE o.id IS NULL
ORDER BY c.name;
result · the customers with zero orders
name
Diego
Jae

This "LEFT JOIN then WHERE right_key IS NULL" is a standard pattern for "things on the left with nothing on the right," and worth memorizing.

A note on the other directions. A RIGHT JOIN keeps every row from the right table instead, and a FULL OUTER JOIN keeps unmatched rows from both sides. SQLite only gained RIGHT and FULL OUTER JOIN in version 3.39 (mid-2022), and PostgreSQL and SQL Server have had both for years; MySQL has RIGHT JOIN but still has no FULL OUTER JOIN (there you emulate it by uniting a LEFT JOIN and a RIGHT JOIN). In practice you rarely need them, because any RIGHT JOIN can be rewritten as a LEFT JOIN by swapping the table order, so LEFT JOIN is the one to know cold.

Chaining more than two tables (a look ahead, not today's work). You are not limited to two tables. If a third table shared a key, you would add another JOIN ... ON naming the next key, and the same matching rules apply to each join in turn:

-- shape only: we have no payments table, so there is no result to run here
SELECT c.name, o.amount, p.method
FROM customers AS c
JOIN orders AS o ON c.id = o.customer_id
JOIN payments AS p ON o.id = p.order_id;   -- each JOIN links on the next key

That is the pattern for when you need it; you will chain joins like this in the capstone (Session 10). For now, two tables is plenty.

D. Summarize across a join

Everything from Session 3 (COUNT, SUM, AVG, GROUP BY) works on a joined result just as it did on one table: join first, then group and aggregate. To total each customer's spending and count their orders, group by the customer:

SELECT c.name, COUNT(*) AS orders, SUM(o.amount) AS spent
FROM customers AS c
JOIN orders AS o ON c.id = o.customer_id
GROUP BY c.id, c.name
ORDER BY c.name;
result · one row per customer who ordered (inner join, so 8 rows)
name    orders  spent
Amara   2       300
Ben     1       50
Chen    3       300
Esi     1       200
Fatima  2       200
Gita    1       150
Hiro    2       200
Iris    1       200

Only eight customers appear: it is an inner join, so Diego and Jae (no orders) are absent. Grouping by c.id, c.name rather than just c.name is a good habit, since id is the truly unique key and two customers could in principle share a name.

The COUNT trap after a LEFT JOIN. Suppose you want every customer's order count, including the zeros. You reach for a LEFT JOIN to keep Diego and Jae, but now which count you use matters. Remember from Session 3 that COUNT(*) counts rows while COUNT(col) skips NULLs. After a LEFT JOIN, a no-match customer still occupies one row, filled with NULLs, so:

SELECT c.name, COUNT(*) AS with_star, COUNT(o.id) AS with_id
FROM customers AS c
LEFT JOIN orders AS o ON c.id = o.customer_id
GROUP BY c.id, c.name
ORDER BY c.name;
result · look at Diego and Jae
name    with_star  with_id
Amara   2          2
Ben     1          1
Chen    3          3
Diego   1          0
Esi     1          1
Fatima  2          2
Gita    1          1
Hiro    2          2
Iris    1          1
Jae     1          0

COUNT(*) reports 1 for Diego and Jae, counting the single NULL-filled row the LEFT JOIN produced, which is wrong for "how many orders." COUNT(o.id) reports 0, because it skips that NULL. So after a LEFT JOIN, count a real column from the right table (COUNT(o.id)), not COUNT(*), whenever the zero-match rows must read as zero. This is the same NULL-skipping rule from Session 3, biting in a new place.

Grouping works on any joined column, including one from the left table. Total revenue per city (inner join, so a city whose only customers never ordered simply will not appear):

SELECT c.city, SUM(o.amount) AS revenue
FROM customers AS c
JOIN orders AS o ON c.id = o.customer_id
GROUP BY c.city
ORDER BY revenue DESC;
result · Reno is absent (its only customer, Jae, never ordered)
city    revenue
Austin  1000
Denver  450
Boston  150

E. Put it together: the milestone

Your milestone stacks the whole session into one query: keep every customer (LEFT JOIN), count each one's orders correctly including the zeros (COUNT(o.id)), one row per customer (GROUP BY), busiest first (ORDER BY). Because ORDER BY runs last it can sort by the aggregate alias you defined:

SELECT c.name, COUNT(o.id) AS orders
FROM customers AS c
LEFT JOIN orders AS o ON c.id = o.customer_id
GROUP BY c.id, c.name
ORDER BY orders DESC, c.name;   -- most orders first, ties A to Z by name
result · all 10 customers, zero-order ones included at the bottom
name    orders
Chen    3
Amara   2
Fatima  2
Hiro    2
Ben     1
Esi     1
Gita    1
Iris    1
Diego   0
Jae     0

The , c.name second sort key breaks the ties (all the 2s and all the 1s) so the order is fully determined. Diego and Jae land at the bottom with 0, which is only possible because you used a LEFT JOIN and COUNT(o.id). Write this one from a blank editor.
