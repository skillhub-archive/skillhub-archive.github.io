Reading a response like an engineer

In Session 1 you read two things out of every response: the status code and the body. There is a third part sitting between them that you have been scrolling past, and it is where the server explains itself. Today you learn to read the whole response, including the case where what you are looking at is not even the answer to the request you sent.

A. A response has three parts, and you have read two of them

Session 1 gave you the request’s anatomy: a method, a URL, headers, and sometimes a body. A response has its own anatomy, and it is three parts, always in this order.

1. Status line
The three-digit code and a short reason phrase, meaning the human-readable words after the number. 200 OK. 404 Not Found.
2. Headers
Key/value pairs describing the response: what shape the body is in, how long the answer stays good, where to go instead. Today’s subject.
3. Body
The actual content, usually JSON. Optional: some perfectly successful responses have no body at all, which you will see in section C.

Headers work the same way in a response as they did in a request in Session 1: key/value pairs riding alongside the main content, describing it rather than being it. The difference is who writes them. You wrote the request headers; the server writes the response headers, and they are its only chance to tell you anything the status code and body do not.

In Postman, they are one tab away and easy to never click. Under the response there is a row of tabs, normally starting on Body, with a Headers tab alongside it. Click it and you get the full list, name on the left, value on the right. Everything in this session lives on that tab.

Your turn Find the tab you have been ignoring
  1. Send GET https://jsonplaceholder.typicode.com/posts/1, the same request as Session 1.
  2. Under the response, click the Headers tab and count the rows. When this session was built that response carried twenty-five of them, and that is the point: a response has been telling you far more than you were reading. Do not worry if your number differs by a few, since a service can add or drop a header at any time.
  3. Find the row named Content-Type. Do not worry yet about what it means; just locate it.

B. Content-Type: what the body actually is

Content-Type is the single most useful response header, because it tells you how to interpret every byte of the body. You met it in Session 1 as a request header, where setting the Body tab to raw JSON told the server how to parse what you were sending. In a response it works the same way pointed the other direction: the server telling you what it just sent.

Its value has two pieces:

  • A media type, written as type/subtype. This is the format. application/json is JSON, text/html is a web page, text/plain is unformatted text, image/png is a PNG image.
  • Optionally one or more parameters, tacked on after a semicolon as name=value. The common one is charset, which names the character encoding, meaning the scheme used to turn the letters in the body into bytes. charset=utf-8 is the modern default and covers every character you are likely to meet.

This matters practically, not just academically. Postman uses Content-Type to decide how to show you the body: a JSON response gets indented and colour-coded for you, and an HTML one can be rendered as a page. When a response arrives looking like unreadable mush, the usual cause is a Content-Type you did not check.

Its usual companion is Content-Length, the size of the body in bytes, not characters. Those are not the same thing: a plain English letter takes one byte in UTF-8, but an accented letter or an emoji takes two to four, so a body of 292 bytes may hold fewer than 292 characters.

Except that you will probably not see a Content-Length at all, and the reason is a good first lesson in a header being absent on purpose. Postman automatically sends a request header called Accept-Encoding, which Session 1 named as routine plumbing and told you to ignore. It says which compression formats you can unpack, normally gzip, br. A server that takes it up compresses the body, and then it cannot know the final size until it has finished sending, so instead of a length it sends Transfer-Encoding: chunked (meaning "in pieces, I will tell you when I stop") plus Content-Encoding naming the compression it used. Same request, same body, two different sets of headers:

the same request twice, differing only in whether the body came back compressed
> GET https://jsonplaceholder.typicode.com/posts/1
> header:  Accept-Encoding: identity      identity means "do not compress"
200 OK

Content-Type: application/json; charset=utf-8
Content-Length: 292

> GET https://jsonplaceholder.typicode.com/posts/1
> header:  Accept-Encoding: gzip, br     what Postman sends for you
200 OK

Content-Type: application/json; charset=utf-8
Content-Encoding: br
Transfer-Encoding: chunked
and no Content-Length row anywhere

Postman decompresses the body for you, so the JSON you read is identical either way. This is worth meeting now because "the header I was told to look for is not there" is otherwise a genuinely confusing first experience, and the answer is not that something broke: it is that a different header is doing the job.

Two last notes on reading a real header list. Header names are case-insensitive, which Session 1 covered: this service actually sends some of them lower case on the wire, and content-type and Content-Type are the same header. And these are a handful of rows out of twenty-five on that response; the rest is section D’s subject.

C. Caching hints: how long this answer stays good

The next group of headers answers a question you have not thought to ask: how long is this response still true? A server that says "this will not change for twelve hours" lets every client in the world skip re-asking, which is most of why the web is fast.

Three headers carry the bulk of it, and jsonplaceholder sends all three:

  • Cache-Control is the instruction. Its most common form is max-age=N, where N is a number of seconds for which this answer stays fresh, meaning safe to reuse without asking again. max-age=43200 is 43200 seconds, which is twelve hours.
  • ETag (short for entity tag) is a fingerprint of this exact body. If the body changes by one character, the ETag changes. It is opaque, meaning you never parse it or do arithmetic on it, you only ever hand it back unmodified. A leading W/ marks it as a weak tag, meaning "same content for practical purposes" rather than byte-identical.
  • Age is how many seconds this particular copy has been sitting in a cache between the server and you. A large Age on a response means you were served a stored copy, not a freshly computed one.

The old way, and why it still shows up. Before Cache-Control existed there were two cruder headers, and both are still emitted by servers being cautious with ancient clients. Expires gives an absolute date after which the answer is stale, and Pragma: no-cache was a blunt "do not store this". They came from HTTP/1.0; Cache-Control arrived with HTTP/1.1 and is strictly better, because a duration is immune to the clock on your machine disagreeing with the clock on the server. Where they conflict, Cache-Control wins, and modern clients ignore the other two entirely when it is present.

That is not a hypothetical. The response you have been fetching all session sends all three, and they flatly contradict each other:

three caching headers on one response, two of them ignored
> GET https://jsonplaceholder.typicode.com/posts/1
200 OK

Cache-Control: max-age=43200      the one that counts: fresh for 12 hours
Expires: -1                       HTTP/1.0 leftover, ignored
Pragma: no-cache                  HTTP/1.0 leftover, ignored
ETag: W/"124-yiKdLzqO5gfBrJFrcdJ8Yq0LGnU"
Age: 15586                        seconds this copy has sat in a cache

Read the first three lines together: one header says the answer is good for half a day, and the two beneath it say do not keep it at all. If you did not know Cache-Control takes precedence, that response looks broken. It is not; it is a server hedging for clients from 1997.

Using an ETag: the conditional request. An ETag is only worth having because of what you can do with it. Send it back on a later request in the If-None-Match request header, and you are asking: only send me the body if it has changed since this fingerprint. That is called a conditional request. If nothing changed, the server answers 304 Not Modified, and here is the part worth sitting with:

a conditional request, and a response with no body at all
> GET https://jsonplaceholder.typicode.com/posts/1
> header:  If-None-Match: W/"124-yiKdLzqO5gfBrJFrcdJ8Yq0LGnU"
304 Not Modified

Cache-Control: max-age=43200
ETag: W/"124-yiKdLzqO5gfBrJFrcdJ8Yq0LGnU"

no body at all: zero bytes, and no Content-Length or Content-Type either

A 304 is a success, not a failure. The server understood you, checked, and told you your copy is still correct, which is why it did not waste the bandwidth of resending 292 identical bytes. Postman will show an empty Body tab, and that is the whole point of this session in one screen: if you only read the body, a 304 looks like the API returned nothing and broke. If you read the status line and the headers, it says something useful and slightly generous.

One practical detail, because you will hit it: the quotes around an ETag are part of the value and must be included in If-None-Match. Sending W/"124-yiKd..." works and so does "124-yiKd..." without the W/, but stripping the quotes down to a bare 124-yiKd... does not match and you get the full 200 and body back.

Your turn Get a 304 out of a real server
  1. Send GET https://jsonplaceholder.typicode.com/posts/1 and, on the Headers tab, find the ETag row. Copy its value, quotes and all.
  2. Read the Cache-Control row and work out in your head how many hours max-age is describing.
  3. Add a request header with the key If-None-Match and paste your own copied ETag as the value. Do not use the one printed above: use whatever your response actually returned.
  4. Send it again. You should get 304 Not Modified and a completely empty Body tab.

D. What to ignore, and the one thing you must not

Twenty-five headers came back on that response, and this session teaches you to read fewer than half of them. The honest reason the rest can be skipped is worth stating plainly, because "read the whole response" is useless advice if it means reading all of it every time. Most response headers are infrastructure plumbing: they describe the machinery that carried the answer, not the answer.

Here is every header from that response, sorted, with a few grouped onto one row. The rule for the bottom group is not "these are unimportant", it is "these are not about your request, so they will never explain your problem".

The exception is the rate-limit group, and it is a big exception. An X-RateLimit- prefix means the server is counting your requests and will start refusing them when the count runs out. That refusal is a 429 Too Many Requests, and a client that never read the header has no idea why a request that worked a minute ago suddenly does not. Session 3 is where you handle it; today it is enough to know the headers exist and that they are the one group in a wall of plumbing that is genuinely about you.

Two things about that X- prefix worth knowing so it does not mislead you later. It originally meant "not an official header, an extension someone invented", and rate limiting still has no single official header, so different APIs spell it differently: X-RateLimit-Remaining, RateLimit-Remaining, and X-Rate-Limit-Remaining are all in the wild and all mean the same thing. So the skill is not memorising one spelling; it is scanning for the word "limit" in the header list.

  2. For each row, say "read it" or "plumbing" out loud before checking against the table above. Getting some wrong is expected; the goal is to stop finding the list intimidating.
  3. Find your own X-RateLimit-Remaining value. Send the same request a few more times and watch what it does.
What you should see happen to the rate-limit number, and why it is strange

It will not count down neatly, and it may not move at all. Four requests sent back to back while building this session, to /posts/1 through /posts/4, returned 999, 867, 766 and 999. That is not a bug and it is worth understanding rather than shrugging at: this service sits behind a cache, so most responses are stored copies, and a stored copy carries whatever the counter happened to say at the moment it was stored. The Age header is the tell, and those four responses had ages ranging from about 19 minutes to about 7 hours.

So the honest lesson is narrower than "watch your quota": on a cached public practice API, treat rate-limit headers as something to recognise, not something to trust as a live count. On an API you authenticate against, which is Session 3, your requests are not shared with anyone and the numbers are genuinely yours.

E. Redirects, the 3xx family, and following one on purpose

Session 1 named the five status families and said 3xx means "go look elsewhere". Here is what that actually involves, and it contains the single most common way a beginner misreads a response.

A redirect is a response whose whole message is "not here, try this other URL instead". It carries a 3xx status and a Location response header holding the URL to try. The body, if any, is a courtesy note for humans and no client reads it.

a redirect, seen on its own
> GET https://postman-echo.com/redirect-to?url=https://postman-echo.com/get
302 Found

Content-Type: text/plain; charset=utf-8
Content-Length: 50
Location: https://postman-echo.com/get
Vary: Accept, Accept-Encoding

Found. Redirecting to https://postman-echo.com/get

That URL is worth reading rather than just pasting. /redirect-to is a postman-echo endpoint whose job is to redirect you, and ?url= is a query string (Session 1) whose value is where you want to be sent. So you are telling the service where to bounce you, which makes redirects something you can practise on demand.

Location here is a complete URL. It is also legal for a server to send just a path, like /get, meaning "same host, this path instead"; postman-echo happens to always send the full URL. The Vary line on that response is section F’s subject, so leave it alone for now.

Now the trap, and it is the important part of this section. If you send that request in Postman as it comes out of the box, you will not see the response above. You will see this:

the same request, with Postman on its default settings
> GET https://postman-echo.com/redirect-to?url=https://postman-echo.com/get
200 OK
{
  "args": {},
  "headers": { whatever your Postman attached, as in Session 1 },
  "url": "https://postman-echo.com/get"
}

A 200, and no sign a redirect ever happened. Postman follows redirects automatically by default, the same way your browser does: it reads the Location, silently sends a second request there, and shows you the response to that. So the status line, headers and body on your screen belong to a request you never typed.

There are two ways to know, and you want both.

  • The tell you can always see. Look at the url field in the body above: it says /get, but you typed /redirect-to?url=.... Whenever a response describes a different URL than the one you sent, you have been redirected. Outside of postman-echo, which conveniently echoes the URL back, the same tell shows up as data that does not match what you asked for.
  • The setting. Postman has an option to stop following redirects, in its settings under the general section, worded along the lines of "automatically follow redirects". The exact wording and location have moved between Postman versions, so look for the word "redirect" rather than a specific menu path. You should find it already switched on, which is why the transcript above is what you get without touching anything, but trust the first tell over this sentence: if your own request returned a 302 rather than a 200, following is already off and you can skip ahead. Turn it off and the same request shows you the raw 302.

A chain, not just a hop. A redirect can point at another redirect. Nothing stops a server doing that and it is common in real life (an old domain redirects to a new one, which redirects to its HTTPS version, which redirects to a login page). With auto-follow on you see only the final answer; with it off you see one hop at a time and have to walk it yourself. Paste this exact URL, which asks postman-echo to redirect you to a second redirect:

a two-hop chain · paste this whole URL
https://postman-echo.com/redirect-to?url=https://postman-echo.com/redirect-to?url=https://postman-echo.com/get

The nesting looks strange but is exactly what it appears to be: the url value is itself a /redirect-to URL with its own url value. Here is what the server actually sends, hop by hop:

1
302 Found · Location: https://postman-echo.com/redirect-to?url=https://postman-echo.com/get
Content-Length 91. The client reads Location and sends a new request there.
2
302 Found · Location: https://postman-echo.com/get
Content-Length 50. Another redirect. Read Location, send another request.
3
200 OK · Content-Type: application/json
The JSON body you were actually after, three responses later. This one is big enough that Postman gets it compressed, so expect Content-Encoding here rather than a Content-Length.

Two 302s and a 200: three responses for one thing you typed. With auto-follow on, Postman shows you the third and hides the first two.

The 3xx family. Six codes below: five that redirect you, and one that is not a redirect at all. They differ in ways you mostly read rather than trigger, so this is a reference table, not a set of things to go and reproduce. (Two further 3xx codes exist, 300 and 305, and you can comfortably go a career without meeting either.)

Code
Name
What it means
301
Moved Permanently
This URL has a new permanent home. Clients and caches are allowed to remember it and skip the old URL next time.
302
Found
Go there for now, but keep using this URL in future. The one postman-echo sends, and the most common in practice.
303

Not a redirect at all. Your cached copy is still good, so here is no body. Section C, and the reason 3xx is "redirection" rather than "redirect".

The 307 and 308 rows are the practical reason all five exist. Historically, clients following a 301 or 302 after a POST would send a GET to the new URL and drop the body, which is a surprising thing to happen to a request that was trying to create something. 307 and 308 were added to say "same redirect, but keep my method and my body". If you only ever remember one thing from this table, remember that 307 and 308 preserve the method and body, and 301 and 302 do not guarantee it. The full rules live in the MDN page linked in your review below.

One last thing, and it is really the thesis of this session. postman-echo’s /redirect-to takes a documented second parameter, status_code, for choosing which 3xx you get. Try it:

asking for a 301, and reading what actually arrived
> GET https://postman-echo.com/redirect-to?url=https://postman-echo.com/get&status_code=301
302 Found

Location: https://postman-echo.com/get

You asked for a 301 and got a 302. This is not a typo in the workbook: the parameter is silently ignored on this service, and the same thing happens for 303 and 307. The point is not the quirk. The point is that a documented parameter, a confident-looking request, and a 3xx status in the response are not evidence that you got what you asked for. Only reading the actual status line is. That is the habit this entire session exists to build, and you now have a live example of a real, well-run service where trusting the documentation over the response would have made you wrong.

F. Content negotiation: asking a server for a different shape

Everything so far has been reading what the server chose to send. Content negotiation is the mechanism for having a say in it: you state which formats you can handle, and the server picks one and tells you what it picked.

Your side is the Accept request header, and the pairing with section B is worth stating explicitly because the two are easy to confuse:

  • Accept is a request header. It lists media types you would like back, using the same type/subtype form. It is a preference you express.
  • Content-Type on a response is the server’s answer about what it actually sent. It is a fact you read.

Postman sets Accept: */* for you automatically, which you saw echoed back in Session 1. */* means "any type at all", which is why every response so far has arrived in whatever the server preferred, normally JSON.

Now override it. Keep auto-follow off, because the endpoint that negotiates here is the redirect one, and with auto-follow on you would be looking at the response to the second request instead.

the same URL twice, differing by one request header
> GET https://postman-echo.com/redirect-to?url=https://postman-echo.com/get
> header:  Accept: text/plain
302 Found
Content-Type: text/plain; charset=utf-8

Found. Redirecting to https://postman-echo.com/get

> GET https://postman-echo.com/redirect-to?url=https://postman-echo.com/get
> header:  Accept: text/html
302 Found
Content-Type: text/html; charset=utf-8

<p>Found. Redirecting to <a href="https://postman-echo.com/get">https://postman-echo.com/get</a></p>

Same URL, same method, same status, same Location. One request header changed and the body came back in a different format, with Content-Type confirming it. That is content negotiation working.

Vary: how you know the server even looked. Notice the Vary: Accept, Accept-Encoding on that redirect response back in section E. Vary is the server listing which request headers changed its answer. Its original job is telling caches not to serve one stored copy to everybody (if the answer depends on Accept, a cache must store a separate copy per Accept), but for you it is a direct signal: if a request header you care about is named in Vary, the server is taking it into account.

And the honest part. Accept is a request, not a command, and most JSON APIs ignore it completely. Try the same trick on the other practice service:

asking jsonplaceholder for XML, and getting JSON anyway
> GET https://jsonplaceholder.typicode.com/posts/1
> header:  Accept: application/xml
200 OK
Content-Type: application/json; charset=utf-8
Vary: Origin, Accept-Encoding

{ "userId": 1, "id": 1,
  "title": "sunt aut facere repellat provident occaecati excepturi optio reprehenderit",
  "body": "quia et suscipit\nsuscipit recusandae consequuntur expedita et cum..." }

JSON, unchanged, with no complaint and no error. And look at that Vary: it names Origin and Accept-Encoding but not Accept, which is the server telling you outright that Accept plays no part in what it decides to send. This is a completely normal, well-behaved API. It only speaks JSON, so it sends JSON.

Two more things you may meet, named so they do not surprise you. A server that genuinely cannot produce anything you asked for may answer 406 Not Acceptable, and one that objects to the format you sent it answers 415 Unsupported Media Type. In practice, ignoring Accept is far more common than either. So the real skill is not composing a clever Accept: it is reading the response’s Content-Type and Vary to find out whether your preference mattered at all.

G. The milestone: read the whole response before deciding anything

Everything above collapses into a reading order. When a response is not what you expected, go through it in this order, and stop as soon as one step explains the surprise. The order matters: three of these five steps catch problems that look identical if you only read the body.

  1. The status line. What family, and what exact code? A 304 and a broken empty response look the same in the body and nowhere else.
  2. Is this even the response to my request? Does the data describe the URL you sent? If not, you were redirected and are reading a later hop.
  3. Content-Type. Is the body the format you assumed? If Postman is not pretty-printing, this is usually why.
  4. The body. Now read it, knowing what shape it is in and which request it answers.
  5. The explaining headers. Location for a 3xx, ETag and Cache-Control for anything about staleness, Vary for whether a header of yours mattered, and anything with "limit" in the name.

This is the session milestone, and it is deliberately about explaining rather than sending. You have already sent all three of these.

  1. The two-hop chain, with auto-follow off. How many responses did the server send in total? What did each Location say? What were the final status and Content-Type? And how would the answer to the first question have looked different with auto-follow on?
  2. A conditional GET returning 304. Why is the Body tab empty, why is that a success rather than a failure, and which request header of yours caused it?
  3. The redirect with Accept: text/html. What is the Content-Type, what does the body hold, and which single response header told you the server had considered your Accept at all?

You have hit the milestone when you can walk all three end to end with the page closed, naming the status line, the headers that mattered, and the body, in that order.

> 1. the two-hop chain
Three responses: 302, 302, 200.
  hop 1 Location: https://postman-echo.com/redirect-to?url=https://postman-echo.com/get
  hop 2 Location: https://postman-echo.com/get
  final: 200 OK, Content-Type: application/json
With auto-follow ON you would see only the 200, and the giveaway
that anything happened is the body naming /get, not what you typed.

> 2. the conditional GET
304 Not Modified. Empty because your ETag matched, so the server
skipped resending an identical body. A success: it answered your
question. Caused by your If-None-Match request header.

> 3. the redirect with Accept: text/html
Content-Type: text/html; charset=utf-8
Body: <p>Found. Redirecting to <a href="...">...</a></p>
The header that proves it looked: Vary: Accept, Accept-Encoding
