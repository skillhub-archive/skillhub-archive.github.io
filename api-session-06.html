A. What a mock server is

Session 5 ended with a contract precise enough to build against, and nothing to build against. A real books server would take someone days or weeks to write, and until it exists, anyone writing a client for it is guessing. A mock server closes that gap. It is a stand-in server that answers requests with saved examples, instead of running any code of its own. Postman builds one from a collection, and the answers it gives are that collection’s saved examples, which is exactly why Session 5 had you write sixteen of them.

Three things become possible the moment a mock exists:

  • A client can be built before the server. Whoever writes the app that lists and adds books can start today, against the contract, while someone else builds the real server against the same contract. The two halves meet later and already agree.
  • The contract gets tested while changing it is still cheap. Session 5 section A called this design-first. A mock is where a design meets its first client, and a missing status code or a confusing field shows up now, as one edit, rather than after someone has shipped code that depends on it.
  • Every refusal can be produced on demand. Making a real server send a 409 means first arranging a duplicate isbn. A mock sends its 409 example whenever you ask for it, which section D shows you how to do, so a client’s error handling can be tested as easily as its success.

You have used a fake server before: jsonplaceholder. The difference is whose fake it is. jsonplaceholder answers with its own data by its own rules, and Session 5 showed it never refuses a write. A mock of Books API v1 answers with your data by your rules, refusals included. Neither one stores what you send it, a point section F makes precise.

A mock does not understand a request. It compares it against the examples it was built from and replays the one that fits best. Postman’s documentation calls this its matching algorithm, and section C tests it, but the outline is short:

1
Keep only examples with the same method. A DELETE is only ever answered by a DELETE example.
2
Score them on the path. The closest path wins. The host, the part before the path, is ignored completely.
3
Then on the query string. Parameters like ?limit=500 count after the path.
4
Replay the winner’s saved response: its status, its headers and its body, exactly as you wrote them.

Two details matter later. Ordinary request headers play no part in the match unless someone turns on header matching, which is off for a new mock. The body counts only as a bonus: Postman’s documentation says that when an example’s saved body matches the request’s body, that example’s score goes up, and when it does not, nothing is taken away. Keep both in mind; they are behind most of what surprises people in sections C and D.

B. Building the mock from Books API v1

Building the mock takes four steps, and the last one is the one Session 5 set up for you. The menus in Postman move between versions, so each step names the word to look for rather than an exact click path.

  • 1. Create the mock from the collection. Open Books API v1, then look for the word “mock”: in the menu beside the collection’s name, or in a “Mock servers” area of the sidebar. Choose to mock this existing collection.
  • 2. Name it, and check one option. Call it Books API v1 mock. Leave the environment empty, since this collection does not use one. Then look for the option about public or private access, and make sure the mock ends up public, which the box below explains. Postman’s documentation says new mocks are public by default, but the control has been worded both ways: as making the mock private (leave it unticked) and as allowing public access (tick it). Postman may also offer to save the mock’s address as a new environment variable: you do not need that, because your collection already has the variable every request uses.
  • 3. Copy the mock’s address. Postman shows it once the mock exists. It looks like https://<mock-id>.mock.pstmn.io, where <mock-id> is a long id belonging to your mock alone; the angle brackets mean a stand-in, as in Session 3.
  • 4. Point baseUrl at it. Open the collection’s variables, the tab Session 5 used to create baseUrl, and replace https://api.example.com with the mock’s address, with no slash at the end. If Postman shows the variable with more than one value column, put the address in each. Save.

Why one variable is enough. Every request in the collection is written {{baseUrl}}/v1/books..., and the mock ignores the host when it matches, so changing that one value moves all six requests to the mock at once. The examples are written {{baseUrl}}/v1/... as well, and even an example saved with some other host would still match, because only the method, path and query string are compared. That is also the second of Session 5’s reasons for putting the version in the path, /v1, rather than in a header: the mock always sees it.

Now send List books, with no changes to the request:

your first request to your own API · a mock, captured live
> GET https://<mock-id>.mock.pstmn.io/v1/books
200 OK
Content-Type: application/json; charset=utf-8
x-ratelimit-limit: 120      Postman’s limit on the mock, not your API’s
x-total-count: 2            whatever count you saved in the example

[ { "id": 8, "title": "A Wizard of Earthsea", "author": "Ursula K. Le Guin", ... },
  { "id": 9, "title": "The Tombs of Atuan", "author": "Ursula K. Le Guin", ... } ]

The status, the x-total-count header and the body are exactly the ones you typed into the 200 example in Session 5. Postman adds a few headers of its own: ; charset=utf-8 on the content type, and a set of x-ratelimit headers. Those are Session 4’s rate-limit headers describing Postman’s limit on your mock, 120 requests a minute by its own x-ratelimit-limit header, and they say nothing about any limit your real API will have.

Optional, not graded: public or private? Read this before you ever put a mock in front of real data.

A public mock answers anyone who has its address. That is what makes section E’s second-person lane possible: a friend can call it with no Postman account at all. The id in the address is long and random, so nobody will stumble on it, but an address is not a secret. Session 3 showed that URLs get logged, bookmarked and pasted, so treat a public mock like an unlisted link: fine for invented books, wrong for anything real.

A private mock refuses any request that does not carry a Postman API key in a header called x-api-key. Postman’s documentation says members of the mock’s workspace can call it too. A request from anyone else without a valid key gets this:

> GET https://<mock-id>.mock.pstmn.io/v1/books        a private mock, no key
401 Unauthorized
{ "error": { "name": "invalidCredentialsError", "header": "Unable to authenticate",
             "message": "Double check your API key and try again." } }

That key is a far more powerful credential than any you met in Session 3. NASA’s DEMO_KEY could only spend a small quota. A Postman API key acts as you, across your whole Postman account, so Session 3 section G’s rules apply in full: never in a URL, never saved into a request in a collection you share, never pasted into a chat. A private mock also means anyone you share it with needs a Postman account and a key of their own. The rule of thumb: keep real data out of examples altogether, and if an example ever has to hold something real, make the mock private first.

C. How a mock chooses its answer

Section A’s outline, method, then path, then query string, sounds harmless. Run it against your collection and every result follows from it, including several a real books server would never give. Start with a request the contract plans for:

the query string decides · a mock, captured live
> GET https://<mock-id>.mock.pstmn.io/v1/books?limit=500
422 Unprocessable Content                  the example built for exactly this
{ "error": { "code": "field_invalid", "message": "limit must be 1 to 100.",
             "field": "limit" } }

> GET https://<mock-id>.mock.pstmn.io/v1/books?limit=50
422 Unprocessable Content                  50 is a perfectly good limit
{ "error": { "code": "field_invalid", "message": "limit must be 1 to 100.",
             "field": "limit" } }

The second answer is wrong by the contract, and it is exactly what the matching algorithm says should happen. Both examples for GET /v1/books have the same method and path. Only one, the 422, was saved with a limit parameter, so any request carrying a limit fits it better than the plain list. A mock matches your rules; it never checks them. It has no idea that 100 is the cut-off, because that number lives in your description, not in anything it compares.

The path works the same way. There is a GET /v1/books/8 example and no other id, so look at what happens to a book the contract has never heard of:

the closest path wins · a mock, captured live
> GET https://<mock-id>.mock.pstmn.io/v1/books/99
200 OK                                     not 404: the closest path is /v1/books/8
{ "id": 8, "title": "A Wizard of Earthsea", "author": "Ursula K. Le Guin", ... }

> GET https://<mock-id>.mock.pstmn.io/v1/authors
404 Not Found                              nothing in the collection is close
{ "error": { "name": "mockRequestNotFoundError", "header": "No matching requests",
             "message": "Double check your method and the request path ..." } }

Asked for book 99, the mock answered with book 8, "id": 8 and all. It does not read the id in your path. Postman’s documentation lists the ways a path can still count as a match, and one of them is a match “after removing alphanumeric IDs”: take the ids out of /v1/books/99 and /v1/books/8 and they are the same path. The 404 for /v1/authors is not your contract’s 404. Look at its body: name, header and message, which is Postman’s error shape, not the { "error": { "code": ..., "message": ... } } your contract promises. It is the mock saying it has no example anywhere near that request. A client that ever gets this one has sent something the contract does not contain.

Two more results go the forgiving way, and the same list in Postman’s documentation explains both: a path also counts as a match ignoring case, and ignoring a trailing slash. The mock answered GET /V1/BOOKS, in capitals, and GET /v1/books/, with a trailing slash, both with the 200 list. Session 5 section B said RFC 3986 treats a path as case-sensitive, so a real server is entitled to treat /V1/BOOKS as an address that does not exist. A mock forgiving it proves nothing about the server you build later, which is one reason the contract is lowercase everywhere. And a POST of an empty {}, which the contract refuses with a 422, was not refused at all by the mock these transcripts came from: it answered 201. No example was saved with an empty body, so the body gave no example a lead, and section D shows what decides the answer then.

Session 5 named every example with its status code first, and promised that this session would show why. Here are the sixteen names the transcripts use, which follow Session 5’s pattern:

Two, four, two, five, two and one: sixteen. Now look at Add a book through the matching algorithm. All four examples are POST, all four have the path /v1/books, and none has a query string. Only the body could separate them, and only if the request sends exactly the body saved in one of them, which a real client adding a real book never will. So they tie. Postman’s documentation says a tie goes to an example whose status is 200 if there is one, and otherwise to whichever comes first in Postman’s own internal order of example ids, which you never see and cannot choose. Read a book and Replace a book have a 200, so their plain requests are predictable. Add a book and Remove a book do not, and that is where the rule stops being theory.

To see it, this session’s author made four identical copies of the collection, gave each its own mock, and sent each one Add a book with a new book in the body (Dune, which no example holds), then Remove a book, with no extra headers:

Mock
Add a book with a new book, then Remove a book
copy 1
201, then 404
copy 2
400, then 204
copy 3
409, then 404
copy 4
422, then 404

The same collection and the same requests: four different answers to adding a book, and two to removing one. Each mock gave the same answer every time it was asked again, but which example wins a tie depends on ids Postman assigned when the examples were created. Your mock’s plain Add a book may answer any of its four examples, and its plain Remove a book 204 or 404, and nothing visible in your collection predicts which. A client developer who gets that 400 for a perfectly good book, or that 404 after a delete, has been misled by the mock, not by your contract.

The body bonus from section A is the one thing that does settle a tie: sent the body saved in the 409 example, all four mocks answered 409, even with the JSON laid out differently. Add one character to the title and all four were back to their four different answers. That is a curiosity, not a method, because a client that has to send one particular body to get one particular answer is not testing anything real.

The fix is to stop leaving it to the tie. A mock reads two request headers that choose an example outright:

  • x-mock-response-name, set to an example’s name, asks for that example.
  • x-mock-response-code, set to a status code such as 409, asks for the example with that status.

You add them on the request’s Headers tab, the same place Session 3 put X-Api-Key:

asking instead of hoping · a mock, captured live
> DELETE https://<mock-id>.mock.pstmn.io/v1/books/8
> x-mock-response-name: 204 removed
204 No Content

> POST https://<mock-id>.mock.pstmn.io/v1/books
> x-mock-response-name: 409 isbn taken
409 Conflict
{ "error": { "code": "isbn_taken", "message": "A book with this isbn already exists." } }

> PUT https://<mock-id>.mock.pstmn.io/v1/books/8
> x-mock-response-code: 409
409 Conflict
{ "error": { "code": "isbn_taken", "message": "A book with this isbn already exists." } }

The rules for a name, each one checked on a real mock:

  • The value must be the example’s name exactly: same capitals, same spaces. 409 ISBN TAKEN, or 409  isbn taken with two spaces, gets the mock’s own 404. The header’s name is a different matter: Session 2 showed header names are case-insensitive, and X-Mock-Response-Name worked just as well.
  • The name is checked against the method, and not against the path. Sending x-mock-response-name: 200 the book on a DELETE gets a 404, because that name belongs to a GET. But on a GET it wins anywhere: GET /v1/authors, a URL your contract does not have, came back 200 with book 8. A name can hide a wrong URL, so when you test a client, check its paths once with no name at all.
  • Send both headers and both must fit. A name of 409 isbn taken with a code of 201 fits no example, so the mock answers 404.
  • A name or code that fits nothing gets the mock’s 404, with a hint in its header field: No matching response when the name fit no example, No matching requests when no example had that status code.

Prefer the name. Today every example of one request has a different status, so a code works. A contract with two kinds of 422 for one request, a missing title and a malformed isbn, could only tell them apart by name. And one more thing worth knowing for section E: an edit to an example reaches the mock within seconds of being saved, with nothing to rebuild or redeploy.

E. Being the stranger

The milestone asks for a mock that a stranger could integrate against from your docs alone, and Session 5 called that the stranger test. The best way to run it is with a real stranger: hand them your mock’s address and your docs, say nothing else, and watch where they get stuck. The box at the end of this section shows how. But you can run it on your own today, honestly, if you hold yourself to three rules.

  • A new, empty collection. Create a collection called Books client and give it its own baseUrl variable, set to your mock’s address. Every request in it you type yourself. Never copy, duplicate or even open a request from Books API v1 while you work.
  • The docs are the description and nothing else. A stranger integrating with a real API gets a written page, not the provider’s collection. So today your docs are what you wrote in Books API v1’s description in Session 5 step 2. Keep that open and read only that.
  • Log every look-up. Each time you need a fact the description does not give you, and you find it somewhere else (in Books API v1’s requests, in Session 5, or simply in your memory), write one line: what you needed, and where you found it. This list is called a look-up log, and every line in it is a gap in your docs.

Here is the stranger’s brief. It says what a library app needs to do, deliberately in a user’s words, never in methods or URLs, because working out the requests from the docs is the whole test:

the stranger’s brief · six goals, no requests named
1  Show a user every book, and how many books there are in all.
2  Add a book, and find out where the new book can now be read.
3  Show the message a user would see if that book's isbn is
   already in the library.
4  Change only the title of book 8.
5  Remove book 8, and show the user that it worked.
6  Ask for 500 books at once, and show the user what went wrong.

A goal is done when its request is built in Books client, sent to the mock, and the response is what the docs said it would be. Expect the log to fill up quickly the first time. Session 5’s description held the shared rules and the field table, and nothing else, so the very first goal needs a URL that it never mentions. That is not a failure. It is exactly what this pass exists to find, while fixing it is one edit.

Then fix the docs, and run it again. Add whatever the log asks for to the description, then delete the requests in Books client and work through the brief once more from nothing. You are done when a whole pass needs zero look-ups and every response matches what the docs promised.

Playing the stranger has one blind spot you cannot remove. You already know the answers, so a gap your memory fills without your noticing never reaches the log. Only a real stranger finds those, which is why the second lane below is the better one whenever you can take it.

F. What a mock proves, and what it never can

A mock feels like an API, and that is the danger. Session 1 pointed ahead to this level for “an API whose data is yours”, and Session 3 for one “whose writes you control”. Here is precisely what that means: you decide every answer it gives, and it keeps nothing you send it. Watch a book go in and not come out:

add, list, remove, read · a mock, captured live, in this order
> POST https://<mock-id>.mock.pstmn.io/v1/books
> x-mock-response-name: 201 created
> { "title": "Dune", "author": "Frank Herbert", "isbn": "9780000000024" }
201 Created
location: /v1/books/8                      the saved example's Location
{ "id": 8, "title": "A Wizard of Earthsea", ... }   not Dune: the saved body

> GET https://<mock-id>.mock.pstmn.io/v1/books
200 OK
x-total-count: 2                           still 2: nothing was added

> DELETE https://<mock-id>.mock.pstmn.io/v1/books/8

{ "id": 8, "title": "A Wizard of Earthsea", ... }

G. The milestone: the Level 3 milestone, unassisted
