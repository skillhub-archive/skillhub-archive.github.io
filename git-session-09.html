Working like a professional

Every session so far quietly assumed two things: that the repository belonged to you, and that "you" meant one person with one email address. Both assumptions break the moment you work somewhere real. This session fixes the identity half, then hands you the three tools that separate somebody who uses Git from somebody who is comfortable in it: stash, tags, and bisect.

A. Everything so far assumed the repository was yours

Look back at what you have built in eight sessions and one thing is true of every single repository in it: you made it, you own it, and nobody could stop you doing anything to it. Session 5 gave you a remote, but the remote was yours too. Session 6 gave you a pull request, but you opened it against your own repository. Session 8 handed you --force-with-lease and a golden rule about not rewriting shared history, which was the first hint that other people exist.

That assumption breaks in two different places, and this session takes them in turn.

one machine,
two peopleYou have a single global user.email. The moment you have work repositories and personal ones on the same laptop, that one address is wrong for half of them, and every commit you make records the wrong one permanently. Sections C and D.
a repository
you do not ownCloning somebody else's project is easy. Working in it without doing something rude or destructive is a matter of choosing a posture up front, and there are four of them. Section H.

Between those two halves sit three tools, and they are here because they are what people reach for daily and almost nobody teaches them in order. git stash handles being interrupted mid-edit. Tags mark the version you shipped. git bisect finds the commit that broke something, and it is the closest thing in Git to a superpower: it will search a hundred commits in seven steps.

Out of scope today, named so you know they exist: signing commits with GPG or SSH, so a commit can prove it came from you rather than merely claiming to; worktrees, which let one repository have several folders checked out at once; submodules, a repository nested inside another; and hooks, scripts Git runs automatically at certain moments, which Session 10 meets on the deploy side. One more deserves a sentence here: git blame shows you who last touched each line of a file, and it is the natural complement to bisect. Blame answers "who wrote this line", bisect answers "which commit broke this behaviour", and the second question is the harder and more useful one.

C. Three config files, and the most specific one wins

Every setting you have ever given Git lives in a plain text file, and there is more than one of them. Git reads three, in a fixed order, and each one can overrule the one before it. This is the entire idea, and once you have it, half of Git's "why is it doing that" moments dissolve.

systemOne file for the whole machine, written by the installer. On Windows it is at C:/Program Files/Git/etc/gitconfig. You will rarely edit it and you did not write what is in it. Read with --system.
globalOne file for you, at .gitconfig in your home folder. This is where your name and email went in Session 1. It applies to every repository you touch. Read and written with --global.
localOne file per repository, at .git/config inside it. It applies to that repository and nothing else. Writing is what defaults here: a git config command with no scope flag writes to this layer. Reading with no flag is a different thing, and the difference matters: it resolves across all three layers and hands back whichever value wins. --local is the flag that reads this layer alone.

Later beats earlier, so local beats global beats system. That last sentence is worth reading twice, because the default with no flag is the most specific one, which is the opposite of what most people assume when they first meet these commands.

The command that makes all of this visible at once is git config --list --show-scope, which prints every setting Git can currently see with the layer it came from in front of it. Run it in config-lab. The output below is filtered to the settings this section is about, because the unfiltered list is long:

run in config-lab · who set what, and where
> git config --list --show-scope
system	init.defaultbranch=master
global	user.name=Rae Okafor
global	user.email=rae@example.com
global	init.defaultbranch=main

Look at init.defaultbranch, which appears twice. The installer wrote master into the system file. Your global file says main. Global is more specific than system, so main wins and a bare git init gives you a branch called main. That is the whole mechanism in one key, and it is also the answer to something Session 1 raised: the reason this track always writes git init -b main is that a machine whose global file is missing that line silently falls through to the system layer and gets master, with no warning printed at all.

There is a second form of the same command, git config --list --show-origin, which prints the file path instead of the layer name. Use --show-scope when you want to know which layer, which is usually the question, and --show-origin when you want to know which file to open. They are otherwise identical.

Any setting layers this way, not just that one. core.editor, which decides what opens when Git needs a message from you, is a common example: an installer may set one machine-wide, you may prefer another for everything you do, and a single repository may need a third. Whichever layer is most specific is the one that answers.

No local line appears above, and that is not an error. The filter accounts for part of it and the repository accounts for the rest: a brand new one has a .git/config holding only bookkeeping Git wrote for itself, keys like core.repositoryformatversion and core.filemode. Run the command unfiltered and you will see those, tagged local. What is missing is a local setting of your own, and section D is about putting one there.

D. More than one identity on one machine

Here is the problem, and it is probably sitting on your laptop right now. Your global user.email was set once, in Session 1, and every commit you have made since has been stamped with it. That is correct for exactly one category of repository. The moment you have a work project and a personal project on the same machine, one of those two categories is getting the wrong address on every commit, forever, because a commit records the author email as part of the commit itself and changing the setting afterwards does not go back and fix it.

What it looks like when it goes wrong is worth naming, because the symptom is not an error message. Push a commit to GitHub with an email GitHub does not recognise and the commit still arrives, still shows your typed name, and simply is not linked to your account: no avatar, no profile link, and it does not appear in your contribution graph. Push one with your other account's email and it is attributed to that other account. Nothing fails, which is exactly why people do it for months without noticing.

The fix is one line, and it uses the local layer from section C. Inside a repository, git config user.email with no scope flag writes to that repository's own .git/config, where it beats the global setting for that repository alone. Run this in config-lab:

run in config-lab · give this one repository its own email
> git config user.email
rae@example.com

> git config user.email "rae@personal.example"

> git config user.email
rae@personal.example

> git config --global user.email
rae@example.com

Setting it printed nothing, which is normal for git config when it writes. Now look at the first and third commands, which are identical and give different answers. A read with no flag does not mean "read the local file", it means "resolve this key across all three layers and tell me which value wins": before the change that was the global address, afterwards it is the local one. The fourth command asks specifically for the machine-wide file, and shows it sitting exactly where it was. You have not changed your identity, you have overridden it in one place. And the file it wrote to is one you can open:

run in config-lab · all three layers, filtered as before
> git config --list --show-scope
system	init.defaultbranch=master
global	user.name=Rae Okafor
global	user.email=rae@example.com
global	init.defaultbranch=main
local	user.email=rae@personal.example

Now the single most useful non-obvious fact in this session, and the one that produces the confusing half-broken cases. Make a third commit, using this exact message, because every transcript from here to the end of section G quotes it back at you:

run in config-lab · a third commit, message and all
PowerShellAdd-Content notes.md "a second line" git add notes.md git commit -m "Add a second line"
Git Bash / macOS / Linuxecho "a second line" >> notes.md git add notes.md git commit -m "Add a second line"

Now read back who Git says made it:

run in config-lab · whose name, whose email?
> git log -1 --pretty="%an <%ae>"
Rae Okafor <rae@personal.example>

The name came from the global file and the email came from the local one. Git resolves configuration per key, not per section and not per file: it looks for user.email through all three layers and takes the most specific answer, then does the same thing separately for user.name. Nothing inherits as a block. That is exactly the mistake that produces half-attributed commits, where somebody sets a personal email on a work laptop and their commits go out with their work display name attached to their personal address.

And the commits you already made keep the old address, which the log shows plainly:

run in config-lab · config applies forwards only
> git log --pretty="%h  %an <%ae>  %s"
f975bb2  Rae Okafor <rae@personal.example>  Add a second line
ff2b677  Rae Okafor <rae@example.com>  Add the app file
27449b1  Rae Okafor <rae@example.com>  Start the notes

Two addresses in one history. Fixing the old ones means rewriting every one of those commits, which is Session 8's territory and its golden rule, and it is the reason this is worth getting right early rather than tidying later.

The advanced form, named but not taught: a [includeIf] block in your global config can pull in a different config file automatically based on the folder a repository sits in, so everything under ~/work/ gets one identity and everything under ~/personal/ gets another, with no per-repository step at all. It is the right answer once you have more than a handful of repositories. Set the local value by hand a few times first, because includeIf is much easier to trust once you have watched the plain version work.

How do I tell whether a repository is "personal" if they are all just folders?

Run git remote -v in it and read the address. A repository whose origin points at your employer's organisation is a work one; a repository whose origin points at your own account, or which has no remote at all, is personal. If you are not sure, leave it alone: setting the wrong local email is harmless and reversible, but there is no point guessing.

E. Credential helpers: what that line in your config is doing

This section is here to make one line in your config stop being magic. It is descriptive rather than hands-on, and there is nothing to run and nothing to set.

Start with the problem. When you push to a remote over HTTPS, the server has to know who you are. Modern GitHub does not accept your account password for this; it wants a token, which is a long generated string. Typing a long generated string on every single push is not a workflow, so Git has a mechanism for delegating the question: a credential helper, which is simply a program Git asks whenever it needs an answer to "who are you and what is your secret".

You almost certainly have at least one already. On Windows the installer sets one machine-wide, in the system layer from section C:

managerThe Git Credential Manager, the Git for Windows default. It stores credentials in the operating system's own vault (Windows Credential Manager) and can open a browser window to log you in the first time. It arrives in the system layer, which is why you never configured it.
the gh CLIIf you have installed GitHub's command line tool and run gh auth login, it can register itself as a helper for GitHub addresses specifically. Git then asks gh for credentials, and gh answers from whichever account it is currently logged in as.
storeWrites the token to a plain text file in your home folder, unencrypted. It exists, it works, and it is worth recognising in somebody else's config so you can point out that it is a poor idea on a shared machine.

Which one is answering for you is a config question like any other, and you can read it with what section C gave you: git config --list --show-scope and look for credential.helper. If you see a line in the system layer saying credential.helper=manager, that is the installer's default doing its job. If you see a longer one in your global layer naming a program, something you installed has taken over for a particular host.

The one rule that matters here. A credential helper exists so that a secret is stored somewhere designed to hold secrets, rather than pasted into things. Never put a token into a repository, a config file you might commit, a screenshot, or a message to anybody, and if you ever print your config in front of another person, check what is in it first. A token is a password that does not look like one, which is precisely why it gets leaked.

The practical upshot for the rest of this session: nothing below needs a credential helper, because every remote is a folder on your own disk. The reason it is in the session at all is that section H is about repositories belonging to other people, and "how does my machine prove who I am to their server" is the question sitting directly underneath that.

F. git stash: the interruption tool

The situation is always the same. You are half way through an edit, nothing is finished, nothing is worth committing, and you need to be on another branch right now. Committing rubbish to get it out of the way is what most people do and it leaves a commit called wip in the history forever. git stash is the tool for exactly this: it takes your uncommitted changes to files Git is already tracking, stores them somewhere Git manages, and leaves you with a clean tree. That qualifier about tracked files is doing real work, and the end of this section is about what it costs you if you miss it.

Run it in config-lab. Change something in notes.md first, so there is an edit to put away:

run in config-lab · put an edit away and get it back
> git status --short
 M notes.md

> git stash
Saved working directory and index state WIP on main: f975bb2 Add a second line

> git status
On branch main
nothing to commit, working tree clean

> git stash list
stash@{0}: WIP on main: f975bb2 Add a second line

The tree is clean and the edit is not lost, it is in a list. stash@{0} is a name you can use, and the numbering works like Session 8's reflog: zero is the most recent, and stashing again pushes everything down so what was stash@{0} becomes stash@{1}. It is a stack.

Getting it back is git stash pop, which applies the top stash and removes it from the list in one move. Be ready for the volume of output, because pop prints a full status report and then tells you what it dropped:

run in config-lab · git stash pop
> git stash pop
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   notes.md

no changes added to commit (use "git add" and/or "git commit -a")
Dropped refs/stash@{0} (e80349328060f89b07da2cfbc9468d0c975ff281)

apply is the sibling of pop and the difference is one word: pop removes the stash from the list, apply leaves it there. Use apply when you want the same set of changes on two branches, or when you are not yet sure the stash applied cleanly and want the safety of still having it. The cost is that you then have to remove it yourself with git stash drop, and stashes nobody ever dropped are how people end up with eleven of them.

A stash with no message is labelled WIP on main, which tells you nothing once you have three. Give it one with git stash push -m, and notice that the prefix in the listing changes from WIP on to On when you do:

run in config-lab · a named stash, and apply rather than pop
> git stash push -m "half-written release notes"
Saved working directory and index state On main: half-written release notes

> git stash list
stash@{0}: On main: half-written release notes

> git stash apply
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   notes.md

no changes added to commit (use "git add" and/or "git commit -a")

> git stash list
stash@{0}: On main: half-written release notes

> git stash drop
Dropped refs/stash@{0} (6f6e2c57921dd3b5a82b58683c5a978c7a1ee8ea)

The stash was still listed after apply and only went away when told to. That is the whole distinction. Note what that has left behind: apply put the edit back onto notes.md and drop removed only the list entry, so the stash list is empty while your working tree is dirty again. Discard the edit before going on, because the next section needs a genuinely clean tree to make its point:

run in config-lab · back to a clean tree
> git restore notes.md

> git status --short

git restore is the Session 7 command for discarding an unstaged edit, and it prints nothing when it works. The empty git status --short underneath it is the confirmation, and it is what the next block depends on.

Now the thing that must not be missed, because it is a genuine data surprise rather than a detail. git stash does not stash untracked files. A file Git has never been told about is invisible to a plain stash, and the command does not warn you that it ignored anything. Create a brand new file, so that it is the only thing in the working tree, and watch:

create the file first · pick your shell
PowerShellSet-Content scratch.md "notes I have not committed yet"
Git Bash / macOS / Linuxecho "notes I have not committed yet" > scratch.md
run in config-lab · the trap
> git status --short
?? scratch.md

> git stash
No local changes to save

> git status --short
?? scratch.md

"No local changes to save", and the file is still sitting there. Git means it precisely: an untracked file is not a change to anything, because there is nothing to compare it against. The reason this matters is what happens next. A learner who stashes, switches branch, and finds their new file still in the folder concludes that stash is broken or that branches do not really isolate anything. Neither is true; the file was never in the stash, and it was never on either branch, because it is not in Git at all yet.

The fix is -u, for untracked:

run in config-lab · git stash -u
> git stash -u
Saved working directory and index state WIP on main: f975bb2 Add a second line

> git status --short

> git stash pop
Already up to date.
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	scratch.md

nothing added to commit but untracked files present (use "git add" to track)
Dropped refs/stash@{0} (f546c658fe6eb13a09f10711f117bfcb17373271)

This time the status printed nothing at all, because the file really was taken off disk, and popping brought it back as an untracked file exactly as it was. The Already up to date. line at the top of the pop is Git reporting on the tracked half, which had nothing in it; it is not an error.

Your turn Stash an edit, then prove the untracked trap to yourself
  1. In config-lab, edit notes.md and stash it with a message: git stash push -m "my first stash". Run git status and confirm the tree is clean.
  2. Run git stash list and read the label. Predict whether it starts WIP on or On before you look.
  3. Run git stash apply, then git stash list again. Is the stash still there? Now run git stash drop and check the list is empty.
  4. The trap. With a clean tree, create a brand new file that Git has never seen: Set-Content scratch.md "notes" in PowerShell, or echo "notes" > scratch.md in Git Bash. Run git stash and read what Git says. Then run git status --short and confirm the file is still there.
  5. Now run git stash -u and check git status --short again. The file should be gone from the folder entirely. Run git stash pop to bring it back.
  6. Put the lab back the way you found it before moving on: delete scratch.md, and run git restore notes.md to discard the edit, which is Session 7's command for exactly that. git status should be clean and git stash list should be empty.
Step 4 did nothing at all. Is that right?

Yes, and that is the lesson. If scratch.md is the only thing in your working tree, Git prints No local changes to save and stops, because from its point of view there are no changes: an untracked file is not a modification of anything it is tracking. If you had also had an edit to notes.md outstanding, the stash would have succeeded, taken the edit, and silently left scratch.md behind, which is the more dangerous version of the same behaviour.

G. Tags: marking the version you shipped

A branch name moves and a tag name does not. That is the whole difference. Every time you commit on main, the name main slides forward onto the new commit, which is what Session 3 meant by calling a branch a pointer. A tag is a name that gets attached to one specific commit and stays there permanently, which is what you want for "this exact commit is what we released as version 1.0".

There are two kinds, and the difference is real rather than cosmetic.

lightweightgit tag v0.1.0. Just a name pointing at a commit. Nothing else is recorded: no author, no date, no message. Fine for a private bookmark you will delete next week.
annotatedgit tag -a v1.0.0 -m "First real release". A genuine object stored in the repository, carrying who tagged it, when, and why. This is what you want for anything anybody else will see.
Always pass -m when you use -a. git tag -a v1.0.0 on its own opens a text editor to ask for the message, the same way a bare git commit does. Session 4 covered what opens on your machine and how to get out of it; the simple move here is to supply the message on the command line and never meet the editor at all.

Make one of each in config-lab and then prove the difference, rather than taking it on trust:

run in config-lab · two tags, and the proof they differ
> git tag v0.1.0

> git tag -a v1.0.0 -m "First real release"

> git tag
v0.1.0
v1.0.0

> git cat-file -t v0.1.0
commit

> git cat-file -t v1.0.0
tag

git cat-file -t prints what type of object a name resolves to, and Session 4 already used it. The lightweight tag resolves straight through to a commit, because that is all it is: a label on a commit. The annotated tag resolves to an object of type tag, which is a thing in its own right that in turn points at the commit. Two words of output, and they settle it.

git show makes the same point in a way you will actually notice day to day. On the annotated tag it prints a header block first, then the commit; on the lightweight one it goes straight to the commit with no header at all:

run in config-lab · git show on the annotated tag
> git show v1.0.0 --stat
tag v1.0.0
Tagger: Rae Okafor <rae@personal.example>
Date:   Thu Aug 20 11:39:24 2026 -0500

First real release

commit f975bb20afa12e22ad4a3cb7e42c425b4b9b0f1b
Author: Rae Okafor <rae@personal.example>
Date:   Thu Aug 20 11:38:23 2026 -0500

    Add a second line

 notes.md | 1 +
 1 file changed, 1 insertion(+)

Note the Tagger line carries the email you set in section D, which is the per-repository identity doing its job on a completely different kind of object.

git tag -n lists tags with a message beside each one, and quietly shows the difference too:

run in config-lab · git tag -n
> git tag -n
v0.1.0          Add a second line
v1.0.0          First real release

The annotated tag shows its own message. The lightweight one shows the commit's message, because it has no message of its own and Git falls back to the only text available. If you ever see a tag list where some entries look like release notes and others look like commit subjects, that is what you are looking at.

Tags show up in the log decoration alongside the branch names Session 3 taught, labelled so you can tell them apart:

run in config-lab · tags in the log
> git log --oneline --decorate=short
f975bb2 (HEAD -> main, tag: v1.0.0, tag: v0.1.0) Add a second line
ff2b677 Add the app file
27449b1 Start the notes

Two things to know about tags and remotes, both of which surprise people. First: git push does not push tags. You can tag a release, push, and find that nothing on the server knows about the tag, because tags travel only when asked. git push origin v1.0.0 sends one; git push --tags sends all of them. Second: a GitHub release is a tag with extra material attached to it. The tag is the part Git knows about; the title, the notes and any downloadable files are GitHub's layer on top. There is no such thing as a release without a tag underneath it.

This is the hook into Session 10. Deploying something raises the question "which exact commit is live right now", and a tag is how that question gets a permanent answer. Session 10 uses one.
Your turn Make both kinds of tag and prove which is which
  1. In config-lab, create a lightweight tag: git tag v0.1.0. It prints nothing.
  2. Create an annotated one: git tag -a v1.0.0 -m "First real release". Include the -m, or an editor opens.
  3. Run git tag and confirm both are listed. Nothing in that output distinguishes them, which is the point of the next step.
  4. Run git cat-file -t v0.1.0 and git cat-file -t v1.0.0. Say what each will print before you press enter. One word each.
  5. Run git tag -n and work out why the two message columns look like they came from different places, then run git show v0.1.0 and git show v1.0.0 and find the header that only one of them has.
  6. Run git log --oneline --decorate=short and find both tags in the decoration next to HEAD -> main.
  7. Tidy up if you like: git tag -d v0.1.0 deletes a tag locally. Leave v1.0.0 in place, it does no harm.
Which kind should I actually use?

Annotated, for anything anyone else will ever see, and for anything you might want to understand six months later. It costs one extra flag and one message, and in exchange the tag can answer who made this release and when. Lightweight tags are for temporary private bookmarks, for example marking where you were before an experiment so you can find your way back.

H. Repositories you do not own: four postures

You are about to clone something you did not write, which every section before this one has avoided. The risk is not that you will break their repository, because you almost certainly cannot: their copy lives on their server and your permissions there are whatever they chose. The real risks are smaller and more embarrassing. Accidentally creating a merge commit in a history that was clean. Pushing to a branch you should not have. Rewriting something and finding out afterwards that four people had it.

The defence is to decide your posture before you start, rather than discovering it halfway through. There are four, in order of how much they let you do:

1. read-only
clonegit clone and then never push. Everything you do is local, and nothing you do can reach anybody. This is the correct posture for reading code, running it, and searching its history, which is most of what you will ever do in somebody else's repository.
2. fast-forward
onlyA read-only clone plus git config pull.ff only, so a pull can never quietly create a merge commit. Set it in any clone you intend to keep in step with somebody else's work.
3. a forkA server-side copy of their repository that belongs to you. You can push to it freely because it is yours. This is the standard way to contribute to a project you have no write access to, and it is what Session 6's pull request model runs on.
4. fork plus
upstreamA clone of your fork with a second remote pointing at the original, so you can keep pulling in their new work while pushing your own to your copy. This is the full working setup.

Posture 2 is worth setting up properly, because it defends against a specific and common accident. Session 5 taught that git pull is fetch plus merge. When your branch and theirs have both moved, that merge is a real merge and it makes a merge commit, in a history that may have been deliberately kept linear. pull.ff only tells Git to refuse in that situation instead:

what an ff-only pull does when the branches have diverged
> git config pull.ff only

> git pull
From C:/Users/you/./rate-tool
   db323bc..b259a2e  main       -> origin/main
hint: Diverging branches can't be fast-forwarded, you need to either:
hint:
hint: 	git merge --no-ff
hint:
hint: or:
hint:
hint: 	git rebase
hint:
hint: Disable this message with "git config set advice.diverging false"
fatal: Not possible to fast-forward, aborting.

Read what actually happened there. The fetch half succeeded, so their new commits are now on your disk and origin/main has moved. The merge half refused. Nothing was lost and nothing was created; Git downloaded the news and then declined to make a decision on your behalf, which is exactly what you want from a repository you do not own. The two hints are Git telling you how to proceed deliberately if you meant to.

Postures 3 and 4 are the fork model, and it is Session 5's picture with one more remote. Session 5 gave you a single remote called origin, which was the shared copy. A fork setup has two, and the names are a convention rather than a rule:

originYour fork. You own it, you can push to it, and it is where your branches go before they become a pull request.
upstreamTheir repository. The one you forked from. You fetch from it to stay current and you never push to it.

Adding the second remote is one command, git remote add <name> <url>, which takes a name you choose and an address. After that git fetch upstream downloads their work under names like upstream/main, and you merge or rebase it into your own branch exactly as Session 5 taught. The transcript below was run against folders on one disk rather than against GitHub, using a bare repository as the stand-in for the fork, so that it can be checked without an account. With a real fork the two addresses would be GitHub URLs and every line would otherwise be identical:

the fork setup, run against folders rather than GitHub
> git remote -v
origin	C:/Users/you/./my-fork.git (fetch)
origin	C:/Users/you/./my-fork.git (push)

> git remote add upstream ../rate-tool

> git remote -v
origin	C:/Users/you/./my-fork.git (fetch)
origin	C:/Users/you/./my-fork.git (push)
upstream	../rate-tool (fetch)
upstream	../rate-tool (push)

> git fetch upstream
From ../rate-tool
 * [new branch]      main       -> upstream/main

> git branch -r
  origin/HEAD -> origin/main
  origin/main
  upstream/HEAD -> upstream/main
  upstream/main

Four lines, two of them theirs. The two HEAD -> lines are pointers to each side default branch rather than branches in their own right, and on older versions of Git the upstream/HEAD one may not appear at all until you ask for it with git remote set-head upstream -a. Three lines instead of four is not a fault. From here, keeping current is git fetch upstream then git merge upstream/main on your main, and contributing is a branch, a push to origin, and a pull request as in Session 6.

Forking itself is a button on a website, not a Git command, and this session does not ask you to press it. The commands above are the part that is Git, and they are what you will need the first time you contribute to somebody's project. Part 4 has a write-it that walks the whole setup, so you have written it once before you need it.

I. git bisect: binary search over history

Here is the situation bisect is for. Something worked in March and it is broken now. There are eighty commits in between, written by several people, and none of the messages says "break the totals". You could read all eighty. You could check out commits at random and hope. Or you could halve the problem seven times.

That is exactly what bisect does, and the idea is worth stating before the commands. You tell Git one commit where the thing was broken and one where it was fine. Git checks out the commit in the middle and asks you which it is. Your answer eliminates half the remaining range. Repeat. A range of eight commits is settled in three tests; a range of a thousand takes ten. The search does not care how big the history is, which is why this scales in a way reading does not.

J. Automating the search, and the milestone

git bisect run hands the good-or-bad judgement to a program. You give it a command, and Git runs that command at every step instead of asking you. The contract is the one every command line tool already uses: exit code 0 means good, and 1 through 124 mean bad. Two ranges are reserved: 125 means this commit cannot be tested and asks Git to skip it, and anything above 127 aborts the search outright.

An "exit code" is a number a program returns when it finishes, invisible unless you look for it, which the shell uses to tell success from failure. You do not need to know more than the two cases above.

The hard part of this is not the flag, it is the test. Bisect run needs a check that can be stated mechanically: something a machine can perform with no judgement. "The totals look wrong" is not one. "calc.txt contains the text TOTAL: 100" is. Writing that test is the actual skill, and on a real bug it is most of the work: you are converting a symptom somebody described in words into a question a script can answer the same way every time. The lab below uses a marker in a file, which keeps the focus on bisect rather than on debugging, but do not let that hide the real cost.

Write the test script in the clone. The two shells need different files, so use the one for your shell:

Add-Content test.ps1 'exit 1'
Git Bash / macOS / Linux · create test.sh in rate-tool-clone
printf '#!/bin/sh\ngrep -q "TOTAL: 100" calc.txt && exit 0\nexit 1\n' > test.sh
chmod +x test.sh

Both scripts say the same thing in two dialects: if calc.txt contains TOTAL: 100 exit 0, meaning this commit is good; otherwise exit 1, meaning it is bad. The chmod +x on the Git Bash version marks the file executable, which is a permission thing on Unix-like systems and has no PowerShell equivalent.
