Now the core pattern. Four objects do all the work, and you meet them in order: you connect to the file, ask it for a cursor, tell the cursor to execute a statement, then fetch the rows it produced.

  • sqlite3.connect("shop.db") opens the database file and returns a Connection. Point it at your file.
  • conn.cursor() gives you a cursor: the object that runs statements and holds onto the results so you can read them.
  • cur.execute("SELECT ...") runs one SQL statement (the same SQL you have been writing all along, now passed as a Python string).
  • cur.fetchone() returns the next row as a tuple, or None if there are no more rows. cur.fetchall() returns all the rows as a list of tuples. Each row is a tuple whose values are in the same order as your SELECT list.
  • conn.close() closes the file when you are done (or wrap the work in a with block, shown below).

Putting it together, here is a first full script that lists the Austin customers by name:

# open shop.db, run one SELECT, print the rows it returns
import sqlite3                       # ships with Python: nothing to install
conn = sqlite3.connect("shop.db")    # open the database file, get a Connection
cur = conn.cursor()                  # a cursor runs SQL and holds the results
cur.execute("SELECT name FROM customers WHERE city = 'Austin' ORDER BY name")
rows = cur.fetchall()                # every matching row, as a list of tuples
print(rows)
conn.close()                         # done: close the connection
terminal · python shop_report.py
[('Amara',), ('Chen',), ('Fatima',), ('Iris',)]

Read that output closely: it is a list of tuples, one tuple per customer. Each tuple looks like ('Amara',) with a trailing comma because it holds a single value (you selected one column, name). That trailing comma is Python's way of writing a one-item tuple. If you had run cur.fetchone() instead of fetchall(), you would get just the first row, ('Amara',), and calling it again walks to the next row until there are none left and it returns None.

Many scripts wrap the connection in a with block. When the block finishes, Python finalizes the transaction for you, committing your changes or rolling them back if an error was raised, which becomes a useful safety net once you start writing data in part D. One thing to know, so it does not surprise you later: the with block does not close the connection, so you still call conn.close() when the program is truly done.

# the with block finalizes the transaction at the end (it does not close conn)
import sqlite3
with sqlite3.connect("shop.db") as conn:
    cur = conn.cursor()
    cur.execute("SELECT COUNT(*) FROM customers")
    print(cur.fetchone())            # -> (10,)
conn.close()                         # still your job: close when done

B. Parameters: the ? placeholder

In the first script the city 'Austin' was written straight into the SQL string. That is fine for a fixed value, but the moment the value comes from outside (a variable, a form, a user), you must not paste it into the string yourself. Instead you leave a placeholder, the single character ?, and pass the real value alongside the query in a tuple. SQLite fills each ? in from that tuple, by position. And since every fetched row is a tuple, you read a single value out of it by position with row[0], where index 0 is the first value in the tuple:

# pass the value separately: a ? in the SQL, the value in a tuple
cur.execute("SELECT COUNT(*) FROM orders WHERE amount > ?", (100,))
row = cur.fetchone()     # one row: the tuple (6,)
print(row)               # -> (6,)
print(row[0])            # just the number inside it -> 6

Two things to notice. First, the result of a COUNT still comes back as a row, so fetchone() gives you the tuple (6,), and row[0] pulls the number out of it. Second, that params argument is (100,) with a trailing comma, and the comma matters: (100,) is a one-item tuple, but (100) is just the number 100 in parentheses, not a tuple at all. A single parameter always needs the trailing comma so Python sees a tuple.

The same placeholder works for text. To make the Austin query take its city from a variable:

# the ? is filled from the tuple; here the city is a variable
target = "Austin"
cur.execute("SELECT name FROM customers WHERE city = ? ORDER BY name", (target,))
print(cur.fetchall())    # -> [('Amara',), ('Chen',), ('Fatima',), ('Iris',)]

If a query needs several values, you write several ? and give a tuple with one value each, in the same order: WHERE city = ? AND plan = ? takes (target, "Pro"). Notice you never put quotes around the ? yourself, even for text; SQLite handles the value as data, which is exactly the point of the next concept.

C. Why placeholders matter: SQL injection

Here is the tempting shortcut you must never take: building the SQL by pasting the value into the string yourself, usually with an f-string. It looks harmless with a normal value:

# DANGER: the value is glued straight into the SQL text
city = "Austin"
cur.execute(f"SELECT name FROM customers WHERE city = '{city}'")

The problem shows up when the value is not friendly. Because the text is spliced into the query, a value that contains SQL punctuation becomes part of the query itself. Feed in a value crafted to always be true and the filter falls apart:

# a crafted value rewrites the WHERE into "match everything"
city = "x' OR '1'='1"
cur.execute(f"SELECT name FROM customers WHERE city = '{city}'")
print(len(cur.fetchall()))   # -> 10  (every customer leaks out)

The injected ' OR '1'='1 closes the intended string early and adds a condition that is always true, so the query returns all ten rows instead of the ones for a single city. A value crafted to end the statement and start a new one, the classic x'; DROP TABLE customers; --, is built to destroy data outright. Two honest details there: cur.execute runs only one statement, so that exact stacked payload actually raises an error here rather than dropping the table (but other drivers, and SQLite's own executescript, do run several statements and would be fully exposed). And notice the leak you just saw needed no second statement at all, so injection is a real danger even through execute. Splicing untrusted text into SQL like this is called SQL injection, and it is one of the oldest and most damaging web vulnerabilities.

The fix is the placeholder from part B. With ?, the value travels separately from the SQL text and SQLite treats it purely as data, never as executable SQL. The very same crafted string now matches nothing, because no city is literally equal to that whole string:

# SAFE: the ? sends the value as data, so it can never run as SQL
city = "x' OR '1'='1"
cur.execute("SELECT name FROM customers WHERE city = ?", (city,))
print(len(cur.fetchall()))   # -> 0  (nothing equals that literal string)

The rule is short: values always go through ? placeholders, never through string formatting. It is safer, and it is also easier to read.

D. Writing data from Python, and making it stick

Reads are only half the job. You run an UPDATE, DELETE or INSERT exactly the same way, through cur.execute with ? parameters. But writes have one extra step: they are not saved until you commit them. The sqlite3 module quietly opens a transaction around your write (the same BEGIN idea from Session 8), so nothing is permanent until you call conn.commit(), which is the COMMIT. If your script ends without committing, the change is rolled back and lost. Two more tools travel with writes: cur.rowcount tells you how many rows the write touched, and conn.rollback() is the matching ROLLBACK that throws a change away on purpose.

# move every Boston customer onto the Pro plan, then save the change
conn = sqlite3.connect("shop.db")
cur = conn.cursor()
cur.execute("UPDATE customers SET plan = ? WHERE city = ?", ("Pro", "Boston"))
print(cur.rowcount)      # -> 2  (Diego and Gita are the two Boston customers)
conn.commit()            # make it permanent; without this the change is lost at close
conn.close()

To add many rows in one go, cur.executemany takes the statement once and a list of tuples, one tuple per row, and fills the ? placeholders for each:

# insert two products at once: one tuple of values per row
new_products = [
    ("MARK",  "Marker",    1.50),
    ("KNIFE", "Box knife", 2.00),
]
cur.executemany("INSERT INTO products (sku, name, price) VALUES (?, ?, ?)", new_products)
print(cur.rowcount)      # -> 2  (two rows inserted)
conn.commit()

Because these examples change shop.db, run them once to see the counts, then re-run the setup script from part A whenever you want the original data back for later parts.

E. The pandas bridge, and the milestone

Reading rows as tuples is fine for a handful of values, but for analysis you want a real table you can sort, group and chart. That is what pandas gives you, and it connects to SQLite in one line. Unlike sqlite3, pandas is not built in, so install it once with pip install pandas (a one-time step at your terminal). Then pd.read_sql_query(sql, conn) runs your query on the connection and returns a DataFrame, a table whose columns are named from your SELECT list:

# run a grouped query and load the result straight into a DataFrame
import pandas as pd                  # installed once with: pip install pandas
df = pd.read_sql_query(
    "SELECT city, COUNT(*) AS n FROM customers GROUP BY city ORDER BY city",
    conn
)
print(df)
terminal · the DataFrame, printed
     city  n
0  Austin  4
1  Boston  2
2  Denver  3
3    Reno  1

The column headers city and n come straight from the SELECT list (n from the AS n alias). The leftmost column of numbers, 0 1 2 3, is not from your data: it is the DataFrame's automatic row index, which pandas adds to label each row. You will work with that index all through the Python track; for now just know it is why the printed table has an extra left column your query did not ask for. Like any DataFrame, it also answers len(df), the number of rows it holds.

read_sql_query is the doorway between the two halves of your training: SQL narrows and summarizes the data inside the database, and pandas takes it from there. Time for the milestone that puts the whole session together.

# a tiny report: one fetched number, one DataFrame
import sqlite3
import pandas as pd

conn = sqlite3.connect("shop.db")
cur = conn.cursor()

# 1) parameterized aggregate: total spend for one city (city passed as ?)
city = "Austin"
cur.execute(
    "SELECT SUM(o.amount) FROM orders o "
    "JOIN customers c ON o.customer_id = c.id "
    "WHERE c.city = ?",
    (city,)
)
total = cur.fetchone()[0]
print(city, "total spend:", total)

# 2) a per-city summary loaded straight into a DataFrame
df = pd.read_sql_query(
    "SELECT c.city, SUM(o.amount) AS total "
    "FROM orders o JOIN customers c ON o.customer_id = c.id "
    "GROUP BY c.city ORDER BY total DESC",
    conn
)
print(df)

conn.close()

Across databases, one pattern. sqlite3 is Python's built-in driver for SQLite specifically. Other databases use their own drivers you install separately: psycopg (or psycopg2) for PostgreSQL, mysql-connector-python or PyMySQL for MySQL, pyodbc for SQL Server. The good news is that they share the same shape, the Python DB-API: connect, get a cursor, execute, fetch, commit. Placeholders are almost the same too, though some drivers write them as %s instead of ?. And pd.read_sql_query works with any of them through a connection, so the bridge you just built is the same bridge everywhere.
