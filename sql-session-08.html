Changing data safely & indexes

You can build tables and add rows. Now change the rows that are already there. So far INSERT added brand-new rows. UPDATE is different: it changes values in rows that are already there. The shape is:

-- the general form; you replace the placeholders with real names
UPDATE t SET col = expr WHERE condition;

Here t, col, expr and condition are all placeholders (you do not type the words t, col, expr or condition): t is the table, col = expr says which column to set and what to set it to, and the WHERE condition picks which rows to touch, exactly the same WHERE you have filtered SELECT with since Session 2. The expr can be a plain value or a calculation using the row's own current values. To raise the price of the packing tape by ten percent, set price to price * 1.10 on just that one row:

-- raise only the TAPE row's price by 10% (price * 1.10 uses its own current price)
UPDATE products SET price = price * 1.10 WHERE sku = 'TAPE';

SQLite reports 1 row changed, and that row's price moves from 3.25 to 3.575. Every other row is untouched because the WHERE matched only TAPE:

result · SELECT sku, price FROM products ORDER BY id (after the update)
sku    price
BOX-S  2.5
BOX-L  4.0
TAPE   3.575
WRAP   6.75
LABEL  1.2

The one mistake that ruins your day: an UPDATE with no WHERE changes every row in the table. There is no confirmation prompt. The statement below sets all five products out of stock (it reports 5 rows changed), which is almost never what you meant:

-- NO WHERE: this touches every single row (all 5 products)
UPDATE products SET in_stock = 0;

That is why part C teaches transactions, and why the safest habit is to write the WHERE first, then the rest. For now, if you run a change you did not mean, re-run the setup script above to restore the tables.

One reassurance: the constraints you set in Session 7 still guard the table on every change, not just the first insert. An UPDATE that would set a price to 0 is rejected by CHECK (price > 0) with the same CHECK constraint failed error a bad INSERT would get, and a NOT NULL or UNIQUE rule stops a bad UPDATE the same way. Your rules protect the data no matter how a value tries to get in.

B. DELETE: removing rows, and how it differs from DROP

DELETE removes whole rows from a table. It takes the same WHERE you already know, and the same warning applies twice over: a DELETE with no WHERE empties the entire table. The shape is:

-- remove the rows the WHERE matches; omit WHERE and you remove them all
DELETE FROM t WHERE condition;

To remove the one product that costs less than 2 dollars (the Label sheet at 1.2), match it in the WHERE:

-- delete just the products cheaper than 2 (only Label sheet qualifies)
DELETE FROM products WHERE price < 2;

SQLite reports 1 row removed and four remain:

result · SELECT sku FROM products ORDER BY id (after the delete)
sku
BOX-S
BOX-L
TAPE
WRAP

DELETE is not DROP. Keep two ideas apart. DELETE FROM products removes rows but the (now empty) table and its columns and constraints all stay, ready for new inserts; it is DML (Data Manipulation Language, the statements that change the data in rows), and inside a transaction it can be undone (part C). DROP TABLE products is DDL (Data Definition Language, the statements that define structure) from Session 7: it removes the whole table, its structure and all, so there is no table left at all. Delete the data, or drop the container: very different outcomes.

Cross-database note. Other databases have a TRUNCATE TABLE command that wipes every row fast. SQLite has no TRUNCATE; a bare DELETE FROM products (no WHERE) is its equivalent and does the same job on the small databases you will meet here.

Your turn Delete matching rows, then restore

Run DELETE FROM products WHERE price < 2; and confirm 1 row is removed and four remain with SELECT * FROM products;. Then re-run the setup script so all five products are back for the next parts. (This is exactly the kind of change part C will teach you to undo without a rebuild.)

C. Transactions: a safety net for risky changes

An UPDATE or DELETE takes effect the instant you run it. A transaction lets you group one or more changes and decide, at the end, whether to keep them all or throw them all away. Three statements do it:

  • BEGIN starts a transaction. From here your changes are pending, not yet final.
  • COMMIT makes every change since BEGIN permanent, all at once.
  • ROLLBACK throws away every change since BEGIN, returning the data to exactly how it was.

All-or-nothing is the key idea (its formal name is atomicity): everything between BEGIN and COMMIT lands together, and a ROLLBACK undoes the whole group, not just the last statement. That gives you a safe way to try a scary change: begin, run it, look at the result with a SELECT, then keep it with COMMIT or undo it with ROLLBACK. Watch a full delete get undone:

-- try a destructive change, inspect it, then undo it completely
BEGIN;
DELETE FROM products;             -- empties the table...
SELECT COUNT(*) FROM products;    -- ...COUNT is now 0, inside the transaction
ROLLBACK;                         -- undo everything since BEGIN
SELECT COUNT(*) FROM products;    -- back to 5, as if the DELETE never happened
result · the two COUNT(*) values, in order
0     -- after DELETE, still inside the transaction
5     -- after ROLLBACK, the rows are back

Autocommit, the default. When you are not inside a BEGIN, SQLite runs in autocommit: each statement is its own little transaction that commits the moment it finishes, which is why every change so far was instant. Wrapping statements in BEGIN ... COMMIT is how you switch that off for a group. In DB Browser you often do this without typing it: the Write Changes button is effectively a COMMIT and Revert Changes is effectively a ROLLBACK of everything since your last write.

Your turn Undo a change with ROLLBACK

You just deleted every product and put them all back without a rebuild. If your tool commits each line separately, run them as a single script so they share one transaction.

D. Indexes: making reads fast

By default, to answer SELECT * FROM orders WHERE customer_id = 3, SQLite reads every row in orders and keeps the ones that match. That is a full scan. It is fine for 13 rows; on a table of millions it is slow. An index is a sorted lookup structure the database builds and maintains on one or more columns, so it can jump straight to the matching rows instead of reading them all, the way a book index sends you to the right pages instead of making you read the whole book. You create one with:

-- build an index on the orders.customer_id column so lookups on it can jump
CREATE INDEX idx_orders_customer ON orders(customer_id);

In CREATE INDEX name ON t(col), the name is a label you choose for the index (a common habit is idx_table_column) and t(col) is the table and column to index; here name, t and col are placeholders. Running it returns no rows: it just builds the structure and SQLite keeps it up to date from then on.

When an index helps: columns you use in a WHERE filter, in a JOIN condition (the ON keys from Session 4), or in an ORDER BY. Those are the columns the database has to search or sort by, so an index on them pays off.

The tradeoff (this is why you do not index everything): an index speeds up reads, but every INSERT, UPDATE and DELETE now has to update the index too, so writes get a little slower, and the index takes extra disk space. So index the columns you actually filter and join on, not every column.

Two you already have for free: a PRIMARY KEY is automatically indexed, and a UNIQUE constraint (like the one on products.sku from Session 7) is enforced by a hidden unique index. So looking a product up by its sku, or any row up by its id, is already fast without you adding anything.

Your turn Create an index

Run CREATE INDEX idx_orders_customer ON orders(customer_id);. It returns no rows, which is expected. You will prove it actually does something in the next concept. (You can list the indexes in your database with SELECT name FROM sqlite_master WHERE type = 'index';.)

E. EXPLAIN QUERY PLAN, and the milestone

How do you know whether a query scans the whole table or uses an index? You ask SQLite. Put EXPLAIN QUERY PLAN in front of any query and, instead of running it, SQLite tells you how it plans to run it. Read the plan for two words: SCAN means it reads every row, and SEARCH ... USING INDEX means it jumps to matching rows through an index. Run it once before you have an index on customer_id:

-- ask how SQLite will run this lookup (before any index on customer_id)
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 3;
result · the plan, before the index
SCAN orders

A full scan. Now add the index from concept D and ask again:

-- create the index, then ask for the plan again
CREATE INDEX idx_orders_customer ON orders(customer_id);
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 3;
result · the plan, after the index
SEARCH orders USING INDEX idx_orders_customer (customer_id=?)

Same query, same answer, but the plan changed from reading all of orders to jumping in through the index. That is the whole point of an index made visible.

Cross-database note. Most databases give you a way to see the plan, but the wording differs: PostgreSQL has EXPLAIN and EXPLAIN ANALYZE, MySQL has EXPLAIN, and SQL Server shows a graphical execution plan instead of an EXPLAIN keyword. The wording varies, but the SCAN-versus-SEARCH idea (read everything, or jump via an index) is universal.

SELECT * FROM orders WHERE customer_id = 3;   -- SEARCH orders USING INDEX ...

-- PART 2: change data safely, then undo it
BEGIN;
UPDATE products SET price = price * 1.10;      -- raise EVERY price 10% (no WHERE, on purpose)
SELECT sku, price FROM products ORDER BY id;   -- eyeball the new prices
