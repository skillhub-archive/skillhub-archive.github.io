A. Frame the question and confirm the schema

Every report starts with a question. Here is the one you will answer today, the kind a shop owner actually asks: for each city, how many customers do we have, how many orders did they place, what is the total revenue, and what is the average order size? One row per city, busiest cities first, and skip any city too small to matter.

You already have the schema to answer it. shop.db holds three tables, and this report leans on the first two:

  • customers (ten rows): one row per customer, with id, name, city, plan, monthly_fee, signup_year and a nullable referrer.
  • orders (thirteen rows): one row per order, with id, a customer_id that points at customers.id (the foreign key from Session 4), amount and order_year.
  • products (five rows): the catalog you built in Session 7. The report does not use it, but it is still in the database.

If you still have shop.db from the earlier sessions, you are ready. If you lost it, rebuild all three tables once from the script below (paste it into DB Browser and Write Changes), then carry on.

B. Build the core report query

Now the heart of the session. You want one row per city, and every column of the report is a tool you already know. There is one new function to meet first. ROUND(x, n) rounds the number x to n decimal places, so ROUND(112.5, 2) stays 112.5 and ROUND(123.456, 2) becomes 123.46. An average like AVG(o.amount) can print a long trailing decimal, and wrapping it in ROUND(AVG(o.amount), 2) keeps the report readable. Here x and n are placeholders: you replace x with the value to round and n with how many decimals you want, you do not type the letters.

Here is the full report query, then a walk through every clause:

-- per-city sales summary: customers, orders, revenue, average order
SELECT c.city,
       COUNT(DISTINCT c.id)    AS customers,
       COUNT(o.id)             AS orders,
       SUM(o.amount)           AS revenue,
       ROUND(AVG(o.amount), 2) AS avg_order
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
GROUP BY c.city
HAVING COUNT(DISTINCT c.id) >= 2
ORDER BY revenue DESC;
result · 3 rows
city    customers  orders  revenue  avg_order
Austin  4          8       1000     125.0
Denver  3          4       450      112.5
Boston  2          1       150      150.0

Walk it clause by clause, and notice how much of the sprint is packed into one query:

  • LEFT JOIN (Session 4) keeps every customer, even Diego and Jae who never ordered, so they still count toward the customers column. An inner join would silently drop them.
  • COUNT(o.id) counts orders, and because a customer with no orders is padded with a NULL o.id after the LEFT JOIN, COUNT(o.id) skips those NULLs (that is the Session 4 trap: COUNT(*) would have counted the padded row as 1).
  • COUNT(DISTINCT c.id) (Session 3) counts each customer once even though the join repeats a customer's row for every order they placed.
  • SUM and AVG (Session 3) add up and average the order amounts per group, and ROUND trims the average.
  • GROUP BY c.city then HAVING (Session 3) collapses to one row per city, then HAVING COUNT(DISTINCT c.id) >= 2 drops any city with fewer than two customers. That is why Reno disappears: it has only Jae.
  • ORDER BY revenue DESC (Session 2) puts the busiest city first. The revenues 1000, 450, 150 have no ties, so the order is unambiguous.
Your turn Run the report query

C. Sharpen it with a CTE and a comparison

The report answers the shop's question, but a good analyst also brings the follow-ups. Two of them reuse tools from Level 3, and both read cleanly as a CTE (the WITH name AS (...) named result from Session 6).

First: which customers spend more than the average customer? This was the Session 5 and 6 milestone. Build a CTE of per-customer totals, take the average of those totals in a second CTE, then keep the customers above it:

-- top spenders: customers whose total spend beats the average customer total
WITH totals AS (
  SELECT c.id, c.name, SUM(o.amount) AS total
  FROM customers AS c
  JOIN orders AS o ON o.customer_id = c.id
  GROUP BY c.id, c.name
),
avg_total AS (
  SELECT AVG(total) AS a FROM totals
)
SELECT name, total
FROM totals
WHERE total > (SELECT a FROM avg_total)
ORDER BY total DESC, name;
result · the average customer total is 200
name   total
Amara  300
Chen   300

Only customers with orders appear in totals (it uses an inner JOIN), the average of those eight totals is 200, and Amara and Chen are the two above it at 300 each.

Second, a data-quality check: which customers placed no orders? Back in Session 5 you saw there are three ways to ask this, and all three return the same two names, Diego and Jae:

-- 1) LEFT JOIN then keep the rows with no match (Session 4)
SELECT c.name FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- 2) NOT EXISTS: no matching order row exists (Session 5, the safe one)
SELECT c.name FROM customers AS c
WHERE NOT EXISTS (SELECT 1 FROM orders AS o WHERE o.customer_id = c.id);

-- 3) NOT IN: works here, but fragile if the subquery can return a NULL (Session 5)
SELECT c.name FROM customers AS c
WHERE c.id NOT IN (SELECT customer_id FROM orders);

All three give Diego and Jae, because orders.customer_id has no NULLs. The NOT IN version is the fragile one: if that subquery column could contain a NULL, NOT IN would return no rows at all (the Session 5 trap). NOT EXISTS is the version that never surprises you.

D. Drive it from Python

A report you have to open DB Browser and run by hand is not really automated. In Session 9 you learned to run this exact SQL from Python: sqlite3.connect to open the file, a cursor to execute and fetchall, and pd.read_sql_query to load a result straight into a pandas DataFrame. The report query is just a (multi-line) string you hand to both. Here it fetches the rows as tuples and prints each one:

# run the per-city report from Python and print each fetched row
import sqlite3
conn = sqlite3.connect("shop.db")
cur = conn.cursor()
report = (
    "SELECT c.city, COUNT(DISTINCT c.id) AS customers, "
    "COUNT(o.id) AS orders, SUM(o.amount) AS revenue, "
    "ROUND(AVG(o.amount), 2) AS avg_order "
    "FROM customers AS c "
    "LEFT JOIN orders AS o ON o.customer_id = c.id "
    "GROUP BY c.city HAVING COUNT(DISTINCT c.id) >= 2 "
    "ORDER BY revenue DESC"
)
cur.execute(report)
for row in cur.fetchall():           # each row is a tuple in SELECT order
    print(row)

# load the same report straight into a pandas DataFrame
import pandas as pd                   # installed once with: pip install pandas
df = pd.read_sql_query(report, conn)

# the capstone: the per-city report, fetched as tuples and as a DataFrame
import sqlite3
import pandas as pd

report = (
    "SELECT c.city, COUNT(DISTINCT c.id) AS customers, "
    "COUNT(o.id) AS orders, SUM(o.amount) AS revenue, "
    "ROUND(AVG(o.amount), 2) AS avg_order "
    "FROM customers AS c "
    "LEFT JOIN orders AS o ON o.customer_id = c.id "
    "GROUP BY c.city HAVING COUNT(DISTINCT c.id) >= 2 "
    "ORDER BY revenue DESC"
)

conn = sqlite3.connect("shop.db")
cur = conn.cursor()

# 1) fetch and print each row as a tuple
cur.execute(report)
for row in cur.fetchall():
    print(row)

# 2) load the same report into a DataFrame
df = pd.read_sql_query(report, conn)
print(df)

conn.close()
