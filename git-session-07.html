Undo, safely

"Undo" is not one operation in Git. It is six, and they differ in exactly one way that matters: which part of your repository they change. Session 1 gave you the three areas a change travels through, and Session 3 gave you the branch pointer. Those four things are the whole vocabulary of this session. Once you can name the thing you want changed, the command stops being something you look up and starts being something you derive.

Milestone Undo a local mistake and say exactly which area you changed.
git

You do not need any folder from an earlier session. Step one below builds a small new repository called undo-lab from nothing, in about twenty seconds. It gets its own folder because this session deliberately destroys things, and it is worth being able to say, at every point, that nothing at risk is anything you care about. Session 6 already told you that remote-lab was finished with; you can delete it whenever you like.

No account and no network. Everything here is local. There is nothing to push and nothing to sign in to.

This is a workbook, not a reading. You will predict what a command does to your repository, reassemble command sequences, fill blanks, and write from scratch, and each part hands you less scaffolding than the last. The goal is the one this whole track is built on: read a Git command and know what it will do before you press enter.

Learn & Do

Short concept, then immediately your turn. Run each task in your own terminal before moving on, and tick the box once you have seen the result with your own eyes.

How to read the transcripts below. A line that starts with > in blue is what you type. Everything underneath it is what Git printed back. Do not type the > itself. Three things will legitimately differ on your machine: commit hashes (short strings like 18eae98), dates, and paths. Everything else should match, including the tab that Git puts in front of a file name inside a git status report.

Two things about this session in particular. First, several of these commands print absolutely nothing when they succeed, and both of the restore commands are among them. Silence is the success message; it is not a sign that the command failed to run. Second, your own hashes will change as you work through this, not just differ from the ones printed here. Whenever you undo a commit and then make it again, the result is a brand new commit with a new hash even though the message and the change are identical. Notice that when it happens; Session 8 explains why.

A. Undo is not one command, it is four things you can move

Every undo command in Git does the same kind of job: it changes one or more of four things. Three of them are the areas from Session 1, and the fourth is the branch pointer from Session 3. Nothing else in this session is new, which is why it is worth writing the four down before you touch a command:

working tree
The files in your folder, as your editor sees them this second.
staging area
The shortlist of what will go into the next commit.
repository
Every commit ever made, stored inside the .git folder.
branch pointer
The 41 bytes that say which commit the name main currently means.

That is the whole trick of this session. You do not memorise six commands and hope you pick the right one. You ask yourself what do I want changed, you name it out of that list of four, and the command follows from the answer. By the end you will build that mapping yourself as a table, and the table is the milestone.

Two things separate the commands more than anything else. The first is how many of the four they touch: some move exactly one, and one of them moves all four. The second is direction. Most of these commands move a branch pointer backwards, over commits you have already made. One of them, revert, moves it forwards by adding a new commit, and that difference turns out to decide which of them is safe to use on work other people already have.

The honest warning, up front rather than buried. The level you are starting says that almost nothing in Git is truly unrecoverable, and that is true. But "almost" is doing real work in that sentence, and a session that did not name the exceptions would be lying to you comfortably. Exactly two things in this session destroy work with no way back, and both of them do it to changes you have not committed: git restore <file> and git reset --hard. Both are flagged again in red where they appear. Everything else here can be undone, and Session 8 is where you learn how.

Out of scope today, so you know these exist and are not missing anything: recovering a commit after you have thrown the branch pointer past it is Session 8, and it is genuinely the sequel to this session rather than an afterthought. So are git commit --amend, git rebase and force pushing. git clean, which deletes untracked files, gets one mention later and no more. And reverting a merge commit needs an extra flag, -m, because Git has to be told which of the two parents to treat as the mainline; it is fiddly, it is rare, and knowing the flag exists is enough for now.

B. Build the lab

A brand new repository with three tiny commits in it. Paste the block for your shell and run the whole thing. It creates a folder in your home directory called undo-lab, puts three files in it, and commits them one at a time so that there is a history to undo:

PowerShell (Windows default) · build undo-lab
cd ~
mkdir undo-lab
cd undo-lab
git init -b main
Set-Content a.txt "one"
git add a.txt
git commit -m "c1 add a"
Set-Content b.txt "two"
git add b.txt
git commit -m "c2 add b"
Set-Content c.txt "three"
git add c.txt
git commit -m "c3 add c"
Git Bash / macOS / Linux · build undo-lab
cd ~
mkdir undo-lab
cd undo-lab
git init -b main
echo "one" > a.txt
git add a.txt
git commit -m "c1 add a"
echo "two" > b.txt
git add b.txt
git commit -m "c2 add b"
echo "three" > c.txt
git add c.txt
git commit -m "c3 add c"

git init -b main rather than a bare git init, for the reason Session 1 gave: the -b flag names the first branch outright, so this works the same on any machine no matter what that machine has configured as its default.

If you are on Git Bash on Windows, you will see a warning line after each git add, reading warning: in the working copy of 'a.txt', LF will be replaced by CRLF the next time Git touches it. That is Session 1's line-ending note doing its job: echo writes the file one way and Git stores it another, so Git tells you it will convert. It is not an error and nothing is wrong. Expect it again at every git add in this session, because every one of them follows another echo. PowerShell writes files in the form Git wants already, so it prints nothing, and none of the transcripts below show it. That difference comes from the core.autocrlf setting the Git for Windows installer puts in place; a Git without that setting does not print these lines at all.
Already have an undo-lab, or something went wrong partway? Wipe it and start clean

Three commits, and (HEAD -> main) on the newest. Session 2 taught that label: HEAD is where you are standing, the arrow says it is standing on a branch name, and main is that name. C. Reading two areas in two characters

Before undoing anything, you need to be able to see which area a change is sitting in, and the full git status report is a slow way to do that. There is a short form, and you have met it once already:

Session 4 gave you git status --short for exactly one code, UU, on a conflicted file, and explained the two letters there as "unmerged, and there are two of them because there are two sides". That reading is right for a conflict and it does not generalise, so here is the actual rule, which is the one worth keeping:

column one
The staging area. What would go into your next commit.
column two
The working tree. The file as it sits on your disk.
a space
Means "nothing to report in this column". Easy to miss, and it is half the answer.

The letters that fill those columns in this session are few:

MModified: a file Git already knows about has been changed.
AAdded: a file Git did not know about is now on the staging shortlist.
??Untracked: Git has never been told about this file at all, so neither column applies and it says so twice.
UUnmerged: Session 4's conflict state. It appears in both columns because a conflict is unresolved on both sides.

So a two-character code is a sentence about two areas. Try it. Edit a.txt without staging it:

PowerShellAdd-Content a.txt "edited by mistake"
Git Bash / macOS / Linuxecho "edited by mistake" >> a.txt
run in undo-lab · the same fact said two ways
> git status --short
 M a.txt

> git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   a.txt

no changes added to commit (use "git add" and/or "git commit -a")

The short line begins with a space, which is the whole message: column one is empty, so the staging area has nothing to say, and the M in column two says the working tree has a modification. Seven lines of report compressed into two characters. If you look at only one thing on that line, look at whether the first character is a space. (cat turns up in a moment: it prints a file to the screen, and it works the same in PowerShell, where it is another name for Get-Content, as it does in Git Bash.)

Now stage it and watch the letter change columns:

run in undo-lab · the same change, one area further along
> git add a.txt

> git status --short
M  a.txt

The M moved from the second column to the first, and a space now sits in column two where it used to be. The staging area holds the change, and the working tree holds nothing that the staging area does not already have. Nothing about the file on disk changed when you ran git add; what changed was which area Git is reporting the difference in.

D. "I did not mean to do that" and the two restores

You are now sitting in a mistake, deliberately. You edited a.txt when you did not mean to, and then staged it on top. There are two separate things to undo there, and Git has a separate command for each, which is exactly the point.

git restore --staged <file> undoes the git add. It puts the staging area back the way the last commit left it, and it does not touch the file on disk. One area moved:

run in undo-lab · undo the add, keep the edit
> git restore --staged a.txt

> git status --short
 M a.txt

Printed nothing, and moved the M back to column two. Your edit is still there; only the staging shortlist changed. This is the safe one: nothing you wrote has been thrown away, because everything you wrote is still in the working tree.

git restore <file>, with no flag, is the dangerous one, and it is the first of this session's two. It overwrites the file on disk, and the edit that was there is gone. Not hidden, not recoverable with a later command, not in the .git folder anywhere: it was never committed, so Git never had a copy of it to give back. Read the file name twice before you press enter on this one. It is the first of this session's two unrecoverable commands, and neither of them warns you first: there is no confirmation prompt and no "are you sure".
run in undo-lab · throw the edit away
> git restore a.txt

> git status --short

> cat a.txt
one

Silence, then an empty status, then the original line back. An empty git status --short is what a clean tree looks like in the short form: no files to report, so no lines. The word "edited by mistake" no longer exists anywhere.

Now the precise version, which is worth having because it explains everything above in one sentence. The two commands are the same command pointed at different areas, and each one copies from the area behind it:

git restore <file>Working tree <- staging area. Makes the file on disk match what is staged.
git restore --staged <file>Staging area <- last commit. Makes the shortlist match what was last committed.

Read that first row again, because it says something surprising. git restore <file> copies from the staging area, not from the last commit. Most of the time those are the same thing and you never notice. When they are not, the difference is visible, and you can cause it on purpose. Edit a.txt, stage it, then edit it again:

PowerShellAdd-Content a.txt "first" git add a.txt Add-Content a.txt "second"
Git Bash / macOS / Linuxecho "first" >> a.txt git add a.txt echo "second" >> a.txt
run in undo-lab · a change in both areas at once
> git status --short
MM a.txt

> git restore a.txt

> git status --short
M  a.txt

MM means both columns have something to say: one version of the file is staged, and a newer version is on disk. Running git restore a.txt threw away only the second edit, the one that was never staged, and left the staged version sitting on disk. That is the row above doing exactly what it says. Undoing all of it takes both commands, in this order:

run in undo-lab · back to clean, one area at a time
> git restore --staged a.txt

> git status --short
 M a.txt

> git restore a.txt

> git status --short

> cat a.txt
one

Unstage first, then discard. Do it the other way round and the first restore only pulls the staged copy back onto disk, which is not what you wanted. The two-character code tells you when you are done: no line at all.

An older spelling you will meet in tutorials. Before restore existed, unstaging was written git reset a.txt, with a file name after it, and that form still works today. It is the same old-way-against-new-way situation as Session 3's git checkout against git switch: reset does several unrelated jobs depending on what you put after it, and restore was added to do this one job under a name that says what it does. Use git restore --staged. Recognise git reset <file> when you see it in somebody else's notes, and know it is the same thing.
Your turn Produce every short-status state and undo each one
  1. With a clean tree, edit b.txt and run git status --short. Say which column the letter is in before you look.
  2. git add b.txt and run it again. Confirm the letter changed columns.
  3. Edit b.txt once more without staging, and confirm you get MM.
  4. Undo the whole thing with the two restores in the right order, checking the short status after each one. Finish with cat b.txt and confirm it reads two.
  5. Create a file Git has never heard of, run git status --short, and find the third code. Then delete the file yourself, because no command in this session removes it for you.

E. "I committed too early" and reset --soft

This is the single most useful thing in the session, so it goes first among the three resets. You committed, and a second later you realised you were not finished: a file was missing, or the message was wrong, or you meant the whole thing to be one commit rather than two.

git reset --soft moves the branch pointer and stops. That is the entire description. It does not touch your files, and it does not touch the staging area. Session 3 spent a whole session establishing that a branch is a movable pointer to a commit; this is the command that moves it deliberately:

run in undo-lab · undo the last commit, keep everything else
> git log --oneline --decorate=short
18eae98 (HEAD -> main) c3 add c
1c6b85c c2 add b
10d0d15 c1 add a

> git reset --soft HEAD~1

> git log --oneline --decorate=short
1c6b85c (HEAD -> main) c2 add b
10d0d15 c1 add a

HEAD~1 is Session 2's notation, one commit back along the parent link, and Session 2 made the point that those names work anywhere a command wants a commit. Here it is naming where the branch pointer should be moved to. Two commits in the log instead of three, and the pointer sits on c2 add b. Now the interesting half:

run in undo-lab · where the commit went
> git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   c.txt

> git status --short
A  c.txt

c.txt is staged, and it is still sitting in your folder. The commit is off the log and its contents are back on the shortlist, ready to be committed again whenever you like, with whatever else you want to include. That is precisely the fix for "I committed too early": undo the commit, add the thing you forgot, commit once.

Now the subtle part, and it is the part that makes the whole session work. It is tempting to say that --soft changed the staging area, because the staging area now shows something it did not show a moment ago. It did not. The staging area holds exactly what it held before you ran the command. What moved was the branch pointer, and git status reports the staging area by comparing it against the commit the pointer is on. Move the pointer back one, and the same unchanged shortlist now differs from it by one file. One thing moved, and two reports changed. Keep that distinction: it is the difference between knowing the command and guessing at it.

Put the commit back so the lab is where it started:

run in undo-lab · commit it again
> git commit -m "c3 add c"
[main 13d0e95] c3 add c
 1 file changed, 1 insertion(+)
 create mode 100644 c.txt

The hash is different from the one you started with, even though the message and the change are identical. That is the second warning from the transcript note arriving on schedule. This is a new commit that happens to contain the same thing. Session 8 is built on that fact.

F. reset --mixed, the one you get if you say nothing

--mixed moves the branch pointer and resets the staging area, and leaves the working tree alone. It is what you get when you type git reset with no flag at all, which makes it the mode you are most likely to run by accident, so it is worth being able to predict.

Do the canonical case first: a commit that changed an existing file. Make one, so there is something to undo:

PowerShellAdd-Content a.txt "a second line" git add a.txt git commit -m "c4 extend a"
Git Bash / macOS / Linuxecho "a second line" >> a.txt git add a.txt git commit -m "c4 extend a"
run in undo-lab · the default reset, on a modified file
> git reset HEAD~1
Unstaged changes after reset:
M	a.txt

> git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   a.txt

no changes added to commit (use "git add" and/or "git commit -a")

Compare that against section E and one line is different. Under --soft the file came back staged; here it came back unstaged. Your second line of text is still in a.txt and nothing you wrote is at risk, but you would have to run git add again before you could commit it. That single difference is all --mixed is.

git reset also volunteers a summary of what it left behind, which --soft never does because --soft never leaves anything unstaged. Unstaged changes after reset: followed by M and a tab and the file name is the same M you learned in section C.

Throw that edit away with the command from section D, so the lab is back to three commits:

run in undo-lab · discard it and check
> git restore a.txt

> git status --short

> git log --oneline --decorate=short
13d0e95 (HEAD -> main) c3 add c
1c6b85c c2 add b
10d0d15 c1 add a

Now the variation, because it looks like a different command and is not. Run exactly the same reset, but on a commit that created a file rather than changing one:

run in undo-lab · the identical command, on a commit that created a file
> git reset HEAD~1

> git status
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	c.txt

nothing added to commit but untracked files present (use "git add" to track)

> git status --short
?? c.txt

Two things are different, and neither is a different command. The reset printed nothing at all this time, and c.txt comes back as untracked rather than as a modification.

Both follow from one fact. The undone commit is what first told Git that c.txt existed. Undo it, empty the staging area, and Git has no record of that file anywhere: not in the commit it is now pointing at, not on the shortlist. A file Git has no record of is untracked, by definition. And because nothing tracked was left unstaged, there was no "unstaged changes" summary to print. The file itself never moved, which is the promise --mixed makes and keeps in both cases.

Put it back, which now takes two commands rather than one, because Git has to be told about the file again:

run in undo-lab · track it again, then commit
> git add c.txt

> git commit -m "c3 add c"
[main 57fb3d0] c3 add c
 1 file changed, 1 insertion(+)
 create mode 100644 c.txt

G. reset --hard, which moves everything

--hard moves the branch pointer, resets the staging area, and overwrites the working tree to match. All three, in one command, with one line of output. It is the mode people reach for when they want a repository to look like it did at some earlier moment and they do not care what is currently in it.

This is the second and last of the session's two unrecoverable commands, and it is the more dangerous one. git reset --hard throws away every uncommitted change in one go: staged, unstaged, across every file, with no list of what it destroyed and no confirmation prompt. Anything you had committed can be recovered and Session 8 shows how. Anything you had not committed cannot be. The habit worth building today is to run git status --short immediately before this command, every single time, so you know exactly what you are agreeing to lose.

Start with the form that does not move the pointer at all, which is a distinct and very common use. Make a mess first:

PowerShellAdd-Content a.txt "junk I do not want"
Git Bash / macOS / Linuxecho "junk I do not want" >> a.txt
run in undo-lab · throw away everything uncommitted, keep the history
> git status --short
 M a.txt

> git reset --hard HEAD
HEAD is now at 57fb3d0 c3 add c

> git status
On branch main
nothing to commit, working tree clean

> cat a.txt
one

HEAD with no ~1 means the commit you are already standing on, so the pointer has nowhere to go and does not move. What the command does here is force the other two areas to match it, which is the shortest way to say "put this whole folder back the way my last commit had it". That one status line was the only warning you got, and it is why the habit above is worth having: the M was the entire inventory of what you were about to destroy.

One thing --hard does not touch. Untracked files survive it, because Git has no committed version of them to reset to. If your folder is full of files Git has never been told about, a hard reset leaves every one of them exactly where it is. The command that deletes those is git clean, and this session is not going to teach it: it is the one command in Git that can destroy files Git has never had a copy of, so it deserves more room than a footnote.

Now the form that does move the pointer, and the reason this session can show it to you safely. Note the hash of your newest commit first, from the log. Yours will not be 57fb3d0; use whatever your own log prints:

run in undo-lab · throw a commit away, then take it back
> git log --oneline --decorate=short
57fb3d0 (HEAD -> main) c3 add c
1c6b85c c2 add b
10d0d15 c1 add a

> git reset --hard HEAD~1
HEAD is now at 1c6b85c c2 add b

> git log --oneline --decorate=short
1c6b85c (HEAD -> main) c2 add b
10d0d15 c1 add a

> git reset --hard 57fb3d0
HEAD is now at 57fb3d0 c3 add c

> git log --oneline --decorate=short
57fb3d0 (HEAD -> main) c3 add c
1c6b85c c2 add b
10d0d15 c1 add a

Read what just happened there, because it is the most important paragraph in the session. The commit came back. It came back because reset never deletes a commit: it moves a pointer, and the commit carries on sitting in the repository with nothing aimed at it. Session 2 taught that a hash names a commit anywhere a command wants one, and that is what the last reset used. Both of these are just names for a commit, HEAD~1 and 57fb3d0; one counts backwards and one is absolute.

So the third area, the repository, is the one thing on this session's list that reset never changes. That is the honest reason "almost nothing in Git is unrecoverable" is true, and it is also exactly why the two red boxes above are about uncommitted work: a commit is the moment Git starts keeping a copy for you.

And the obvious question is the one this session is going to leave with you. That only worked because you wrote the hash down. If you had not, the commit would still be sitting in the repository, unreachable and invisible to git log, and you would have no name to call it by. There is a command that gives you that name back, and it is the first thing in Session 8.

Your turn Run all three modes from the same starting point
  1. Edit b.txt, stage it, and commit it with the message c5 change b. Then git reset --soft HEAD~1 and run git status --short. Which column is the letter in?
  2. Commit it again, which takes only git commit -m "c5 change b" because soft left it staged. Now git reset HEAD~1 with no flag, and run git status --short. Which column now?
  3. Stage it again and commit it a third time. That extra git add is the whole difference between the two modes, and skipping it is how you find out. Write the short hash down somewhere outside the terminal. Then git reset --hard HEAD~1 and confirm with git log --oneline that the commit is gone and the file is back to its old contents.
  4. Bring it back with git reset --hard and the hash you wrote down.
  5. Say out loud, for each of the three, which of the four things from section A it moved. That sentence is the milestone in miniature.
  6. Now put the lab back. Run git reset --hard HEAD~1 once more to drop your c5 change b practice commit, then git log --oneline --decorate=short to confirm you are on three commits with c3 add c on top. The transcripts in the next two sections assume exactly that, and you have just used the command that guarantees it.

H. The three modes, in three lines

Worth memorising, because it is small and it is the whole of reset. All three move the branch pointer to wherever you named. They differ only in how far the change follows:

branch pointerstaging areaworking tree
--softmovesleft aloneleft alone
--mixed (default)movesresetleft alone
--hardmovesresetoverwritten

The order is the point. Soft, mixed, hard, in that order, is a ramp: each one reaches one area further than the last, and the danger goes up with it. If you can recite the ramp you can derive any of the three, and you will never reach for --hard when --soft was what you meant.

None of the three touches the repository. Every commit you had before you ran any of them is still there afterwards. That is not a detail; it is the reason all three are survivable.

I. "It is already pushed" and git revert

Everything so far has moved a branch pointer backwards, which quietly assumes that nobody else has the commits you are stepping over. The moment that assumption is wrong, all three resets become the wrong tool, and Git has a completely different answer.

git revert does not remove anything. It writes a NEW commit that undoes an old one. If the old commit added a line, the new one deletes that line. If the old commit created a file, the new one deletes that file. History gets longer, not shorter, and nothing anybody already has is disturbed:

run in undo-lab · undo by adding, not by removing
> git log --oneline --decorate=short
57fb3d0 (HEAD -> main) c3 add c
1c6b85c c2 add b
10d0d15 c1 add a

> git revert --no-edit HEAD
[main 2b95aec] Revert "c3 add c"
 Date: Thu Aug 13 18:26:58 2026 -0500
 1 file changed, 1 deletion(-)
 delete mode 100644 c.txt

> git log --oneline --decorate=short
2b95aec (HEAD -> main) Revert "c3 add c"
57fb3d0 c3 add c
1c6b85c c2 add b
10d0d15 c1 add a

Four commits, not two. Put that log beside the one in section E and the contrast is the clearest teaching in this session. reset left you with two commits and the third one unreachable. revert leaves you with four: the commit you did not want is still right there in the history, and a new one above it cancels its effect out. c.txt really is gone from your folder, but the record of it having existed is not.

Two small things in that output are worth naming. Git wrote the message for you, Revert "c3 add c", quoting the original. And there is a Date: line, which none of your commit outputs have had before: it appears when a commit's author date and its committer date are not the same, which is normal for a revert and means nothing is wrong.

--no-edit is not optional decoration. git revert builds a commit, a commit needs a message, and without that flag Git opens your text editor so you can edit the one it prepared. On Windows that is usually vim inside your terminal, which is exactly the situation Session 4 warned you about: it looks like the terminal has frozen, and it has not. If it happens, get out the way Session 4 taught, and check what will open on your machine with git var GIT_EDITOR. --no-edit accepts the prepared message and never opens anything, which is what you want nine times out of ten.

So the rule that decides between reset and revert is a question about other people, not about Git:

Nobody else has itreset. The commit is yours alone, and moving your own pointer harms nobody.
Somebody else has itrevert. Adding a commit is something they can simply receive. Removing one from under them is not.

revert is the only command in this session that is safe on shared history, and that is worth carrying forward as a sentence rather than a feeling. Session 8 turns it into an actual rule, with the honest nuance about when rewriting is perfectly fine, and this is the half of it you already have.

J. Detached HEAD, which is not an error

Sooner or later Git will print a screenful of text at you that begins with the words "detached HEAD", and it will look like something has gone badly wrong. Nothing has. It is worth meeting on purpose, in a lab, rather than for the first time on real work.

Ordinarily HEAD points at a branch name and the branch name points at a commit. That is the (HEAD -> main) label you have been reading since Session 2, and the arrow is the indirection. A detached HEAD is what you get when HEAD points straight at a commit with no branch name in the middle. You are standing on a commit rather than on a branch.

Getting there deliberately shows you something about switch first. Session 3 taught that git switch exists because git checkout does several unrelated jobs, and here is one of the jobs it does not do:

run in undo-lab · switch refuses, and says why
> git switch HEAD~2
fatal: a branch is expected, got commit 'HEAD~2'
hint: If you want to detach HEAD at the commit, try again with the --detach option.

switch switches branches, and HEAD~2 is not a branch, so it stops and tells you the flag you would need. That refusal is the safety Session 3 promised. git checkout has no such scruples, and it is how nearly everybody lands here by accident:

run in undo-lab · the message in full, because it is alarming unquoted
> git checkout HEAD~2
Note: switching to 'HEAD~2'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

If you want to create a new branch to retain commits you create, you may
do so (now or later) by using -c with the switch command. Example:

  git switch -c <new-branch-name>

Or undo this operation with:

  git switch -

Turn off this advice by setting config variable advice.detachedHead to false

HEAD is now at 1c6b85c c2 add b

Read it as what it is: a help page, not an error. There is no fatal, no error:, and no warning: anywhere in it. Git is telling you where you are, what you can safely do, and two different ways out, one of which is a single command. The reason it is so long is that it is the only warning you get, and Git would rather over-explain once than let you lose a commit.

Now read the state from three different commands, because each one says it differently and you should recognise all three:

run in undo-lab, detached · three ways to notice
> git status
HEAD detached at 1c6b85c
nothing to commit, working tree clean

> git branch --show-current

> git branch
* (HEAD detached at 1c6b85c)
  main

> git log --oneline --decorate=short
1c6b85c (HEAD) c2 add b
10d0d15 c1 add a

git branch --show-current from Session 3 prints nothing at all, and that is the cleanest single test there is: no current branch, because you are not on one. git branch puts the star beside a description rather than a name, for the same reason.

And the log line is the one to really look at. It reads (HEAD) on its own, with no -> main after it. Every session since Session 2 has shown you (HEAD -> main), and Session 3 explained the arrow as the pointer aiming at a name. Here the arrow is missing because the thing it pointed at is missing. That two-character absence is the whole state, and you can now spot it in any log without running another command. Note also that the log only goes back from where you stand: c3 add c and the revert are not listed, because git log shows what is reachable from HEAD, and from here they are ahead of you rather than behind.

Getting back is one command, and it was the second one the advisory offered:

run in undo-lab · back to where you were
> git switch -
Previous HEAD position was 1c6b85c c2 add b
Switched to branch 'main'

git switch -, with a bare dash, means "the place I was before this". It works between branches too, and it is worth adopting as a habit for that alone.

There is also a way to detach on purpose, and it behaves noticeably differently:

run in undo-lab · the deliberate form says almost nothing
> git switch --detach HEAD~2
HEAD is now at 1c6b85c c2 add b

> git status
HEAD detached at 1c6b85c
nothing to commit, working tree clean

Same state, one line of output instead of eighteen. Git prints the long advisory when it thinks you might have arrived by accident, and skips it when you spelled out --detach, because you can hardly have typed that flag without meaning it. Use git switch --detach when you mean it, and recognise the long message as what git checkout says when it suspects you did not.

Finally, the part that actually matters: what happens if you commit while you are here. You are detached right now, so make one:

PowerShellSet-Content o.txt "an experiment" git add o.txt git commit -m "Orphan commit"
Git Bash / macOS / Linuxecho "an experiment" > o.txt git add o.txt git commit -m "Orphan commit"
run in undo-lab, detached · a commit with no branch on it
[detached HEAD e7f4199] Orphan commit
 1 file changed, 1 insertion(+)
 create mode 100644 o.txt

> git log --oneline --decorate=short
e7f4199 (HEAD) Orphan commit
1c6b85c c2 add b
10d0d15 c1 add a

[detached HEAD e7f4199] instead of the [main ...] you have seen on every commit since Session 1. Git puts the branch name in those brackets, and there is no branch name to put, so it says where you are instead. The commit itself is completely ordinary.

A perfectly ordinary commit, with nothing pointing at it but HEAD. The moment you leave, nothing will point at it at all. Git knows this, and it will not let you go quietly:

run in undo-lab · Git hands you the way back on your way out
> git switch main
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  e7f4199 Orphan commit

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> e7f4199

Switched to branch 'main'

Git printed the hash and the exact command. git branch <name> <hash> is new here, and it points a name at any commit you can name without moving you there, which is different from every branch command Session 3 gave you. It works for exactly the reason Session 3 established: a branch is only a movable pointer, so creating one costs nothing and moves nothing. The command to read it back is git log with a branch name after it, which shows that branch's history rather than the one you are standing on. Take Git up on the offer:

run in undo-lab · rescue it, using the hash Git just gave you
> git branch rescued e7f4199

> git log --oneline --decorate=short rescued
e7f4199 (rescued) Orphan commit
1c6b85c c2 add b
10d0d15 c1 add a

Silence, and then the commit has a name. You never left main to do it, which is what makes this the safest possible rescue. Session 3's whole thesis, doing something useful: you did not move a commit, you pointed a name at one.

And there is the same question again, sharper this time. That worked because Git printed the hash and you were still looking at the terminal. Close the window, and you have no name for that commit and no way to list it. It is not gone; there is simply nothing to call it by. The command that answers this is the first thing in Session 8, and this is exactly why it goes there.

Your turn The milestone: make five mistakes, undo each, and name the area

Work in undo-lab. Do not scroll back up. For each mistake below: cause it deliberately, run git status --short and read it, undo it, then say out loud which of the four things your undo command changed before you move on. The naming is the graded part, not the typing.

  1. You edited a.txt and did not mean to. Nothing is staged. Undo it.
  2. You edited b.txt and then staged it, and you want the staging undone but the edit kept. Undo it.
  3. You committed a change to b.txt before adding a second file you meant to include. Undo the commit so the change comes back staged, create the second file, add it, and commit once with a message covering both.
  4. You committed something and want the commit gone, the shortlist emptied, and the file left on disk so you can rework it. Undo it, and confirm from the short status which column the letter lands in. Then get back to a clean tree, either by staging and committing that change or by throwing it away; the next step needs one.
  5. Pretend the commit on top of your history has already been pushed and a teammate has it. Undo its effect the only way that is safe, and confirm the log got longer.

If step 5 refuses with error: Your local changes to the following files would be overwritten by merge, that is step 4 catching up with you: revert has to change a file on disk, and it will not do that on top of an edit you have not dealt with. Clean the tree and run it again. Refusing rather than overwriting is the same protectiveness you have seen all session.

Then, still in undo-lab, create a file called undo-table.md and write your own decision table into it: one row per mistake above, each naming the command and which of the four things it changed. Do it from memory. Commit it.

You have hit the milestone when all five undos worked, undo-table.md holds five rows in your own words, and you named the right areas without checking. Then check yourself against section K and fix any row you got wrong, because a table you corrected is worth more than one you copied.
