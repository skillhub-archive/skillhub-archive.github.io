Worktrees: one repository, many agents

Everything in the ten sessions happened in one working folder, where one branch is checked out at a time. That is fine for one person doing one thing. It breaks the moment two things happen at once: an urgent fix in the middle of a change, or two coding agents working side by side. Worktrees give one repository several working folders, each on its own branch, all sharing one history. This workbook is how to run parallel work, and parallel agents, without anyone overwriting anyone.

Milestone Run two agents in two worktrees on the same repository, merge both into main, resolve the conflict they cause, and clean up.
git

This one is a bonus, and it sits outside the graded ten. There is no level number, no checkbox on the Hub, and nothing here changes your 10/10. It assumes everything the ten sessions taught, branches and merge conflicts above all.

You do not need any folder from an earlier session. Step one builds a new folder called worktree-lab from nothing, and it is disposable like the others. No account and no network.

This is a workbook, not a reading. You will predict what a command prints before running it, reassemble sequences, fill blanks, and write commands from scratch. The goal is the one the whole track was built on: read a worktree command and know which folder it will touch before you press enter.

A. One folder, one branch

Every session so far had one working folder per repository, and in that folder exactly one branch was checked out at a time. Session 3 showed what git switch does: it swaps the files in your folder for the ones on the other branch. That is fine when one person does one thing at a time. It stops being fine in two situations you will meet constantly.

interruptedYou are halfway through a change when something urgent lands on another branch. To switch, you first have to commit half-done work or tuck it away with git stash, then switch, fix, switch back and unpick it. Every switch also rewrites the files under any program you had running.
parallelTwo coding agents, or you and one agent, working at the same time. In one folder they edit the same files on disk, so one overwrites the other mid-task, and only one branch can be checked out, so their work cannot even sit on separate branches.

A worktree is the fix: a second working folder attached to the same repository. Each folder has its own checked-out branch and its own files, while all of them share one history. The term comes straight from Session 1, where the working tree was the folder of files you edit. Git calls your original folder the main worktree and every extra one a linked worktree.

Why this is not just "clone it again". A second clone is a second repository: its own copy of every commit, its own branches, and you would have to push and fetch to move work between the two. Linked worktrees share one repository, so a commit made in one folder is visible from every other folder the instant it exists. No push, no fetch, no copy of the history.

Out of scope, so you know where the edges are. Moving a worktree with git worktree move, worktrees for repositories with submodules, and the --orphan option. The commands in this workbook cover everyday use, including everything a team running several agents needs.

B. Build the lab

This time the lab is a folder that holds folders. worktree-lab is just a container. The repository lives in worktree-lab/app, and every worktree you add will sit beside it as a sibling, so the whole exercise lives in one place and goes in one delete at the end.

PowerShell (Windows default) · build worktree-lab
cd ~
mkdir worktree-lab
cd worktree-lab
git init -b main app
cd app
Set-Content README.md "# Rate tool", "", "Status: draft"
Set-Content .gitignore ".env"
Set-Content rates.txt "standard 100"
git add .
git commit -m "Start the rate tool"
Add-Content rates.txt "weekend 120"
git add .
git commit -m "Add the weekend rate"
Git Bash / macOS / Linux · build worktree-lab
cd ~
mkdir worktree-lab
cd worktree-lab
git init -b main app
cd app
printf '# Rate tool\n\nStatus: draft\n' > README.md
printf '.env\n' > .gitignore
printf 'standard 100\n' > rates.txt
git add .
git commit -m "Start the rate tool"
printf 'weekend 120\n' >> rates.txt
git add .
git commit -m "Add the weekend rate"
Two things about that block.

The .gitignore line tells Git never to track a file called .env, the usual home for secrets such as API keys. Nothing uses it yet. Section G is why it is there.

Git Bash users will see a warning after each git add on Windows, LF will be replaced by CRLF the next time Git touches it. It is the line-ending conversion Session 1 described, and it is harmless. The transcripts on this page show the PowerShell path, which prints no warning.

Confirm the starting point:

run in worktree-lab/app · two commits on main
> git log --oneline --decorate=short

C. git worktree add, and what is shared

One command makes a new folder, creates a new branch and checks that branch out in the folder. The general form is git worktree add <path> -b <branch>, where <path> is the folder to create and <branch> is the new branch's name; both are placeholders you replace. It is the worktree version of Session 3's git switch -c, except your current folder is left exactly as it was.

run in worktree-lab/app · a second folder on a new branch
> git worktree add ../agent-a -b agent-a
Preparing worktree (new branch 'agent-a')
HEAD is now at 956fa6f Add the weekend rate
> git worktree list
C:/Users/you/worktree-lab/app     956fa6f [main]
C:/Users/you/worktree-lab/agent-a 956fa6f [agent-a]

../agent-a means "a folder called agent-a, one level up", which puts it beside app inside worktree-lab. git worktree list prints one line per folder: its full path, the commit it is on, and the branch in square brackets. Both start on the same commit, because the new branch was made from where main stood.

Now go into the new folder. It is an ordinary working folder: every command from the ten sessions works in it.

run in worktree-lab/agent-a · a normal folder, on its own branch
> cd ../agent-a
> git status
On branch agent-a
nothing to commit, working tree clean
> Get-Content .git
gitdir: C:/Users/you/worktree-lab/app/.git/worktrees/agent-a

That last command is the whole trick. In app, .git is a folder holding the entire repository. In a linked worktree, .git is a one-line file that points back into app/.git. Git follows it, so every command you run in agent-a reads and writes the one repository in app. (Git Bash users: cat .git. File Explorer hides .git by default, so read it from the terminal.)

shared
Commits and branches. Every commit and every branch name lives once, in app/.git, and every folder sees all of them.
shared
Settings and remotes. The repository's config, including any origin, is the same in every folder.
per folder
The files on disk. Each folder has its own working tree, including untracked and ignored files.
per folder
HEAD and the staging area. Each folder has its own checked-out branch and its own index (Session 1's staging area).

Watch both halves of that table at once. Make a commit in agent-a, then look from app:

PowerShell · commit in agent-a (Git Bash: printf 'holiday 150\n' >> rates.txt)
Add-Content rates.txt "holiday 150"
git add rates.txt
run in worktree-lab/agent-a, then worktree-lab/app
> git commit -m "Add the holiday rate"
[agent-a a9c5ff9] Add the holiday rate
 1 file changed, 1 insertion(+)
> cd ../app
> git log --oneline --all --decorate=short
a9c5ff9 (agent-a) Add the holiday rate
956fa6f (HEAD -> main) Add the weekend rate
4e07307 Start the rate tool
> Get-Content rates.txt
standard 100
weekend 120

The commit is visible from app immediately, with no push and no fetch, because it was written into the one shared repository. But the file in app still has two lines, because files belong to each folder and app is still on main. Shared history, separate files: that is the model for everything that follows. (--all asks git log for every branch, not just the current one.)

Your turn Add a worktree and prove what is shared
  1. From app, run the git worktree add above, then git worktree list. Find both folders in your file explorer too.
  2. Go into agent-a, run git status, and read the .git file.
  3. Make the holiday-rate commit in agent-a exactly as shown.
  4. Go back to app and confirm the commit shows in git log --oneline --all --decorate=short while rates.txt in app still has two lines. Say out loud why both are true.

D. The one-branch rule, and --detach

A branch can be checked out in only one folder at a time. If two folders both had agent-a checked out, a commit from either would move the branch out from under the other, and the second folder's files would silently stop matching its own HEAD. So Git refuses, in two places:

run in worktree-lab/app · agent-a is already checked out in ../agent-a
> git worktree add ../agent-a2 agent-a
Preparing worktree (checking out 'agent-a')
fatal: 'agent-a' is already used by worktree at 'C:/Users/you/worktree-lab/agent-a'
> git worktree list
C:/Users/you/worktree-lab/app     956fa6f [main]
C:/Users/you/worktree-lab/agent-a a9c5ff9 [agent-a]
> git switch agent-a
fatal: 'agent-a' is already used by worktree at 'C:/Users/you/worktree-lab/agent-a'

Notice two things. Without -b, git worktree add checks out a branch that already exists rather than making a new one, which is why it says checking out this time. And when it refuses, it creates no folder at all: the list still shows two. The git switch refusal is the same rule from the other side: app cannot take a branch another folder is holding.

git branch shows you which branches are held elsewhere with a +, next to the familiar * for the branch in this folder:

run in worktree-lab/app · + means checked out in another worktree
> git branch
+ agent-a
* main

Sometimes you want a folder on an older commit with no branch at all: to run last week's version, or to read a commit without touching anything. --detach does that. It is Session 7's detached HEAD, in a folder of its own, so your real work is never disturbed:

run in worktree-lab/app · a throwaway folder on an older commit
> git worktree add --detach ../review HEAD~1
Preparing worktree (detached HEAD 4e07307)
HEAD is now at 4e07307 Start the rate tool
> git worktree list
C:/Users/you/worktree-lab/app     956fa6f [main]
C:/Users/you/worktree-lab/agent-a a9c5ff9 [agent-a]
C:/Users/you/worktree-lab/review  4e07307 (detached HEAD)

A detached worktree holds no branch, so it never trips the one-branch rule, and it shows (detached HEAD) where the others show a branch name. HEAD~1 is Session 7's "one commit before HEAD", and since you ran this in app, that is the commit before main's tip.

Your turn Hit the rule, then step around it
  1. From app, try to add a second worktree on agent-a, and try git switch agent-a. Read both refusals and confirm no agent-a2 folder appeared.
  2. Run git branch and find the +.
  3. Add the detached review worktree on HEAD~1, then look inside it: rates.txt there should have one line. Say why.

E. Cleaning up: remove, --force and prune

Finishing a task in a worktree has a shape: bring its work into main, delete the folder, delete the branch. The folder and the branch are two different things, so they are deleted by two different commands.

run in worktree-lab/app · finish review and agent-a
> git worktree remove ../review
> git merge agent-a
Updating 956fa6f..a9c5ff9
Fast-forward
 rates.txt | 1 +
 1 file changed, 1 insertion(+)

git worktree remove printed nothing, which is success: the review folder is gone. The merge is Session 3's fast-forward, since main had not moved since agent-a branched off. Now suppose agent-a left a note behind, an untracked file nobody committed:

PowerShell · leave a stray file (Git Bash: printf 'check the rounding\n' > ../agent-a/todo.txt)
Set-Content ../agent-a/todo.txt "check the rounding"
run in worktree-lab/app · remove refuses, then is forced
> git worktree remove ../agent-a
fatal: '../agent-a' contains modified or untracked files, use --force to delete it
> git worktree remove --force ../agent-a
> git branch -d agent-a
Deleted branch agent-a (was a9c5ff9).

remove refuses a folder with modified or untracked files, because deleting the folder would delete them and Git has no copy. --force says you have looked and the files can go. Then git branch -d deletes the branch, which is safe because its commit is already on main (Session 3's -d, which refuses a branch whose work is not merged). Removing a folder never deletes a branch or a commit: had you skipped the merge, agent-a would still exist with all its work.

One more case: a folder deleted by hand, in your file explorer or with Remove-Item -Recurse -Force (the -Force matters: Git marks the .git file inside a linked worktree as hidden, and without it PowerShell refuses to delete the folder). Git still has its record of the worktree inside app/.git, and it tells you so:

run in worktree-lab/app · scratch's folder was deleted in the file explorer
> git worktree add ../scratch -b scratch
Preparing worktree (new branch 'scratch')
HEAD is now at a9c5ff9 Add the holiday rate
> git worktree list
C:/Users/you/worktree-lab/app     a9c5ff9 [main]
C:/Users/you/worktree-lab/scratch a9c5ff9 [scratch] prunable
> git worktree prune
> git worktree list
C:/Users/you/worktree-lab/app a9c5ff9 [main]
> git branch -d scratch
Deleted branch scratch (was a9c5ff9).

prunable means "this record points at a folder that no longer exists", and git worktree prune clears every such record. Until you prune, the stale record still holds its branch: the one-branch rule from section D keeps refusing scratch anywhere else, and even git branch -d scratch refuses with cannot delete branch 'scratch' used by worktree. That is why the prune comes before the branch delete. The habit is simple: delete worktrees with git worktree remove, and keep prune for when a folder went some other way.

Your turn Clean up three ways
  1. Remove review, merge agent-a into main, then leave the stray todo.txt in agent-a and watch remove refuse. Force it, and delete the branch.
  2. Add the scratch worktree, then delete its folder in your file explorer, not with Git.
  3. See prunable in git worktree list, prune, and delete the scratch branch. Finish with git worktree list showing only app.

F. Running agents in parallel

The pattern is one worktree and one branch per agent, each started from main. Each agent works in its own folder, commits to its own branch, and never sees the other's half-finished files. You, in app, are the one who merges. Three things about it are worth knowing before you rely on it.

conflictsThey wait until you merge. Two agents can change the same line in their own folders all day; nothing collides until the second branch is merged into main. That is Session 4's merge conflict, met at a time you choose.
setupEvery folder needs its own. Untracked and ignored files are per folder, so a new worktree has no .env, no node_modules and no Python venv. Each agent's folder needs its own install and its own copy of any settings file. (node_modules is where a JavaScript project keeps its installed packages; a venv is the Python equivalent.)
ignored filesremove deletes them without asking. Section E's refusal covers modified and untracked files, not ignored ones. A .env listed in .gitignore goes with the folder, silently. Copy out anything you need first.

Claude Code has this built in. Starting it with claude --worktree <name> (or -w) creates a worktree for that session at .claude/worktrees/<name> inside your repository, on a new branch called worktree-<name>, so each Claude session you start that way gets its own folder and branch. It also locks the worktree, and git worktree list --verbose shows the reason, such as locked: claude session demo (pid 68264). A locked worktree refuses remove with cannot remove a locked working tree and tells you to unlock it first. In a test run here, the lock and the folder were both still in place after Claude exited, so git worktree unlock <path> then git worktree remove <path> was the cleanup. Because those folders sit inside the repository, git status in your main folder also lists them as untracked: ?? .claude/ in a repository with no .claude folder of its own.

To see an ignored file, ask for it. git status --short --ignored adds a !! line for every file .gitignore is hiding, which is the quickest way to check what a remove would take with it.

G. The milestone: two agents, one merge

Two simulated agents get a task each, in parallel, and both touch the same line. Agent B marks the tool as beta. Agent C adds a night rate and marks the tool ready for review, and it also creates a .env with a key in it, the way a real agent would. You merge both into main, resolve the one conflict, and clean up.

run in worktree-lab/app · one folder and one branch per agent
> git worktree add ../agent-b -b agent-b
Preparing worktree (new branch 'agent-b')
HEAD is now at a9c5ff9 Add the holiday rate
> git worktree add ../agent-c -b agent-c
Preparing worktree (new branch 'agent-c')
HEAD is now at a9c5ff9 Add the holiday rate
PowerShell · each agent does its work in its own folder
cd ../agent-b
Set-Content README.md "# Rate tool", "", "Status: beta"
git add .
git commit -m "Mark the tool as beta"

cd ../agent-c
Set-Content README.md "# Rate tool", "", "Status: ready for review"
Add-Content rates.txt "night 90"
Set-Content .env "API_KEY=agent-c-only"
git add .
git commit -m "Add the night rate"
Git Bash / macOS / Linux · the same work
cd ../agent-b
printf '# Rate tool\n\nStatus: beta\n' > README.md
git add .
git commit -m "Mark the tool as beta"

cd ../agent-c
printf '# Rate tool\n\nStatus: ready for review\n' > README.md
printf 'night 90\n' >> rates.txt
printf 'API_KEY=agent-c-only\n' > .env
git add .
git commit -m "Add the night rate"

Check the .env before going on. git add . skipped it, because it is ignored, and it exists only in agent-c:

run in worktree-lab/agent-c, then worktree-lab/agent-b
> git status --short --ignored
!! .env
> cd ../agent-b
> git status --short --ignored

Now merge both, from app. Agent B's branch is a fast-forward. Agent C's is not, because main has moved, and both agents changed the Status line:

run in worktree-lab/app · one clean merge, one conflict
> cd ../app
> git merge --no-edit agent-b
Updating a9c5ff9..23cabdd
Fast-forward
 README.md | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
> git merge --no-edit agent-c
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
> git status --short
UU README.md
M  rates.txt
> Get-Content README.md
# Rate tool

<<<<<<< HEAD
Status: beta
=======
Status: ready for review
>>>>>>> agent-c

This is Session 4's conflict, exactly. rates.txt merged cleanly and is staged (M), while README.md is unmerged (UU) with both versions between the markers. Both agents were right, so keep both statements:

PowerShell · resolve (Git Bash: printf '# Rate tool\n\nStatus: beta, ready for review\n' > README.md)
Set-Content README.md "# Rate tool", "", "Status: beta, ready for review"
git add README.md
run in worktree-lab/app · finish the merge and look at the shape
> git commit -m "Merge agent-c"
[main 7c4652e] Merge agent-c
> git log --oneline --graph --decorate=short
*   7c4652e (HEAD -> main) Merge agent-c
|\  
| * 91170ca (agent-c) Add the night rate
* | 23cabdd (agent-b) Mark the tool as beta
|/  
* a9c5ff9 Add the holiday rate
* 956fa6f Add the weekend rate
* 4e07307 Start the rate tool

The graph is the parallel work made visible: two branches leave Add the holiday rate side by side and meet again at the merge. (git commit -m finishes the merge without opening an editor.) Now clean up both agents:

run in worktree-lab/app · both folders and both branches go
> git worktree remove ../agent-b
> git worktree remove ../agent-c
> git branch -d agent-b agent-c
Deleted branch agent-b (was 23cabdd).
Deleted branch agent-c (was 91170ca).
> git worktree list
C:/Users/you/worktree-lab/app 7c4652e [main]

Look at what did not happen. remove ../agent-c did not refuse, even though agent-c held a .env with a key in it. That file was ignored, not untracked, so section E's safety check never looked at it, and it is gone. With a real agent and a real key, that is the moment to have copied it somewhere first.

Your turn The milestone: run two agents and merge them
  1. Add both agent worktrees from app and do each agent's work in its own folder, including agent C's .env.
  2. Prove the .env exists in agent-c only, with git status --short --ignored in each folder.
  3. From app, merge agent-b (a fast-forward) and then agent-c (a conflict). Resolve it, stage it, and commit with -m.
  4. Run git log --oneline --graph --decorate=short and point at where the two agents' work split and rejoined.
  5. Remove both worktrees, delete both branches, and confirm git worktree list shows only app and rates.txt has all four rates.

You have hit the milestone when the graph shows the split and the merge, both agent folders and branches are gone, and you can say why the .env vanished without a warning.
