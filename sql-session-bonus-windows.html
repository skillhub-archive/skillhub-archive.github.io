Window functions

This one is optional. It sits outside the graded ten sessions and does not change your 10/10 completion. Session 6 named window functions in a one-paragraph aside but never taught them; here they are, for real, built on everything the sprint already gave you: JOIN, GROUP BY, CTEs and ROUND. The one-line idea: a window function computes across a set of rows without collapsing them, which is the one thing GROUP BY cannot do.

Everything today runs on top of one shared building block: a CTE of per-customer totals. It is exactly the pieces you already know, a CTE (Session 6) wrapping a JOIN (Session 4) and a GROUP BY (Session 3):

-- per-customer totals: one row per customer, with their summed order amounts
WITH cust AS (
  SELECT c.name, c.city, SUM(o.amount) AS total
  FROM customers c JOIN orders o ON o.customer_id = c.id
  GROUP BY c.id, c.name, c.city
)
SELECT name, city, total FROM cust ORDER BY name;

Because that inner JOIN only keeps customers who actually placed an order, Diego and Jae drop out (they never ordered), and since Jae was Reno's only customer, Reno disappears too. So this base has eight rows, not ten, and every result grid below shows eight. That is expected, not a bug:

the cust CTE · 8 rows (the base for every example today)

Amara   Austin  300
Ben     Denver  50
Chen    Austin  300
Esi     Denver  200
Fatima  Austin  200
Gita    Boston  150
Hiro    Denver  200
Iris    Austin  200

Now the shift. When you GROUP BY city (Session 3), SQLite collapses each city down to a single summary row: three cities in, three rows out, and the individual customer rows are gone. A window function does the opposite. It computes an aggregate across a set of rows but keeps every original row, adding the answer as an extra column. You attach it with the keyword OVER, and the simplest window of all is written OVER () with empty parentheses, which means "the whole result set is one window":

-- SUM over an empty window () = grand total of every row, placed on each row
SELECT name, total, SUM(total) OVER () AS all_customers
FROM cust
ORDER BY name;

All eight customer rows survive, and each one carries the same grand total (300+50+300+200+200+150+200+50 = 1600) in a new column. No collapsing:

result · every row kept, grand total added
name    total  all_customers
Amara   300    1600
Ben     50     1600
Chen    300    1600
Esi     200    1600
Fatima  200    1600
Gita    150    1600
Hiro    200    1600
Iris    200    1600

That is the whole mental model: GROUP BY squashes rows into groups; a window keeps the rows and reports alongside them. Everything else today is just choosing which rows each window covers.

B. PARTITION BY: a window within each group

An empty OVER () treats every row as one big window. Add PARTITION BY and you split the rows into groups first, then compute the window separately within each group, still returning one row per input row. It is the group-awareness of GROUP BY without the collapse. To put each customer's city total beside them, partition the window by city:

-- sum total within each city, but keep every customer row
SELECT name, city, total, SUM(total) OVER (PARTITION BY city) AS city_total
FROM cust
ORDER BY city, total DESC, name;
result · each customer keeps their row, city total added
name    city    total  city_total
Amara   Austin  300    1000
Chen    Austin  300    1000
Fatima  Austin  200    1000
Iris    Austin  200    1000
Gita    Boston  150    150
Esi     Denver  200    450
Hiro    Denver  200    450
Ben     Denver  50     450

Every Austin customer shows 1000, every Denver customer 450, Boston's single customer 150, and all eight rows are still here. Compare that with the GROUP BY you already know, which answers the same "total per city" question by collapsing to one row each:

-- the Session 3 way: three cities in, three rows out (customers gone)
SELECT city, SUM(total) AS city_total
FROM cust
GROUP BY city
ORDER BY city;
result · GROUP BY collapses to one row per city
city    city_total
Austin  1000
Boston  150
Denver  450

Same three totals, but GROUP BY gives you three rows and forgets who the customers were; PARTITION BY gives you all eight rows with the city total attached. Reach for the window when you want the group figure and the detail rows together.

C. Ranking rows: ROW_NUMBER, RANK, DENSE_RANK

The most common thing to do inside a partition is rank the rows. Three ranking functions all take an OVER (...) with an ORDER BY inside it that says what to rank by (this ORDER BY lives inside the window and is separate from the query's final ORDER BY). To rank customers within each city by total, highest first, the window is OVER (PARTITION BY city ORDER BY total DESC). Here are all three side by side:

-- three ways to number rows within each city, ranked by total (highest first)
SELECT name, city, total,
  RANK()       OVER (PARTITION BY city ORDER BY total DESC)       AS rnk,
  DENSE_RANK() OVER (PARTITION BY city ORDER BY total DESC)       AS drnk,
  ROW_NUMBER() OVER (PARTITION BY city ORDER BY total DESC, name) AS rn
FROM cust
ORDER BY city, total DESC, name;
result · the three ranking functions compared
name    city    total  rnk  drnk  rn
Amara   Austin  300    1    1     1
Chen    Austin  300    1    1     2
Fatima  Austin  200    3    2     3
Iris    Austin  200    3    2     4
Gita    Boston  150    1    1     1
Esi     Denver  200    1    1     1
Hiro    Denver  200    1    1     2
Ben     Denver  50     3    2     3

Watch Austin, where Amara and Chen tie at 300. The three functions handle that tie differently:

  • RANK() gives tied rows the same rank, then skips: Amara and Chen are both 1, so the next customers jump to 3 (the sequence is 1, 1, 3).
  • DENSE_RANK() gives tied rows the same rank but does not skip: 1, 1, 2. The next distinct total is always the next whole number.
  • ROW_NUMBER() always hands out distinct numbers 1, 2, 3, 4 with no ties, so among equal totals it has to pick an order. That choice is arbitrary unless you make it deterministic, which is why this window adds , name as a tiebreaker (Amara before Chen). Without it, which of the two 300s gets rn 1 would be undefined, the same "no ORDER BY, no guaranteed order" caution from Session 1.

One gotcha worth knowing now. Say you want only the top spender per city. You cannot write WHERE rnk = 1 in the same query, because WHERE runs before the window is computed, so the rank does not exist yet. The fix is to wrap the ranking query in a CTE (or subquery) and filter the rank on the outside:

-- top spender per city: rank inside a CTE, then filter the rank outside it
WITH ranked AS (
  SELECT name, city,
    RANK() OVER (PARTITION BY city ORDER BY total DESC) AS rnk
  FROM cust
)
SELECT name, city FROM ranked WHERE rnk = 1 ORDER BY city, name;
result · the top-ranked customer(s) in each city
name    city
Amara   Austin
Chen    Austin
Gita    Boston
Esi     Denver
Hiro    Denver

Austin and Denver each return two names because of the ties, which is often exactly what you want from RANK. Swap in ROW_NUMBER if you need precisely one per city.

D. Ordered aggregate windows: running totals

You have seen an aggregate over a whole window (OVER ()) and over a partition (PARTITION BY). Add an ORDER BY inside the window to an aggregate like SUM and something new happens: instead of one total for the whole window, each row shows a running total, the sum of itself and every row before it in that order. To accumulate customer totals from the biggest spender down:

-- running total: each row = its own total plus all rows above it in this order
SELECT name, total, SUM(total) OVER (ORDER BY total DESC, name) AS running
FROM cust
ORDER BY total DESC, name;
result · the running total climbs to the grand total
name    total  running
Amara   300    300
Chen    300    600
Esi     200    800
Fatima  200    1000
Hiro    200    1200
Iris    200    1400
Gita    150    1550
Ben     50     1600

Amara starts at 300, Chen adds 300 for 600, and it climbs row by row to the 1600 grand total you saw in concept A. The ORDER BY total DESC, name uses a unique ordering key (the , name breaks the ties), which keeps the running total unambiguous.

One aside on the frame, then we move on. An ordered aggregate window has a default frame (the set of rows it sums): RANGE from the start of the window up to the current row. You can set the frame explicitly with a ROWS BETWEEN ... clause, which is how you would build moving averages and the like. The reason this example uses a unique ordering key matters here: with a non-unique key (say plain ORDER BY total), the default RANGE frame treats tied rows as peers and gives them all the same running total, which surprises people. Ordering by a unique key sidesteps that. We name ROWS BETWEEN so you recognize it; going deeper on frames is a topic for another day.

Your turn Build a running total

Run the running-total query and confirm the running column climbs 300, 600, 800, 1000, ... and ends at 1600 on the last row. Change the inner ORDER BY to total alone (drop , name) and notice the tied rows now share a running total, the frame behavior described above.

E. The milestone: rank and share, in one query

Now combine the pieces into one report. For each city, rank the customers by spend and show what percentage of the city total each one represents. That needs the CTE (Session 6) over a JOIN (Session 4), a RANK window, a SUM partition window for the city total, and ROUND (Session 10) for a clean percentage:

-- per city: rank by spend, and each customer's share of the city total
WITH cust AS (
  SELECT c.name, c.city, SUM(o.amount) AS total
  FROM customers c JOIN orders o ON o.customer_id = c.id
  GROUP BY c.id, c.name, c.city
)
SELECT name, city, total,
  RANK() OVER (PARTITION BY city ORDER BY total DESC) AS city_rank,
  ROUND(100.0 * total / SUM(total) OVER (PARTITION BY city), 1) AS pct_of_city
FROM cust
ORDER BY city, city_rank, name;
result · the finished report, 8 rows
name    city    total  city_rank  pct_of_city
Amara   Austin  300    1          30.0
Chen    Austin  300    1          30.0
Fatima  Austin  200    3          20.0
Iris    Austin  200    3          20.0
Gita    Boston  150    1          100.0
Esi     Denver  200    1          44.4
Hiro    Denver  200    1          44.4
Ben     Denver  50     3          11.1

Read one row: Ben is in Denver, ranked 3rd, and his 50 is 100.0 × 50 / 450 = 11.11..., which ROUND(..., 1) trims to 11.1. Notice the 100.0, not 100: writing 100.0 * total forces real division, so the decimal survives. With all integers, 100 * total / 450 would do integer division (the multiply happens first, then the divide throws the fraction away), turning Ben's 11.1 into a bare 11 and Denver's 44.4 into 44. That truncation is the same integer-division trap from Session 1, where 7 / 2 gave 3, not 3.5.

Cross-database note, and where this travels. Window functions are part of the SQL standard and work almost everywhere: SQLite 3.25+ (2018), PostgreSQL, MySQL 8+, SQL Server and Oracle all support OVER, PARTITION BY and the ranking functions with the same syntax. Learn them once here and the skill carries to every database you are likely to meet.
