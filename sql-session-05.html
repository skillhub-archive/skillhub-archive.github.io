Subqueries & derived tables

A subquery is a query nested inside another. It lets one question feed the next: find the orders above the average, the customers who match a set, or the ones with no match at all. Today you meet scalar subqueries, IN and EXISTS, the famous NOT IN NULL trap, and derived tables that let you summarize a summary.

A. Meet the subquery: a query inside a query

A subquery is a complete SELECT written inside another query, wrapped in parentheses. The database runs the inner query first, then hands its result to the outer query. The most common kind is a scalar subquery: one that returns exactly a single value (one row, one column). Because it stands for one value, you can drop it anywhere SQL expects a value, such as the right-hand side of a WHERE comparison or as a column in the SELECT list.

Now the scalar subquery. Suppose you want every order whose amount beats the average order amount. You do not need to know the average in advance; you compute it in a subquery and compare against it. The parenthesized (SELECT AVG(amount) FROM orders) is a scalar subquery: AVG returns one number, so the whole parenthesized expression stands in for that number:

SELECT id, amount
FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders)   -- the inner query yields one number, ~123.08
ORDER BY amount, id;
result · the six orders above the ~123.08 average
id  amount
6   150
10  150
12  150
2   200
7   200
13  200

Read it inside-out: SQLite runs (SELECT AVG(amount) FROM orders) once, gets the single value (about 123.08), then the outer query keeps every order whose amount is above it. The three 150s and the three 200s qualify; the 50s and 100s do not.

A scalar subquery can also sit in the SELECT list, where it becomes a column with the same value on every row. Here each Austin customer is shown next to the single highest fee in the whole table:

SELECT name, monthly_fee, (SELECT MAX(monthly_fee) FROM customers) AS top_fee
FROM customers
WHERE city = 'Austin'
ORDER BY name;
result · top_fee is the same 60 on every row
name    monthly_fee  top_fee
Amara   40           60
Chen    40           60
Fatima  60           60
Iris    60           60

The single-value rule. A scalar subquery must logically return one value. In PostgreSQL, MySQL and SQL Server, a scalar subquery that returns more than one row raises an error. SQLite is more lenient: it silently uses the first row, which is arguably worse, because you get a wrong answer with no warning. Either way, only put a subquery in a scalar position when you know it returns a single value, which is usually because it is an aggregate like AVG or MAX, or it filters on a unique key.

To see the misuse concretely, here is a subquery that returns three rows dropped into a spot that expects one:

-- this subquery returns three amounts, Chen's three orders: 50, 100, 150
SELECT amount FROM orders WHERE customer_id = 3;

-- misuse: a three-row subquery where a single value is expected
SELECT id FROM orders
WHERE amount > (SELECT amount FROM orders WHERE customer_id = 3);

PostgreSQL, MySQL and SQL Server reject that second query outright with a "more than one row" error. SQLite runs it, but quietly compares each order against just one of those three amounts, and which one is not even guaranteed (row order without ORDER BY is undefined, from Session 1), so the result is both wrong and unpredictable. The fix is to make the subquery genuinely scalar: if you meant "orders above Chen's largest order," wrap it in an aggregate, > (SELECT MAX(amount) FROM orders WHERE customer_id = 3), which returns the single value 150.

B. Subqueries with IN, and the correlated kind

A subquery does not have to return a single value. When it returns a whole column of values, you can test membership against that list with IN, the same IN you met in Session 2, except the list is now computed by a query instead of typed out by hand. To pull the orders placed by Austin customers, let a subquery gather the Austin customer ids and test each order against that set:

SELECT id, customer_id, amount
FROM orders
WHERE customer_id IN (SELECT id FROM customers WHERE city = 'Austin')
ORDER BY id;
result · the eight orders whose customer lives in Austin
id  customer_id  amount
1   1            100
2   1            200
4   3            50
5   3            100
6   3            150
8   6            100
9   6            100
13  9            200

The inner query SELECT id FROM customers WHERE city = 'Austin' returns the set of ids 1, 3, 6, 9. IN then keeps every order whose customer_id is one of those. The database can run that inner query once, remember the set, and reuse it for every order.

Correlated versus non-correlated. The subquery above is non-correlated (also called uncorrelated): it makes no reference to the outer query, so it runs once and stands alone. A correlated subquery is the opposite: it references a column from the outer row, so it cannot run just once; it must be re-run for each outer row. Here is a correlated scalar subquery that looks up each 200-amount order's customer name (using the AS c and AS o table aliases from Session 4, where o.customer_id is a column of the outer query):

SELECT o.id, o.amount, (SELECT c.name FROM customers AS c WHERE c.id = o.customer_id) AS who
FROM orders AS o
WHERE o.amount = 200
ORDER BY o.id;
result · the name is looked up per order row
id  amount  who
2   200     Amara
7   200     Esi
13  200     Iris

Because the inner query mentions o.customer_id, which belongs to the outer orders row, it re-runs for each order the outer query produces. That flexibility has a cost: a correlated subquery re-runs per outer row, so on large tables it can be slower than an equivalent join. You do not need to optimize that today; just know the two terms and which one references the outer query.

Your turn Membership and correlation

Run the Austin-orders query and confirm eight rows. Then run the correlated "who" query and confirm the three 200-amount orders show Amara, Esi and Iris. Change city = 'Austin' in the first query to city = 'Reno' and note you get no rows, because Reno's only customer (Jae) has no orders.

C. The NOT IN trap with NULLs

NOT IN is the natural opposite of IN: keep the rows whose value is not in the list. It usually behaves exactly as you would expect, but it hides a trap that catches almost everyone, and it comes straight from the three-valued NULL logic you met in Session 2.

Your customers table has a nullable referrer column (who referred this customer). Say you want the customers who have never referred anyone: their name should not appear in the list of referrers. The obvious query is:

SELECT name
FROM customers
WHERE name NOT IN (SELECT referrer FROM customers)   -- looks right, returns nothing
ORDER BY name;
result · zero rows, which is clearly wrong
name
(no rows)

Nothing comes back, even though plenty of customers never referred anyone. Here is why. The subquery SELECT referrer FROM customers returns every referrer value, and four of those are NULL (Amara, Diego, Gita and Jae have no referrer). So the list contains a NULL. Now name NOT IN (list) is evaluated as name <> each_value AND ... (<> means "not equal", from Session 2), and one of those comparisons is name <> NULL. From Session 2: any comparison with NULL is NULL (unknown), never true. A chain of ANDs that includes an unknown can never come out true, so every row fails and you get zero rows.

The fix is to make sure the subquery never yields a NULL. Guard it with WHERE referrer IS NOT NULL:

SELECT name
FROM customers
WHERE name NOT IN (SELECT referrer FROM customers WHERE referrer IS NOT NULL)
ORDER BY name;
result · the six customers who never referred anyone
name
Diego
Fatima
Gita
Hiro
Iris
Jae

Now the subquery returns only the real referrers (Amara, Ben, Chen, Esi), and NOT IN correctly keeps the six customers whose name is not among them. Two things worth remembering: plain IN does not have this problem (a NULL in the list does not stop IN from finding real matches), it is specifically NOT IN that collapses to nothing. And this is standard SQL: PostgreSQL, MySQL and SQL Server all behave the same way, so no engine saves you. The next concept shows a cleaner tool that sidesteps the trap entirely.

Your turn Spring the trap, then fix it

Run the first NOT IN query and watch it return nothing. Then add WHERE referrer IS NOT NULL inside the subquery and confirm you now get the six names. Seeing zero rows turn into the right answer is the lesson.

D. EXISTS and NOT EXISTS

There is a cleaner, NULL-safe way to ask existence questions: EXISTS. EXISTS takes a subquery and is true when that subquery produces at least one row, false when it produces none. It does not care what the rows contain, only whether any exist, so by convention you select the constant 1 inside it: EXISTS (SELECT 1 FROM ... WHERE ...). The 1 is a throwaway placeholder; you are not selecting a real column because the values are ignored, only their presence matters. EXISTS is naturally correlated: its inner WHERE references the outer row. To list the customers who have placed at least one order:

SELECT c.name
FROM customers AS c
WHERE EXISTS (SELECT 1 FROM orders AS o WHERE o.customer_id = c.id)
ORDER BY c.name;
result · the eight customers with orders
name
Amara
Ben
Chen
Esi
Fatima
Gita
Hiro
Iris

For each customer, the inner query asks "is there any order whose customer_id equals this customer's id?" If yes, EXISTS is true and the customer is kept. NOT EXISTS is simply the negation: true when the subquery finds nothing. That gives a direct, NULL-safe way to ask "which customers have no orders":

SELECT c.name
FROM customers AS c
WHERE NOT EXISTS (SELECT 1 FROM orders AS o WHERE o.customer_id = c.id)
ORDER BY c.name;
result · the two customers with no orders
name
Diego
Jae

Three ways to answer the same question. "Which customers have no orders" can be written three different ways, and it is worth seeing them side by side, because they are not equally safe:

  • LEFT JOIN then IS NULL (Session 4): LEFT JOIN orders AS o ON c.id = o.customer_id WHERE o.id IS NULL. Keeps every customer, then keeps only the ones with a NULL on the orders side. Works fine.
  • NOT IN: WHERE id NOT IN (SELECT customer_id FROM orders). Works here only because orders.customer_id happens to have no NULLs. Add one order with a NULL customer_id and it would silently return nothing, the Concept C trap all over again. Fragile.
  • NOT EXISTS: the query above. Immune to the NULL trap and reads plainly as "there is no matching order." The robust default.

All three return Diego and Jae on today's data. Reach for NOT EXISTS (or the LEFT JOIN ... IS NULL pattern) for "no match" questions, and treat NOT IN with a subquery as safe only when its column can never be NULL. EXISTS and NOT EXISTS behave identically across SQLite, PostgreSQL, MySQL and SQL Server.

Your turn Ask it three ways

Run the NOT EXISTS query and confirm Diego and Jae. Then write the same question as a LEFT JOIN ... WHERE o.id IS NULL (from Session 4) and as WHERE id NOT IN (SELECT customer_id FROM orders), and confirm all three give the same two names.

E. Derived tables, and the milestone

So far every subquery sat in WHERE or SELECT. A subquery can also sit in the FROM clause, where it acts as a temporary table built on the fly from another query's result. That is a derived table. You wrap the inner SELECT in parentheses and, crucially, give it an alias with AS, because the outer query needs a name to refer to its columns. The general form is FROM (SELECT ...) AS t, where t is a name you choose (any label works, just like a table alias).

Here the inner query produces one row per customer with an order count; naming that result t lets the outer query select t.customer_id and t.n from it and filter on the count:

SELECT t.customer_id, t.n
FROM (SELECT customer_id, COUNT(*) AS n
      FROM orders
      GROUP BY customer_id) AS t
WHERE t.n >= 2
ORDER BY t.n DESC, t.customer_id;
result · customers with two or more orders
customer_id  n
3            3
1            2
6            2
8            2

You could get that particular result with HAVING too. So why a derived table? Because it lets you do something a single GROUP BY cannot: aggregate over an aggregate. Suppose you want the average number of orders per customer. That is an AVG of a COUNT, and SQL does not let you nest one aggregate inside another (AVG(COUNT(*)) is an error). The way through is a derived table: first compute each customer's count, then average that:

SELECT AVG(n) AS avg_orders
FROM (SELECT customer_id, COUNT(*) AS n
      FROM orders
      GROUP BY customer_id) AS t;
result · average of the eight per-customer counts (13 / 8)
avg_orders
1.625

The derived table t holds the eight ordering customers with their counts (2, 1, 3, 1, 2, 1, 2, 1). AVG(n) then averages those eight numbers: 13 divided by 8 is 1.625. Note that a derived table must be aliased in PostgreSQL, MySQL and SQL Server; SQLite is lenient and lets you omit the alias, but always write one so your queries port cleanly.

Your milestone puts both tools together. To find the customers whose total spend beats the average customer's total spend, you need a derived table of per-customer totals (to compare each customer against), and a scalar subquery for the average of those totals (the single number to beat):

SELECT c.name, t.total
FROM customers AS c
JOIN (SELECT customer_id, SUM(amount) AS total
      FROM orders
      GROUP BY customer_id) AS t ON c.id = t.customer_id
WHERE t.total > (SELECT AVG(total)
                 FROM (SELECT SUM(amount) AS total
                       FROM orders
                       GROUP BY customer_id) AS s)
ORDER BY t.total DESC, c.name;
result · the average per-customer total is 200; two beat it
name   total
Amara  300
Chen   300

The derived table t totals each customer's orders and is joined back to customers for the name. The scalar subquery averages those same per-customer totals, giving 200 (its own inner derived table is aliased s, just another name we chose, the same idea as t). Only Amara and Chen (300 each) spend more than that, so they are the result. Write this one from a blank editor.
