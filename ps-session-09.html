A. From a script to a module: Import-Module

Session 8’s Write-Log lives inside error-report.ps1. A second script that wants it has to copy it, and then the two copies drift apart. Session 6 showed one way out: keep a function in its own file and dot-source it. A module is the tidy version of that idea: a file of functions, saved with the extension .psm1 (PowerShell script module), that any script or prompt loads with Import-Module PATH. By custom a module sits in a folder of the same name, so this one is Fernhill/Fernhill.psm1; section C shows why the name matters.

The module starts with one function, Format-LogLine. It builds the line Write-Log used to build: the time, a space, and the message. Its -Time parameter is new in two ways. Its type, [datetime], is a date and a time together, the kind of value Get-Date gives back. And its default, (Get-Date), is a command in parentheses: as in Session 8, PowerShell runs what is inside the parentheses first, so when you leave -Time out, the time is now. Handing Get-Date a [datetime] through -Date uses that exact moment, with no text to read. To try it with a fixed time, store one in a variable first, as the tests in section E will:

~/ps-scripts/Fernhill/Fernhill.psm1 · a module file, typed in VS Code
# Fernhill.psm1: the Fernhill Goods log tools, for any script that imports them.
function Format-LogLine {
  param(
    [Parameter(Mandatory)][string]$Message,
    [datetime]$Time = (Get-Date)
  )
  "$(Get-Date -Date $Time -Format 'yyyy-MM-dd HH:mm:ss') $Message"
}

B. What a module shares, and what it keeps to itself

Unless it says otherwise, a module shares every function in it. Export-ModuleMember -Function NAME, NAME, as the last line of the module, shares only the ones it names; the others still work inside the module, but the prompt and your scripts cannot call them by name. That is how a module keeps a helper to itself. Try it by sharing Write-Log alone:

C. Where modules live: $env:PSModulePath

In Session 8 you used Get-ScheduledTask without importing anything. That worked because PowerShell keeps a list of folders where modules live, in $env:PSModulePath. The $env: part means an environment variable, a setting the computer gives every program, not one PowerShell made. A module saved in one of those folders, in a folder of its own name, is found and loaded by itself the first time you use one of its commands. The list is one piece of text, the folders separated by a ; on Windows. -split ';' cuts a piece of text apart at every ;, so each folder prints on a line of its own:

E. Your first test: Describe, It and Should

Word
What it does
Here

F. Tests for code that touches files: TestDrive

Fernhill gets its third function now, the counting from Session 7’s error report, as Get-ErrorSummary: give it a folder, and it returns the ERROR count for each log, biggest first, or stops with an error if the folder is not there:

~/ps-scripts/Fernhill/Fernhill.psm1 · a module file, typed in VS Code
# Fernhill.psm1: the Fernhill Goods log tools, for any script that imports them.
$ErrorActionPreference = 'Stop'

function Format-LogLine {
  param(
    [Parameter(Mandatory)][string]$Message,
    [datetime]$Time = (Get-Date)
  )
  "$(Get-Date -Date $Time -Format 'yyyy-MM-dd HH:mm:ss') $Message"
}

function Write-Log {
  param(
    [Parameter(Mandatory)][string]$Path,
    [Parameter(Mandatory)][string]$Message
  )
  Format-LogLine -Message $Message | Add-Content $Path
}

function Get-ErrorSummary {
  param([Parameter(Mandatory)][string]$Path)
  if (-not (Test-Path $Path)) { throw "No folder to search: $Path" }
  Get-ChildItem $Path -Recurse -File | Select-String ERROR |
    Group-Object Filename | Sort-Object Count, Name -Descending |
    Select-Object @{ Name = 'Log'; Expression = { $_.Name } }, Count
}

Export-ModuleMember -Function Format-LogLine, Write-Log, Get-ErrorSummary

G. Run the tests before every change

Tests earn their keep when you change the code. The habit is a short loop, done the same way every time:

  1. Name the bug you want gone, or the thing the code should do but does not.
  2. Write a test for it, and run the tests: the new one should fail. If it passes, it is not testing what you think.
  3. Change the code, as little as it takes.
  4. Run every test again: the new one passes, and the old ones still do, so the change broke nothing your tests check.
