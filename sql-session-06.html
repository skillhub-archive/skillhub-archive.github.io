CTEs & set operations

A common table expression (CTE) is a subquery you name and define up front with WITH, then use in the main query as if it were a table. It does the same job as the Session 5 derived table but reads far better and can be reused. You will also meet the set operations that stack the rows of two queries: UNION, UNION ALL, INTERSECT and EXCEPT.

A. Meet the CTE: a subquery with a name

In Session 5 you built a derived table: a subquery tucked into the FROM clause. It works, but the query reads inside-out, and if you need that subquery twice you have to write it twice. A common table expression (CTE for short) fixes both problems. You define the subquery once, up front, give it a name, and then the main query reads from that name as if it were a real table.

The syntax is WITH name AS (SELECT ...) followed by the main query. Here name is a placeholder: you replace it with a label you choose for the CTE (any identifier works, like order_counts below), you do not literally type the word name. The parentheses hold an ordinary SELECT. After the closing parenthesis comes the main query, which can mention that name in its FROM clause.

First, make sure you still have both tables from Session 5. If shop.db is open with customers and orders, you are set. If you lost it, run the full setup below once, then Write Changes.

To see the readability win, take the Session 5 query for customers with two or more orders. As a derived table it read inside-out, the summarizing subquery buried in the FROM clause:

-- Session 5 style: the subquery is buried inside FROM
SELECT t.customer_id, t.n
FROM (SELECT customer_id, COUNT(*) AS n
      FROM orders
      GROUP BY customer_id) AS t
WHERE t.n >= 2
ORDER BY t.n DESC, t.customer_id;

The exact same result, rewritten as a CTE. The summary is lifted out and named order_counts, so the main query at the bottom reads top-to-bottom in plain English: from the order counts, keep those with two or more, sorted:

WITH order_counts AS (
  SELECT customer_id, COUNT(*) AS n
  FROM orders
  GROUP BY customer_id
)
SELECT customer_id, n
FROM order_counts
WHERE n >= 2
ORDER BY n DESC, customer_id;
result · same rows as the derived table, but the query reads in order
customer_id  n
3            3
1            2
6            2
8            2

CTEs are standard SQL: WITH works the same in SQLite, PostgreSQL, MySQL 8+ and SQL Server. One more thing a CTE gives you that a buried subquery cannot: because it has a name, the main query (or a later CTE) can reference it more than once without repeating its text. You will use that in the next concept.

B. Chaining several CTEs

One WITH can define several CTEs, separated by commas: WITH a AS (...), b AS (...) SELECT .... They are defined in order, and a later CTE is allowed to build on an earlier one, which is what makes chains so readable. Each named step does one clear thing, and the next step reads from it.

This is where the Session 5 milestone becomes much clearer. Back then, to find the customers whose total spend beat the average customer's total, you nested a derived table inside another derived table inside a scalar subquery, and it was genuinely hard to read. With two chained CTEs it reads as three plain steps: total each customer, average those totals, then keep the customers above that average.

WITH customer_totals AS (
  SELECT customer_id, SUM(amount) AS total
  FROM orders
  GROUP BY customer_id
),
avg_total AS (
  SELECT AVG(total) AS a
  FROM customer_totals            -- this CTE builds on the one above
)
SELECT c.name, ct.total
FROM customer_totals AS ct
JOIN customers AS c ON c.id = ct.customer_id
WHERE ct.total > (SELECT a FROM avg_total)
ORDER BY ct.total DESC, c.name;
result · the average per-customer total is 200; two customers beat it
name   total
Amara  300
Chen   300

The first CTE, customer_totals, sums each customer's orders. The second, avg_total, reads from the first to get the single average (200). The main query joins the totals back to customers for the name and keeps only those above 200: Amara and Chen, at 300 each. Compare that to the Session 5 version and the win is obvious: same answer, but every step has a name and the logic flows downward.

Aside: recursive CTEs. There is a special form, WITH RECURSIVE, that lets a CTE refer to itself so it can walk hierarchies (an org chart, a category tree) or generate sequences (every date in a month). It is powerful and widely supported, but a topic of its own, so it is out of scope here. Just know the phrase, so when you meet a WITH RECURSIVE in the wild you know it is a CTE that repeats until it runs out of new rows.

C. Stacking rows: UNION and UNION ALL

A join glues tables together side by side, adding columns. A set operation does something different: it stacks the rows of two separate SELECT queries on top of each other, one result below the other. You write the first query, then a set operator, then the second query.

There are two rules to respect. First, the two queries must produce the same number of columns, with compatible types, because the rows have to line up: the first column of the top query pairs with the first column of the bottom query, and so on (they line up by position, the column names do not have to match). Second, the result's column names come from the first query. Today both of our queries return a single city column, so they line up cleanly.

UNION ALL stacks the rows and keeps everything, including duplicates. Here we stack the cities of the Team-plan customers on top of the cities of customers who placed a 200 order:

SELECT city FROM customers WHERE plan = 'Team'
UNION ALL
SELECT city FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE amount = 200);
result · 7 rows: 4 Team cities then 3 big-order cities, duplicates kept
city
Austin
Denver
Austin
Reno
Austin
Denver
Austin

Four rows from the top query (Austin, Denver, Austin, Reno), three from the bottom (Austin, Denver, Austin), stacked into seven. UNION ALL did no thinking; it just concatenated. Now swap UNION ALL for plain UNION, which stacks and then removes duplicate rows. This version also adds ORDER BY city at the end: a set operation takes a single ORDER BY, written after the last query, that sorts the whole combined result (you cannot sort the two halves separately):

SELECT city FROM customers WHERE plan = 'Team'
UNION
SELECT city FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE amount = 200)
ORDER BY city;
result · the same rows deduplicated: 3 distinct cities
city
Austin
Denver
Reno

The seven rows collapse to the three distinct cities. That is the whole difference: UNION ALL keeps duplicates (and is faster, since it skips the dedup step), plain UNION removes them. Reach for UNION ALL when you know there are no duplicates or you want to keep them, and plain UNION when you want a distinct combined set.

Why order is not guaranteed on its own. That trailing ORDER BY matters for a reason worth stating plainly: without an ORDER BY, the row order of a set operation is not guaranteed. SQLite happens to return UNION output sorted, but that is an implementation detail you must not rely on, exactly like the "no ORDER BY, no guaranteed order" caveat from Session 1. If you need a specific order, add an ORDER BY at the end. UNION and UNION ALL are standard everywhere: SQLite, PostgreSQL, MySQL and SQL Server.

Your turn See duplicates kept, then removed

Run the UNION ALL query and count seven rows. Then change it to plain UNION and confirm it drops to three (Austin, Denver, Reno). Seeing the same two queries give 7 rows one way and 3 the other is the lesson.

D. INTERSECT and EXCEPT

Two more set operators ask about overlap between the two queries. INTERSECT keeps only the rows that appear in both queries. EXCEPT keeps the rows in the first query that are not in the second (order matters here: first-minus-second is not the same as second-minus-first). Both remove duplicates, like plain UNION does, and both follow the same column rules.

Using the same two city queries as before, INTERSECT finds the cities that are both a Team city and a big-order city:

SELECT city FROM customers WHERE plan = 'Team'
INTERSECT
SELECT city FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE amount = 200)
ORDER BY city;
result · cities in both lists
city
Austin
Denver

The Team cities are Austin, Denver and Reno; the big-order cities are Austin and Denver. The two they share are Austin and Denver. Now EXCEPT, which subtracts the second list from the first:

SELECT city FROM customers WHERE plan = 'Team'
EXCEPT
SELECT city FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE amount = 200)
ORDER BY city;
result · Team cities that are not big-order cities
city
Reno

The Team cities minus the big-order cities (Austin, Denver) leave just Reno. Swap the two queries around and EXCEPT would instead give you the big-order cities that are not Team cities, which is nothing, since both big-order cities are also Team cities. That asymmetry is the thing to remember about EXCEPT.

Cross-database note. INTERSECT and EXCEPT work in SQLite, PostgreSQL and SQL Server, but MySQL only added them in version 8.0.31; older MySQL emulates them with joins or NOT IN. And Oracle spells EXCEPT as MINUS. The behavior is the same; only the keyword differs.

Your turn Overlap and difference

Run the INTERSECT query and confirm Austin and Denver. Run the EXCEPT query and confirm Reno. Then swap the top and bottom queries in the EXCEPT and confirm you get no rows, proving that first-minus-second is not the same as second-minus-first.

E. The milestone, and a look ahead

Now put a CTE and a set operation together on a real question: which customers have placed at least one order but are never named as anyone's referrer? Read it as two sets subtracted: the buyers, minus the referrers. A CTE names the buyers cleanly, and EXCEPT does the subtraction.

The buyers CTE lists the customers who have an order (using the IN-subquery pattern from Session 5). Then EXCEPT removes every name that appears as a referrer. The WHERE referrer IS NOT NULL guard (from Session 2) keeps a NULL out of the referrer list, and the single ORDER BY at the end sorts the whole result:

WITH buyers AS (
  SELECT name FROM customers
  WHERE id IN (SELECT customer_id FROM orders)
)
SELECT name FROM buyers
EXCEPT
SELECT referrer FROM customers WHERE referrer IS NOT NULL
ORDER BY name;
result · the buyers who never referred anyone
name
Fatima
Gita
Hiro
Iris

Eight customers have placed an order (everyone except Diego and Jae). Four of those, Amara, Ben, Chen and Esi, appear as someone's referrer, so EXCEPT subtracts them out. What remains is Fatima, Gita, Hiro and Iris: the four customers who bought something yet never brought anyone in. Write this one from a blank editor.

A look ahead: window functions. Sometimes you want a per-row calculation that also sees across a group, without GROUP BY collapsing the rows. That is what window functions do. For example, RANK() OVER (ORDER BY total DESC) gives every customer a rank by spend while keeping one row per customer:

WITH customer_totals AS (
  SELECT customer_id, SUM(amount) AS total
  FROM orders
  GROUP BY customer_id
)
SELECT customer_id, total, RANK() OVER (ORDER BY total DESC) AS rnk
FROM customer_totals
ORDER BY rnk, customer_id;
result · ranked by spend, rows not collapsed (ties share a rank)
customer_id  total  rnk
1            300    1
3            300    1
5            200    3
6            200    3
8            200    3
9            200    3
7            150    7
2            50     8

Both top spenders share rank 1, then the next distinct total picks up at rank 3, and so on. Window functions are a big topic (they are not taught or graded here), but now you know what they are and when you would reach for one: a calculation that runs per row yet looks across a set. If they click for you, a later bonus session can cover them properly.
