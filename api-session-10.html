A. The brief, and what “shipped” means

The library wants reading lists: a named list of books, each with a one-line description, that a reader can browse. Wikipedia already groups books into categories, pages that list other pages, such as Category:Earthsea novels, the five novels in Ursula K. Le Guin’s Earthsea series. So the integration fills a reading list from a Wikipedia category. It has Session 9’s three owners: a new API that you design and own, Wikipedia’s, which you do not, and the glue between them, which is yours.

It is three requests, but they do not simply run once each in order. A category’s members come back a page at a time, so two of the requests take turns until the category runs out:

B. Your side first: Reading Lists API v1

Design comes before use, as Session 5 said. The library has two kinds of thing here: a list, and the items on it, and an item belongs to one list. So, in Session 5’s nested shape, a list lives at /v1/lists/{listId} and its items at /v1/lists/{listId}/items/{itemId}, where the braces mark a stand-in for a real id.

Whose id is the item’s? This is the decision that makes the whole integration safe to repeat. If the library made up an item’s id when it was saved, with POST /v1/lists/4/items, then running the integration twice would save every book twice, which is Session 8’s problem, and would need Session 8’s idempotency key. Instead, an item’s id is the Wikipedia page id of the book it describes. Every Wikipedia page has a number, its pageid, which Session 9 saw (2890 for A Wizard of Earthsea), and it never changes. So the same book always lands at the same address, and saving it is a PUT to that address: save it twice and the list still has one item. The choice of id did the work a key would otherwise do.

A PUT that may create. Session 9’s about existed from the start, so its PUT always answered 200. An item does not exist until the first save. RFC 9110, the HTTP rulebook from Session 5, says what a PUT answers in that case. It calls the stored thing a representation, here the saved item, and the program that sent the request the user agent: “If the target resource does not have a current representation and the PUT successfully creates one, then the origin server MUST inform the user agent by sending a 201 (Created) response. If the target resource does have a current representation and that representation is successfully modified in accordance with the state of the enclosed representation, then the origin server MUST send either a 200 (OK) or a 204 (No Content) response to indicate successful completion of the request.” So saving an item has two successes: 201 the first time, 200 after that. C. Their side: one member of a category at a time

Session 4 walked a category’s members with a cursor: list=categorymembers gave back titles, a page at a time, and continue.cmcontinue held the bookmark for the next page. That gave titles only. To get each book’s description as well, Session 9’s prop=description has to be asked about those members, and Wikipedia has a form that does both in one request: a generator.

generator=categorymembers says “take the members of this category, and treat them as the pages this request is about”. Every prop in the request, here prop=description, then applies to them. A generator’s own parameters carry a g in front of their usual names, so Session 4’s cmtitle, cmlimit and cmcontinue become gcmtitle, gcmlimit and gcmcontinue:

The cursor is continue.gcmcontinue, and you send it back exactly as it came as the next request’s gcmcontinue. The second field, "continue": "gcmcontinue||", is Wikipedia’s own bookkeeping; sending only gcmcontinue back was enough every time this was tested, as with Session 4’s cmcontinue. The members come in the category’s own order, which files a title under its first word after a leading “The” or “A”: The Farthest Shore, The Other Wind, Tehanu, The Tombs of Atuan, A Wizard of Earthsea. When there is no next member, there is no continue at all.

D. The loop: two requests that take turns

Session 4 walked pages by sending one request over and over. Today two requests take turns, Ask then Save, five times, and the Runner has to be told to go back. Session 8 showed pm.execution.setNextRequest(null), which ends a run. Give setNextRequest a request’s name instead, in quote marks and spelt exactly as the request is named, case and spaces included, and the Runner sends that request next. Spell it wrong, even by one capital letter, and no request matches: in the runs checked for this session the run then simply ended, with no error, exactly as if you had written null. So the end of Save’s script can say pm.execution.setNextRequest("Ask Wikipedia for the next member"), and the run goes back. (Session 4 showed the same idea in an optional box, with pm.info.requestName, which is the name of the request whose script is running: a request can send itself again that way.) As Postman’s documentation says, this works only in a run, never on a single Send.

Four more pieces of JavaScript, each new today:

  • pm.collectionVariables.get("cursor") reads a collection variable inside a script. Session 8’s set writes one; get gives back what it holds.
  • && means “and” between two tests: the whole test is true only if both sides are. It is Session 9’s ||’s partner, and it stops early the other way round: if the left side is already false, it never looks at the right.
  • else if (test) { ... } goes between an if and its else. It is tried only when the test before it was false, so the three branches of an if, else if, else are three cases, and exactly one of them runs.
  • A line that starts with // is a note, as Session 8 said. Putting // in front of a line of code switches that line off without deleting it, which programmers call commenting it out; take the // away and it runs again. Section E uses this.

Why call 1 empties the cursor. The cursor is a collection variable, and Postman keeps a variable’s value after a run ends. A run that stopped half way leaves a cursor pointing at the middle of the category. So the first thing a run does, once it has its list, is put the cursor back to empty, which asks Wikipedia for the first member. Section E shows what happens when it does not.

Now the three scripts. Every value going into a URL gets encodeURIComponent and every value going into a JSON body gets JSON.stringify, Session 9’s rule. The one exception is the page id: it is only digits, which encodeURIComponent would leave exactly as they are, so it goes into the path as it is.

// Read the list, post-response: keep the category, start from the first member
if (pm.response.code !== 200) {
  pm.execution.setNextRequest(null);
} else {
  pm.collectionVariables.set("categoryParam", encodeURIComponent(pm.response.json().category));
  pm.collectionVariables.set("cursor", "");
}
// Ask Wikipedia for the next member, post-response: keep one book and the next cursor
if (pm.response.code !== 200 || pm.response.json().query === undefined) {
  pm.execution.setNextRequest(null);
} else {
  var body = pm.response.json();
  var page = body.query.pages[0];
  if (page.description === undefined) {
    pm.execution.setNextRequest(null);
  } else {
    pm.collectionVariables.set("pageId", page.pageid);
    pm.collectionVariables.set("itemTitle", JSON.stringify(page.title));
    pm.collectionVariables.set("itemDescription", JSON.stringify(page.description));
    if (body.continue === undefined) {
      pm.collectionVariables.set("cursor", "");
    } else {
      pm.collectionVariables.set("cursor", encodeURIComponent(body.continue.gcmcontinue));
    }
  }
}
// Save the item, post-response: stop on a failed save, else go back for the next member
if (pm.response.code !== 200 && pm.response.code !== 201) {
  pm.execution.setNextRequest(null);
} else if (pm.collectionVariables.get("cursor") !== "") {
  pm.execution.setNextRequest("Ask Wikipedia for the next member");
} else {
  pm.execution.setNextRequest(null);
}

An empty cursor is how call 2 says the category is finished, so Save goes back only while the cursor holds something. E. Breaking it, and the rerun question

Session 9’s breaks still apply, and the loop stops cleanly on each: listAnswer set to 404 list not found sends one request, and a misspelt category sends two, because call 2’s query check stops it. The new question a loop raises is this one: a save fails half way through the list. What do you do next?

the third save fails · captured live with newman, with a pre-request script added for this capture making only the third save ask for 503 unavailable
1 Read 200   2 Ask 200 The Farthest Shore   3 Save 201
4 Ask 200 The Other Wind                    5 Save 201
6 Ask 200 Tehanu                            7 Save 503    stopped
cursor left behind: page|5046...dc08|78145    points at The Tombs of Atuan

Two books saved, Tehanu not, and the run stopped, as it should. There are two ways to go on.

Start again from the top. Call 1 empties the cursor, and the run saves all five. The Farthest Shore and The Other Wind are saved a second time, which changes nothing, because a save is a PUT to the book’s own address: section B’s choice of id paying off.

Carry on from where it stopped, by keeping the cursor instead of emptying it. That sounds cheaper, and here is what it does:

the same rerun, with call 1’s cursor line commented out · captured live with newman, the failed run’s cursor set by hand
1 Read 200
2 Ask 200 The Tombs of Atuan     3 Save 201
4 Ask 200 A Wizard of Earthsea   5 Save 201    stop: five requests

Tehanu was never saved, and every status is green.

Look back at call 2’s script. It keeps the next cursor as soon as Wikipedia answers, before call 3 has tried to save the book in hand. So when Tehanu’s save failed, the cursor had already moved past Tehanu. The rule this teaches holds far beyond Wikipedia: a bookmark must only move past work that is done. Either move it after the save succeeds, which Part 4 asks you to design, or, as this integration does, restart from the top, which is safe only because every write can be repeated. A loop that saved with POST and no key could do neither safely.

Two Runner settings bear on this. Keep variable values, ticked when you first open the Runner, which remembers your choice after that, is what keeps the cursor after a run, which is why call 1 empties it. And Session 9’s Stop run if an error occurs does not come into it: a 503 is an answer, not an error, and call 3’s own test is what stops the run.

G. Where this track stops

> Ask Wikipedia for the next member, post-response
if (pm.response.code !== 200 ||
    pm.response.json().error !== undefined) {
  pm.execution.setNextRequest(null);
} else {
  var body = pm.response.json();
  if (body.continue === undefined) {
    pm.collectionVariables.set("cursor", "");
  } else {
    pm.collectionVariables.set("cursor",
      encodeURIComponent(body.continue.gcmcontinue));
  }
  if (body.query === undefined ||
      body.query.pages[0].description === undefined) {
    // nothing to save here: ask for the next member, if any
    if (body.continue === undefined) {
      pm.execution.setNextRequest(null);
    } else {
      pm.execution.setNextRequest(pm.info.requestName);
    }
  } else {
    var page = body.query.pages[0];
    pm.collectionVariables.set("pageId", page.pageid);
    pm.collectionVariables.set("itemTitle", JSON.stringify(page.title));
    pm.collectionVariables.set("itemDescription",
      JSON.stringify(page.description));
  }
}

> where yours may honestly differ
Stopping is defensible if the README says so. Adding
gcmnamespace=0, which leaves categories out, is a good
instinct, but measured here it saved no requests: with one
member per answer, Wikipedia still answers for each left-out
member, with a continue and no query at all. A script that
treats "no query" as the end stops there. This one checks
for an error object instead, and lets "no query" mean
"nothing to save".
