Now the topic. Every query so far returned one output row per matching table row. An aggregate function is different: it reads a whole column of values and collapses them into a single value. The five core ones:

  • COUNT(*) counts rows  ·  SUM(col) adds the values  ·  AVG(col) averages them
  • MIN(col) and MAX(col) return the smallest and largest value (these also work on text, low to high alphabetically)

In these forms col is a placeholder: you replace it with the name of a real column, such as monthly_fee. You do not type the word "col". The * in COUNT(*) is special: it means "count the rows themselves" rather than the values in any one column.

Each returns exactly one row, because it summarizes the whole table at once:

SELECT COUNT(*) FROM customers;        -- how many rows: 10
SELECT SUM(monthly_fee) FROM customers; -- total of every fee: 440

You can compute several at once. Give each a readable name with AS (the aliasing you learned in Session 1), which is how the result columns get labelled:

SELECT COUNT(*) AS n, SUM(monthly_fee) AS total,
       AVG(monthly_fee) AS avg_fee,
       MIN(monthly_fee) AS lowest, MAX(monthly_fee) AS highest
FROM customers;
result · one summary row for the whole table
n   total  avg_fee  lowest  highest
10  440    44.0     20      60

Notice avg_fee is 44.0, not 44. AVG always returns a decimal (a floating-point number), even when it divides evenly, so expect a decimal point in every average. COUNT and SUM of whole numbers stay whole.

You are not limited to the whole table. Add a WHERE and the aggregate summarizes only the rows that pass it, since WHERE filters the rows before the aggregate runs:

SELECT AVG(monthly_fee) FROM customers WHERE city = 'Austin';  -- Austin only, so 50.0

B. COUNT and NULLs, and counting distinct values

There are two forms of COUNT, and the difference is the whole lesson. COUNT(*) counts rows, full stop. COUNT(col), where col is an actual column name such as referrer, counts only the rows where that column is not NULL: it skips the missing values (recall from Session 2 that NULL means missing or unknown). Four of our customers have no referrer, so:

SELECT COUNT(*) AS all_rows, COUNT(referrer) AS with_referrer
FROM customers;
result
all_rows  with_referrer
10        6

COUNT(referrer) is 6, not 10: it skipped the four NULL rows. This NULL-skipping is not unique to COUNT. SUM, AVG, MIN and MAX all ignore NULLs too, which matters for AVG especially: it divides by the count of non-null values, not by the total number of rows. So a missing value never drags an average toward zero; it is simply left out.

You often want the number of distinct values, not the number of rows. Put DISTINCT inside the count:

SELECT COUNT(DISTINCT city) AS cities FROM customers;  -- 4 distinct cities

There are ten rows but only four different cities (Austin, Denver, Boston, Reno), so COUNT(DISTINCT city) is 4. Like the column form, COUNT(DISTINCT ...) also ignores NULLs.

C. GROUP BY: one summary row per group

A single aggregate summarizes the whole table. GROUP BY is what makes aggregates powerful: it splits the rows into groups that share a value, then computes the aggregate once per group and returns one row for each group. To count customers per plan:

SELECT plan, COUNT(*) AS customers
FROM customers
GROUP BY plan
ORDER BY plan;
result · one row per plan
plan   customers
Basic  2
Pro    4
Team   4

Ten rows went in; three rows came out, one per distinct plan, each with its own count. You can aggregate more than one thing per group, and mix in AVG:

SELECT city, COUNT(*) AS customers, AVG(monthly_fee) AS avg_fee
FROM customers
GROUP BY city
ORDER BY city;
result · count and average fee per city
city    customers  avg_fee
Austin  4          50.0
Boston  2          30.0
Denver  3          40.0
Reno    1          60.0

The SELECT-list rule. When you use GROUP BY, every column in the SELECT list must either be one of the grouping columns or be wrapped in an aggregate. The reason is that each result row now stands for a whole group, so a plain column that varies inside the group has no single value to show. SELECT city, name ... grouped by city is meaningless: which of the four Austin names would it print?

One caution across databases: SQLite is unusually lax about this rule. It will let you select an ungrouped column and quietly pick an arbitrary row value instead of erroring. That is a SQLite quirk, not standard SQL. PostgreSQL and SQL Server reject the query, and modern MySQL rejects it by default too. Write to the strict rule (group it or aggregate it) so your queries work unchanged on any database.

D. HAVING vs WHERE, and the clause order

You already filter rows with WHERE. But how do you filter groups, for example "only cities with at least 3 customers"? You cannot use WHERE COUNT(*) >= 3, and it is worth knowing why: WHERE runs before the groups are formed, so the count does not exist yet. (SQLite reports misuse of aggregate if you try.) The clause for filtering groups is HAVING:

SELECT city, COUNT(*) AS customers
FROM customers
GROUP BY city
HAVING COUNT(*) >= 2
ORDER BY city;
result · Reno (1 customer) is filtered out
city    customers
Austin  4
Boston  2
Denver  3

So the division of labor is: WHERE filters individual rows before grouping; HAVING filters whole groups after grouping, using an aggregate. You can use both in one query. WHERE trims the rows that feed the groups, then HAVING trims the groups themselves:

SELECT plan, COUNT(*) AS n
FROM customers
WHERE signup_year >= 2022
GROUP BY plan
ORDER BY plan;
result · only 2022-and-later signups are grouped
plan   n
Basic  1
Pro    3
Team   3

That works because SQL runs the clauses in a fixed order, no matter how you type them:

  • FROM → WHERE (filter rows) → GROUP BY (form groups) → HAVING (filter groups) → ORDER BY (sort what is left)

That order explains everything: WHERE cannot see an aggregate because groups do not exist when it runs; HAVING can, because it runs after grouping; and ORDER BY runs last, so it can sort by an aggregate or by an AS alias you defined. This clause set and its order are the same across SQLite, PostgreSQL, MySQL and SQL Server.

Your turn Filter the groups

Run the HAVING COUNT(*) >= 2 query and confirm Reno drops out. Then change >= 2 to >= 3 and watch Boston drop too, leaving Austin and Denver.

E. Put it together: the milestone

Everything today stacks into one shape: filter rows, form groups, aggregate each group, keep the groups you want, and sort them. Sorting by an aggregate is common, and because ORDER BY runs last it can sort by the aggregate expression itself or by an AS alias you defined in the SELECT list. To list the plans busiest first, sort by COUNT(*):

SELECT plan, COUNT(*) AS customers
FROM customers
GROUP BY plan
ORDER BY COUNT(*) DESC, plan;   -- busiest plan first, ties by name
result · groups sorted by the count itself
plan   customers
Pro    4
Team   4
Basic  2

Writing ORDER BY customers DESC (the alias) would sort exactly the same way; use whichever reads more clearly. The milestone below does just this with an alias.
