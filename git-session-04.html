Real merges & conflicts

A conflict is not an error and it is not a punishment. It is Git telling you that two people changed the same lines and it has no rule for choosing between them, so it hands you the decision. This session has you cause conflicts on purpose, read them, and resolve them, until the word stops being frightening and starts being a task.

Milestone Cause, read, and resolve a merge conflict calmly.
git

You do not need branch-lab from Session 3. Step one below builds a brand new repository called merge-lab from scratch, in under a minute. It has to be a new one: a conflict needs two branches that have each moved in a specific way, and branch-lab ended up as a straight line. No account and no internet are needed for any of this session.

This is a workbook, not a reading. You will predict what a command does to your repository, reassemble command sequences, fill blanks, and write from scratch, and each part hands you less scaffolding than the last. The goal is the one this whole track is built on: read a Git command and know what it will do before you press enter.

A. Build a fresh lab

This session needs a repository whose history forks: two branches that have each moved on from a shared starting point. That is the one shape Session 3 never produced, so you build it here from scratch, and everybody starts from the same place.

Everything in the block below is a command you already know from Sessions 1 and 3. git init -b main creates the repository and names the first branch main in one step, so it behaves the same on any machine regardless of that init.defaultBranch setting from Session 1.

One thing to notice as you paste: plan.md is deliberately three lines long. That matters later. A one-line file would make a conflict look like the whole file exploded, and hide the fact that Git quietly merges everything that did not actually collide.

PowerShell (Windows default) · build merge-lab
cd ~
mkdir merge-lab
cd merge-lab
git init -b main
Set-Content plan.md "title: report"
Add-Content plan.md "owner: unassigned"
Add-Content plan.md "status: draft"
git add plan.md
git commit -m "Add plan.md"
Git Bash / macOS / Linux · build merge-lab
cd ~
mkdir merge-lab
cd merge-lab
git init -b main
echo "title: report" > plan.md
echo "owner: unassigned" >> plan.md
echo "status: draft" >> plan.md
git add plan.md
git commit -m "Add plan.md"
Already have a folder called merge-lab? Read this first

The mkdir line will fail if the folder already exists. The cd line after it will then succeed anyway and take you into the folder you already had, so the rest of the block runs against whatever is already in there instead of a clean start. The giveaway is the git init -b main line, which prints two lines instead of Initialized empty Git repository:

warning: re-init: ignored --initial-branch=main
Reinitialized existing Git repository in .../merge-lab/.git/

Read that warning, because it matters more than it looks. On an existing repository Git ignores the -b main part, so it does not rename anything. If that old repository happened to be on a branch called master, you stay on master, and every transcript below saying On branch main will not match what you see. That is the second reason to prefer a fresh folder. Two ways out.

The safe one: pick another name. Replace merge-lab with merge-lab-2 in the mkdir and cd lines and carry on. Everything else in the session is identical.

The other one: delete the old folder first. This permanently removes that folder and everything inside it, so only run it if you are certain you do not need what is in there.

PowerShellcd ~ Remove-Item -Recurse -Force merge-lab
Git Bash / macOS / Linuxcd ~ rm -rf merge-lab

B. When a merge cannot fast-forward

Session 3 ended on a rule, and this section breaks it on purpose. A fast-forward merge is possible precisely when the branch you are on has not moved since the other branch split off. Git had nothing to combine, so it slid a pointer forward and created no commit at all.

So now let both branches move. Make a branch, commit something on it, come back to main, and commit something different there. Each side changes a different file, which matters: for now there is nothing to argue about, and you will see that a real merge is normally silent.

PowerShell · move both branches
git switch -c topic
Set-Content extra.md "Extra notes."
git add extra.md
git commit -m "Add extra.md"
git switch main
Set-Content readme.md "Read me first."
git add readme.md
git commit -m "Add readme.md"
Git Bash / macOS / Linux · move both branches
git switch -c topic
echo "Extra notes." > extra.md
git add extra.md
git commit -m "Add extra.md"
git switch main
echo "Read me first." > readme.md
git add readme.md
git commit -m "Add readme.md"

Now draw the history with the command Session 3 told you to memorise. This is the first genuinely forked graph in the whole track, so read it slowly:

git log --oneline --graph --all --decorate=short · a fork
> git log --oneline --graph --all --decorate=short
* 98791fb (HEAD -> main) Add readme.md
| * 9df15a5 (topic) Add extra.md
|/  
* eae0e4d Add plan.md

Reading it from the bottom up: one commit that both branches share, then the line splits into two columns. The left column carries main, the right column carries topic. The |/ line is the split itself, drawn as the two columns joining as you read downward. Neither branch is an ancestor of the other any more: each has one commit the other does not.

That last sentence is the whole reason this session exists. There is no pointer Git can slide. Moving main up to topic would silently throw away readme.md, and moving it the other way would throw away extra.md. Git will not guess, so it has to genuinely combine the two.

The shared commit at the bottom has a name: the merge base. It is the most recent commit that both branches can reach, in other words the last point at which the two sides agreed. Git can tell you which one it is:

git merge-base · the last commit the two branches shared
> git merge-base main topic
eae0e4dd6d701130ade3e8b521ecfaad7b239c6b

That is the full 40-character form of the hash Session 1 introduced, and it is the Add plan.md commit sitting at the bottom of the graph. You will rarely type git merge-base in real work; it is here so that "merge base" is a thing you can point at on a graph rather than a phrase from a manual.

C. What a three-way merge actually is

The name is literal. A merge like this one has three inputs, not two, and once you can name all three the rest of the session follows from it:

the merge base
the last commit both branches shared. What the file looked like before either side touched it.
→
your side
the tip of the branch you are standing on. Git calls this ours.
→
their side
the tip of the branch you named in the merge command. Git calls this theirs.

Git compares each side against the base, which is what lets it work out not just that the two files differ but who changed what. If only one side changed a line, that side's version is obviously the one to keep, and Git takes it without asking. It only has to stop when both sides changed the same line, because then "who changed it" has two answers.

The result is a new commit, and it is a new kind of commit: a merge commit, which has two parents instead of one. Session 1 told you every commit records a pointer to its parent, and added that this stays true "until Session 4, where merging produces the one kind of commit with two". This is that. You will prove it with your own eyes in section F.

D. Before you merge: the editor, and how to get out of it

Read this section before running any merge. It is short, and skipping it is how people end up stuck in a program they did not ask for and cannot close.

Here is why it matters. A fast-forward creates no commit, so Session 3's merges never needed a message. A real merge creates a commit, and a commit needs a message. Git writes a perfectly good one for you (Merge branch 'topic'), but by default it then opens an editor to let you change it before it commits.

One word needs unpacking first, because this track has used it in a different sense. In Sessions 1 and 2, "your editor" meant the program you write files in, like Notepad or VS Code, and you opened it yourself. Here, "the editor" means a program Git launches for you, usually right inside the terminal window, with the prepared message already in it. You did not open it and there may be no obvious way to close it, which is exactly why it catches people.

So find out which one your Git will open, before it opens. One command, and it only prints a name:

git var GIT_EDITOR · which editor will Git launch?
> git var GIT_EDITOR
vim

vim is what a standard Git for Windows install answers when nothing has been configured, and it is the answer you are most likely to get. It is a perfectly good editor and a genuinely confusing one to meet by accident, because typing text into it does not work the way you expect. You may get a different answer, so find yours in this table and remember the escape:

vim · vi · editorPress Esc, then type :wq and press Enter. That means write and quit. To abandon it instead: Esc, then :q!, then Enter.
nanoPress Ctrl+O then Enter to write, then Ctrl+X to quit. Nano lists these at the bottom of the screen.
notepadA normal Notepad window opens. Ctrl+S to save, then close the window.
code --waitA tab opens in VS Code. Ctrl+S to save, then close the tab. Git waits until you close it, which is what --wait means.

The first row covers three answers because they are the same program or a pointer to it: vi is the usual answer on macOS and on Linux, and editor is what some Linux installations answer. If your answer is not in this table at all, do not run the merge yet. Search for "how to save and quit" plus the name you got, find the two key presses, and come back. Knowing the exit before you go in is the entire point of this section.

You do not have to deal with any of that right now, though. --no-edit tells Git to accept the message it prepared and skip opening anything:

Both shellsgit merge --no-edit <branch>

As always, <branch> in angle brackets is a placeholder for a real branch name. You will use --no-edit for the next merge so that nothing unexpected opens, and then in section J you will leave it off on purpose, so that you meet the editor once, deliberately, knowing how to get out.

E. A clean three-way merge, with no conflict at all

Before the conflicts, see the normal case, because merging is not the same thing as conflicting and it would be easy to leave this session believing it is. Most real merges look like this one: you run a command and Git just does it.

You are on main. Bring in topic, which changed a different file:

git merge --no-edit topic · run from main
> git merge --no-edit topic
Merge made by the 'ort' strategy.
 extra.md | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 extra.md
  • Merge made by the 'ort' strategy. replaces the word Fast-forward you were looking for in Session 3. It is Git telling you which kind of merge it did, and this one built a real commit.
  • ort is just the name of Git's default merge algorithm. You do not choose it, you will not need to change it, and it will appear in this line every time. It is mentioned here only so the word is not a mystery when you see it.
  • The last three lines are the same changed-files summary a commit prints, showing what arrived in your working tree.

Now the graph, and it has a shape you have not seen:

the diamond
> git log --oneline --graph --all --decorate=short
*   8eff447 (HEAD -> main) Merge branch 'topic'
|\  
| * 9df15a5 (topic) Add extra.md
* | 98791fb Add readme.md
|/  
* eae0e4d Add plan.md

Read it bottom to top: one shared commit, the line splits (|/), the two sides run in parallel for one commit each (* | and | *), and then the line joins back together (|\) at a single new commit on top. That new commit is the merge commit, and the diamond is the picture of a three-way merge.

Two small things in that drawing, both of which are real and neither of which is a mistake. A merge commit prints three spaces after its *, where an ordinary commit prints one, which is how Git makes room for the branching lines. And the |\ and |/ lines have two trailing spaces after them. You cannot see them, they do nothing, and they are only mentioned so that you do not think your output differs from this page when you compare the two.

And the thing worth noticing most: both files are in your folder, and Git never asked you anything.

List the folder with the command Session 3 gave you for your shell:

PowerShellGet-ChildItem -Name
Git Bash / macOS / Linuxls -1
both sides arrived
> Get-ChildItem -Name
extra.md
plan.md

F. Two parents, proved

Time to check the claim from section C rather than take it on trust. git cat-file -p <thing> prints the raw contents of an object in the repository, which for a commit means the plain text Git actually stored. The -p means pretty-print. Point it at HEAD, which Session 2 taught is a reference to the commit you are standing on:

git cat-file -p HEAD · the merge commit, raw
> git cat-file -p HEAD
tree a1d377526c1154cba5a311e05db83de9293569e1
parent 98791fbb02627c142260992ce68bf44ef8a721db
parent 9df15a5b2a64acbb578c4db8edc66f83e01ae058
author Your Name <you@example.com> 1786048007 -0500
committer Your Name <you@example.com> 1786048007 -0500

Merge branch 'topic'

Two parent lines. That is the whole point, and it is the first commit in this track with more than one. The first parent is where main was, the second is where topic was, and the merge commit ties them together. Your own name and email will appear on the author and committer lines, because those come from the identity you set in Session 1, and the long numbers are timestamps.

Compare it against an ordinary commit and against the very first one, so the pattern is unmistakable:

an ordinary commit has one parent; the root commit has none

> git cat-file -p eae0e4d

The root commit has no parent line at all. Session 1 called it the root commit and said it is the one with no parent; here is that fact as raw stored text. So the count runs zero, one, two: the first commit in a repository has none, every ordinary commit has one, and a merge commit has two.

One more command, because it extends the log-shaping vocabulary from Session 2. --merges filters the log down to merge commits only:

git log --merges · show me only the merges
> git log --merges --oneline
8eff447 Merge branch 'topic'

One merge so far. Keep that number in mind; it goes up.

G. Causing a conflict on purpose

Everything so far merged silently because the two sides touched different files. Now make them touch the same line of the same file.

Say this out loud before you run it, because the framing is the point of the session: you are not about to make a mistake. You are going to construct a situation Git cannot resolve alone, because that is the only way to practise resolving it. Nothing here is broken and nothing is at risk.

The plan: a branch called rename-owner sets the middle line of plan.md to owner: Rae, and meanwhile main sets that same line to owner: Sam. Both sides rewrite all three lines of the file, using only the Set-Content and Add-Content pattern from Session 1, so there is no new file-editing technique to learn here:

PowerShell · two branches, one line, two answers
git switch -c rename-owner
Set-Content plan.md "title: report"
Add-Content plan.md "owner: Rae"
Add-Content plan.md "status: draft"
git add plan.md
git commit -m "Set owner to Rae"
git switch main
Set-Content plan.md "title: report"
Add-Content plan.md "owner: Sam"
Add-Content plan.md "status: draft"
git add plan.md
git commit -m "Set owner to Sam"
Git Bash / macOS / Linux · two branches, one line, two answers
git switch -c rename-owner
echo "title: report" > plan.md
echo "owner: Rae" >> plan.md
echo "status: draft" >> plan.md
git add plan.md
git commit -m "Set owner to Rae"
git switch main
echo "title: report" > plan.md
echo "owner: Sam" >> plan.md
echo "status: draft" >> plan.md
git add plan.md
git commit -m "Set owner to Sam"

The graph forks again, this time above the diamond you already made:

a second fork, sitting on top of the first merge
> git log --oneline --graph --all --decorate=short
* 9266a96 (HEAD -> main) Set owner to Sam
| * 91afc99 (rename-owner) Set owner to Rae
|/  
*   8eff447 Merge branch 'topic'
|\  
| * 9df15a5 Add extra.md
* | 98791fb Add readme.md
|/  
* eae0e4d Add plan.md

Now merge, and leave --no-edit off this time. That is safe here for a reason worth knowing: a merge that hits a conflict stops before it creates any commit, so there is no message to write and no editor opens.

git merge rename-owner · the conflict
> git merge rename-owner
Auto-merging plan.md
CONFLICT (content): Merge conflict in plan.md
Automatic merge failed; fix conflicts and then commit the result.

Three lines, and each one is doing a job. Auto-merging plan.md says Git tried. CONFLICT (content) names the file it could not finish. And the last line is an instruction, not a telling-off: fix conflicts and then commit the result. That is the entire procedure, and the rest of this session is just carrying it out slowly.

One technical detail worth one sentence, because you will meet it eventually. This command finished with a nonzero exit code, which is the invisible number a program hands back to say "this did not fully succeed". It is how automated scripts notice a conflict. It does not mean you broke something.

H. Reading the conflict, three ways

You have the merge output already. There are two more places to look, and you should get in the habit of checking both.

First, git status, which you have used since Session 1 and which now has new vocabulary in it:

git status · during a conflict
> git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   plan.md

no changes added to commit (use "git add" and/or "git commit -a")
  • Unmerged paths is a new heading, alongside the Changes to be committed and Changes not staged for commit from Session 1. A path is just a file here.
  • both modified: is a new state word, alongside new file: and modified:. It says precisely what went wrong: both sides changed this file.
  • Git puts the way out in its own hint text, on the fourth line. That is where you are about to get git merge --abort from.

There is a short form of status too. git status --short prints one line per file with a two-letter code instead of the full report, and it is what people actually use once they know the codes:

git status --short · the two-letter form
> git status --short
UU plan.md

UU means unmerged, on both sides: the U stands for unmerged, and there are two of them because there are two sides. If you remember one piece of shorthand from this session, make it this one, because UU is the fastest possible answer to "which files do I still have to deal with".

Second, and most importantly, the file itself. Open plan.md and look at what Git did to it:

plan.md · with the conflict written into it
> Get-Content plan.md
title: report
<<<<<<< HEAD
owner: Sam
=======
owner: Rae
>>>>>>> rename-owner
status: draft

Those three gold lines are the conflict markers, and here is the single most important sentence in this session: they are ordinary text that Git wrote into your file. They are not a special mode, not a lock, and not a Git feature that has to be switched off. Git edited your file, the same way you would, and left a note in it. Here is what each one means:

<<<<<<< HEADEverything below this line, until the divider, is your side: what the branch you are standing on says. HEAD is that branch, which is main here.
=======The divider. Nothing above or below it is more correct; it just separates the two versions.
>>>>>>> rename-ownerEverything above this line, back to the divider, is their side: what the branch you are merging in says. Git labels it with that branch's name.

Now look at the lines that are not marked. title: report at the top and status: draft at the bottom are sitting there untouched, exactly as they always were. Neither side changed them, so Git merged them silently and never mentioned them. A conflict is confined to the lines that actually collided, and it is worth seeing that in a three-line file, because in a three-hundred-line file it is the difference between a small decision and a panic.

One last place you could look, mentioned so that it does not ambush you. If you run git diff during a conflict, you get something that does not look like the diffs Session 2 taught you to read:

git diff during a conflict · a different format
> git diff
diff --cc plan.md
index eae5a08,021dc22..0000000
--- a/plan.md
+++ b/plan.md
@@@ -1,3 -1,3 +1,7 @@@
  title: report
++<<<<<<< HEAD
 +owner: Sam
++=======
+ owner: Rae
++>>>>>>> rename-owner
  status: draft

The doubled + signs and the three-at-sign header are not a bug and you have not misread them. This is a combined diff, a special format Git uses when it has to show you a change against two parents at once. It is named here only so that it is not a mystery, and you can safely ignore it for the whole of this session. Read the file itself instead; it tells you everything the combined diff does, in a form you can act on. Nothing in this workbook will ask you about this format.

I. Backing out, before you ever need to

You are going to learn the escape hatch before the thing you might need to escape from. That ordering is deliberate. Reading conflict markers is a calm, ordinary job if you know you can undo the whole situation with one command, and a stressful one if you do not.

git merge --abort puts everything back exactly as it was before you ran the merge. The markers vanish, the file returns to your side's version, the merge is called off, and no commit is created:

git merge --abort · and it prints nothing at all
> git merge --abort

> git status
On branch main
nothing to commit, working tree clean

> Get-Content plan.md
title: report
owner: Sam
status: draft

It printed nothing, which as ever means it worked. The tree is clean, and plan.md says owner: Sam again, which is what main said before you started. The rename-owner branch is untouched and still holds its own version. It is as if the merge never happened.

So the rule to carry out of this session: if a conflict ever looks like more than you want to deal with, you are one command away from putting it back. Nothing is committed until you commit it.

  2. Draw the graph and confirm it forks again above the diamond.
  3. Run git merge rename-owner. Read all three output lines rather than skimming them.
  4. Run git status and find both modified:. Then run git status --short and confirm you get UU plan.md.
  5. Read plan.md. Find the three markers, and then find the two lines that merged silently.

J. Resolving it deliberately

Do it again, and this time see it through. Run the same merge to get back to the conflicted state:

back into the conflict, on purpose
> git merge rename-owner
Auto-merging plan.md
CONFLICT (content): Merge conflict in plan.md
Automatic merge failed; fix conflicts and then commit the result.

Step one: edit the file until it says what you want, and the markers are gone. That is the whole of resolving. Open plan.md in whatever you normally write files in (Notepad, VS Code, anything), and make it read like this. Notice that the answer here is neither side: both people are genuinely involved, so the honest resolution keeps both names.

plan.md · resolved by hand
title: report
owner: Rae and Sam
status: draft

Delete the three marker lines, delete or keep whichever of the two versions you like, type something new if that is the right answer. There is no command for this step and there is not meant to be. You are the part of the process Git could not automate, which is precisely why it stopped and asked.

Would rather not leave the terminal? Rewrite the file instead

Editing by hand is the honest version of this step and it is what you will do in real work. But if you would rather stay in the terminal for now, the Session 1 write-the-whole-file pattern produces exactly the same result, because the markers are only text and overwriting the file removes them along with everything else:

PowerShellSet-Content plan.md "title: report" Add-Content plan.md "owner: Rae and Sam" Add-Content plan.md "status: draft"
Git Bash / macOS / Linuxecho "title: report" > plan.md echo "owner: Rae and Sam" >> plan.md echo "status: draft" >> plan.md

Step two: tell Git you have resolved it, with git add. This is a command you have known since Session 1 as "stage this file", and during a merge it quietly takes on a second job: it also means "I have dealt with this conflict". Same command, extra meaning, and nothing on screen announces the difference. Watch what it does to the status:

git add · which here means "resolved"
> git add plan.md

> git status
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
	modified:   plan.md

All conflicts fixed but you are still merging. Stop and read that line properly, because it is the most reassuring sentence Git ever prints. It tells you the hard part is over and exactly one step remains. both modified: has become an ordinary modified:, and the file is no longer unmerged.

A real trap, and it is worth knowing now. git add does not check whether you actually removed the markers. If you stage the file with <<<<<<< still in it, Git accepts it without a word and commits those marker lines into your project as if they were content. Nothing warns you. This is the single most common way a beginner's conflict goes wrong, and the guard against it costs nothing: read the file once more before you stage it.

Step three: commit, and meet the editor. You know what to expect from section D and you know how to get out, so run it without -m and without --no-edit, on purpose:

git commit · the editor opens here
> git commit

Your editor opens with a message already written in it. Everything starting with a # is a comment that Git strips out, so the actual message is just the first line:

what is in the editor when it opens
Merge branch 'rename-owner'

# Conflicts:
#	plan.md
#
# It looks like you may be committing a merge.
# If this is not correct, please run
#	git update-ref -d MERGE_HEAD
# and try again.

K. Taking one side wholesale (a footnote)

Sometimes you know immediately that one side is simply right and you do not want to hand-edit anything. Two commands do that, and they are worth recognising rather than reaching for:

your sidegit checkout --ours <file>
their sidegit checkout --theirs <file>

Each replaces the whole conflicted file with one side's version, markers and all removed. You still have to git add the file afterwards, because taking a side is not the same as saying you are finished with it.

The honest warning, which is why this is a footnote and not a lesson. "Ours" and "theirs" are genuinely confusing during a merge. They do not mean "mine" and "my colleague's"; they mean the branch you are standing on and the branch you named, and which is which flips depending on where you are standing when you run the merge. It is very easy to be certain and wrong. The safe habit, and the one to build now, is to open the file and decide line by line. These two exist so you recognise them in someone else's instructions.

Merge tools also exist, meaning graphical programs that show you the two sides in side-by-side panes. They are named here once so you know the category exists; you do not need one, and every conflict in this session is easier to understand as text.

Out of scope, so you know where the edges are. Conflicts that arrive from someone else's copy of a repository are Session 5. rebase, the other way of combining branches, which rewrites history instead of merging it, is Session 8.

L. The milestone: two conflicts, on purpose

Section J walked you through one conflict with every output printed. The milestone is two more with the scaffolding removed, and they differ in kind, because real conflicts do:

  • A trivial one, where the two sides are just two different choices and the resolution is to pick one and delete the other.
  • A genuine one, where both sides made a real change that deserves to survive, and the resolution is to write a version that keeps both.

Knowing which kind you are looking at is most of the skill. Work in merge-lab, on main, with a clean tree. Do not scroll back up; if you get stuck, git status tells you where you are and what it wants next, which is the habit this whole session is really teaching.

Your turn The milestone: cause and resolve two conflicts

Conflict one, the trivial kind.

  1. Create a branch called mark-final, move onto it, and change the status: line of plan.md to status: final. Commit it with the message Mark the plan final.
  2. Go back to main and change that same line to status: review. Commit it with the message Mark the plan in review.
  3. Merge mark-final into main. Predict before you press enter whether this will conflict, and say why.
  4. Read the file and the short status. Then resolve it by keeping status: final and deleting the other line, along with all three markers.
  5. Stage the resolution and conclude the merge. Delete the branch afterwards.

Conflict two, the genuine kind.

  1. Create a branch called add-chart and add a fourth line to plan.md: note: needs a chart. Commit it with the message Note that a chart is needed.
  2. Go back to main and add a fourth line there instead: note: needs a summary. Commit it with the message Note that a summary is needed.
  3. Merge add-chart into main. It will conflict, because both sides added a different line in the same place.
  4. Resolve it by keeping both note lines, one after the other. Neither side is wrong here, and throwing one away would lose real information.
  5. Stage, conclude the merge, delete the branch.
  6. Finally, run git log --merges --oneline and confirm it lists four merge commits, and read plan.md one last time.

You have hit the milestone when you did both conflicts without scrolling back, and you can say in one sentence why the second one needed a different resolution from the first.
