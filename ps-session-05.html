$lab = Join-Path $HOME 'ps-lab'
Set-Location $HOME   # step out first: a folder you are standing in cannot be deleted
if (Test-Path $lab) { Remove-Item $lab -Recurse -Force }
$enc = New-Object System.Text.UTF8Encoding($false)
function Add-LabFile($rel, $lines, $when) {
  $path = Join-Path $lab $rel
  $dir = Split-Path $path -Parent
  if (-not (Test-Path $dir)) { New-Item -ItemType Directory -Path $dir | Out-Null }
  $text = ''
  if ($lines.Count -gt 0) { $text = ($lines -join "`n") + "`n" }
  [System.IO.File]::WriteAllText($path, $text, $enc)
  (Get-Item $path).LastWriteTime = [datetime]$when
}

A. Variables: keeping a result to use again

In Session 1 you typed $PSVersionTable, and Session 2 said the $ marks a variable: a name that holds a value. PowerShell made that one. Now make your own. $shop = 'Fernhill Goods' means “store the text 'Fernhill Goods' in a variable named shop”: the = stores whatever is on its right in the variable on its left, and prints nothing. To see what a variable holds, type its name on its own. A name can use letters, digits and _, and, like a command’s name, its case does not matter:

store a value, then read it back · captured live
PS C:\Users\you\ps-lab> $shop = 'Fernhill Goods'
PS C:\Users\you\ps-lab> $shop
Fernhill Goods
PS C:\Users\you\ps-lab> $Shop
Fernhill Goods

A variable can hold the result of a whole command. $orders = Import-Csv data/orders.csv reads the file once and keeps its eight rows. A variable that holds several objects is a list, and its .Count property says how many it holds. You can send a variable down a pipe exactly as you would a command’s output:

a command’s result in a variable · captured live
PS C:\Users\you\ps-lab> $orders = Import-Csv data/orders.csv
PS C:\Users\you\ps-lab> $orders.Count
8
PS C:\Users\you\ps-lab> $orders | Where-Object Status -eq 'pending' |
  Select-Object OrderId, Customer, Total                                     one line, wrapped here

OrderId Customer Total
------- -------- -----
5006    Ana Ruiz 29.00
5008    Gus Lind 82.00

The file was read once; every later use of $orders reads the variable, not the file. Storing a new value in a variable replaces the old one, without asking. And a name you never stored anything in is not an error: it simply holds nothing, so typing it prints nothing at all, and its Count is 0. A misspelt variable name therefore fails quietly, the same way Session 2’s misspelt property did:

a filtered list, a misspelling, a replaced value · captured live
PS C:\Users\you\ps-lab> $open = Import-Csv data/tickets.csv | Where-Object State -eq 'open'
PS C:\Users\you\ps-lab> $open.Count
3
PS C:\Users\you\ps-lab> $opne.Count
0
PS C:\Users\you\ps-lab> $shop = 'Fernhill Goods Ltd'
PS C:\Users\you\ps-lab> $shop
Fernhill Goods Ltd

So when a variable comes back empty, or with a Count of 0, check its spelling first. A variable lives until you close the window; a new window starts with none of yours.

B. What type is a value?

New window?If you closed PowerShell since the last section, type these first, in ps-lab: they store the variables this section uses. In the same window as before, you can skip them; typing them again does no harm. 
PS C:\Users\you\ps-lab> $orders = Import-Csv data/orders.csv
PS C:\Users\you\ps-lab> $tickets = Import-Csv data/tickets.csv

Session 4 showed that a CSV column is text even when it looks like a number, and that when PowerShell combines two values, the value on the left decides how. Every value has a type, the kind of value it is. Type a number without quotes and it is stored as a number; put it in quotes and it is text:

a number and some text · captured live
PS C:\Users\you\ps-lab> $n = 5
PS C:\Users\you\ps-lab> $t = '5'
PS C:\Users\you\ps-lab> $n + 1
6
PS C:\Users\you\ps-lab> $t + 1
51

To find out a value’s type, ask it. Session 2’s Get-Member listed methods as well as properties: a method is an action an object can carry out, and you call it by its name followed by ( ), even when there is nothing to put inside. Every value has the method GetType(), which hands back a description of its type; that description’s .Name is the type’s name. A number typed straight in, such as 34.5, goes in parentheses before the dot, so PowerShell reads the dot as the start of .GetType():

ask a value its type · captured live
PS C:\Users\you\ps-lab> $n.GetType().Name
Int32
PS C:\Users\you\ps-lab> $t.GetType().Name
String
PS C:\Users\you\ps-lab> (34.5).GetType().Name
Double

A variable that holds nothing has no type, so asking it is an error: a misspelt $tikets.GetType() prints You cannot call a method on a null-valued expression. When you see that, check the spelling.

The names are .NET’s, the system PowerShell is built on. String is text. Int32 is a whole number: it is the very type that Session 4’s [int] makes, and int is just PowerShell’s short name for it. Double is a number that can have a decimal point, the type [double] makes. To ask a yes-or-no question instead, the -is operator tests whether a value is of a type, written in square brackets as in a conversion; [string] is the name for text:

yes or no: is it this type? · captured live
PS C:\Users\you\ps-lab> $n -is [int]
True
PS C:\Users\you\ps-lab> $t -is [int]
False
PS C:\Users\you\ps-lab> $t -is [string]
True

Now a value from a CSV file. Select-Object -First 1 keeps the first row, and its Total is text, as Session 4 said. Convert it once, store the number in a variable, and every later use of that variable is a number:

convert once, keep the number · captured live
PS C:\Users\you\ps-lab> $first = $orders | Select-Object -First 1
PS C:\Users\you\ps-lab> $first.Total
34.00
PS C:\Users\you\ps-lab> $first.Total.GetType().Name
String
PS C:\Users\you\ps-lab> $price = [double]$first.Total
PS C:\Users\you\ps-lab> $price.GetType().Name
Double
PS C:\Users\you\ps-lab> $price + 1
35

One more shape you will use in every loop: a variable can be worked out from its own old value. In $count = $count + 1, PowerShell first works out the right-hand side, using the value $count holds now, then stores the result back in $count:

counting up · captured live
PS C:\Users\you\ps-lab> $count = 0
PS C:\Users\you\ps-lab> $count = $count + 1
PS C:\Users\you\ps-lab> $count
1

C. Messages with values in them: single and double quotes

New window?If you closed PowerShell since the last section, type these first, in ps-lab: they store the variables this section uses. In the same window as before, you can skip them; typing them again does no harm. 
PS C:\Users\you\ps-lab> $orders = Import-Csv data/orders.csv
PS C:\Users\you\ps-lab> $tickets = Import-Csv data/tickets.csv
PS C:\Users\you\ps-lab> $tk = $tickets | Select-Object -First 1

Scripts print messages, and a message usually has a value in it. The way you already know is Session 4’s: with text on the left, + joins, so 'Open tickets: ' + $open.Count works. It gets clumsy fast with two or three values. The better way is double quotes. Text in single quotes is printed exactly as typed. Text in double quotes has every $variable in it swapped for the value it holds:

joining with +, then single and double quotes · captured live
PS C:\Users\you\ps-lab> $open = Import-Csv data/tickets.csv | Where-Object State -eq 'open'
PS C:\Users\you\ps-lab> 'Open tickets: ' + $open.Count
Open tickets: 3
PS C:\Users\you\ps-lab> $shop = 'Fernhill Goods'
PS C:\Users\you\ps-lab> 'Welcome to $shop'
Welcome to $shop
PS C:\Users\you\ps-lab> "Welcome to $shop"
Welcome to Fernhill Goods

That is why Sessions 1 to 4 always used single quotes: 'pending' and '*ERROR*' are meant exactly as typed. Use double quotes for a message with values in it.

The trap: a property inside double quotes. In double quotes, PowerShell swaps in only the variable; a .Customer after it stays plain text. So you get the whole row, written the way Session 4’s JSON depth trap wrote it, followed by .Customer. The fix is a subexpression, $( ): PowerShell works out whatever is inside the parentheses and puts the result in the text:

a property in a message, wrong then right · captured live
PS C:\Users\you\ps-lab> $first = $orders | Select-Object -First 1
PS C:\Users\you\ps-lab> "First order: $first.Customer"
First order: @{OrderId=5001; Date=2026-03-01; Customer=Ana Ruiz;             one line, wrapped here
Product=Cast iron pan; Qty=1; Total=34.00; Status=shipped}.Customer
PS C:\Users\you\ps-lab> "First order: $($first.Customer)"
First order: Ana Ruiz
PS C:\Users\you\ps-lab> "$($first.Customer) paid $($first.Total)"
Ana Ruiz paid 34.00
PS C:\Users\you\ps-lab> "Open tickets: $($open.Count)"
Open tickets: 3
PS C:\Users\you\ps-lab> "Two plus two is $(2 + 2)"
Two plus two is 4

The rule for messages: a plain variable goes in as $name; anything with a dot or a sum goes in as $( ).

D. Making a decision: if, elseif, else

New window?If you closed PowerShell since the last section, type these first, in ps-lab: they store the variables this section uses. In the same window as before, you can skip them; typing them again does no harm. 
PS C:\Users\you\ps-lab> $orders = Import-Csv data/orders.csv
PS C:\Users\you\ps-lab> $tickets = Import-Csv data/tickets.csv
PS C:\Users\you\ps-lab> $open = $tickets | Where-Object State -eq 'open'
PS C:\Users\you\ps-lab> $high = $tickets | Where-Object Priority -eq 'high'

A script often has to choose. if (TEST) { CODE } runs CODE only when TEST is True; TEST and CODE in capitals are placeholders for your own. TEST, in parentheses, is any comparison from Session 2, such as $open.Count -gt 2, and CODE goes in braces, a script block as in Session 2. When TEST is False, the block is skipped and nothing prints:

a test that passes, and one that does not · captured live
PS C:\Users\you\ps-lab> if ($open.Count -gt 2) { 'Busy day' }
Busy day
PS C:\Users\you\ps-lab> if ($open.Count -gt 5) { 'Busy day' }

Add else { CODE } for what to do when the test is False, and elseif (TEST) { CODE }, as many times as you need, for more choices in between. PowerShell checks the tests from the top and runs only the first block whose test is True; else runs only when none was:

two ways, then three · captured live
PS C:\Users\you\ps-lab> if ($open.Count -gt 5) { 'Busy day' } else { 'Quiet day' }
Quiet day
PS C:\Users\you\ps-lab> if ($open.Count -gt 5) { 'Busy day' } elseif ($open.Count -gt 2) {
  'Steady day' } else { 'Quiet day' }                                        one line, wrapped here
Steady day

Session 4’s trap, again. A test on a CSV column compares text unless you convert it. Order 5008 cost 82.00, yet as text it is “over 100”, because the character 8 comes after 1. Converted, the answer is right:

an if on a CSV value · captured live
PS C:\Users\you\ps-lab> $big = $orders | Where-Object OrderId -eq '5008'
PS C:\Users\you\ps-lab> $big.Total
82.00
PS C:\Users\you\ps-lab> if ($big.Total -gt 100) { 'Over 100' } else { 'Not over 100' }
Over 100
PS C:\Users\you\ps-lab> if ([double]$big.Total -gt 100) { 'Over 100' } else { 'Not over 100' }
Not over 100
PS C:\Users\you\ps-lab> if ($big.Status -eq 'pending') { "$($big.OrderId) is still pending" }
5008 is still pending

The rule: an if on a CSV column converts first, with [int] or [double], exactly as a filter or a sort did in Session 4. A block can hold any code, such as a message built with $( ), as the last command shows.

E. Doing it for each one: foreach

New window?If you closed PowerShell since the last section, type these first, in ps-lab: they store the variables this section uses. In the same window as before, you can skip them; typing them again does no harm. 
PS C:\Users\you\ps-lab> $tickets = Import-Csv data/tickets.csv

foreach ($o in $orders) { CODE } runs CODE once for each object in $orders, and each time round, $o holds the object it is on: the first order, then the second, and so on. Running the same code again and again like this is a loop, and $o is the loop variable. You choose its name; $o for an order reads well. Inside the braces, use it like any variable:

once for each order · captured live
PS C:\Users\you\ps-lab> $orders = Import-Csv data/orders.csv
PS C:\Users\you\ps-lab> foreach ($o in $orders) { $o.Customer }
Ana Ruiz
Ben Okafor
Chen Wei
Dara Singh
Eli Moss
Ana Ruiz
Femi Adeyemi
Gus Lind

Put an if inside a foreach and you have the shape most scripts are built from: for each one, decide, then act. And with section B’s counting up, a loop can keep a running total: start a variable at 0 before the loop, add to it each time round, and read it after:

decide inside a loop; keep a total · captured live

F. Your first script: a .ps1 file

Everything so far disappears when you close the window. A script is a plain-text file of PowerShell lines whose name ends in .ps1. Running it runs every line in it, top to bottom, as if you had typed them, and you can run it again tomorrow, or next month. Any plain-text editor can write one. Microsoft’s recommended editor for PowerShell scripts is VS Code (Visual Studio Code, a free code editor from Microsoft) with its PowerShell extension, an add-on that colours your code as you type and knows PowerShell’s commands.

Install it.

  1. VS Code. On Windows, in PowerShell: winget install --id Microsoft.VisualStudioCode --source winget (winget is the installer Session 1 used for PowerShell 7). On macOS and Linux, follow VS Code’s own pages: VS Code on macOS, VS Code on Linux. This workbook was checked on a Windows computer that already had VS Code, so the install steps are Microsoft’s, not run here.
  2. The PowerShell extension. In VS Code, open the Extensions view (Ctrl+Shift+X, or Cmd+Shift+X on a Mac), search for PowerShell, and install the one published by Microsoft. If VS Code’s code command works in your terminal, code --install-extension ms-vscode.powershell does the same.

Check before you change anything. Get-ExecutionPolicy prints the policy in force. With -List, it shows the policy set at each scope, from the most powerful at the top. MachinePolicy and UserPolicy are set by an organisation for its computers, through Windows’ Group Policy, and beat everything. Process is this window only, CurrentUser is your account, and LocalMachine is everyone on the computer. The first row, from the top, that is not Undefined is the one in force. # lab-report.ps1: ERROR lines per log, saved as a CSV, with a summary on screen.
$lab = "$HOME/ps-lab"
$summary = Get-ChildItem "$lab/logs" -Recurse -File | Select-String ERROR |
  Group-Object Filename | Sort-Object Count, Name -Descending |
  Select-Object @{ Name = 'Log'; Expression = { $_.Name } }, Count
$summary | Export-Csv "$lab/out/error-summary.csv" -Encoding utf8BOM

$total = 0
foreach ($row in $summary) {
  "$($row.Log): $($row.Count)"
  $total = $total + $row.Count
}
if ($total -gt 0) {
  "$total ERROR lines in all. Saved to out/error-summary.csv"
} else {
  'No ERROR lines today.'
}
