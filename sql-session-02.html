A. Add a column, then filter rows with WHERE

First, one change to your table. So far every column has a value in every row. Real data is messier: often a value is simply missing. To practice with that, we add a referrer column that records which existing customer referred each person, and we leave it empty for the two customers who signed up on their own.

Paste and run this in the Execute SQL tab, then click Write Changes. You will learn to write ALTER and UPDATE yourself in Level 4; for now, just run it:

-- add a new, empty text column to the existing table
ALTER TABLE customers ADD COLUMN referrer TEXT;

-- record who referred whom; ids 1 and 4 are left empty on purpose
UPDATE customers SET referrer = 'Amara' WHERE id IN (2, 3);
UPDATE customers SET referrer = 'Ben'   WHERE id = 5;

Now the real topic. In Session 1 the SELECT list chose which columns came back. The WHERE clause chooses which rows come back: it keeps only the rows for which its condition is true. It goes after FROM:

SELECT name, city FROM customers WHERE city = 'Austin';  -- only rows where city is Austin
result
name   city
Amara  Austin
Chen   Austin

Text values go in single quotes ('Austin'); numbers do not (40). A condition compares two things with a comparison operator:

  • = equal to  ·  <> not equal to (you may also see !=; <> is the standard spelling)
  • < less than  ·  > greater than  ·  <= less than or equal  ·  >= greater than or equal

Note that SQL uses a single = to test equality (not == as in many programming languages). A couple more:

SELECT name FROM customers WHERE monthly_fee > 20;   -- fee above 20: Amara, Chen, Esi
SELECT name FROM customers WHERE plan <> 'Pro';      -- plan is not Pro: Ben, Diego

One SQLite quirk to know: comparing text with = is case-sensitive, so city = 'austin' would match nothing here. (The LIKE operator in Concept C behaves differently, watch for it.)

B. AND, OR, NOT, and precedence

Combine conditions with the logical keywords AND (both must be true), OR (at least one is true), and NOT (flips a condition):

SELECT name FROM customers WHERE city = 'Austin' AND plan = 'Pro';  -- both true: Amara, Chen
SELECT name FROM customers WHERE city = 'Austin' OR city = 'Denver'; -- either condition is true
SELECT name FROM customers WHERE NOT plan = 'Pro';                   -- not Pro: Ben, Diego

Precedence matters. When a condition mixes AND and OR, AND is evaluated first (it binds more tightly), just like * before + in arithmetic. So this:

SELECT name FROM customers WHERE plan = 'Basic' OR city = 'Austin' AND signup_year = 2022;

is read as plan = 'Basic' OR (city = 'Austin' AND signup_year = 2022). The AND pair groups first, so it matches the two Basic customers (Ben, Diego) plus Chen (Austin and 2022): Ben, Chen, Diego. Add parentheses to force the other grouping and change the answer:

SELECT name FROM customers WHERE (plan = 'Basic' OR city = 'Austin') AND signup_year = 2022;

Now the OR group is required and the year must be 2022, so only Ben, Chen qualify. When in doubt, add parentheses to say exactly what you mean; they cost nothing and remove all ambiguity.

C. BETWEEN, IN, and LIKE

Three keywords make common conditions shorter and clearer.

BETWEEN a AND b matches values in a range, inclusive of both ends. It is exactly the same as >= a AND <= b, just tidier:

SELECT name FROM customers WHERE signup_year BETWEEN 2021 AND 2022;  -- 2021 through 2022, inclusive

IN (list) matches a value against a list of options. It is shorthand for a chain of OR equality tests:

SELECT name FROM customers WHERE city IN ('Austin', 'Boston');  -- shorthand for OR on each city

You can negate it with NOT IN (for example city NOT IN ('Austin', 'Denver') returns Diego). One caution for later: NOT IN behaves surprisingly when the list can contain NULL, a trap we cover in Level 3, so keep NOT IN lists to plain known values for now.

LIKE matches text against a pattern built from two wildcards: % stands for any run of characters (zero or more), and _ stands for exactly one character:

SELECT name FROM customers WHERE name LIKE 'A%';   -- starts with A: Amara
SELECT name FROM customers WHERE city LIKE '%n';   -- ends with n: Amara, Chen, Diego
SELECT name FROM customers WHERE name LIKE '_e%';  -- any 1 char, then e, then anything: Ben

A SQLite gotcha worth locking in: LIKE is case-insensitive for ordinary letters, so 'a%' would still match Amara. That is the opposite of plain =, which was case-sensitive. (In PostgreSQL LIKE is case-sensitive and you would use ILIKE for case-insensitive matching; MySQL matches SQLite's behavior by default.)

D. NULL and three-valued logic

NULL means missing or unknown. It is not zero, and it is not an empty string, it is the absence of any value. Two of our customers have a missing referrer (its value is NULL) because they signed up on their own.

Here is the part that surprises everyone. In SQL a condition is not just true or false, it can also be unknown. This is called three-valued logic (true, false, unknown). Any comparison with NULL produces unknown, never true, because you cannot say whether an unknown value equals anything. And WHERE keeps a row only when its condition is true. So this returns no rows at all, even though NULLs exist:

SELECT name FROM customers WHERE referrer = NULL;   -- 0 rows: "= NULL" is never true

The correct tests are the special operators IS NULL and IS NOT NULL, which ask directly whether a value is missing:

SELECT name FROM customers WHERE referrer IS NULL;      -- missing referrer: Amara, Diego
SELECT name FROM customers WHERE referrer IS NOT NULL;  -- has a referrer: Ben, Chen, Esi

This also means a plain inequality quietly skips NULLs. WHERE referrer <> 'Amara' returns only Esi, not the NULL rows, because NULL <> 'Amara' is unknown, not true. Whenever a column can be missing, decide on purpose whether to include the NULL rows, and use IS NULL / IS NOT NULL to do it. This behavior is the same across SQLite, PostgreSQL, MySQL and SQL Server, it is core SQL.

Your turn Find the missing values

Run SELECT name FROM customers WHERE referrer = NULL; and see that it returns nothing. Then run the same with IS NULL and confirm you get Amara and Diego. Feel the difference between the broken test and the correct one.

E. ORDER BY, LIMIT, and OFFSET

In Session 1 you learned that rows come back in no guaranteed order unless you ask for one. ORDER BY is how you ask. It sorts the result by one or more columns, ASC for ascending (the default, low to high, A to Z) or DESC for descending:

SELECT name, monthly_fee FROM customers ORDER BY monthly_fee DESC, name;
result · fee high to low, then name A to Z to break ties
name   monthly_fee
Amara  40
Chen   40
Esi    40
Ben    20
Diego  20

That query sorts on two keys: first by monthly_fee descending, then, for rows that tie on fee, by name ascending. Note that name has no direction word after it, so it uses the default, ASC. A direction applies only to the one key it follows, so the DESC here affects monthly_fee alone; name is really name ASC, you just do not have to type ASC. Extra keys only decide ties left over from the earlier ones, so reach for a tiebreaker whenever the first key has duplicates, otherwise the order among the tied rows is still not guaranteed.

Now that rows have a defined order, LIMIT becomes precise. LIMIT n keeps the first n rows of the sorted result, and OFFSET m skips the first m rows before that. Together they let you page through results:

SELECT name, monthly_fee FROM customers
ORDER BY monthly_fee DESC, name LIMIT 2;            -- top 2: Amara, Chen
SELECT name, monthly_fee FROM customers
ORDER BY monthly_fee DESC, name LIMIT 2 OFFSET 1;   -- skip 1, take 2: Chen, Esi

Two flags. First, on NULL ordering: SQLite treats NULL as the smallest value, so ORDER BY referrer puts the missing-referrer rows first in ascending order (PostgreSQL defaults the other way, NULLs last). Second, LIMIT / OFFSET is the syntax in SQLite, PostgreSQL and MySQL; SQL Server instead uses TOP or OFFSET ... FETCH.
