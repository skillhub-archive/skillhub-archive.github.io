Ship it, break it, fix it

There is almost nothing new here, and that is the point. Nine sessions handed you the pieces one at a time: branch, commit, merge, push, review, undo, recover, tag, search. This session runs them as one loop, on a project that is actually live, and then breaks it on purpose so that recovering stops being theory. The one genuinely new idea is small and it changes everything: on some repositories, git push is not a save, it is a release.

Milestone Maintain a real project end to end, and fix it when you break it.
git

You do not need any folder from an earlier session. Step one builds a fresh one called ship-lab, and it is disposable like the others. A new lab is needed here because this session is the only one where a push has to cause something to happen, which means the lab has to contain the thing that happens.

No account and no network, all the way to the end. The deploy target is a script on your own disk that you can open and read, which is a better teacher than a hosted pipeline because nothing about it is hidden. Section I shows the same loop against real GitHub Pages, with captured output for every claim that a capture can settle, and it is entirely optional: every task, the write-its and the comprehensive final can all be completed without an account.

Three sections ask you to break something deliberately, and each one puts it back. Section F breaks a heading on a practice page and section G reverts it, section G then makes a deliberately bad local commit and resets it away, and section H breaks the same heading a second way and reverts that too. All of it happens inside ship-lab. Nothing in this session touches any repository you actually use.

Part 1

Learn & Do

Short concept, then immediately your turn. This is the shortest teaching section on the track and the longest hands-on one, because by now you know the commands. What you are practising is running them as a sequence, under the mild pressure of something being live.

How to read the transcripts below. A line that starts with > in blue is what you type. Everything underneath it is what Git printed back. Do not type the > itself. Three things will legitimately differ on your machine: commit hashes (short strings like 52ca712), dates, and paths. Where a transcript shows a path under C:/Users/you/, that stands for your own home folder. The transcripts were captured in PowerShell. On Git Bash you will also see a warning: line about LF and CRLF after the git add and git commit -am steps, which is Session 1's line-ending note and is harmless. It comes from Git reading the file, not from the command that wrote it, which is why it lands on the commit rather than on the printf.

A. The whole track, as one loop

Write down what you would do to change something on a project other people can see. Not the commands, the steps. If you have been through the last nine sessions the answer is already in your head, and it looks like this:

branchWork somewhere that is not the branch everyone else depends on. Session 3.
commitSmall, described steps, so the history can be read later by somebody who was not there. Sessions 1 and 2.
push and
reviewGet it off your machine and in front of someone, then merge it with a strategy you can justify. Sessions 5 and 6.
tagMark what shipped, so "since the last good version" becomes something you can actually ask Git about. Session 9.
and when
it breaksDiagnose, then pick the recovery tool that matches who else already has the commit. Sessions 7, 8 and 9.

You are not here to learn those. You are here to run them once, in order, without a checklist, on something that is live, and to find out that the last row is the one deciding whether you feel comfortable or frightened. So this session teaches only three new ideas, all of them about the word "live", plus two small pieces of vocabulary noted where they appear (git hooks in section B, and the A..B commit range in section F):

  1. A branch can be a trigger. Pushing to one particular branch makes something happen outside Git.
  2. So push is not a save. On a repository wired that way, pushing is releasing, and that reframes every careful thing the last nine sessions told you.
  3. A deploy can fail in four different places, needing four different fixes. Beginners treat all four as one problem called "it did not work".

Out of scope, deliberately: writing CI/CD pipelines, GitHub Actions syntax, hosting configuration, Docker, environments and secrets management. This session teaches the Git side of shipping, which is what your own commands cause. The tooling that does the deploying is a separate subject and a large one, and you do not need any of it to understand the part that is yours.

B. Build the lab, and read the trigger

Session 5 built a bare repository to stand in for GitHub. This lab does the same and adds one file: a hook, which is a script Git runs automatically at a set moment. Put a script called post-receive in a bare repository's hooks folder and Git runs it every time a push lands there. That is the whole mechanism behind "I pushed and the site updated", minus a great deal of scale.

Hooks are the only new vocabulary here, and you only ever need to read one. Do not memorise the script. Read it once for what it decides, then forget the syntax: the decisions are the lesson.

PowerShell (Windows default) · build ship-lab
cd ~
mkdir ship-lab
cd ship-lab
git init --bare origin-repo.git
mkdir site

$hook = @(
  '#!/bin/sh',
  'DEPLOY_BRANCH=main',
  'LAB="$(cd "$(dirname "$0")/../.." && pwd)"',
  'while read old new ref; do',
  '  if [ "$ref" != "refs/heads/$DEPLOY_BRANCH" ]; then',
  '    echo "trigger: $ref is not the deploy branch, nothing to do"',
  '    continue',
  '  fi',
  '  echo "trigger: fired for $ref"',
  '  if git show "$new:index.html" | grep -q "<h1>"; then',
  '    git --work-tree="$LAB/site" checkout -f -q "$DEPLOY_BRANCH"',
  '    echo "deploy: published $(git rev-parse --short $new)"',
  '    git rev-parse --short $new >> "$LAB/deploy.log"',
  '  else',
  '    echo "build: FAILED, index.html has no h1 heading"',
  '    echo "deploy: skipped, the site still shows the previous version"',
  '  fi',
  'done'
)
Set-Content -Path 'origin-repo.git\hooks\post-receive' -Value $hook

git clone ./origin-repo.git project
cd project

cat > origin-repo.git/hooks/post-receive <<'HOOK'
#!/bin/sh
DEPLOY_BRANCH=main
LAB="$(cd "$(dirname "$0")/../.." && pwd)"
while read old new ref; do
  if [ "$ref" != "refs/heads/$DEPLOY_BRANCH" ]; then
    echo "trigger: $ref is not the deploy branch, nothing to do"
    continue
  fi
  echo "trigger: fired for $ref"
  if git show "$new:index.html" | grep -q "<h1>"; then
    git --work-tree="$LAB/site" checkout -f -q "$DEPLOY_BRANCH"
    echo "deploy: published $(git rev-parse --short $new)"
    git rev-parse --short $new >> "$LAB/deploy.log"
  else
    echo "build: FAILED, index.html has no h1 heading"
    echo "deploy: skipped, the site still shows the previous version"
  fi
done
HOOK
chmod +x origin-repo.git/hooks/post-receive

git clone ./origin-repo.git project
cd project

You now have four things in ship-lab: origin-repo.git, the bare repository standing in for the hosting service; site, an empty folder standing in for the live website; project, your working clone; and shortly a deploy.log the hook writes to. The clone printed warning: You appear to have cloned an empty repository, which is correct and expected here.

Read the script once, for its four decisions.

is this the
deploy branch?It compares the incoming ref against refs/heads/main. Anything else and it says so and stops. That single comparison is the whole of what makes a branch a trigger.
does the
build pass?It checks that index.html still contains an <h1>. A real pipeline runs a test suite instead; the shape is identical and only the check is bigger.
publishIt copies the committed files into site. That copy, and nothing else, is what "the live site" means in this lab.
leave a
recordIt appends the published hash to deploy.log. Section F is entirely about why that record earns its keep.
Two honest notes about hooks, so they do not surprise you later. First, hooks are not copied by git clone. They live in one repository's own hooks folder and travel with nothing: clone this bare repository and the copy holds only the .sample files Git ships. That is a deliberate safety decision, because a hook is a program, and cloning a repository should never run somebody else's programs. Second, Git's own documentation says "Hooks that don't have the executable bit set are ignored", which is why the Git Bash version runs chmod +x. Windows has no executable bit to set, so the PowerShell version needs no equivalent step, and that was confirmed by running it rather than assumed.

The tag reached the server and deployed nothing. That is worth sitting with, because it kills the most natural wrong model: it is not "pushing causes a deploy", it is "pushing this one ref causes a deploy". Everything else is an ordinary upload. A repository can have any number of branches and tags flying at it all day while exactly one of them is wired to the outside world.

The hook did not run, which almost always means it is in the wrong place or under the wrong name. D. So push is not a save, it is a release

This is the sentence to take away from the session. For nine sessions git push has been a way of getting work off your machine, closer to a backup than anything else. On a repository wired the way ship-lab now is, that is no longer what it means:

On a repository with a deploy trigger, git push to the trigger branch is a release. Not a save, not a backup, not "getting it off my laptop". The moment it lands, strangers are looking at it.

And now every careful thing the last nine sessions said makes sense at once. None of it was pedantry. Each piece was protecting this moment:

why branch
at allFeature branches are not tidiness. They exist so the trigger branch stays deployable while unfinished work still needs somewhere to live. Push a branch and nothing ships, which you just proved with the tag and will prove again in section E. Session 3.
why review
before mergeBecause merging into the trigger branch is the deploy decision. A pull request is not bureaucracy, it is the last point at which the release is still cheap to stop. Session 6.
why tagA tag turns "the last version that worked" from a memory into a name Git can compute against. That is what makes v1.1.0..main in section F possible at all. Session 9.
why revert
and not resetgit revert adds a commit that undoes another one, so it moves forward and never argues with anyone else's copy. On a deploy branch that is also the fastest fix, because a push is all it takes to ship the undo. Session 7.
why the
golden ruleSession 8's rule was "do not rewrite history somebody else already has". A deploy branch is the most-shared history there is, so it is exactly where rewriting hurts most, and exactly where the temptation is strongest, because rewriting looks tidier than admitting the mistake. Session 8.

The practical version, in one line: on a deploy branch you go forwards. Revert, fix, push again. You do not go back and edit what happened, because the outside world already saw it.

Now the decision Session 6 trained you for, with a reason attached. Three strategies were on the table there: a merge commit, a squash, or a rebase. On a branch that deploys, the squash has a specific and practical argument in its favour, and it is not about tidiness:

Why squash, here. A squash puts one commit on main per change that shipped. That matters because the deploy branch is the branch you will one day have to reason about under pressure: "which release broke this, and what do I revert?" One commit per change makes the answer one commit, and git revert takes one argument. A merge commit would also work and would preserve the two steps; a rebase would put both commits on main individually. Neither is wrong. What matters is that you can say why, which is the actual level milestone.
> git merge --squash add-rates
Auto-merging index.html
Squash commit -- not updating HEAD
Automatic merge went well; stopped before committing as requested
> git commit -m "Add the local and long distance rates"

> git push origin main

remote: deploy: published 354b0ea
To C:/Users/you/ship-lab/./origin-repo.git
   5d21a80..354b0ea  main -> main
Two details in that transcript, both real. One: those three lines come from two different streams. Auto-merging and Squash commit -- not updating HEAD are printed to standard output, while Automatic merge went well goes to standard error, so the order the three interleave in can differ from run to run and no ordering is a fault. That Git splits its output across two streams at all is worth knowing on its own: it is why piping a Git command somewhere can look like it lost half of what you saw. Two: git merge --squash deliberately stops before committing, which is why a separate git commit follows. Give that commit -m: Session 4 showed you what opens when you leave the message off, and this is one of the places it would.
The one step this lab cannot give you, said plainly. On a real hosted repository the merge above would happen through a pull request: you would open it, somebody would read the diff, and the merge button would offer you exactly the three strategies named here. A bare repository on your own disk has no pull request mechanism, so the offline path does the merge directly and you lose the review half. That half is not skipped on this track, it is Session 6, which ran the whole cycle against a real remote with captured output. If you have an account, section I is where the two rejoin. If you do not, Session 6 read alongside this section is the honest equivalent, and nothing later in this session depends on it.

F. Break it, then read the failure in four questions

Three more commits go onto main, and one of them is wrong. The middle commit removes the closing </h1> from the heading, which is the kind of mistake that looks like nothing in a diff and swallows an entire page in a browser. All three get pushed together, which is also realistic: people push a morning's work, not one commit.

> git push origin main
remote: trigger: fired for refs/heads/main
remote: deploy: published c17919e
To C:/Users/you/ship-lab/./origin-repo.git
   354b0ea..c17919e  main -> main
> Get-Content ..\site\index.html
<h1>Rate Tool
<p>Version 1.</p>
<p>Local rate: 145 per hour.</p>
<p>Long distance: 210 per hour.</p>
<p>Packing: 60 per hour.</p>
<p>Questions: dispatch@example.com</p>
<p>Office hours: 8 to 5.</p>
<p>Updated August 2026.</p>

It deployed, and it is broken, and the deploy reported success. Both of those are true at once and that combination is the normal case rather than an unlucky one. The hook did its job perfectly: it published what you gave it.

Here is the thing a beginner gets wrong. "The deploy is broken" is not one problem, it is four, and they are distinguished by where the chain stopped. Ask them in this order, because each one is cheap and rules out the next:

1. did the
push land?Is the commit actually on the server, or is it still sitting on your laptop? git fetch origin, and then git log --oneline -1 origin/main. The fetch is not optional, for the reason Session 5 gave: origin/main is only your own note of where the server was the last time you asked. Astonishingly often the answer here is no, because the push was rejected and the message scrolled past.
2. did the
trigger fire?The push landed, but did anything react? Here the evidence is the remote: block the push itself printed, where trigger: fired means it ran. On a hosted service it is the run list. If the trigger never fired, nothing about your code is the problem: you pushed the wrong branch, or the wiring is off.
3. did the
build fail?It fired, but did it finish? Again the push output is what says so, with a build: FAILED line. A failed build means the live site is untouched and still serving the last good version. That is a much better position than it feels like.
4. did it deploy
something broken?It fired, it succeeded, and the result is wrong. deploy.log is the evidence here, because the hook appends to it only on a successful publish: if its last line is the commit you just pushed, the site took your change. Now it is your code, and only now. This is the only one of the four where the fix is a commit.

Run questions one and four against the lab now. Two and three were answered by the push output you already read. Question three gets its own demonstration in section H, because you have not yet seen a build refuse.

The fetch printed nothing at all, which is itself the answer: there was nothing new to collect, so the note was already current. Question 1: yes, origin/main is at c17919e. Four cheap checks, and the problem is now precisely located: it is in a commit, and the commit is one of the three you just pushed.

An honest limit of a fifteen-line hook, and the one real argument for a hosted pipeline. This hook writes to deploy.log only when it actually publishes, so a build that failed and a hook that was never installed leave that file looking identical. Only the remote: block at push time tells those two apart, and that block scrolls away. A hosted service keeps a permanent record of every run and its outcome instead, which is exactly what section I shows: there, one glance separates a build that failed from one that was cancelled from one that never started at all. If you want the same thing here it is one more echo in the hook, writing a line before the build check rather than after it.

Which one? This is where the tag stops being decoration. You do not need to search the whole history, only what shipped since the last release you trust. The two dots are the one piece of new syntax in this section, so here is what they mean: A..B is "everything reachable from B that is not reachable from A", so v1.1.0..main reads as "the commits on main that the v1.1.0 release did not have". That is the notation which turns a tag into a question you can ask.

G. Fix it forward, and the two kinds of broken

The commit is shared. It is on the server, it deployed, and anyone could have pulled it. Session 7 and Session 8 gave you two families of answer, and this is the first time you have had to pick. The rule is not about which command you like:

shared
historySomebody else may already have this commit. Go forwards: git revert. It adds a new commit that undoes the old one, so nobody's copy is contradicted, and on a deploy branch the fix ships with the same push you were going to make anyway.
local
onlyThe commit has never left your machine. Remove it: git reset, with git reflog as the safety net. Nobody can be contradicted by history they never had, so there is nothing to preserve and no reason to leave a scar in the log.

So, the shared half. Revert the commit you found, push, and watch the site come back:

> git revert --no-edit 3b75017
Auto-merging index.html
[main f73ce04] Revert "Tidy the page heading"
 Date: Thu Aug 20 20:22:16 2026 -0500
 1 file changed, 1 insertion(+), 1 deletion(-)
> git push origin main
remote: trigger: fired for refs/heads/main
remote: deploy: published f73ce04
To C:/Users/you/ship-lab/./origin-repo.git
   c17919e..f73ce04  main -> main
> Get-Content ..\site\index.html
<h1>Rate Tool</h1>
<p>Version 1.</p>
<p>Local rate: 145 per hour.</p>
<p>Long distance: 210 per hour.</p>
<p>Packing: 60 per hour.</p>
<p>Questions: dispatch@example.com</p>
<p>Office hours: 8 to 5.</p>
<p>Updated August 2026.</p>

Look closely at what came back. The heading is fixed and "Updated August 2026" is still there, even though that commit came after the broken one. A revert is surgical: it undoes one commit's changes, not everything since. That is the property that makes it usable in an emergency, because you do not have to work out what collateral you are about to lose.

Use --no-edit. Session 4 covered what opens when you leave a message off, and git revert is one of the commands that would open it. Then tag the fix, because a fix is a release too:

> git tag -a v1.1.1 -m "Fix the broken heading"
> git push origin v1.1.1
remote: trigger: refs/tags/v1.1.1 is not the deploy branch, nothing to do
> git log --oneline -4
f73ce04 Revert "Tidy the page heading"
c17919e Add a last updated line
3b75017 Tidy the page heading
8755328 Add the packing rate

The mistake is still in the history and that is correct. Nothing was hidden, nothing was rewritten, and anyone who pulled the broken version gets the fix by pulling again rather than by being told their copy is wrong. That is what "go forwards" buys.

Now the other kind of broken. Same lab, different situation: a commit that never left your machine. git status -sb is the command that tells you which situation you are in, and it is the one worth building the habit around:

> git commit -am "Try something out"
[main 6ed62c8] Try something out
 1 file changed, 1 insertion(+), 8 deletions(-)
> git status -sb
## main...origin/main [ahead 1]
> git reset --hard origin/main
HEAD is now at f73ce04 Revert "Tidy the page heading"
> git log --oneline -2
f73ce04 Revert "Tidy the page heading"
c17919e Add a last updated line
> git reflog -3
f73ce04 HEAD@{0}: reset: moving to origin/main
6ed62c8 HEAD@{1}: commit: Try something out
f73ce04 HEAD@{2}: revert: Revert "Tidy the page heading"

[ahead 1] is the whole decision, printed for you. Ahead means you hold a commit the server does not, which means nobody else can possibly have it, which means resetting it away contradicts nobody. Had the bracket been absent altogether, printing just ## main...origin/main the way it does everywhere else in this session, the commit would already be shared and revert would be the answer instead. Git omits the bracket when there is nothing to report rather than printing a zero, so the thing to look for is the presence of the bracket, not a number inside it. One command distinguishes the two cases, and origin/main is the natural thing to reset to because it is the definition of what everyone else has.

And the discarded commit is not gone, as Session 8 promised: 6ed62c8 is sitting in the reflog. Resetting is safe on local work precisely because the reflog remembers what the branch forgot.

Your turn Fix both kinds, and feel the difference
  1. The shared half. Revert the commit you identified in the last task, with --no-edit. Push it. Confirm the site recovered and that the later good commit's line survived.
  2. Tag the fix v1.1.1 and push the tag.
  3. Run git log --oneline -4 and confirm the broken commit is still there. Say why that is right rather than untidy.
  4. The local half. Make a deliberately bad commit and do not push it. Run git status -sb and read the [ahead 1].
  5. Reset it away with git reset --hard origin/main, then find it again in git reflog. Confirm ..\site never changed at any point.
  6. The question that is the actual milestone. Write one sentence: what single fact decided which of the two tools you used? If your sentence mentions how bad the mistake was, or how recent, try again. There is only one fact that matters.
My git reset --hard origin/main threw away more than I expected.

Then you were more than one commit ahead, and --hard discarded all of them plus any uncommitted edits, exactly as Session 7 described. Everything committed is recoverable: git reflog, find the hash your branch was on before the reset, and git reset --hard <that hash> to put it back. Uncommitted edits are the exception and are genuinely gone, which is why git status before --hard is a habit worth having. Note also what --hard does not touch: untracked files survive it, because Git has no committed version of them to reset to.

H. The third answer: when the build refuses

Question three of the checklist has not happened to you yet, so make it happen once. The difference between "it deployed something broken" and "the build failed" is the difference between a live outage and a non-event, and reading the two apart in the moment is worth practising while nothing is at stake.

Break it in a way the build's own check catches. The hook only publishes if index.html still has an <h1>, so turn the heading into a paragraph and push:

> git commit -am "Make the heading a paragraph"
[main 0101d23] Make the heading a paragraph
 1 file changed, 1 insertion(+), 1 deletion(-)
> git push origin main
remote: trigger: fired for refs/heads/main
remote: build: FAILED, index.html has no h1 heading
remote: deploy: skipped, the site still shows the previous version
To C:/Users/you/ship-lab/./origin-repo.git
   f73ce04..0101d23  main -> main

Now run the same four questions and watch them land differently. The push landed and the trigger fired, exactly as before. What changed is the third and fourth answers:

> git log --oneline -1 origin/main
0101d23 Make the heading a paragraph
> Get-Content ..\deploy.log -Tail 3
354b0ea
c17919e
f73ce04
> Get-Content ..\site\index.html -TotalCount 1
<h1>Rate Tool</h1>

The evidence is the absence. deploy.log still ends at f73ce04, the previous commit, so nothing was published this time, and the live page still has its proper heading. Compare that against section F, where the log's last line was the commit you had just pushed. That comparison settles question four either way: if the log ends at your new commit, the site has your change and the problem is the change; if it ends earlier, the site never took it at all. What separates a failed build from a trigger that never ran is the push output rather than this file, which is the limit section F named, and here it is the build: FAILED line that settles it.

The counter-intuitive part is worth saying plainly. A failed build is good news compared to a successful one that published nonsense. Nobody outside ever saw it, the previous version is still serving, and you have as long as you like to fix it. The failure that hurts is the one that reports success. That is why the fourth question exists at all: three of the four leave the public site untouched, and only one of them is an outage.

Put the lab back. Revert and push, and the deploy recovers, which also demonstrates that the same forward-moving fix works whichever of the two happened:

> git revert --no-edit HEAD
[main 23ed988] Revert "Make the heading a paragraph"
 Date: Thu Aug 20 20:22:21 2026 -0500
 1 file changed, 1 insertion(+), 1 deletion(-)
> git push origin main
remote: trigger: fired for refs/heads/main
remote: deploy: published 23ed988
To C:/Users/you/ship-lab/./origin-repo.git
   0101d23..23ed988  main -> main
> git status -sb
## main...origin/main

No task box on this one, because it is one command and its opposite, and the tasks are already carrying the session. Run it anyway. It is the cheapest way to feel the difference the checklist is built on, and git status -sb printing nothing after the branch name is your confirmation that the lab is back where it started.

I. The same loop against real GitHub Pages (optional)

Everything in this section is optional and needs a GitHub account. Nothing later in the session depends on it: the drills, the write-its and the comprehensive final are all answerable from sections A to H. Read it even if you have no account, because it shows that the local hook was not a toy analogy, and it names the one place a hosted service tells you something the hook cannot.

GitHub Pages is a deploy trigger with the same shape. Point it at a branch and every push to that branch rebuilds the site. Two commands and a setting, done once:

> gh repo create <you>/deploy-lab --public
> gh api -X POST repos/<you>/deploy-lab/pages -f "source[branch]=main" -f "source[path]=/"

The second command is the whole wiring, and its reply names the address the site will appear at. Trimmed to the fields that matter:

{"html_url":"https://<you>.github.io/deploy-lab/","build_type":"legacy",
 "source":{"branch":"main","path":"/"},"status":null,"public":true}

"source" is the trigger, stated back to you: branch main, folder /. Serving a site from a private repository needs a paid plan, so a free account has to make the repository public, which is worth knowing before you wonder why nothing ever appears. That part is GitHub policy rather than something these captures show.

Then it behaves exactly like the lab. Pushing main starts a build; pushing a feature branch starts nothing. The captures below come from a throwaway repository built for this session and deleted afterwards, with the account and repository name replaced by <you> and deploy-lab:

> gh run list
STATUS  TITLE            WORKFLOW       BRANCH  EVENT    ID           ELAPSED  AGE
✓       pages build ...  pages-buil...  main    dynamic  32435197335  40s      about 15 m...
X       pages build ...  pages-buil...  main    dynamic  32434586535  35s      about 26 m...
X       pages build ...  pages-buil...  main    dynamic  32434565525  25s      about 26 m...
✓       pages build ...  pages-buil...  main    dynamic  32434500169  46s      about 27 m...
A gh transcript can never be exactly reproducible, and it is honest to say so once. gh lays its tables out to your terminal's width and truncates the columns to fit, so pages build ... is the tool abbreviating, not the output being cut here. It also prints relative ages, so about 15 m... becomes something else a minute later. Read the shape, not the spacing.

Four pushes, four runs, and the middle two both show X. They are not the same failure, and this is the one thing the hosted version teaches that the hook cannot:

The table does not tell you which is which, so ask for the conclusion directly. This is the command the previous note said to reach for:

> gh api repos/<you>/deploy-lab/actions/runs --jq '.workflow_runs[] | "\(.head_sha[0:7]) \(.conclusion)"'
43ba5e5 success
69305ae failure
b6169c1 cancelled
53e19d5 success
b6169c1:
cancelledA second push arrived twenty seconds after this build started, so GitHub abandoned the in-flight build and began again on the newer commit. Nothing was wrong with this commit at all. Note what the table above showed for it: a plain X, the same mark as a real failure.
69305ae:
failureA genuinely broken commit: an unterminated quote in a configuration file, so the build tool could not read its own settings. This is question three of the checklist, on a real service.

And the two surfaces disagree about the cancelled one. The Pages-specific summary for b6169c1 reported "status": "errored" with the message "Page build failed.", which is simply wrong: nothing failed, it was superseded. The Actions view above is the one that told the truth. Prefer the run conclusion over any summary status, or you will spend an afternoon debugging a commit that was never broken.

So go to the run itself rather than the summary. The log names the file, the line and the column, which is more than the local hook ever tells you. That output is abridged here: every real log line carries the job name, the step name and a full timestamp in front of the message, and the error arrives as one very long line, so the prefix is shown as ... and the message is wrapped to fit this page.

> gh run view 32434586535 --log-failed
build   Build with Jekyll   ... Error: (/github/workspace/./_config.yml):
found unexpected end of stream while scanning a quoted scalar
at line 2 column 14
Two practical notes if you try this. First, do not read too much into a single X: cancelled and failed are different events and only one of them is about your code, so check the conclusion, with the command shown above, before you start debugging something that was never broken. Second, this section deliberately shows only the deploy half. The pull request half of the loop is Session 6, which captured gh pr create, gh pr list and gh pr merge, along with all three merge strategies, against a real remote, so it is not repeated here. Run this section for the trigger and re-read Session 6 for the review, and between them you have the whole cycle on real hosting.

The point of the section, in one sentence: the hook in section B and GitHub Pages differ in scale, logging and polish, and not at all in the thing that matters, which is that one branch is wired to the outside world and pushing to it is a release.
