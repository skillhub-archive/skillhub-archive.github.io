A. Why an API paginates, and the two shapes it uses

In Session 1 you dropped the /1 from /posts/1 and got all hundred posts in one response. Session 1 called what comes next "Session 4’s problem", and this is it. A hundred posts is small. A real collection of orders, messages or customers can be millions of records, and handing those over in one response would be slow to build, slow to send, and more than any client wants at once.

So the server hands the collection out a slice at a time. That is pagination: each slice is a page, and the number of records in one slice is the page size. Fetching a whole collection then means asking for page after page until the server says there are no more. Every API that paginates has to answer two questions, and how it answers them is what separates the two shapes you will meet:

  • How do you ask for the next slice?
  • How do you know you have had the last one?

Shape 1, page numbers. You say which page you want and how big pages are: "page 3, ten per page". A close cousin is the offset, meaning "skip the first 20, then give me 10", which is the same idea counted in records instead of pages. You can jump straight to any page, and if the server tells you the total you can work out how many pages there are before you start.

Shape 2, cursors. Each page comes back with a cursor, a bookmark the server made for you that means "continue from here". To get the next page you send that bookmark back. A cursor is opaque, the word Session 3 used for API keys: you never read anything out of it or build one yourself, you copy it back exactly. That means you cannot jump to page 5. You can only reach page 5 by walking pages 1 to 4, because each page hands you the bookmark for the next.

Question
Page numbers against cursors
How you ask
Page numbers: a page number and a size you choose. Cursors: the bookmark from the previous response.
Can you jump ahead
Page numbers: yes, to any page. Cursors: no, only to the next one.
How you know you are done
Whatever the server uses to signal it. Sections B and C show one of each, and they are different.
When records change mid-walk
Page numbers: everything shifts. Cursors: the bookmark holds its place.

That last row is why cursors exist, so it is worth seeing once. Say you are walking ten per page and have just read page 1. Before you ask for page 2, someone adds a new record at the front. Every record moves back one place, so the record that was tenth, which you already read, is now eleventh, and page 2 hands it to you again. A deletion does the opposite and one record slides from page 2 onto page 1, which you have already left, so you never see it at all. Page numbers count positions, and positions move. A cursor marks a place in the data rather than a count, so it is not thrown off by what happens in front of it. That is why APIs over fast-changing data, feeds and message lists especially, tend to use cursors.

This session uses one service of each shape: jsonplaceholder pages by number (section B) and Wikipedia pages by cursor (section C).

B. Page numbers, on jsonplaceholder

jsonplaceholder takes two query-string parameters, the ?name=value pairs Session 1 taught: _page for the page number and _limit for the page size. The leading underscore is this service’s own spelling, not a standard. Other APIs say page and per_page, or limit and offset, and there is no rule about it, so this is the same lesson as Session 3’s key header names: the API’s documentation is the only authority. Ask for page 1, ten per page:

page 1 of the posts · the two headers that matter
> GET https://jsonplaceholder.typicode.com/posts?_page=1&_limit=10
200 OK
x-total-count: 100
link: <https://jsonplaceholder.typicode.com/posts?_page=1&_limit=10>; rel="first",
      <https://jsonplaceholder.typicode.com/posts?_page=2&_limit=10>; rel="next",
      <https://jsonplaceholder.typicode.com/posts?_page=10&_limit=10>; rel="last"

[ { "userId": 1, "id": 1, ... },  ... ten posts, ids 1 to 10 ... ]

The body is the array-of-objects shape from Session 1, only ten long now. The two headers are what make it walkable:

  • x-total-count is how many records the whole collection holds: 100. With ten per page, that is ten pages, worked out before you have asked for a second one.
  • link is one header listing ready-made URLs, each with a rel label, short for relation, saying how that URL relates to this page. first and last are the ends of the collection, next is the page after this one, and prev, which page 1 has no use for, is the page before. It is a single header, shown here broken across three lines so it fits; Postman shows it as one long line.

One thing about those angle brackets. Session 3 used <token> as a stand-in for a value you supply. These are not that. In a link header the angle brackets are real characters the server sends, wrapping each URL so the rel after it cannot be mistaken for part of the address. Session 3’s convention still holds everywhere else on this page; inside a link header the brackets are literal.

Now the last page, which is where the "how do you know you are done" question gets answered:

page 10 · look at which rel is missing
> GET https://jsonplaceholder.typicode.com/posts?_page=10&_limit=10
200 OK
x-total-count: 100
link: <https://jsonplaceholder.typicode.com/posts?_page=1&_limit=10>; rel="first",
      <https://jsonplaceholder.typicode.com/posts?_page=9&_limit=10>; rel="prev",
      <https://jsonplaceholder.typicode.com/posts?_page=10&_limit=10>; rel="last"

[ ... ten posts, ids 91 to 100 ... ]

There is no next. That absence is the server telling you this is the end, and it is the signal to stop on. And if you ask past the end anyway:

page 11 · past the end, and still a 200
> GET https://jsonplaceholder.typicode.com/posts?_page=11&_limit=10
200 OK
x-total-count: 100
link:

[]

An empty array and a blank link, with a 200. Nothing went wrong, there is simply nothing there. Plenty of APIs do this, so an empty page is the other common stop signal, and a client that keeps going until it gets an error will never stop.

Now the trap that makes page numbers dangerous, and it is not in any documentation. Use the wrong parameter names, the ones a different API would have wanted:

plausible names, wrong for this service · and no complaint at all
> GET https://jsonplaceholder.typicode.com/posts?page=2&limit=10
200 OK

[ ... one hundred posts, ids 1 to 100 ... ]

A 200, no error, and all hundred posts starting from id 1. The server did not recognise page or limit, so it ignored them silently and answered as if you had sent neither. The same happens with the right names in the wrong case: _Page=2&_LIMIT=10 also comes back with all hundred, because parameter names here are case-sensitive. A 200 means the server answered, not that it understood your parameters. The tell is in the body: you asked for page 2 and the first id is 1. This is Session 2’s habit, read the whole response before deciding what happened, catching a bug that the status line cannot.

C. Cursors, on Wikipedia

Wikipedia’s API answers on a single URL, https://en.wikipedia.org/w/api.php, and you say what you want entirely in the query string. It is long, so here it is one parameter at a time, before you see it whole:

Parameter
What it says
action=query
"I want to read something."
format=json
"Answer in JSON."
list=categorymembers
"List the pages filed under one category." The other parameters for this list all start with cm, for category members.
cmtitle=Category:Hypertext_Transfer_Protocol
Which category: the one for HTTP itself, which is why the titles below look familiar.
cmlimit=20
The page size: twenty per page.

The request is shown on two lines to fit; type it as one URL with no spaces. The cursor is cmcontinue, inside an object called continue, and you can see why the word opaque fits. Do not try to read it. To get page 2, send the identical request with one more parameter, cmcontinue, set to exactly that value:

A new cursor, different from the last. Each page hands you the bookmark for the next one and nothing else, so there is no way to ask for page 3 without having read page 2. Send page 3 with the new value:

page 3 · compare its top-level keys with pages 1 and 2
> GET ...&cmlimit=20&cmcontinue=page|56322c302a54030656322c302a54011101e0c0e0c4dcdcdc|179849
200 OK
{
  "batchcomplete": "",
  "query": {
    "categorymembers": [ ... eight titles, "WebDAV" to "Category:Web server software" ... ]
  }
}

No continue object at all. That is Wikipedia’s stop signal, and notice it is a different signal from jsonplaceholder’s missing rel="next", in a different place: the body rather than a header. That is the general lesson about cursors: every API signals the end in its own way, and the documentation tells you which. The rule underneath does not change: keep going while the server hands you a way to continue, and stop the moment it does not.

What must match yours, and what need not. On 2026-10-01 this walk took three pages, 20, 20 and 8, and one of the last eight titles was "Webhook", which is Session 7. Wikipedia’s editors add and remove pages from categories, so your counts, titles and cursor values may differ. What will not differ is the shape: a continue object on every page but the last, and none on the last.

And a cursor you made up? Replace the cursor with something that was obviously never issued, page|zzzz|1, and send it:

a forged cursor · read past the status line
> GET ...&cmlimit=20&cmcontinue=page|zzzz|1
200 OK
{
  "error": {
    "code": "badcontinue",
    "info": "Invalid continue param. You should pass the original value returned by the previous query."
  }
}

A 200 wrapping an error. Wikipedia reports this problem in the body and leaves the status at 200, the opposite habit from NASA in Session 3, which at least changed the status to 403. It is the strongest argument yet for reading the body every time. The message says the rest: the only valid cursor is one the server gave you.

Now the more dangerous case. Change a single hex digit near the end of a real cursor and Wikipedia usually does not complain at all: it answers 200 with a normal-looking page of titles, just not the page you were owed. Building this session, a cursor with its last hex digit changed came back starting at "Webhook", partway through page 3, so a walk using it would have silently skipped titles. A refused cursor is the lucky outcome; an edited one that is accepted hands you the wrong slice of data and says nothing. That is the practical reason behind "opaque": never edit, shorten or build a cursor, only copy one back exactly.

Two details, so they do not trip you. The cursor contains | characters; Postman sends them as they are and Wikipedia accepts them, so paste the value unchanged. And the continue object holds a second field, "continue": "-||", which Wikipedia uses for more complex queries than this one. For this list, sending cmcontinue alone was verified to work, and that is all this session asks you to send. Wikipedia’s own documentation puts the opacity rule plainly: you "should not manipulate or depend on any specifics of the values returned inside the continue element, as they may change."

D. Rate-limit headers, and which service is telling the truth

Session 2 named the X-RateLimit- group as the one piece of header plumbing that is genuinely about you, and Session 3 showed you a counter that really counts. Walking pages multiplies your requests, so this is where those numbers start to matter. As a reminder, they come in three:

  • X-RateLimit-Limit, how many requests the allowance holds;
  • X-RateLimit-Remaining, how many are left;
  • X-RateLimit-Reset, when the allowance refills. On jsonplaceholder that is a Unix timestamp, a count of seconds since midnight UTC on 1 January 1970, which is how computers commonly write a moment in time. Any "Unix timestamp converter" turns it into a date.

The four services on this track tell four different stories about rate limits, and only one of them is a live count you can act on:

Service
What its rate-limit headers are worth
jsonplaceholder
Present, and not counting anything you can use. Most answers are stored copies, so the numbers are frozen at whatever they read when the copy was stored. Shown below.
api.nasa.gov
Real, and shared. They count down as requests are spent, as Session 3 showed, but per network address, so they count your whole address, not you.
postman-echo
None at all. It sends no rate-limit headers, yet it will hand you a 429 on demand, which section E uses.
Wikipedia
None in these responses either. Which is not the same as no limit: Wikipedia does refuse clients that send too much, with a real 429.

The jsonplaceholder story is worth seeing for yourself, because it is the one that would mislead you. Here is the same page requested three times, a second or so apart:

three identical requests · watch Remaining, Reset and Age
> GET https://jsonplaceholder.typicode.com/posts?_page=3&_limit=10
date: Thu, 01 Oct 2026 14:10:32 GMT
x-ratelimit-limit: 3600000
x-ratelimit-remaining: 3599997
x-ratelimit-reset: 1790812826
age: 25289

> GET https://jsonplaceholder.typicode.com/posts?_page=3&_limit=10
date: Thu, 01 Oct 2026 14:10:34 GMT
x-ratelimit-remaining: 3599997                  <- has not moved
age: 25291

> GET https://jsonplaceholder.typicode.com/posts?_page=3&_limit=10
date: Thu, 01 Oct 2026 14:10:35 GMT
x-ratelimit-remaining: 3599997                  <- still has not moved
age: 25292

Three things in there each say "do not trust me". The first is the one to rely on, because the other two depend on how old the cached copy happens to be when you ask:

  • Remaining never moved. Eighteen requests sent while building this session, six each to three different URLs, did not move a single counter: each URL stayed frozen at its own value. A counter that does not count is not a counter.
  • age: 25289 is about seven hours. Session 2 taught that Age is how long a stored copy has been sitting in a cache. A copy that is seven hours old carries a seven-hour-old counter. Yours may be much younger, and even a fresh copy stays frozen once it is stored.
  • The reset is in the past. 1790812826 converts to Thu, 01 Oct 2026 00:00:26 GMT, fourteen hours before the date on the same response. An allowance cannot be due to refill at a time that has already gone by. A freshly stored copy can carry a reset in the future, so this sign comes and goes; the frozen counter does not.

One more piece of evidence, from your own track. Session 2 recorded this service’s limit as 1000. Today it says 3600000. Nothing about your requests changed; the cached headers did. So the rule from Session 2 still stands and now has its reason spelled out: on a cached public service, rate-limit headers are something to recognise, not a count to act on. The habit worth taking to a real API is to check Age before believing any counter: a response a cache has been holding for hours cannot tell you about the request you just sent.

And the services with no headers? postman-echo and Wikipedia simply do not send them. That does not mean they will serve you without limit; it means they are not telling you the count. No header is not permission to hammer, and section F is how to behave when you cannot see the number at all.

E. After a 429: how long, and whether to retry at all

Session 3 showed you a real 429 Too Many Requests from NASA, with Retry-After: 22797. That told you what running out looks like. This section is what you do next, and it comes down to two questions you answer from the response, in order: should this request be retried at all, and if so, how long should you wait first.

First, which failures are worth retrying. A retry sends the identical request again, so it only helps when the problem is on the server’s side and temporary. When the problem is in your request, the same request fails the same way every time:

Code
Retry it?
Why
429
Yes, after waiting
Nothing is wrong with the request. You sent too many too quickly, and the same request will succeed once you have slowed down.
503
Yes, after waiting
Service Unavailable: the server is overloaded or down for a moment. Temporary by definition, and it may carry a Retry-After of its own.
400
No
Bad Request: the server could not make sense of what you sent. Sending it again unchanged gets the same answer.
401 / 403
No
Session 3’s pair. A missing or wrong credential is still missing or wrong a second later; fix the credential.
404
No
Nothing is at that URL, and waiting will not put anything there.

Second, how long to wait. If the response carries Retry-After, that is the answer, and it overrides any schedule of your own. It comes in two forms, and you should be able to read both:

a number of secondsRetry-After: 120
a date and timeRetry-After: Thu, 01 Oct 2026 14:05:00 GMT

The first is the form NASA used. The second means "not before this moment", and to turn it into a wait you subtract the response’s own Date header from it, not the clock on your computer, which may be off. A response dated 14:03:00 GMT carrying the date form above means wait two minutes.

And sometimes there is no Retry-After at all. MDN’s page for 429 says the header "may be included", and may is the honest word. postman-echo will give you a 429 on demand, costing nothing and spending no shared quota, and it is a real example of the bare kind:

a 429 with nothing to tell you how long
> GET https://postman-echo.com/status/429
429 Too Many Requests
content-type: application/json; charset=utf-8
content-length: 14

{ "status": 429 }

No Retry-After, and no rate-limit headers either. The server has told you to slow down and not by how much, so the waiting schedule is now yours to choose, and section F is how to choose it well. Two honesty notes about this endpoint: it is a simulated 429, sent because the URL asked for one rather than because you used anything up, and it will answer 429 however long you wait, so it is for reading, never for practising a retry against.

To see a Retry-After on your own screen without spending anything, postman-echo has an endpoint that sends back whatever response header you name in the query string:

a Retry-After header, made to order · and a 200, so not a real limit
> GET https://postman-echo.com/response-headers?Retry-After=5
200 OK
retry-after: 5

{ "Retry-After": "5" }

That is the header exactly as a real server would send it, though the status is 200 because nothing was actually limited. It is there so you know where to look on the Headers tab, not to stand in for a real refusal.

One request you must never retry blindly, which is Session 8’s whole subject. Everything above is safe for a GET, which only reads. A POST that timed out may have created the thing before the answer was lost, and sending it again can create a second one. jsonplaceholder cannot show you this, because it persists nothing. Session 8 covers the pattern that makes a retried write safe; until then, retry reads, always with backoff, and never retry writes.

F. Backing off instead of hammering

When a retry is the right call and the server has not said how long to wait, the tempting move is to try again straight away, and keep trying until it works. That is the one move guaranteed to make things worse, and the arithmetic shows why better than any warning can.

The naive loop. Say a server is overloaded for 30 seconds, and your client retries every tenth of a second until it gets through. That is 300 requests from you, every one refused. Now remember you are rarely the only client. If a thousand clients do the same, the struggling server receives 300,000 requests in the half minute it most needs quiet, which can keep it overloaded long after it would otherwise have recovered. A crowd of clients retrying in a tight loop is called a retry storm, and it is a classic way a brief outage becomes a long one.

Exponential backoff is the fix. Wait before each retry, and double the wait after every failure: one second, then two, then four, then eight. Against the same 30-second outage:

0s
First request fails. Wait 1 second.
1s
Retry 1 fails. Wait 2 seconds.
3s
Retry 2 fails. Wait 4 seconds.
7s
Retry 3 fails. Wait 8 seconds.
15s
Retry 4 fails. Wait 16 seconds.
31s
Retry 5 succeeds, because the outage ended at 30 seconds.

Six requests instead of 300, and you got through only one second after the earliest possible moment. That is the whole bargain: you trade a little speed at the very end for asking fifty times less of a server that is already in trouble. Three refinements turn the idea into something you would actually ship:

  • A cap. Doubling grows fast: the tenth wait would be over eight minutes. So set a ceiling, and once the doubled wait would pass it, wait the ceiling instead. With a 20-second cap, the waits go 1, 2, 4, 8, 16, 20, 20.
  • A limit on attempts. Decide in advance how many retries you will make, five is common, and after that stop and report the failure. A loop that never gives up is still a loop that hammers, only more slowly.
  • Jitter. If a thousand clients all failed at the same instant and all back off by the same schedule, they all retry at exactly 1 second, then exactly 3, in lockstep, and the storm arrives in synchronised waves. Jitter means adding a little randomness to each wait, for example waiting any amount between zero and the computed wait, so the crowd spreads out instead of arriving together.

And Retry-After beats all of it. When the server tells you how long, wait that long, even if your schedule would have tried sooner. Backoff is for when you have to guess.

Postman will not back off for you, and this track does not program a client that does, so today backoff is something you reason about and plan. What Postman can do is the gentler half of the same idea: when it runs a whole collection, it can wait a fixed delay between requests, so you never send them in a burst in the first place. Pacing prevents a 429; backoff is how you respond to one. You set that delay in section G.

G. A free account, a collection, and a run that walks every page

Everything so far, you did by hand: one request, read it, change a number, send again. A collection is Postman’s name for a saved, named group of requests, and once requests are saved together Postman can run them for you, as many times as you like, with different values each time. That is how you walk a whole dataset without clicking ten times. It is also the first thing on this track that Postman has to keep for you, which is why the account arrives now.

Step 1, the account. In the no-account client, look for the button offering to sign in or create an account (it usually sits at the top of the window), and choose to create one. Postman typically offers email or an existing Google account; either is fine. The plan you want is the free one. It should not ask for payment details; if a screen does, you are on a paid-plan page, so go back. Once signed in you land in a workspace, which is just the space your collections live in.

From here on, what you save leaves your machine. A signed-in Postman syncs your collections to Postman’s servers, which is what makes them reachable from anywhere. That makes Session 3’s section G rules real rather than practice: never save a real credential into a request. Nothing in this session uses one, so there is nothing to leak today.

Step 2, a collection with one request in it. Create a new collection and name it, say, S4 pagination. Postman’s menus have moved between versions, so look for the word "New" or a plus sign, then "Collection". Add a request to it and give it this URL:

the requestGET https://jsonplaceholder.typicode.com/posts?_page={{page}}&_limit=10

{{page}} is a variable, Session 3’s double-curly-brace reference: a name standing in for a value supplied somewhere else. This time the value comes from a file, one row per run. Save the request into the collection.

Step 3, a check on every page. Open the request’s Scripts tab and its Post-response section (older versions call this tab Tests), the code Postman runs after each response arrives. Most versions offer a list of ready-made snippets beside it; choose the one named along the lines of "Status code: Code is 200". If yours has no list, paste this line, which is the same check that snippet inserts, written on one line:

a status check · fails loudly on anything that is not a 200
pm.test("Status code is 200", function () { pm.response.to.have.status(200); });

It is a line of JavaScript, but you do not need to write any: it is a test, which says "this response should have status 200" and is reported as passed or failed. This is what makes a run trustworthy. A page that comes back 429 in the middle of a run then shows up as a failure, instead of quietly being counted as a page of data. You will watch it fail in step 6.

Step 4, the data file. A data file is a plain text file that hands the run one set of values per pass. In a CSV, short for comma-separated values, the first line holds the variable names and every line after it is one pass. You only need one column, so there are no commas at all:

Ten rows, because section B already told you there are ten pages: x-total-count: 100 at ten per page, or the rel="last" URL ending _page=10. Reading the size of the walk off the first response, then building the file, is the whole technique. The column name must match the variable exactly, case included, which Postman’s documentation states plainly: page in the file and {{page}} in the URL.

Windows, NotepadFile > Save As, set "Save as type" to All files, name it pages.csv (if file extensions are hidden, check it did not become pages.csv.txt)
macOS, TextEditFormat > Make Plain Text first, then save as pages.csv (if it asks, choose Use .csv)

Step 5, run it, paced. Open the collection’s Run option, which opens what Postman calls the Collection Runner. Select pages.csv as the data file; Postman reads it, and the number of passes, which it calls iterations, becomes ten, one per row. Look for a delay setting and give it 500 milliseconds: that is the pacing from section F, a half-second gap so ten requests do not go out in a burst. Then run.

Click into the last iteration and check its link header: no rel="next", so the file was the right size. At time of writing, Postman’s free plan does not cap how many of these runs you make; older plans did, and plans change, so if Postman ever tells you that you have hit a run limit, that is the reason.

Two traps worth knowing before you hit them.

  • Every request in the collection runs once per row. Put a second request beside the first and a ten-row file sends it ten times too. Keep a walking collection to the one request that walks.
  • A mistyped variable still comes back green. If the URL says {{Page}} and the file says page, Postman has no value for {{Page}} and sends the literal text. jsonplaceholder ignores a page number it cannot read, exactly as in section B, so every iteration returns 200 with posts 1 to 10. Ten passed tests and ten copies of page 1. The status check cannot catch this. Two other things can: the ids, and the link header, which still says rel="next" on the last iteration, the very check from step 5.

Step 6, watch the check catch a 429. In the same request, temporarily change the URL to https://postman-echo.com/status/429 and press Send, not Run, so it goes once. Open the Test Results tab: the status check has failed, naming the 429 it got. That is the rate-limit response being caught rather than swallowed. Change the URL back and save.

Optional, not graded: following a cursor automatically. Read this only if you are curious; it is the one place this session shows code you would have to understand to change.

A data file works for page numbers because you know every page number before you start. It cannot work for a cursor, because page 2’s cursor does not exist until page 1 has answered, which is section A’s point turned into a practical limit. The way through is a post-response script that reads the cursor and tells the Runner to send the same request again. This was verified against the section C walk with Postman’s command-line runner: three pages, then it stopped on its own.

// URL ends ...&cmlimit=20&cmcontinue={{cmcontinue}}
// and the collection has a variable cmcontinue, starting empty
const body = pm.response.json();
if (body.continue) {
  // more to come: keep the bookmark, and send this request again
  pm.collectionVariables.set("cmcontinue", body.continue.cmcontinue);
  pm.execution.setNextRequest(pm.info.requestName);
} else {
  // no continue object: last page, so clear the bookmark and stop
  pm.collectionVariables.set("cmcontinue", "");
}

An empty cmcontinue asks Wikipedia for the first page, which is why the variable starts empty. Postman’s documentation is explicit that setNextRequest only takes effect in a collection run, never on a single Send.

H. The milestone: a full dataset, and a plan for when it pushes back

The milestone is a collection that pulls a whole paginated dataset and handles a rate-limit response gracefully. Gracefully has two halves, and you have now done both: the run is paced and checked, so a 429 is caught rather than counted as data, and you can say exactly what you would do about one instead of trying again at once.
