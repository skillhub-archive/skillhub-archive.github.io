A. What an API actually is

An API (Application Programming Interface) is a defined way for one piece of software to ask another piece of software to do something or hand over some data, over the internet, using a shared set of rules both sides agree on. A weather app on your phone does not know how to read weather balloons; it sends a request to a weather company's API and gets back a JSON message describing today's forecast. Your bank's app does not store your balance on your phone; it asks the bank's API every time you open it.

This track is specifically about web APIs that speak HTTP, the same protocol your browser uses to load a page. That is not a coincidence: a web API is built on exactly the same request/response exchange as browsing the web, just carrying data meant for a program instead of a page meant for a human.

Two roles, and the vocabulary for them, used throughout this whole track:

  • Client: whatever sends the request. Today that is you, driving a tool called Postman. Later it could be a phone app, a website, or another server.
  • Server: whatever receives the request, does the work, and sends back a response. Today that is a public practice API that exists specifically to be sent test requests.

The whole exchange has a name worth learning now because it explains the shape of everything else in this session: the request/response cycle. The client sends one request; the server sends back exactly one response to it. Nothing happens outside that pair until the client sends another request.

Client
Sends a request: a method, a URL, and sometimes headers and a body.
→request
Server
Does the work: looks something up, saves something, checks something.
→response
Client
Gets back a status code, headers, and usually a body, then decides what to do next.

The two practice services this session uses are both free, public, and built by their owners specifically for people to send test requests to, so nothing here needs a key, a login, or a real-world account:

  • postman-echo.com, run by the Postman team. Whatever you send it, it sends straight back to you as JSON, which makes it the clearest possible way to see exactly what a request looked like.
  • jsonplaceholder.typicode.com, a free fake REST API of blog-style posts. Reads return real, consistent data; writes are accepted and answered convincingly but nothing is actually saved on their server.

B. Installing Postman, and sending a request with no setup at all

Postman is a free application built for exactly this: composing a request by hand, sending it, and reading back what happened, without writing any code. It is the real environment for this whole track.

  • Windows, macOS or Linux: go to postman.com/downloads and download the installer for your system, then run it.
  • Any system, no install at all: the same page offers Postman in a web browser instead, which works the same way for everything this session covers.

Open Postman and you will land on a sign-in screen. You do not need an account for this session. Look for a smaller, less prominent option below the main sign-in buttons, worded along the lines of "skip" or "continue without an account" (the exact wording has changed across Postman's own history, so read the small print rather than the button color). Taking that path drops you into what Postman calls its lightweight API client: you can build and send requests, and see your history, entirely without signing in, and everything you do stays on your machine.

One honest limit worth knowing now rather than discovering it mid-session: without an account you cannot save requests into named Collections or share them, and Level 3 of this track (designing your own mocked API) does need a free account for its Mock Server feature. Today does not, so it is fine to defer that signup until then.

Once you are in, find the button that starts a new request, usually labelled + or New. It opens one row with a method dropdown (defaulted to GET) on the left and a URL field taking up the rest of the row, and a Send button on the right. That row is the entire request for now. Paste this URL in and press Send:

your first request · GET, sent from Postman
> GET https://postman-echo.com/get?greeting=hello
200 OK
{
  "args": { "greeting": "hello" },
  "headers": { "host": "postman-echo.com", "user-agent": "PostmanRuntime/...", "accept": "*/*",
                "accept-encoding": "gzip, br", "x-forwarded-proto": "https" },
  "url": "https://postman-echo.com/get?greeting=hello"
}

Read what just happened: you asked postman-echo for that exact URL, and it answered by handing your own request straight back to you as JSON, so you can see precisely what left your machine. args is the part of the URL after the ?, called a query string, parsed into a key and a value. headers lists the extra information Postman attached automatically, including user-agent, which is every HTTP client's way of identifying what sent the request (yours will say Postman; a browser's says the browser). The other two headers, accept-encoding and x-forwarded-proto, are worth naming once and then ignoring: they are routine plumbing (compression support, and the fact that postman-echo sits behind a proxy) that every request carries automatically and that no task in this track ever asks you to read. Postman shows you the same information in its own Headers and Body tabs under the response, which is worth a look now so you know they exist.

Your turn Install Postman and send your first request
  1. Install Postman (or open it in a browser), and skip past sign-in into the no-account lightweight client.
  2. Start a new request, leave the method on GET, paste in https://postman-echo.com/get?greeting=hello, and press Send.
  3. Find the status (it should read 200 OK) and the response body below it, and confirm your greeting comes back inside args.

C. The anatomy of a request: method, URL, and headers

Every request you will ever send has the same three parts, and you have already used two of them.

The method is a word that states your intent, sent as the very first thing in the request. Five matter for this track, and this session uses the first two:

  • GET: fetch something. Never changes anything on the server. You used this in section B.
  • POST: create something, or trigger an action. Section F below.
  • PUT, PATCH, DELETE: replace, partially update, and remove something. Named here so you recognise them; Session 3 is where you use them.

The URL is where the request goes, and it has a shape worth splitting apart once: a scheme (https://), a host (postman-echo.com, which computer answers), a path (/get, which thing on that computer), and an optional query string (?greeting=hello, extra key/value filters tacked onto the end after a ?, with additional pairs joined by &).

Headers are extra information riding alongside the method and URL, as key/value pairs, describing the request rather than being the point of it. Postman attaches several for you automatically, which is what you saw echoed back in section B. You can also add your own in Postman's Headers tab, directly under the URL bar. Add one now:

the same request, with one header you added yourself
> GET https://postman-echo.com/get?greeting=hello
> header:  X-Learner: your-name-here
200 OK
{
  "args": { "greeting": "hello" },
  "headers": { "host": "postman-echo.com", "user-agent": "PostmanRuntime/...", "accept": "*/*",
                "accept-encoding": "gzip, br", "x-forwarded-proto": "https", "x-learner": "your-name-here" },
  "url": "https://postman-echo.com/get?greeting=hello"
}

Your header comes back inside headers exactly like the automatic ones, in lower case; HTTP header names are case-insensitive, so the server treats X-Learner and x-learner as the same thing, and postman-echo happens to print them lower case. Two headers you will meet by name later in this track and are worth having seen once: Content-Type, which describes the shape of a request or response body (section F below sends one), and Authorization, which carries proof of who you are (Session 3).

Your turn Add a header and watch it come back
  1. In your GET request from section B, open the Headers tab and add a key of X-Learner with your own name as the value.
  2. Send it again and find your header echoed back inside headers in the response, in lower case.

D. Reading a response: the status code

Every response leads with a status code, a three-digit number that tells you, before you read a single character of the body, roughly what happened. You have already seen 200. The first digit sorts every status code into one of five families:

1xx
Informational
rare, mostly invisible to you
2xx
Success
it worked
3xx
Redirection
go look elsewhere
4xx
Client error
your request was the problem
5xx
Server error
their end broke

Four exact codes are worth knowing by number now, because you will meet all four by name across this track:

  • 200 OK: the general-purpose success code. Most GET requests that work return this.
  • 201 Created: success, and specifically something new now exists because of this request. Section F below gets one.
  • 404 Not Found: the client error for "there is nothing at that URL". Worth its own line: 404 does not mean broken, it means asked-for-a-thing-that-is-not-there, and it is entirely normal to hit one on purpose while testing.
  • 500 Internal Server Error: the server hit a bug or crashed while handling your request. The one status family that is never your fault to fix.

postman-echo has a small endpoint (a single specific URL path on an API, built to do one job, the way /status/:code is about to do here) built exactly for practising this, that returns whatever status code you ask it for in the URL, with a matching JSON body:

asking for specific status codes on purpose
> GET https://postman-echo.com/status/201
201 Created
{ "status": 201 }

> GET https://postman-echo.com/status/404
404 Not Found
{ "status": 404 }

Notice both of those "worked" in the sense that Postman got an answer back and did not error; a 404 is a completely normal, successful round trip that happens to be reporting bad news. Confusing "the request completed" with "the outcome was good" is a common beginner mix-up, and separating them now avoids it. A real "something actually broke" failure in Postman looks different again: no status code at all, and an error like Could not get response, which means the request never reached a server, usually a typed-wrong URL or no internet connection.

Your turn Request three different outcomes on purpose
  1. Send GET https://postman-echo.com/status/201 and note the status and body.
  2. Send GET https://postman-echo.com/status/404 and note the status and body.
  3. Send GET https://postman-echo.com/status/500 and note the status and body.
  4. Say out loud which family (2xx/4xx/5xx) each one belongs to before checking your notes.

E. JSON: the shape almost every response takes

JSON (JavaScript Object Notation) is a plain-text way of writing structured data, and it is what almost every modern web API sends back. You have already been reading it since section B. Its whole grammar is four things:

  • Objects: { }, holding "key": value pairs separated by commas. Every key is a string in double quotes.
  • Arrays: [ ], an ordered list of values separated by commas. A value in an array has no key of its own, only a position.
  • Values: a string in double quotes, a number with no quotes, true/false, null (meaning "no value"), or another object or array, nested inside. That nesting is what lets JSON describe something with structure, not just a flat list of fields.
  • Whitespace between all of that is cosmetic. Postman's "Pretty" view adds indentation for you to read; the bytes that actually cross the network have none of it.

Send a GET to a real resource on jsonplaceholder and read a real object:

a single practice "post" · a real object with five fields
> GET https://jsonplaceholder.typicode.com/posts/1
200 OK
{
  "userId": 1,
  "id": 1,
  "title": "sunt aut facere repellat provident occaecati excepturi optio reprehenderit",
  "body": "quia et suscipit\nsuscipit recusandae consequuntur expedita et cum\nreprehenderit molestiae ut ut quas totam\nnostrum rerum est autem sunt rem eveniet architecto"
}

Four keys, all inside one object, no nesting or arrays yet: userId and id are numbers (no quotes), title and body are strings (quoted). The \n characters inside body are an escaped line break sitting inside one JSON string, not four separate lines; Postman's Pretty view renders it as one paragraph with breaks.

Drop the /1 and you get every post back at once, which is where arrays enter the picture: a top-level [ ] holding a hundred objects shaped exactly like the one above, back to back. Pagination, meaning fetching a huge collection like this a page at a time instead of all at once, is Session 3's problem, not today's; for now the shape is what matters, an array of objects, each object built from the same keys.

Ask for a post that does not exist and you get the 404 family from section D, JSON-shaped:

asking for a post id that was never created
> GET https://jsonplaceholder.typicode.com/posts/9999
404 Not Found
{}

An empty object, {}, is still valid JSON: zero keys, not an error in the JSON itself. The 404 status is what tells you the request failed; the empty body is simply this particular API's way of saying "nothing to show you".

Your turn Read real fields out of a real response
  1. Send GET https://jsonplaceholder.typicode.com/posts/1 and find the value of userId.
  2. Send GET https://jsonplaceholder.typicode.com/posts/1 again with just the number changed to 7. Note its title.
  3. Send GET https://jsonplaceholder.typicode.com/posts/9999 and confirm you get 404 and an empty object.

F. Sending a POST: a request with a body

A GET asks for something and carries no body. A POST usually carries one: data you are sending TO the server, most often to create something. In Postman, switch the method dropdown from GET to POST, then open the Body tab, choose raw, and set the type dropdown next to it to JSON. That last step matters more than it looks: choosing JSON there is what sets a header called Content-Type: application/json on your request, which is how you tell the server "the text I am sending you should be parsed as JSON." Send the wrong Content-Type, or none, and a real API may refuse to parse a body that is otherwise perfectly good JSON.

Type this into the Body tab and send it to postman-echo first, since it echoes back exactly what arrived:

POST with a JSON body, to the echo service
> POST https://postman-echo.com/post
> header:  Content-Type: application/json
> body:
{ "title": "hello", "body": "world" }

200 OK
{
  "args": {},
  "data": { "title": "hello", "body": "world" },
  "files": {},
  "form": {},
  "headers": { "host": "postman-echo.com", "user-agent": "PostmanRuntime/...", "accept": "*/*",
                "accept-encoding": "gzip, br", "x-forwarded-proto": "https",
                "content-type": "application/json", "content-length": "37" },
  "json": { "title": "hello", "body": "world" },
  "url": "https://postman-echo.com/post"
}

data and json both show your body parsed back as an object, which is postman-echo proving it understood what you sent, and headers confirms content-type: application/json made it across. args, files and form come back empty: they are postman-echo's slots for a query string, an uploaded file, and an HTML form submission, and this request used none of those, only a JSON body. Notice the status is a plain 200 here: postman-echo's whole job is echoing, not creating a resource, so it never has anything to report as newly Created.

Now send the same idea to jsonplaceholder, which plays along with actually creating something:

POST with a JSON body, to a fake-create endpoint
> POST https://jsonplaceholder.typicode.com/posts
> header:  Content-Type: application/json
> body:
{ "title": "foo", "body": "bar", "userId": 1 }

201 Created
{
  "title": "foo",
  "body": "bar",
  "userId": 1,
  "id": 101
}

This time the status is 201 Created, from section D: something new exists as a direct result of this request. The response body hands back everything you sent, plus a new id the server assigned. One honest caveat about this particular practice API, so it does not mislead you: jsonplaceholder answers every POST convincingly, including the new id, but nothing is actually persisted on its servers; send that same GET for post 101 afterwards and you will get a 404, not the post you just "created". That trade-off is exactly why it is a safe place to practice writes, and Session 3 covers services where a write genuinely sticks.

Your turn Send a POST with a JSON body
  1. Switch a request to POST, point it at https://postman-echo.com/post, set the Body tab to raw JSON, and send { "title": "hello", "body": "world" }. Confirm your body comes back inside both data and json.
  2. Point the same body at https://jsonplaceholder.typicode.com/posts instead, send it, and confirm you get 201 Created with an id added.

G. The milestone: predict, then send

This is the Session 1 milestone, and the point of it is the prediction, not the clicking. Before every single request, say out loud what you expect the status code and body to look like. Then send it and check yourself.

Your turn The milestone: three requests, all predicted first
  1. Predict, then send GET https://jsonplaceholder.typicode.com/posts/3. What status, and what does the title field hold?
  2. Predict, then send GET https://postman-echo.com/status/500. What family is 500 in, and whose fault is it, yours or the server's?
  3. Predict, then send a POST to https://postman-echo.com/post with body { "learner": "your-name-here" } and header Content-Type: application/json. Which two keys in the response hold your data back?

Part 2

Predict the Output

This is the whole track in miniature: work out what the response will hold before you send the request, type your answer, then check. Do not send it first, committing to a guess is what builds the model. Each drill tells you the shape of answer it wants, a single value, a count, or a list. They get harder toward the end, and after you check you can reproduce any of them in Postman.

Unless a drill says otherwise, assume this starting point: a fresh request against one of this session's two practice services, with no special headers beyond what Postman adds automatically. Where a drill needs something to have happened first, it is shown in the grey already sent box.
