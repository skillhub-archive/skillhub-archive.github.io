A. From a dict + a function to a class

In Session 3 you stored one job as a dictionary, and in Session 4 you wrote a standalone function like total_with_tax(job) that took that dict and computed a number. The data lived in one place and the behavior in another, connected only by you remembering to pass the right dict to the right function. A class closes that gap: it is a blueprint for a kind of thing that bundles the data together with the functions that act on it, in one named type.

Five words to name up front, because the rest of the session uses them constantly:

  • A class is the blueprint (the kind of thing, e.g. "a Job").
  • An object, also called an instance, is one specific thing built from that blueprint (e.g. Amy's particular job).
  • An attribute is a piece of data stored on an instance (the customer name, the price).
  • A method is a function defined inside the class and called on an instance (it acts on that instance's data).
  • Instantiation is the act of creating an instance from the class.

Here is a Job class with one attribute pair and one method:

class Job:                              # define the blueprint, named with a capital by convention
    def __init__(self, customer, price):   # runs automatically when you create a Job
        self.customer = customer        # store this Job's customer on the instance
        self.price = price              # store this Job's price on the instance
    def total(self):                    # a method: a function that lives on the class
        return self.price * 1.1         # price plus 10% tax, using THIS instance's price

Two pieces need naming. __init__ (two underscores each side, said "dunder init") is a special method Python runs for you at instantiation to set the object up. And self is the first parameter of every method: it is the instance the method is working on, so self.price means "this particular Job's price". You never pass self yourself; Python fills it in.

Now instantiate and use it. Calling the class like a function runs __init__:

j = Job("Amy", 100)     # instantiation: build one Job, __init__ stores "Amy" and 100
print(j.customer)       # read an attribute off the instance -> Amy
print(j.total())        # call a method on the instance -> 110.00000000000001
print(round(j.total(), 2))   # round it for clean money -> 110.0

Notice j.total() returns 110.00000000000001, not 110.0. That is the same float wobble you met in Sessions 1 and 4: 100 * 1.1 cannot be stored exactly in binary. So any method that reports money should round or format it, exactly as before, with round(value, 2) or an f-string to two decimals.

B. __init__ and self, up close, plus a default argument

__init__ runs once, automatically, at instantiation. You do not call it by hand; Job("Amy", 100) triggers it. Its job is setup: take the arguments and attach them to the instance with self.name = value. Because each instance carries its own attributes, two Jobs made from the same class hold different data:

a = Job("Amy", 100)
b = Job("Lee", 300)
print(a.price, b.price)     # each instance kept its own -> 100 300

You can give __init__ a default argument, the same idea as Session 4: a parameter with a fallback value used when the caller leaves it out. Here the tax rate defaults to 0.1 but can be overridden per Job, and the method reads it from self:

class Job:
    def __init__(self, customer, price, rate=0.1):   # rate defaults to 0.1 if not given
        self.customer = customer
        self.price = price
        self.rate = rate                # store the rate on the instance too
    def total(self):
        return self.price * (1 + self.rate)   # uses this Job's own rate

print(round(Job("Amy", 100).total(), 2))        # default rate 0.1 -> 110.0
print(round(Job("Lee", 300, 0.2).total(), 2))   # rate overridden to 0.2 -> 360.0

C. Readable objects with __repr__

Print a Job right now and you get something unhelpful:

print(j)     # with no __repr__ defined -> <__main__.Job object at 0x000001F2...>

That is Python's default: the class name and a memory address, which tells you nothing about the Job and even changes run to run. You fix it by defining a special method named __repr__ that returns a string. Python calls it whenever it needs to show the object, including inside a list:

class Job:
    def __init__(self, customer, price):
        self.customer = customer
        self.price = price
    def __repr__(self):
        return f"Job({self.customer!r}, {self.price})"   # build a readable line

The !r inside the f-string means "use the repr form of this value", which for a string wraps it in quotes. So the customer shows as 'Amy' with quotes (the way you would type it) rather than bare. Now the object prints usefully, and a list of Jobs shows each one:

j = Job("Amy", 100)
print(j)                                  # -> Job('Amy', 100)
print([Job("Amy", 100), Job("Lee", 300)]) # the list uses __repr__ per item -> [Job('Amy', 100), Job('Lee', 300)]

D. Inheritance: a specialized RushJob

Suppose a rush job is a Job that costs the same but adds a flat fee. You could copy the whole class, but inheritance lets one class build on another. class RushJob(Job): makes RushJob a subclass of Job: it automatically gets all of Job's attributes and methods, and you only add or change what is different. The quick sanity check is the is-a test: use inheritance when the subclass truly is a kind of the parent. A rush job is-a job, so this fits, and the built-in isinstance(object, ClassName) confirms that relationship at runtime, returning True when the object is that class or any subclass of it.

Two tools do the work. super() reaches the parent class, so super().__init__(...) runs Job's own setup instead of repeating it, and then you add the new attribute. And overriding means defining a method again in the subclass to replace the inherited one; inside it, super().total() reuses the parent's result so you extend rather than rewrite:

class RushJob(Job):                       # RushJob is-a Job (subclass)
    def __init__(self, customer, price):
        super().__init__(customer, price) # run Job's own __init__ first
        self.rush_fee = 50                # then add what is new to RushJob
    def total(self):                      # override Job's total
        return super().total() + self.rush_fee   # reuse Job's math, add the fee

r = RushJob("Sam", 200)
print(r.rush_fee)              # the new attribute -> 50
print(round(r.total(), 2))     # 200*1.1 then +50 -> 270.0
print(isinstance(r, Job))      # is r a Job? -> True

isinstance(r, Job) is True because a RushJob is-a Job. But there is an honest wrinkle. In the version above RushJob defines no __repr__, so it inherits Job's, which is hard-coded to say "Job":

print(r)     # RushJob with no __repr__ inherits Job's -> Job('Sam', 200)

That is misleading: r is a RushJob but prints as a Job. Inherited special methods are real and will surface like this, so the fix is to give RushJob its own __repr__ that names it correctly. That is the version you will build, so it never lies about what it is:

    def __repr__(self):
        return f"RushJob({self.customer!r}, {self.price})"   # now print(r) -> RushJob('Sam', 200)

E. The milestone: model a domain with a list of objects

Now put it together the way real code does. In Session 3 you held a list of dict records; here you hold a list of objects, mixing plain Jobs and RushJobs. One loop calls total() on each, and each object runs its own version, the plain calculation for a Job, the fee-added one for a RushJob. Writing one loop that handles different types because each knows its own behavior is called polymorphism, and it is the everyday payoff of classes. After the loop, the built-in sum(...) (which adds up numbers) totals every job:

jobs = [Job("Amy", 100), RushJob("Sam", 200), Job("Lee", 300)]
for job in jobs:
    print(job.customer, round(job.total(), 2))   # each uses its own total()
Amy 110.0
Sam 270.0
Lee 330.0
print(round(sum(x.total() for x in jobs), 2))    # add every total -> 710.0

That last line feeds x.total() for each job in the list (the same comprehension style from Session 3) into sum, then rounds the grand total. If you prefer, a plain accumulator loop that keeps a running grand = grand + job.total() works just as well.
