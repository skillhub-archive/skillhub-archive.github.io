A. First, so it never scares you: the pager

The moment you run git log or git diff on anything real, the output is longer than one screen, and Git hands it to a pager: a little full-screen reader called less that shows one screenful and waits. Your normal typing stops working, and to a newcomer that looks exactly like a freeze. It is not. Git is simply waiting for you to read.

  • Press q to quit the pager and get your prompt back. This is the one you will use constantly.
  • Press the space bar or the arrow keys to scroll through the output.
  • If you would rather the output just print straight to the terminal with no pager at all, put --no-pager right after git, once: git --no-pager log. Good for a quick glance, or when you want to copy the text.

That is the whole trick. Whenever a Git command seems to hang with a coloured bar or a : at the bottom of the screen, you are in the pager. Press q.

C. What HEAD actually points at

Session 1 gave you a one-line placeholder for HEAD and promised the real explanation here. This is it, because everything else in this session refers to it.

HEAD is a reference to the commit you are currently on. It does not usually point straight at a commit, though. It points at the current branch (main, for you), and the branch points at a commit. So the full chain is HEAD → main → the newest commit. That is exactly what the label (HEAD -> main) in your log has been telling you all along: HEAD is here, by way of main. Branches are Session 3; for now, HEAD means "where I am standing right now", which in a fresh repository is the newest commit.

The useful part is that you can count backwards from HEAD without ever typing a hash:

HEADthe commit you are on: 9a0306d Add alpha
HEAD~1one commit back (its parent): 4f3a8d5 Add a second line of notes
HEAD~2two commits back: 23ec62a Add notes.md
HEAD^the parent, identical to HEAD~1: 4f3a8d5 Add a second line of notes

So HEAD~1 is "one step back along the parent pointer", HEAD~2 is two steps, and so on. HEAD^ (a caret) is an older way to write the parent and means the same thing as HEAD~1. You will meet both in tutorials, which is why both are named here. These names work anywhere a command wants a commit: you will feed them to git show and git diff in a moment.

And that quirk from Session 1, now that HEAD is the topic. The (HEAD -> main) label only appears when Git is printing to a terminal for a human to read. If you pipe git log into another command or redirect it into a file, Git strips the label so the output stays clean and machine-readable. Nothing broke: Git just decides the decoration is for humans, not for programs.

D. Open one commit: git show

git log lists commits. git show opens a single one and shows you everything about it: who, when, the message, and the exact changes it made. Point it at any commit by hash, or by one of the HEAD names you just learned.

git show HEAD · the newest commit, in full
> git show HEAD
commit 9a0306d97763b27e34b274cc3bdd8e1aad82f571 (HEAD -> main)
Author: Ada Lovelace <ada@example.com>
Date:   Tue Jul 28 14:17:08 2026 -0500

    Add alpha

diff --git a/alpha b/alpha
new file mode 100644
index 0000000..7898192
--- /dev/null
+++ b/alpha
@@ -0,0 +1 @@
+a

The top half is the commit itself: its full hash, the author and date stamped on it, and the message. The bottom half, starting at diff --git, is what the commit changed. Here it created alpha, so Git shows the whole file as added: --- /dev/null means "there was no old version", and the +a line is the one line the file gained. You will read that diff shape properly in section F; for now, notice that git show hands you the change for free.

Two everyday variations. git show HEAD~1 opens the commit one step back instead of the newest. And if you only want the summary, not every changed line, add --stat:

git show --stat HEAD · just the summary of what changed
> git show --stat HEAD
commit 9a0306d97763b27e34b274cc3bdd8e1aad82f571 (HEAD -> main)
Author: Ada Lovelace <ada@example.com>
Date:   Tue Jul 28 14:17:08 2026 -0500

    Add alpha

 alpha | 1 +
 1 file changed, 1 insertion(+)

The alpha | 1 + line means "the file alpha, one line changed, and it was an addition". The little bar of + and - marks grows with the size of the change. This --stat summary is the same one you will see on git log --stat next.

E. Shaping git log to answer a question

git log --oneline from Session 1 is the workhorse. The rest of log is a set of flags that each answer a different question about the history. You do not need them all memorised; you need to know they exist so you can reach for the right one.

How much to show. -n 2 (or just -2) limits the log to the newest 2 commits, however many the repository has:

git log -n 2 --oneline · just the two newest
> git log -n 2 --oneline
9a0306d (HEAD -> main) Add alpha
4f3a8d5 Add a second line of notes

What each commit changed. --stat adds the changed-files summary to every commit; -p (short for --patch) goes further and shows the actual added and removed lines. Here is -p on just the newest commit:

git log -p -1 · the newest commit, with its changes
> git log -p -1
commit 9a0306d97763b27e34b274cc3bdd8e1aad82f571 (HEAD -> main)
Author: Ada Lovelace <ada@example.com>
Date:   Tue Jul 28 14:17:08 2026 -0500

    Add alpha

diff --git a/alpha b/alpha
new file mode 100644
index 0000000..7898192
--- /dev/null
+++ b/alpha
@@ -0,0 +1 @@
+a

The shape of the history. --graph draws a text diagram down the left edge:

git log --oneline --graph
> git log --oneline --graph
* 9a0306d (HEAD -> main) Add alpha
* 4f3a8d5 Add a second line of notes
* 23ec62a Add notes.md

On a straight line of commits like yours it is just a column of dots, so it looks like a lot of nothing. Its value shows up once history splits and rejoins, which is branching and merging, Session 3 and Session 4. It is introduced here so you recognise it when it matters.

Filtering to what you care about. Three filters do most of the work:

  • --grep=notes keeps only commits whose message contains that text. In your sandbox two messages mention notes, so two lines come back: 
    > git log --grep=notes --oneline
4f3a8d5 Add a second line of notes
23ec62a Add notes.md
  • --author="Ada Lovelace" keeps only commits by that person. Your sandbox has one author, so it returns all three; in a shared project this is how you see one person's work. Dates use --since and --until, for example git log --since=2026-03-01 --until=2026-04-01, which keeps commits made in that window. On a one-day-old sandbox they are not interesting, but you will use them for real on the multi-author repository in this session's milestone.
  • -- notes.md keeps only commits that changed one file. The -- is a separator: it tells Git that everything after it is a path (a file or folder name), not a branch or a flag. alpha was added in its own commit and never touched notes.md, so it drops out: 
    > git log --oneline -- notes.md
4f3a8d5 Add a second line of notes
23ec62a Add notes.md

One optional nicety. If you want the who, when, and what all on one line, --pretty=format lets you lay it out. You do not need to memorise this; just recognise the pieces when you see it:

a custom one-line format: short hash, author, date, message
> git log --pretty=format:"%h  %an  %ad  %s" --date=short

%h is the short hash, %an the author name, %ad the date, and %s the message (its "subject"). --date=short trims the date to YYYY-MM-DD. The result is one tidy row per commit, which is a handy way to eyeball who did what and when.

Your turn Read your history three ways

All in the sandbox. Before each command, say what you expect, then run it and check.

  1. Run git show HEAD, then git show HEAD~1. Confirm the second one is the commit before the first, and remember HEAD^ would give you the same thing as HEAD~1.
  2. Run git log --stat, then git log -p. Watch how -p shows the actual lines. Use q to leave the pager each time.
  3. Run git log --oneline --graph and notice the dots down the side.
  4. Run git log --grep=notes --oneline and git log --oneline -- notes.md. Notice they can return different commits, because one filters by message and the other by which file changed.

F. Seeing changes: git diff across the three areas

This is the heart of the session, and it maps exactly onto the three areas from Session 1: working tree (the files as you see them), staging area (what git add put on the shortlist), and the last commit. A diff is just a comparison of two of those, and which two you compare is set by how you call git diff:

Working tree
Your files right now.
↔git diff
Staging area
What you have added.
↔git diff --staged
Last commit
HEAD.
  • git diff compares the working tree against the staging area: changes you have made but not yet staged.
  • git diff --staged compares the staging area against the last commit: what you have staged and would commit next. (--cached is an older name for the exact same thing; you will see it in tutorials, so know they are identical.)
  • git diff HEAD skips the staging area and compares the working tree against the last commit: everything that has changed since you committed, staged or not.

These three genuinely differ, and the cleanest way to feel it is to set up a file with a staged change on one line and an unstaged change on a different line. Do this in your sandbox. First replace notes.md with three known lines and commit, so there is a clean starting point:

PowerShellSet-Content notes.md "Git sandbox`nCreated while learning Git.`nSafe to delete."
Git Bash / macOS / Linuxprintf 'Git sandbox\nCreated while learning Git.\nSafe to delete.\n' > notes.md

Then git add notes.md and git commit -m "Rewrite notes as three lines". Now make two changes: edit line 2 and stage it, then edit line 3 and leave it unstaged. (Edit in your editor, or reuse the write-the-whole-file commands above with the new text.) The staged line becomes Created while learning Git, in session 2. and the unstaged line becomes Safe to delete anytime. Here is what each diff then shows.

git diff · working tree vs staging: only the UNSTAGED line 3
> git diff
diff --git a/notes.md b/notes.md
index b332d6f..336ccf9 100644
--- a/notes.md
+++ b/notes.md
@@ -1,3 +1,3 @@
 Git sandbox
 Created while learning Git, in session 2.
-Safe to delete.
+Safe to delete anytime.

Now read that diff, because the shape is the same every time:

  • The first two lines (diff --git ... and index ...) are Git's header naming the file. The two short codes on the index line are internal fingerprints; ignore them, and expect them to differ on your machine.
  • --- a/notes.md is the old side of the comparison, +++ b/notes.md is the new side.
  • @@ -1,3 +1,3 @@ is the hunk header. It says this chunk covers lines 1 to 3 on the old side and lines 1 to 3 on the new side, so you know where in the file you are looking.
  • A line with a leading space is unchanged context, shown so you can see the surroundings. A line starting with - was removed, a line starting with + was added. Those are removed and added lines, not minus and plus in the arithmetic sense.

So plain git diff shows only line 3, the change you did not stage. Compare the other two:

git diff --staged · staging vs last commit: only the STAGED line 2
> git diff --staged
diff --git a/notes.md b/notes.md
index 0a62d83..b332d6f 100644
--- a/notes.md
+++ b/notes.md
@@ -1,3 +1,3 @@
 Git sandbox
-Created while learning Git.
+Created while learning Git, in session 2.
 Safe to delete.
git diff HEAD · working tree vs last commit: BOTH changes
> git diff HEAD
diff --git a/notes.md b/notes.md
index 0a62d83..336ccf9 100644
--- a/notes.md
+++ b/notes.md
@@ -1,3 +1,3 @@
 Git sandbox
-Created while learning Git.
-Safe to delete.
+Created while learning Git, in session 2.
+Safe to delete anytime.

Three calls, three answers, and now you can predict which is which: git diff is what is left to stage, git diff --staged is what is ready to commit, and git diff HEAD is the full picture since the last commit. This is the habit worth building: run git diff --staged right before you commit, so you always know exactly what you are about to record.

G. .gitignore, and why it cannot hide what you already committed

Session 1 warned that git add . can sweep up files you never meant to commit, and named .gitignore as the real fix. Here it is. .gitignore is a plain text file in the root of your repository, listing the files and folders Git should pretend it cannot see. It is itself committed, so everyone who clones the project ignores the same things.

The rules are simple: one pattern per line.

  • *.log ignores every file ending in .log (the * means "any name").
  • node_modules/ ignores a whole folder; the trailing / means "a directory".
  • !keep.log un-ignores one thing; a leading ! negates a pattern, carving out an exception to a broader rule above it.

Watch it work in the sandbox. Create a throwaway log file, and notice git status lists it as untracked along with beta:

two untracked files cluttering status
> git status
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	beta
	debug.log

nothing added to commit but untracked files present (use "git add" to track)

Now create .gitignore with two lines, *.log and beta (that is what to do with the leftover beta from Session 1: tell Git you are deliberately not tracking it). Run git status again and both are gone, leaving only .gitignore itself to commit:

after adding .gitignore · the ignored files vanish from status
> git status
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore

nothing added to commit but untracked files present (use "git add" to track)

Commit .gitignore (git add .gitignore then git commit -m "Add .gitignore") and the tree is clean. So far so good. Now the gotcha that catches everyone.

.gitignore only affects files Git is not already tracking. A file that is already in a commit keeps being tracked no matter what you add to .gitignore. Prove it: alpha is already tracked. Add a line alpha to your .gitignore, then edit alpha and run git status:

alpha is in .gitignore, yet Git still tracks its changes
> git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   alpha

no changes added to commit (use "git add" and/or "git commit -a")

Git ignored the .gitignore line completely, because alpha was already tracked. To actually stop tracking it, you need the command you first saw as a hint in a Session 1 status message: git rm --cached.

git rm --cached · stop tracking, but keep the file on disk
> git rm --cached alpha
rm 'alpha'
> git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	deleted:    alpha

Read that word carefully. Git says deleted: alpha, but your file alpha is still sitting right there in the folder. deleted here means "removed from Git's tracking", not "removed from your disk". The --cached part is exactly what protects the file on disk: it removes only Git's copy in the staging area, not your working copy. Commit that and, combined with the .gitignore line, alpha is both untracked and ignored from now on. (For the rest of the session you want alpha back to normal, so you can skip committing this last step, or just re-add it; nothing here changed notes.md.)

H. What must never be committed

This is the one place a Git mistake can genuinely hurt you, so it gets its own section. Never commit secrets: passwords, API keys, access tokens, private certificates, or .env files that hold them. The reason is everything you learned about commits in Session 1.

A commit is a permanent snapshot. If a secret goes into a commit, it is in the history, and here is the part that burns people: deleting it in a later commit does not remove it. The later commit just records a new snapshot without it, while the old snapshot, secret and all, sits in the history forever, one git show away.

  • Getting a secret out of history for real means rewriting history, which is advanced, disruptive, and covered in Session 8. It is not a quick fix.
  • And even after a rewrite, anyone who already pulled or saw the repository still has the secret. So the only response you can actually rely on is this: if a secret is ever committed, treat it as compromised and rotate it. Rotate means change it, revoke the old key and issue a new one, at the source.

.gitignore is the prevention: list .env and secret files there before you ever git add, so they never reach a commit. But be clear about what .gitignore does and does not do: it stops a file from being committed in the first place, and it does nothing to protect a secret you already committed. Prevention only.

Your turn Ignore, untrack, and reason about secrets
  1. In the sandbox, create debug.log, then a .gitignore containing *.log and beta. Run git status and confirm both disappear from the untracked list. Commit .gitignore.
  2. Add a line alpha to .gitignore, edit alpha, and run git status. Confirm Git still reports alpha as modified: an already-tracked file is not affected by .gitignore.
  3. Run git rm --cached alpha and read the status. Note that it says deleted, yet alpha is still in your folder.
  4. No command needed for this one, just answer it in your head: you committed an API key yesterday and removed it in today's commit. Is the key safe? (No. It is still in yesterday's snapshot. You would rotate the key.)
