Pull requests & review

A pull request is not a Git feature. Git has never heard of one. It is a wrapper a website puts around three things you already have: a branch, a diff, and a merge. Once you can see that, the interface stops being intimidating and one real decision is left in it, which is how the branch gets joined on. This session builds all three answers to that question with your own hands, so the choice becomes something you can defend rather than a button you click.

A. What a pull request actually is

Start here, because the name is the most misleading thing about it. A pull request does not pull anything, and it is not part of Git. If you type git pull-request you get nothing, because there is no such command and there never was.

A pull request is a message on a website. It says: here is a branch I pushed, please join it onto that other branch. GitHub invented it, GitLab copied the idea and called it a merge request, Bitbucket has its own. Every one of them is a layer sitting on top of a repository, and underneath the layer the operation is the git merge you already ran in Session 4.

What the website adds on top is genuinely useful, and it is worth naming, because these are the parts that are not Git:

  • A diff view. Session 2's git diff, drawn in a browser with colours and line numbers.
  • A comment thread, including comments attached to individual lines of the diff.
  • A verdict from a reviewer: comment, approve, or request changes.
  • A merge button that offers you a choice of how to merge. That choice is the real content of this session.

Here is the whole cycle, start to finish. You already know how to do steps 1, 2 and 3, and step 7. Steps 4, 5 and 6 are the website's part:

1. branchMake a branch for the work. Session 3.
2. commitCommit onto it, as many times as the work takes. Session 1.
3. push the branchSend the branch to the shared copy. Session 5 taught the push; this session adds the small change for a branch that is not main.
4. open the pull requestAsk the platform to join it onto main. Not a Git step.
5. reviewRead the diff, leave comments, give a verdict. Not a Git step.
6. merge, one of three waysThe button. Underneath it, one of three things you are about to do by hand.
7. clean up and pullDelete the branch on both sides, and bring the result down. Session 5, plus one new flag.

So the plan for this session is to do steps 1, 2, 3, 6 and 7 offline, in the lab you already have, where you can see exactly what each one does to the history. Step 6 is where nearly all the value is, and it needs no website at all. Steps 4 and 5 are shown on GitHub at the end for anyone who wants them.

Three things this session deliberately does not cover. Automated checks (tests that a service runs on your branch and reports back on the pull request) get named here and nothing more; Session 10 is where a service runs something of yours. Protected branches, a setting that can require a review or a passing check before the merge button works, are worth knowing the name of and nothing else today. And forks, which are how you contribute to a project you cannot push to, are Session 9.

C. Pushing a branch that is not main

A pull request needs the branch to exist on the shared copy, because that is the only copy the website can see. So the branch has to be pushed, and this is the one genuinely new Git mechanic in the first half of the session. It is smaller than you expect.

Make the branch and put three commits on it, using git switch -c from Session 3:

PowerShellgit switch -c chart Set-Content chart.md "chart: draft one" git add chart.md git commit -m "Start the chart" Add-Content chart.md "axis labels" git add chart.md git commit -m "Add axis labels" Add-Content chart.md "legend" git add chart.md git commit -m "Add the legend"
Git Bash / macOS / Linuxgit switch -c chart echo "chart: draft one" > chart.md git add chart.md git commit -m "Start the chart" echo "axis labels" >> chart.md git add chart.md git commit -m "Add axis labels" echo "legend" >> chart.md git add chart.md git commit -m "Add the legend"

Three separate commits on purpose. Whether those three deserve to survive on main is exactly the question the three merge strategies answer differently, and you cannot feel the difference with a one-commit branch.

Now send the branch. It is Session 5's first-push command with the branch name swapped in, and that is the entire lesson:

run in work-a, on chart · git push -u origin chart
> git push -u origin chart
To ../origin-repo.git
 * [new branch]      chart -> chart
branch 'chart' set up to track 'origin/chart'.

Word for word the shape Session 5 printed for main, with chart in place of main. * [new branch] because the shared copy had no branch by that name, and the -u line because you asked for the pairing. There is no special "push a feature branch" command. A branch is a branch.

run in work-a, on chart · what the pairing bought you
> git status -sb
## chart...origin/chart

> git branch -vv
* chart 0e70e9b [origin/chart] Add the legend
  main  bed2aaf [origin/main] Add roadmap.md

Two branches, two pairings, and they are independent. chart is paired with origin/chart, main with origin/main. Every ahead and behind reading you learned in Session 5 now applies separately to each one, which is why git branch -vv earns its keep the moment you have more than one branch in flight.

The one thing that looks different against a real GitHub remote. The same git push -u origin chart aimed at GitHub prints several extra lines beginning with remote:, offering you a link to open the pull request there and then. They come from the server rather than from your Git, which is why the local bare repository never prints them. Nothing else about the command changes. Section L shows the real thing.

D. Somebody else moves main, and why that matters here

A pull request that could just slide into place is not interesting. The whole reason there are three merge strategies is that main usually moves while your branch is out being reviewed. So make that happen, using Session 5's teammate:

PowerShellcd ../work-b git pull --no-edit Set-Content readme.md "readme: start here" git add readme.md git commit -m "Add readme.md" git push cd ../work-a git switch main git pull --no-edit
Git Bash / macOS / Linuxcd ../work-b git pull --no-edit echo "readme: start here" > readme.md git add readme.md git commit -m "Add readme.md" git push cd ../work-a git switch main git pull --no-edit

Look at the shape you are now in. This is the picture the rest of the session works on:

run in work-a, on main · the fork
> git log --oneline --graph --decorate=short --all -5
* a0c0add (HEAD -> main, origin/main, origin/HEAD) Add readme.md
| * 0e70e9b (origin/chart, chart) Add the legend
| * 239b290 Add axis labels
| * b9f48f8 Start the chart
|/  
* bed2aaf Add roadmap.md

You have seen this drawing twice before, in Session 4 between two of your own branches and in Session 5 between your branch and your note of the shared copy. Same shape, third time: two lines of work leaving the same commit and going different ways. Add roadmap.md is the fork point, and it is where all three strategies below will start.

Now a small piece of stage machinery, and it is worth explaining rather than just running. You are about to join chart onto main three different ways. The trouble is that the first one moves main, and then the second and third would start somewhere else and could not be compared. So instead of touching main, make three throwaway branches that all start exactly where main is now, and do one strategy on each:

run in work-a, on main · three identical starting points
> git switch -c try-merge
Switched to a new branch 'try-merge'

> git switch main
Switched to branch 'main'
Your branch is up to date with 'origin/main'.

> git switch -c try-squash
Switched to a new branch 'try-squash'

> git switch main
Switched to branch 'main'
Your branch is up to date with 'origin/main'.

> git switch -c try-rebase
Switched to a new branch 'try-rebase'

> git switch main
Switched to branch 'main'
Your branch is up to date with 'origin/main'.

git switch -c makes a branch at the commit you are standing on, which is Session 3's lesson doing exactly what it always did. Going back to main between each one is what guarantees all three start in the same place:

run in work-a, on main · four names, one commit
> git branch -v
  chart      0e70e9b Add the legend
* main       a0c0add Add readme.md
  try-merge  a0c0add Add readme.md
  try-rebase a0c0add Add readme.md
  try-squash a0c0add Add readme.md

Three of those rows are the same hash as main. Session 3 made the point that a branch is just a name pointing at a commit, and here are four names on one commit, costing nothing. In real work you would not make these; you would pick one strategy and use it on main. They exist so that you can see all three answers side by side, once, and never have to guess again.

E. Strategy one: the merge commit

This is Session 4's merge, unchanged. Nothing new to learn in the command; the new part is knowing what it leaves behind and when that is what you want.

run in work-a · switch to the first lane and merge
> git switch try-merge
Switched to branch 'try-merge'

> git merge --no-edit chart
Merge made by the 'ort' strategy.
 chart.md | 3 +++
 1 file changed, 3 insertions(+)
 create mode 100644 chart.md

--no-edit is there for the reason Session 5 gave: a real merge builds a commit, a commit needs a message, and without the flag Git opens your editor to let you edit the one it prepared. Leave the flag off if you would rather see it, and get out the way Session 4 showed.

Now the result:

run in work-a, on try-merge · what a merge commit leaves
> git log --oneline --graph --decorate=short try-merge -6
*   b966400 (HEAD -> try-merge) Merge branch 'chart' into try-merge
|\  
| * 0e70e9b (origin/chart, chart) Add the legend
| * 239b290 Add axis labels
| * b9f48f8 Start the chart
* | a0c0add (origin/main, origin/HEAD, try-squash, try-rebase, main) Add readme.md
|/  
* bed2aaf Add roadmap.md

Everything is still there. All three of your commits, the teammate's commit, and a new one on top with the two of them joined underneath it. That top commit is the diamond from Session 4, and you can ask Git to prove it has two parents:

run in work-a, on try-merge · a merge commit has two parents
> git log -1 --format="%h has parents: %p"
b966400 has parents: a0c0add 0e70e9b

--format lets you ask for exactly the fields you want, and the two here are %h, the short hash of the commit, and %p, the short hashes of its parents. Two hashes come back, and they are the tip of main and the tip of chart. That is what "merge commit" means, spelled out: a commit whose job is to have two parents, so both lines of history stay reachable.

What you end up withEvery commit from the branch, plus one merge commit. Four new commits on the target from a three-commit branch.
When it is rightWhen the fact that this work happened on a branch is worth recording, and when the individual commits are worth reading later.
What it costsA busier graph. On a project with many branches the picture becomes genuinely hard to read, which is the honest argument against it.

F. Strategy two: the squash merge

Squashing takes every commit on the branch and lands them on the target as one single new commit. The branch's own commits do not appear on the target at all. The word is worth unpacking: to squash commits is to flatten several into one, keeping all of the changes and none of the separate steps.

Switch to the second lane and run it. Read the output before you read the explanation, because there is a surprise in it:

run in work-a · the squash, which does not do what its name implies
> git switch try-squash
Switched to branch 'try-squash'

> git merge --squash chart
Automatic merge went well; stopped before committing as requested
Squash commit -- not updating HEAD
Those two lines may come out in either order on your machine, and neither order is wrong. Git sends one of them to its normal output and the other to its error channel, and which lands first depends on your terminal. Session 5's point about error: applies here in reverse: a line arriving on the error channel is not automatically a complaint.

git merge --squash does not commit anything. It works out the combined change, puts it in the staging area from Session 1, and stops, which is precisely what stopped before committing as requested is telling you. not updating HEAD is the same fact in Session 3's vocabulary: you have not moved.

Check with a command you have had since Session 1:

run in work-a, on try-squash · staged, and nothing more
> git status
On branch try-squash
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   chart.md

Staged, waiting for you, exactly as if you had made the change yourself and run git add. That is the honest reading of the whole command: the squash is a way of preparing a commit, not of making one. So make it:

run in work-a, on try-squash · one commit for the whole branch
> git commit -m "Add the chart"
[try-squash d44575f] Add the chart
 1 file changed, 3 insertions(+)
 create mode 100644 chart.md

Git also prepares a message for you, and it is worth knowing about even though this transcript does not use it. The squash writes a draft into a file called SQUASH_MSG inside .git, listing every commit it flattened. Run a bare git commit with no -m and your editor opens with that draft already in it, which is often exactly what you want. Using -m as above ignores the draft and takes your message instead.

run in work-a, on try-squash · what a squash leaves
> git log --oneline --graph --decorate=short try-squash -3
* d44575f (HEAD -> try-squash) Add the chart
* a0c0add (origin/main, origin/HEAD, try-rebase, main) Add readme.md
* bed2aaf Add roadmap.md

> git log -1 --format="%h has parents: %p"
d44575f has parents: a0c0add

Compare that to section E and the difference is stark. No fork in the drawing, no branch commits, no merge commit, one parent. Your three commits still exist over on chart, untouched, but from this branch's point of view they were never here. The changes arrived; the history of how they were made did not.

What you end up withExactly one new commit on the target, whatever the branch contained. A straight line.
When it is rightWhen the branch history is wip, wip, fix typo, actually fix typo, and nobody will ever benefit from reading it.
What it costsThe detail is gone from the target for good. And it makes deleting the branch complain, which section I is about.

G. Strategy three: the rebase merge

Rebasing replays your commits onto a different starting point, one at a time. The base of your branch is the commit it grew out of, so to rebase is to give it a new one. Your three commits stay three commits, in order, but they end up sitting on top of the teammate's work instead of beside it, and the fork disappears.

Do this one last, because unlike the other two it changes the branch itself. Note the hashes before you start:

run in work-a · the branch, before
> git switch chart
Switched to branch 'chart'
Your branch is up to date with 'origin/chart'.

> git log --oneline -4
0e70e9b Add the legend
239b290 Add axis labels
b9f48f8 Start the chart
bed2aaf Add roadmap.md

Now replay them onto the third lane. You run this from the branch that is moving, and you name the branch it should land on, which is the opposite way round from git merge and the single most common thing people get backwards:

run in work-a, on chart · git rebase
> git rebase try-rebase
Successfully rebased and updated refs/heads/chart.

While it works, Git also prints a counter reading Rebasing (1/3), then 2/3, then 3/3, redrawing itself on one line as it goes. Depending on your terminal you may be left looking at the last count, or at nothing but the success line. Either is normal. refs/heads/chart is the long spelling of the branch called chart, the same full form Session 5 showed you in git ls-remote.

Now look at the same four commits again:

run in work-a, on chart · the branch, after
> git log --oneline -4
b6e52f7 Add the legend
cd0c75d Add axis labels
461568a Start the chart
a0c0add Add readme.md

Every hash is different, and the commit underneath is now the teammate's instead of the roadmap one. The messages are the same and the changes are the same, but these are new commits. That is the thing to take away from this section, and it is the first time in this track that something has rewritten history rather than added to it.

Git will tell you as much, if you ask the branch how it compares to its pair on the shared copy:

run in work-a, on chart · you and your own pushed branch now disagree
> git status -sb
## chart...origin/chart [ahead 4, behind 3]

Read that with Session 5's four states in mind and it is alarming until you work it out. You have not written any new work, yet you are diverged from your own branch on the shared copy. behind 3 is the three original commits, which still sit over there with their old hashes. ahead 4 is the three replacements plus the teammate's commit that they now sit on. The same three changes are counted as six different commits, because a commit is identified by its hash and every hash changed.

This is the edge of Session 8, and the right move is to stop here. Rewriting commits you have already pushed is genuinely the one Git operation that can cause somebody else real trouble, and there is a rule about when it is safe. Session 8 is that rule, along with the flag you would need to push this branch. For today, notice the effect and go no further: the workbook does not ask you to push chart again.

Finish the strategy. The branch now sits directly on top of the lane, so joining them needs no merge commit at all:

run in work-a · the second half of a rebase merge
> git switch try-rebase
Switched to branch 'try-rebase'

> git merge --ff-only chart
Updating a0c0add..b6e52f7
Fast-forward
 chart.md | 3 +++
 1 file changed, 3 insertions(+)
 create mode 100644 chart.md

--ff-only means "fast-forward or fail". Session 3 taught the fast-forward: when your branch has not moved and the other one is straight ahead, Git slides the pointer instead of building anything. The flag says do that and nothing else, so if a real merge were needed the command would refuse rather than quietly make a merge commit. After a rebase it always succeeds, which is the point of running the rebase first.

run in work-a, on try-rebase · what a rebase merge leaves
> git log --oneline --graph --decorate=short try-rebase -5
* b6e52f7 (HEAD -> try-rebase, chart) Add the legend
* cd0c75d Add axis labels
* 461568a Start the chart
* a0c0add (origin/main, origin/HEAD, main) Add readme.md
* bed2aaf Add roadmap.md

A straight line, with all three commits still individually there. That is the trade this strategy makes: you keep the steps, you lose the record that they happened on a branch, and the hashes are not the ones you originally made.

What you end up withThe branch's commits, in order, in a straight line, with no merge commit. Three new commits from a three-commit branch.
When it is rightWhen each commit is worth keeping on its own, and the project wants its history to read as one sequence.
What it costsNew hashes for every commit, which is a real problem if anyone else already has the old ones. Session 8.
Your turn Produce all three histories from the same fork
  1. Move main using work-b, then make the three try- branches and confirm with git branch -v that all three sit on the same hash.
  2. On try-merge, run git merge --no-edit chart, then draw it, then prove the top commit has two parents.
  3. On try-squash, run git merge --squash chart and stop. Run git status and see the change sitting staged. Then commit it and draw the result.
  4. On chart, note the three hashes, run git rebase try-rebase, and note them again. Then run git status -sb and work out where ahead 4, behind 3 comes from.
  5. Finish with git merge --ff-only chart from try-rebase and draw that too.

H. Choosing, and being able to say why

Put the three drawings side by side and the decision stops being abstract. Same branch, same fork, same changes, three shapes:

merge commitsquashrebase
new commits on the target413
branch's commits surviveyesnoyes
a commit with two parentsyesnono
hashes changenonoyes
records that a branch existedyesnono

Here is a rule you can actually apply, and it turns on one question: was this branch's commit history worth keeping?

No, it was scrappySquash. One clean commit on the target beats four commits nobody wants to read.
Yes, and the branch mattersMerge commit. Keeps the steps and records that they were done together, as a unit, off to one side.
Yes, but keep it linearRebase. Keeps the steps and drops the fork, at the price of new hashes.

Now the honest part. Most teams pick one of these and standardise on it, and the setting lives on the repository rather than in your hands. So the odds are that you will not choose day to day. What you will be asked, sooner or later, is why your team does it that way, and the difference between someone who can answer that and someone who cannot is the whole point of this session. Having a reason matters more than which one you land on.

I. After the merge: deleting the branch, and the complaint

The work has landed, so the branch has done its job. There are two copies of it to remove, and they are separate: the one on the shared copy, and your own. Take the shared one first, with a flag that is new but reads exactly as it looks:

run in work-a · remove the branch from the shared copy
> git push origin --delete chart
To ../origin-repo.git
 - [deleted]         chart

git push origin --delete chart is a push that sends nothing and removes a name instead. That is worth sitting with for a second, because it is the same command you have been using to send work. A push updates a branch on the other side; deleting is the case where you update it to nothing. On GitHub this is what the "Delete branch" button does after a merge.

Your own copy of the branch is untouched by that, and Git now says so:

run in work-a · your branch outlived its pair
> git branch -vv
  chart      b6e52f7 [origin/chart: gone] Add the legend
  main       a0c0add [origin/main] Add readme.md
  try-merge  b966400 Merge branch 'chart' into try-merge
* try-rebase b6e52f7 Add the legend
  try-squash d44575f Add the chart

[origin/chart: gone] is Session 5's pairing reporting a death. The branch is still paired with origin/chart, and origin/chart no longer exists. Nothing is broken; the note simply has nothing left to point at.

Now the part that confuses people, and it is worth causing on purpose. Delete your local branch from the lane where you squashed:

run in work-a · standing on try-squash, where the branch was squashed
> git switch try-squash
Switched to branch 'try-squash'

> git branch -d chart
error: the branch 'chart' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D chart'
hint: Disable this message with "git config set advice.forceDeleteBranch false"

It looks wrong. It is not. This is the same refusal Session 3 showed you, and it is Git correctly reporting a fact: the commits on chart are not in this branch's history. Squashing did not bring them here. It built one brand new commit that happens to contain the same changes, and Git has no way to know those changes came from anywhere in particular. As far as history is concerned, chart was never merged.

Prove that reading is right by running the identical command from a different branch:

run in work-a · standing on try-rebase, where the commits really did arrive
> git switch try-rebase
Switched to branch 'try-rebase'

> git branch -d chart
Deleted branch chart (was b6e52f7).

Same branch, same command, opposite answer. That is the rule, and it is worth learning as a sentence: git branch -d asks whether the branch's commits are reachable from where you are standing right now. On try-rebase they are, because the rebase put them there. On try-squash they are not, because the squash replaced them.

One extra condition, so this does not surprise you later. Git also accepts the delete when the branch is fully merged into its pair on the shared copy, even if it is not merged where you are standing, and in that case it goes through with a warning rather than a refusal. That is why the complaint you just saw normally turns up only after the branch has been deleted on the platform, which is the order things happen in after a real pull request. Do not go looking for that second case in this lab: section G rebased chart, so it no longer matches origin/chart either, and it would be refused for that reason instead. Both behaviours are one rule said twice: Git lets a name go once the commits are safe somewhere else.

And if you genuinely want it gone regardless, the capital -D from Session 3 forces it, which is what the hint offers. After a squash merge that is normally the correct thing to do: the changes are safely on the target, and only the scrappy history is being thrown away. Read the refusal, decide, then override it deliberately. That is different from being blocked.

Your turn Clean up, and get both answers out of one command
  1. Run git push origin --delete chart and read the one-line report.
  2. Run git branch -vv and find [origin/chart: gone].
  3. From try-squash, run git branch -d chart and get the refusal.
  4. From try-rebase, run the same command and watch it succeed.
  5. Without looking back: say in one sentence what git branch -d is actually checking.

J. What makes a review worth doing

This is the part that transfers straight into a job, and it has nothing to do with Git. Reviewing is reading somebody's change and saying something useful about it. Most people freeze because they think the job is to find bugs, and if they cannot find one they approve and move on.

Three questions will get you further than looking for bugs, and they work on a change in any language, including one you barely know:

Does it do what it says?Read the description, then read the diff. If the description promises one thing and the diff also quietly does another, that is worth a comment every time.
Could I change this in six months?Not "is it clever" but "will the next person understand it". A name that means nothing, a number with no explanation, a missing note about why.
What happens when the input is wrong?Empty, missing, enormous, the wrong type. Most real defects live here rather than in the case the author was thinking about.

And be honest about reviewing your own work, which is what you are doing on a solo project. You will not catch what you did not think of the first time, and no amount of ceremony changes that. What it does do is force you to read the change as a whole, on a screen, away from the editor you wrote it in, which catches a surprising amount. Do it for that, not for the tick.

To review a branch you first have to see it as one change, and Session 2's diff has a form that does exactly that. Compare a branch against the one it will join, and use three dots:

Both shellsgit diff main...chart

The number of dots matters much more than it looks. Two dots, git diff main chart, compares the two branch tips as they stand right now. That sounds like what you want, and it is not: anything that landed on main while you were away appears in that diff as though your branch deleted it, which is alarming and completely false. Three dots measures from the merge base instead, Session 4's word for the commit where the two lines parted, so you see what your branch added and nothing else. It is also exactly what a pull request shows you, which is the other reason to learn this form rather than the two-dot one.

Offline, the way to make the review itself real is to write it down. That is the last piece of the milestone below.

One full cycle, unassisted, plus the thing that actually gets graded: the reason. Work in remote-lab. Do not scroll back up; if you get stuck, git status and git branch -vv will tell you where you are, which is the habit this whole track is teaching.

Your turn The milestone: run the cycle, review it, and defend the strategy
  1. Start clean. In work-a, get level with the shared copy and make a branch called legend off main. Put two commits on it that change a file, and push the branch so it exists on the shared copy.
  2. Make main move underneath you. Go to work-b, commit a change to a different file, and push it. Come back to work-a and bring main up to date.
  3. Review your own branch. Run git diff main...legend, three dots, and read it as if a stranger wrote it. Create a file called review.md on main and write three comments in it, one for each of the three questions in section J. Commit it.

L. The same cycle on GitHub (entirely optional)

Nothing below is required, and nothing below is graded. Skip it with a clear conscience: the milestone above covers everything this session is assessed on. This section exists because the three merge strategies you just built by hand are, on GitHub, three items in a dropdown, and seeing the buttons land on the commands makes both halves stick.

What the platform genuinely adds, and the local lab cannot. Two things, and they both need another person: a threaded conversation on the diff, and the approve or request-changes verdict from someone who is not you. Everything else you have already done.

The commands below come from the GitHub CLI, a separate program called gh that talks to GitHub from your terminal. It is not part of Git, and you install it separately. Everything it does is also doable by clicking around the website, and the buttons are named the same as the flags, so reading these is useful even if you only ever click.

These transcripts were captured against gh version 2.93.0, on a throwaway private repository. Wherever you see <you> and <repo>, your own account and repository names appear instead; they are stand-ins, not something to type. Two further things will differ and neither means anything is wrong: gh lays its tables out to fit your terminal, so columns sit differently at other widths, and it prints times as relative phrases like about 1 minute ago. Compare the words and the structure, not the spacing.

Step one is a push you have already done. Same command as section C, aimed at a repository on GitHub rather than the folder next door. What comes back is different:

on chart, against a GitHub remote · the same push, a chattier answer
> git push -u origin chart
remote:
remote: Create a pull request for 'chart' on GitHub by visiting:
remote:      https://github.com/<you>/<repo>/pull/new/chart
remote:
To https://github.com/<you>/<repo>.git
 * [new branch]      chart -> chart
branch 'chart' set up to track 'origin/chart'.

The last three lines are the ones you already know, identical to the local push apart from the address. The remote: lines are new, and the prefix is the giveaway: they were spoken by the server and passed through to you. GitHub noticed a branch arriving with no pull request attached and offered a link to open one. Your Git did not generate that and the bare repository in remote-lab never could, because a bare repository is storage and has no opinions. (The branch ... set up to track line may appear above the block rather than below it, for the same two-channel reason as the squash in section F.)

Now open the pull request. This is the step with no Git equivalent at all:

on chart · gh pr create
> gh pr create --draft --title "Add the chart" --body "Adds chart.md with axis labels and a legend."
https://github.com/<you>/<repo>/pull/4

The address of the thing you just made comes back, and that is the part you want. One note on the transcript: this was captured with the output sent to a file, and in an ordinary interactive terminal gh also prints a line above the address naming the two branches it is opening the pull request between. Seeing more than one line is normal.

--draft opens it as a draft, which means visible to everyone but explicitly not ready to merge, and GitHub disables the merge button until you say otherwise. It is the honest way to share work in progress. gh pr ready takes it out of draft when you are done.

The pull request has a number, and from here on that number is how you refer to it. Yours will not be 4 unless you also made three others first.

Reading the change is the same diff you have had since Session 2, fetched from the platform:

on chart · gh pr diff
> gh pr diff
diff --git a/chart.md b/chart.md
new file mode 100644
index 0000000..3af4dff
--- /dev/null
+++ b/chart.md
@@ -0,0 +1,3 @@
+chart: draft one
+axis labels
+legend

Not one character of that is new to you. --- /dev/null on the left is Session 2's way of saying the file did not exist before. This is the exact text the website draws in colour with line numbers beside it, and knowing that the pretty version is only this makes the pretty version much less intimidating. It is also the three-dot diff from section J rather than the two-dot one, which is the other reason to have learned that distinction.

One practical warning before you run it. When the diff is longer than your screen, gh pr diff hands it to a pager, a small program that shows one screenful at a time and waits. It looks like the terminal has stopped responding to you. Press q to leave it, the same kind of escape Session 4 taught for the editor.

Two more worth knowing: gh pr list shows every open pull request on the repository with its number, title and branch, and gh pr checks reports on any automated tests configured to run against the branch. With none set up it complains, on the error channel, that there are no checks reported on the 'chart' branch, which is what you should expect on a practice repository and is not a problem.

Reviewing. A review is a comment plus, optionally, a verdict. There are three verdicts and the command names them plainly. The two that must carry words need -b, short for --body, and refuse to run without it:

gh pr review --comment -b "..."Say something, without judging. Always available, including on your own pull request.
gh pr review --approveNeeds to be somebody else. GitHub does not accept an approval from the author.
gh pr review --request-changes -b "..."The same, and also from somebody else: it is a verdict on another person's work.

That second row is not a convention, it is enforced, and it is worth seeing refused rather than taking on trust:

on your own pull request · gh pr review --approve
> gh pr review 1 --approve --body "Looks good to me."
failed to create review: GraphQL: Review Can not approve your own pull request (addPullRequestReview)

So on a solo project you can comment on your own pull request and that is all, which is worth knowing before you go hunting for the approve button and conclude you have broken something. Reviewing your own work is still worth the ten minutes, for the reason section J gave: you read the change as a whole, on a screen, away from the editor you wrote it in.

If you have a second account, that is the one case where the full thing is available to you. The owner invites the other account to the repository, and once the invitation is accepted that account can review properly, verdict included:

as the ownergh api -X PUT /repos/<you>/<repo>/collaborators/<other> -f permission=push
as the other accountgh pr review 4 --repo <you>/<repo> --approve --body "Looks good."

The invitation has to be accepted before the second command works, which is done from the notification GitHub sends or from the repository page while signed in as that account. Worth being honest about the payoff: it is the same two things named at the top of this section, a real conversation and a real verdict, and nothing about the merge itself changes.

The merge, and the whole reason this section exists. GitHub's merge button is a dropdown with three items in it, and you have now built all three by hand:

Three branches, three buttons, one repository. Pull main afterwards and every one of this session's three shapes is sitting in a single real history, which is the clearest possible proof that the buttons are the commands:

Read it from the bottom and all three sections are there in order:

  • The diamond is pull request 1, merged with a merge commit. Its three branch commits sit off to one side and Merge pull request #1 from ... joins them back on. That is section E, and GitHub wrote the message for you.
  • Add the chart (squash lane) (#2) is pull request 2, squashed. One commit, no fork, and its branch commits appear nowhere. That is section F. GitHub appends the pull request number in brackets, which is the one cosmetic thing it adds that your own git merge --squash did not.
  • The top three commits are pull request 3, rebased. Three separate commits, in a straight line, no merge commit. That is section G, and their hashes are not the ones the branch had before it was merged, for the reason you proved by hand.

A repository owner can switch any of the three buttons off in the settings, which is how a team standardises. If a project offers you only one, somebody decided that on purpose, and you now know both what they decided and why it might have been a perfectly reasonable call.

Then you are back on ground you know. The merge happened on the shared copy, so your own main is behind until you ask, exactly as in Session 5. git pull, and you are level.
