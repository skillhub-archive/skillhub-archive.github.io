A. What a webhook is

In every session so far, your side started the conversation: you sent a request and something answered. That works when you know when to ask. It works badly when you are waiting for something to happen. Say a reading app wants to know the moment a member returns a book to the library. With only the requests you know, the app has to keep asking:

the old way: polling, asking again and again · an illustration
> GET https://library.example.com/v1/loans?member=31   9:00, nothing new
> GET https://library.example.com/v1/loans?member=31   9:05, nothing new
> GET https://library.example.com/v1/loans?member=31   9:10, nothing new
... about sixty more, and the book came back at 14:05

That is called polling: asking the same question on a timer, hoping the answer has changed. Nearly every answer is “nothing new”, each one spends some of the rate limit Session 4 taught you to respect, and the news still arrives up to five minutes late. A webhook turns it around. The reading app gives the library one address, once, and the library sends a request to that address the moment the book comes back:

the new way: a webhook, the library calls you · an illustration
14:05, the library sends, and the reading app answers
> POST https://reading-app.example.com/webhooks/library
> { "id": "evt_1001", "type": "book.returned", ... }
200 OK

A webhook is an ordinary HTTP request, the kind you have sent since Session 1, made by the other system, to you. Everything you know about methods, headers, bodies and status codes still applies; only the direction has changed. Five words you need for the rest of the session:

Means

“Both directions” is about which side you build. A receiver writes the endpoint, and has to understand whatever arrives. A sender decides what every delivery looks like, and has to write that down so a stranger can build a receiver for it. Today you are the library’s designer, as you were for Books API v1, so you are the sender. But you will test every decision from the receiver’s side, because that is who has to live with it.

Why a mock is an honest receiver today. A real receiver is a server someone writes code for, which this track does not do. Session 6 showed what a mock is: something that answers each request with a saved example and stores nothing. What a receiver promises the sender is exactly that kind of thing: when you send me this, I answer that. So a mock built from the receiver’s half of the contract can stand in for a receiver, and Postman keeps a log of every request it gets, which is how you will see what arrived.

C. Being the sender, and seeing what arrived

Now play the library. A sender needs nothing special: it sends a POST, which Postman has done for you since Session 1. Make a second collection, Library sender, whose baseUrl is your mock’s address, and give it one request, Deliver book.returned: the same method, URL, headers and one-line body as the box in section B. Then send it:

a delivery reaches the receiver mock · captured live
> POST https://<mock-id>.mock.pstmn.io/webhooks/library
> Library-Timestamp: 1790863500
> Library-Signature: sha256=fb8e8778...4b8f3     shortened here, send it in full

{ "received": true }                         the 200 received example

The 200 is the receiver mock saying what a real receiver would say. But a sender never sees what the receiver actually got, and a receiver’s builder needs to. Postman keeps a call log for every mock: its documentation says each entry “shows the time the request was sent, the request method and path, and a response overview”, and that selecting an entry gives “more details about the request headers and body or the response headers and body”. To find it, look for “Mock servers” in the sidebar and choose your mock; the log is kept for 7 days on the free plan, according to Postman’s support pages. On the mock built for this session, the delivery above showed up like this:

  content-type       application/json               names in lower case
  library-timestamp  1790863500

Three things in it matter. The response column names the example the mock chose, which is a fast way to see how a mock matched. The header names are in lower case, which changes nothing, because Session 2 showed header names are case-insensitive; Postman also adds a dozen headers of its own about its network, which you can ignore. And the body is shown as a tree of fields, not as the text that was sent. That last one matters more than it looks. Section E shows that a signature is computed over the exact characters of the body, and the call log does not keep them: on the mock built for this session, the body behind that tree was stored with every space after a colon and after a comma removed, 123 bytes, so it no longer matched the 135 bytes its own content-length records. The call log shows you the shape of what arrived, never its exact bytes.

On the mock built for this session it did so even when the request asked for the 400 invalid json example by name, and even though this body is exactly the one saved in that example. D. Designing a payload a stranger can implement against

The body of a delivery is called its payload. Nobody can ask the sender what a field means at the moment a delivery arrives, so the payload has to be designed, and documented, as carefully as Session 5’s books contract. The library’s payloads share one outer shape, called an envelope, with the details of each event inside it:

the book.returned payload, laid out to read · sent as one line
{ "id": "evt_1001",                       this event, and no other
  "type": "book.returned",                 what happened
  "occurredAt": "2026-10-01T14:05:00Z",     when it happened
  "data": { "bookId": 8, "memberId": 31, "daysLate": 0 } }
Field
Type, always present?
Meaning
id
string, always
unique to this event; the same on every delivery attempt of it (section F)
type
string, always
which event: book.returned or book.overdue; decides what is in data
occurredAt
string, always
when it happened in the library, in UTC, in the form 2026-10-01T14:05:00Z
data.bookId
integer, always
the book, as /v1/books/{id} in Books API v1
data.memberId
integer, always
the member who had it
data.daysLate
integer, always
0 if on time; days past the due date otherwise

Each choice there answers a question a receiver’s builder would otherwise have to ask:

  • A type, written thing.what-happened. One endpoint receives every event, so the receiver needs one field that says which event this is before it reads anything else. Naming it as the thing, then what happened to it, in the past tense, keeps every event name readable on its own: book.returned, book.overdue, and later perhaps member.joined.
  • An id for the event itself. It is not the book’s id. One book is returned many times, and each return is a different event with a different id. Section F shows why the receiver needs it.
  • A time, with its timezone. The Z at the end means UTC, so a receiver anywhere reads the same moment. A date without a timezone forces a stranger to guess, which is exactly what a contract exists to prevent.
  • Ids, not copies, for anything the API already serves. bookId and memberId are enough, because a receiver that needs the title can read it from /v1/books/8. Copying the whole book into every payload is allowed, but then two documents describe a book, and they will eventually disagree.

The rule that keeps a payload from breaking receivers later: a receiver must ignore fields it does not know. Session 5 section E said adding a field is only safe if clients were written to skip fields they do not know, and that a good contract tells them to, in writing. A webhook receiver is a client you never meet, so this contract says it too: new fields may appear in data at any time; removing a field, renaming one or changing its type is a breaking change, and needs a new version, the way /v1 did for the books API.

E. Proving the library sent it

The reading app’s endpoint is a public address. That is the point of it, and it is also the problem: anyone who learns it can send a request that looks like a delivery. If a forged book.returned could clear a member’s late fees, someone will forge one. The receiver needs a way to check that a delivery came from the library and that nobody changed it on the way. The common answer is a signature, and it is built from two ideas.

First idea: a hash. A hash turns any amount of text into a short, fixed-length fingerprint, the way Session 2’s ETag stood for a whole body. The one used here, SHA-256, always produces 32 bytes, written as 64 characters of hex, the digits 0 to 9 and the letters a to f. The same input always gives the same fingerprint; change one character of the input and the fingerprint changes completely, not just a little; and there is no calculation that runs it backwards, from the fingerprint to the text.

Second idea: a shared secret. A hash alone proves nothing, because anyone can compute one. So the library and each receiver agree on a secret, a random string the library hands the receiver once, when the endpoint is set up, and that never travels in a delivery. HMAC, defined in RFC 2104, mixes the secret into the hash, so only someone who holds the secret can produce the right fingerprint for a given text. The library’s contract says exactly what goes in:

1
The signed string is the Library-Timestamp value, a dot, then the body exactly as sent: 1790863500.{"id": "evt_1001", ...}
2
The signature is HMAC-SHA256 of that string, with the secret as the key, written in lower-case hex.
3
The header carries it with a prefix that names the method: Library-Signature: sha256=fb8e8778...

1790863500 is a Unix timestamp: a count of seconds since the start of 1970, in UTC, the most common way for two computers to agree on a moment. This one is 2026-10-01 at 14:05:00 UTC. It is inside the signed string so that a delivery cannot be reused, which comes up below. The two header names have no X- at the front, because RFC 6648 says new names “SHOULD NOT” be given one; GitHub’s older webhook headers, such as X-Hub-Signature-256, still have it, and either style works.

To verify a delivery, the receiver does the library’s calculation again, with its own copy of the secret, and compares. Here is that check on four deliveries. Every value was computed with the practice secret practice-secret-7f3a, by two separate tools that agreed on every one:

Delivery
Receiver computes, against the header’s fb8e8778...4b8f3
1 as sent
fb8e8778...4b8f3: the same. Act on it.
2 one digit changed
"memberId": 32 instead of 31: c8ac0fc8...b479f7. Nothing alike. Refuse it: 401.
3 re-indented
the same JSON, laid out over several lines: c28b9396...213ea7. Refuse it too.
4 sent again later
the same bytes, a perfect match, arriving at 14:20 with the timestamp of 14:05. Refuse it: too old.

Delivery 2 is a forgery, or damage: one digit changed and the fingerprint has nothing in common with the genuine one. The forger cannot fix the header to match without the secret. Delivery 3 is the one that catches people out. The JSON means exactly the same thing, but its characters are different, so its signature is different. A signature covers the exact bytes of the body, not what the JSON means. That is why a receiver must verify the body as it arrived, before anything parses it, tidies it or re-indents it, and why section C’s call log, which stores a reformatted copy, cannot be used to check a signature. Stripe’s documentation puts it plainly: “Any manipulation to the raw body of the request causes the verification to fail.”

Delivery 4 is a replay: someone who captured a genuine delivery sends it again, unchanged, later. Its signature is perfect, because it is the library’s own. The timestamp is what stops it. It is inside the signed string, so changing it breaks the signature, and the receiver refuses any delivery whose timestamp is too far from its own clock. The library’s contract allows 5 minutes, which is also the default in Stripe’s libraries. 14:20 is fifteen minutes after 14:05, so delivery 4 is refused even though everything about it is genuine.

So a receiver’s check is: keep the body exactly as it arrived; read the two Library- headers; join the timestamp, a dot and the raw body; compute HMAC-SHA256 of that with the secret; compare the result with the signature header; check the timestamp is no more than 5 minutes from the receiver’s own clock; then, and only then, read the JSON and act. Most of that order is forced, because each step needs what the one before it produced. The timestamp check is the exception: Stripe’s documentation does it after the comparison, but done first it refuses exactly the same deliveries. One detail of the comparison matters to whoever writes it: it should be constant-time, checking every character even after the first difference, so an attacker cannot learn from how quickly a refusal comes back how much of a forged signature was right. GitHub’s documentation says “Never use a plain == operator” for exactly this reason.

Now the mock. Send delivery 2 to your receiver mock and it answers 200 received, as it did on the mock built for this session for a changed body, a wrong signature and no signature at all. That is Session 6’s rule again, a mock matches your rules and never checks them, and it is why the 401 bad signature example exists: a client can only see the refusal by asking for it, by name or by code. A mock can show a sender what a receiver will answer; it can never show that the signature was right.

Session 4 met post-response scripts. A pre-request script is the same kind of JavaScript, run just before a request is sent. This one does the library’s calculation and sets both headers on the request it is attached to. It was run through newman, Postman’s command-line runner, on three bodies, and each signature it produced was recomputed separately and agreed.

  1. Add a collection variable webhookSecret to Library sender, with the value practice-secret-7f3a.
  2. Open the Deliver book.overdue request’s scripts, look for the word “Pre-request”, and paste this. Put it on that one request, not on the collection: on the collection it would re-sign Forged and Retry of evt_1001 too, and quietly undo the tasks in sections E and F.
// Optional, not graded: sign this delivery the way the library does.
const hmacLib = require('crypto-js');
const secret = pm.collectionVariables.get('webhookSecret');
const timestamp = Math.floor(Date.now() / 1000).toString();
const body = pm.request.body.raw;
const signed = timestamp + '.' + body;
const signature = hmacLib.HmacSHA256(signed, secret).toString();
pm.request.headers.upsert({ key: 'Library-Timestamp', value: timestamp });
pm.request.headers.upsert({ key: 'Library-Signature', value: 'sha256=' + signature });

Every line maps onto a step above: read the secret, take the time now as a Unix timestamp, take the body exactly as written, join them with a dot, compute HMAC-SHA256, and set the two headers, replacing the ones you typed by hand. Because it uses the time now, its signatures differ from the ones printed in this session, and that is correct. One trap, found while testing it: the library variable is called hmacLib, not CryptoJS, because Postman already has a CryptoJS of its own and declaring a second one stops the script with an error.

F. When a delivery fails: retries, and the same event twice

A sender only knows a delivery worked if the receiver says so, so the contract has to define “worked”. The library’s is the common one: any 2xx answer, within 10 seconds. RFC 9110 says a 2xx means the request “was successfully received, understood, and accepted”, which is exactly what a sender needs to hear. Anything else is a failed attempt: a 4xx or 5xx, a redirect, which Stripe’s documentation says it also treats as a failure, or no answer within 10 seconds, which GitHub also asks of receivers.

A failed attempt is retried, and every sender words that differently, so the contract must spell it out. The library’s retries come 1 minute, 10 minutes and 1 hour after the first attempt, and then it gives up: four attempts in all. Real senders vary. Stripe’s documentation says it “attempts to deliver events to your destination for up to three days with an exponential back off in live mode”, the same backoff Session 4 taught, used by a sender rather than a client. GitHub’s says the opposite: “GitHub does not automatically redeliver failed deliveries”, and leaves it to a person pressing a Redeliver button. Neither is wrong; a receiver’s builder just has to be told which one they are dealing with.

This looks like it breaks Session 4’s rules, and it is worth seeing why it does not. Session 4 said never retry a 400, 401, 403 or 404, and never retry a write. Those rules are for a client, which can read the refusal and fix its own request. A sender cannot: it has no way to tell a receiver’s permanent refusal from a passing fault, such as a receiver halfway through being updated, so senders like Stripe retry every failed attempt and leave the receiver to cope with seeing an event again. And a delivery is a write, which is exactly why Session 4 kept writes for Session 8: retrying one is only safe when the receiver is built for it, which is this section’s point.

Retries have a consequence that surprises everyone the first time. Picture a receiver that does all its work first, which takes 12 seconds, and then answers 200. The work happened. But the library stopped waiting at 10 seconds, counted a failure, and a minute later sends the same event again. The receiver now has the same event twice, and nothing it did wrong caused it. That is why every delivery attempt of one event carries the same id, while the timestamp and the signature are new on each attempt, because the library signs each attempt when it sends it, as Stripe’s documentation says Stripe does. Here are two attempts at evt_1001, both genuine:

two attempts at one event · both signatures verified
attempt 1, 14:05:00
> Library-Timestamp: 1790863500
> Library-Signature: sha256=fb8e8778a7b825ea...4b8f3
> {"id": "evt_1001", "type": "book.returned", ...}

attempt 2, 14:06:00, after the first got no answer in time
> Library-Timestamp: 1790863560                    new
> Library-Signature: sha256=0583ae65bf94799f...77a46   new
> {"id": "evt_1001", "type": "book.returned", ...}    the same body, the same id

Two more things a stranger needs to hear, both about what the library cannot promise. It makes up to four attempts at every event, so an event may arrive more than once, and if all four attempts fail, not at all. And it does not promise order: Stripe’s documentation says it “doesn’t guarantee the delivery of events in the order that they’re generated”, and a retried book.overdue can arrive after the book.returned that followed it. That is what occurredAt is for.

A receiver that adds a returned book to a member’s reading count each time a delivery arrives will now count book 8 twice. Making a receiver handle the same event twice safely is Session 8’s subject, and the id you just designed is what it starts from. Today’s job is the contract: say plainly that duplicates will happen, so nobody building a receiver is surprised by one. The other half of the fix is already in the contract: answer within 10 seconds. A receiver that has more work to do should store the event, answer 200, and do the work afterwards, which Stripe and GitHub both recommend, so that slow work never turns into a retry.
