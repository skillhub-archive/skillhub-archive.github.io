A. Errors that carry on: -ErrorAction

When a command fails, PowerShell prints a message, usually in red. That does not mean it stopped. To see what happens next, put a second command on the same line after a semicolon, ;: PowerShell runs the first command, then the second, exactly as if you had pressed Enter between them. The file data/nope.txt does not exist; today it stands for any file that is missing.

an error, and then the next command anyway · captured live
PS C:\Users\you\ps-lab> Get-Content data/nope.txt; 'next line ran'
Get-Content: Cannot find path 'C:\Users\you\ps-lab\data\nope.txt' because it does not exist.
next line ran
PS C:\Users\you\ps-lab> Get-Content data/nope.txt, data/orders.csv | Measure-Object |
  Select-Object -ExpandProperty Count                                        one line, wrapped here
Get-Content: Cannot find path 'C:\Users\you\ps-lab\data\nope.txt' because it does not exist.
9

This is a non-terminating error: the command reports the problem and carries on with the rest of its work. In the second command, Get-Content could not read the first file, said so, and still read all 9 lines of orders.csv, and the next command on the line ran too. (Get-Content takes a wildcard in its path as well, as Session 3’s Select-String did: data/*.csv reads every CSV file in data.) Many errors from cmdlets are this kind.

Choosing what happens: -ErrorAction. Session 6 named -ErrorAction as one of the common parameters that every cmdlet takes. It tells one command what to do when it meets a non-terminating error. It takes four values you will use:

-ErrorAction
What the command does with the error
Then
Continue
shows it (the default, when you give no -ErrorAction)
carries on
Stop
shows it, and makes it a terminating error
stops
SilentlyContinue
hides it
carries on
Ignore
hides it, and leaves it out of $Error (below)
carries on

A terminating error is one that stops instead of carrying on. This one stops everything after it: neither the rest of the line at the prompt nor the rest of a script runs. With Stop, next line ran never prints; with SilentlyContinue, there is no message at all:

Stop, then SilentlyContinue · captured live
PS C:\Users\you\ps-lab> Get-Content data/nope.txt -ErrorAction Stop; 'next line ran'
Get-Content: Cannot find path 'C:\Users\you\ps-lab\data\nope.txt' because it does not exist.
PS C:\Users\you\ps-lab> Get-Content data/nope.txt -ErrorAction SilentlyContinue; 'next line ran'
next line ran

PowerShell also keeps a list of recent errors in the variable $Error, newest first. SilentlyContinue hides the message but still adds the error to that list; Ignore leaves it out of the list as well.

Hiding an error is rarely what you want in a script: an error nobody sees is exactly how a report goes quietly wrong. Keep SilentlyContinue for a command whose failure genuinely does not matter.

B. Catching an error: try and catch

try { CODE } catch { CODE } runs the code in the try block. If a terminating error happens there, PowerShell stops the try block at that point and runs the catch block instead; with no error, it skips catch. The word catch comes straight after the try block’s closing brace. One thing to watch: try sees only terminating errors.

try misses a non-terminating error · captured live
PS C:\Users\you\ps-lab> try { Get-Content data/nope.txt } catch { 'caught' }
Get-Content: Cannot find path 'C:\Users\you\ps-lab\data\nope.txt' because it does not exist.
PS C:\Users\you\ps-lab> try { Get-Content data/nope.txt -ErrorAction Stop } catch { 'caught' }
caught

The first error was non-terminating: Get-Content reported it and finished normally, so as far as try could tell, nothing went wrong, and catch never ran. The rule to remember: inside try, add -ErrorAction Stop to a command whose error you want to catch.

What went wrong: $_ in catch. Inside catch, $_ holds the error itself, the way it held each object in Session 2’s Where-Object. The error is an object of the type ErrorRecord. Its Exception property holds the details, and $_.Exception.Message is just the message text, ready to put into a message of your own with Session 5’s $( ). A try can be typed over several lines, as functions were in Session 6:

your own words around the message · captured live
PS C:\Users\you\ps-lab> try {
>>   Get-Content data/nope.txt -ErrorAction Stop
>>   'Read it'
>> } catch {
>>   "Could not read it: $($_.Exception.Message)"
>> }
Could not read it: Cannot find path 'C:\Users\you\ps-lab\data\nope.txt' because it does not exist.
PS C:\Users\you\ps-lab> try { Get-Content nope.txt -ErrorAction Stop } catch { $_.GetType().Name }
ErrorRecord

Read it never printed: the error stopped the try block on the line before. A terminating error also stops the whole pipeline it is in, not just the command that failed. Here the missing file comes first, and Stop ends everything, so orders.csv is never counted:

a terminating error stops the whole pipeline · captured live
PS C:\Users\you\ps-lab> try { Get-Content data/nope.txt, data/orders.csv -ErrorAction Stop |
  Measure-Object } catch { 'caught' }                                        one line, wrapped here
caught

C. Errors that stop only their own line

Terminating errors come in two sizes, which Microsoft names by how far they reach. A script-terminating error stops everything after it: the rest of the line at the prompt, the rest of a script. The Stop error in section A was this kind. A statement-terminating error stops only the statement it happened in, one command line, pipe and all, and then PowerShell goes on to the next statement. Some cmdlets report their failures this way, and Import-Csv on a missing file is one:

a statement-terminating error · captured live
PS C:\Users\you\ps-lab> Import-Csv data/nope.csv; 'next line ran'
Import-Csv: Could not find file 'C:\Users\you\ps-lab\data\nope.csv'.
next line ran
PS C:\Users\you\ps-lab> try { Import-Csv data/nope.csv } catch { 'caught' }
caught
PS C:\Users\you\ps-lab> Import-Csv data/nope.csv -ErrorAction SilentlyContinue; 'next line ran'
Import-Csv: Could not find file 'C:\Users\you\ps-lab\data\nope.csv'.
next line ran

Three things to see. It stops its own statement, then the next one runs: that is why Session 5’s script, whose Import-Csv could not find its file, carried on to its last line. try catches it as it is, with no -ErrorAction Stop. And -ErrorAction does not change it at all: SilentlyContinue did not hide it, and Stop would not stop a script after it either. Writing into a folder that does not exist is the same kind of error for Export-Csv:

Export-Csv into a missing folder · captured live
PS C:\Users\you\ps-lab> Import-Csv data/orders.csv | Export-Csv out/missing/x.csv; 'next line ran'
Export-Csv: Could not find a part of the path 'C:\Users\you\ps-lab\out\missing\x.csv'.
next line ran

Notice the wording, too. Each cmdlet words its own messages: Get-Content says Cannot find path, Import-Csv says Could not find file, and a missing folder is Could not find a part of the path. So which kind of error does a command give? The message will not tell you. Try it, as here, or stop guessing: section D makes a script stop on every kind.

D. Make a script stop: $ErrorActionPreference

A script that runs on its own, as Session 8’s will, should stop when something goes wrong, not carry on and report a half-done job. Adding -ErrorAction Stop to every command is easy to forget, and it does nothing for section C’s kind anyway. $ErrorActionPreference is a preference variable: it holds the -ErrorAction that every command uses when it is not given one, and it starts as Continue. Set it to Stop as the first line of a script’s code, and an error of any of the three kinds stops the script. First, a script without it:

~/ps-scripts/stop-demo.ps1 · a script file, typed in VS Code
# stop-demo.ps1: reads a file that is not there.
Import-Csv "$HOME/ps-lab/data/nope.csv"
'Still going'
it carries on · captured live
PS C:\Users\you\ps-lab> ~/ps-scripts/stop-demo.ps1
Import-Csv: C:\Users\you\ps-scripts\stop-demo.ps1:2
Line |
   2 |  Import-Csv "$HOME/ps-lab/data/nope.csv"
     |  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
     | Could not find file 'C:\Users\you\ps-lab\data\nope.csv'.
Still going

Now add the preference as the first line of code, after the comment, and save it over the old one:

~/ps-scripts/stop-demo.ps1 · a script file, typed in VS Code
# stop-demo.ps1: reads a file that is not there, and stops.
$ErrorActionPreference = 'Stop'
Import-Csv "$HOME/ps-lab/data/nope.csv"
'Still going'
it stops, and the prompt is untouched · captured live
PS C:\Users\you\ps-lab> ~/ps-scripts/stop-demo.ps1
Import-Csv: C:\Users\you\ps-scripts\stop-demo.ps1:3
Line |
   3 |  Import-Csv "$HOME/ps-lab/data/nope.csv"
     |  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
     | Could not find file 'C:\Users\you\ps-lab\data\nope.csv'.
PS C:\Users\you\ps-lab> $ErrorActionPreference
Continue

Still going is gone: the script stopped at the error. And back at the prompt, $ErrorActionPreference is still Continue. That is Session 5’s rule about a script’s variables: what a script sets is cleared away when it ends, so the setting reaches only that script, and set inside a function, only that function. Typed at the prompt, though, it would hold for everything you type in that window afterwards, which is rarely what you want. In a script with a param() block, the line goes just below it, since param() comes first in the code (Session 6).

An error that does not matter. A single command can still choose for itself: -ErrorAction on a command beats the preference for that command alone. With $ErrorActionPreference = 'Stop' at the top, a line ending -ErrorAction SilentlyContinue carries on quietly past its own non-terminating error, and every other line still stops. That does not work for section C’s kind, which -ErrorAction does not reach: the preference stops the script on it all the same, so put that one command in a try instead. So the habit is: Stop at the top, and choose otherwise only line by line, on purpose.

E. Your own errors: throw, and warnings

Some failures raise no error at all. When only the last folder in a path is missing, Get-ChildItem with -Recurse does not complain, not even with Stop, so neither try nor the preference sees it. Instead it takes that last part as a name to look for in every folder further down from the one that does exist, and lists whatever it finds. There is no nofolder anywhere in the lab, so here it finds nothing:

no error at all · captured live
PS C:\Users\you\ps-lab> Get-ChildItem nofolder -Recurse -File -ErrorAction Stop; 'next line ran'
next line ran

There is no archive folder at the top of the lab either, but there is one inside logs, so the same command lists that one instead, again with no error. A mistyped path can hand a script the wrong files without a word:

a different folder, and no error · captured live
PS C:\Users\you\ps-lab> Get-ChildItem archive -Recurse

    Directory: C:\Users\you\ps-lab\logs

F. Always tidy up: finally

A finally { CODE } block goes after catch, and its code runs every time: after try succeeds, after catch has run, and even when catch stops the script with throw. Use it to undo something the try started, such as a working file. This script copies a file into a working file in out, and removes the working file however the copy went. It uses Session 3’s Set-Content, Add-Content and Remove-Item:

~/ps-scripts/tidy.ps1 · a script file, typed in VS Code
# tidy.ps1: copies a file through a working file, and always removes the working file.
param([string]$Source = "$HOME/ps-lab/data/orders.csv")
$ErrorActionPreference = 'Stop'
$work = "$HOME/ps-lab/out/working.tmp"
try {
  'Copy of the file' | Set-Content $work
  Get-Content $Source | Add-Content $work
  'Copied it'
} catch {
  throw "Stopped: $($_.Exception.Message)"
} finally {
  Remove-Item $work
  'Removed the working file'
}

G. Exit codes: exit, $LASTEXITCODE and $?

Every program ends with a number, its exit code: 0 means it went fine, and anything else means it did not. You do not see it on screen, but a program that runs another one reads it to decide whether the run failed, and in Session 8, Windows’ Task Scheduler will read your scripts’ codes this way. exit N ends a script at once, with exit code N.

To see a script’s exit code, run it the way another program would: pwsh -NoProfile -File SCRIPT starts a new PowerShell 7, runs that one script, and closes again (-NoProfile skips any start-up settings of your own, so the run is the same everywhere). Then the automatic variable $LASTEXITCODE holds the code it ended with. A script that stops on an error it did not catch ends with exit code 1; one that reaches its end ends with 0. This script exits with 1 when any order is pending:

if ($pending.Count -gt 0) {
  "$($pending.Count) orders pending"
  exit 1
}
