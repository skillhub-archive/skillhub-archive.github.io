Auth: proving who you are

Every request so far has been anonymous, and every service answered anyway because it had nothing to protect. Real APIs want to know who is asking before they hand over private data, spend your money, or let you change anything. Today you authenticate three genuinely different ways, learn where a credential must never be put, and send your first requests that are shaped to change something.

A. Why an API asks who you are

Sessions 1 and 2 sent perhaps forty anonymous requests and never met a refusal, because both practice services are built to answer anybody. That is unusual. Most APIs want proof of identity before they will act, and the reasons sort into three kinds:

Private data
Your messages, your orders, your customer list. The server has to know whose data to hand over, and that you are that person.
Cost and limits
Someone pays per request, and Session 2’s rate-limit headers only mean something once the count belongs to a known caller.
Changing things
Creating, replacing and deleting are not reversible by the server. Section F is those requests, and this is why they need proof first.

Two words get used loosely and are worth separating once, because the rest of the session depends on the difference:

  • Authentication is who are you. You present a credential and the server decides whether it believes you.
  • Authorisation is what are you allowed to do. A server can believe exactly who you are and still refuse, because that account is not permitted to do this particular thing.

That distinction has a visible consequence in status codes, and it is the most commonly muddled pair in HTTP:

Code
Name
What it is actually saying
401
Unauthorized
"I do not know who you are." You sent no credential, or one the server rejected. It should carry a WWW-Authenticate header naming what it wants. Despite the name, this is the authentication failure.
403
Forbidden
"I am not letting you do that." Usually you are known and simply not permitted. This is the authorisation failure.

The names are the wrong way round and you cannot fix that, so learn the pair rather than the words: 401 is about identity, 403 is about permission. You will see both live in this session, from two different services, within about five minutes of each other.

And a warning that will save you real debugging time: plenty of production APIs do not follow that rule. You will meet a 403 that really means "you forgot your key" and a 401 that really means "your plan does not include this". So read the response body as well as the status, exactly as Session 2 taught, because the body is usually where the server says which of the two it meant. One of the two examples in this session gets it arguably wrong, and section B says which.

This session covers three mechanisms, in the order of how much machinery each needs:

Mechanism
In one line
API key
One long string identifying an account or app. Sections B and C.
Basic auth
A username and password, encoded into one header. Section D.
Bearer token
A string standing for a granted permission, usually short-lived. Section E, and what OAuth2 hands out.

B. The API key, and a service that genuinely requires one

An API key is a single long opaque string identifying the account or application making a request. Opaque means you never parse it or read anything out of it: it is a name the server recognises, nothing more. It is the simplest credential there is, which is why it is everywhere, and its simplicity is also its weakness: anyone holding the string is you, for as long as it is valid.

Neither postman-echo nor jsonplaceholder has keys, and that is the reason a third service joins today. Both of them answer every request no matter what you send, so neither can show you a credential actually gating access. NASA’s public API can.

Read this before you send a NASA request. NASA publishes a shared key, literally the string DEMO_KEY, so anybody can try the API with no signup. It is deliberately small: the responses in this session showed X-Ratelimit-Limit: 10, and building this session exhausted it in about ten requests. When it runs out you get a 429 and a Retry-After measured in hours, not minutes, and it is shared with everyone else on your network. So: you need exactly two successful NASA requests in this whole session, one here and one in section C. Send those, read them, and do your repeating and experimenting against postman-echo, which has no limit at all. Nothing that gets marked right or wrong today needs a live NASA call: every NASA question in Parts 2 to 6 is answerable from the transcripts in this section, and the two tasks that ask you to send one accept a 429 just as readily as a 200.

First, ask for something with no key, which costs nothing against the budget:

no credential at all · the refusal
> GET https://api.nasa.gov/planetary/apod
403 Forbidden
{
  "error": {
    "code": "API_KEY_MISSING",
    "message": "No api_key was supplied. Get one at https://api.nasa.gov:443"
  }
}

Read that against section A and you can see the inconsistency being warned about. Nothing was supplied, so by the letter of the spec this should be a 401 with a WWW-Authenticate header saying what to send. NASA answers 403. It is not a bug and NASA is not unusual; it is what a large share of real APIs do. The body is what saves you: API_KEY_MISSING says plainly which of the two problems it is, and that is why Session 2 spent a whole session on reading the whole response rather than the status alone.

Now spend one request. api_key goes on the end of the URL as a query string, which Session 1 taught:

the same URL, with the demo key · costs 1 of your 10
> GET https://api.nasa.gov/planetary/apod?api_key=DEMO_KEY
200 OK
X-Ratelimit-Limit: 10
X-Ratelimit-Remaining: 8

{
  "date": "2026-09-10",
  "title": "LDN 1295: The Giraffe Nebula",
  "media_type": "image",
  "url": "https://apod.nasa.gov/apod/image/2609/LDN1295_giraffe_1024.jpg",
  "service_version": "v1"
}

A real credential, a real API, and the picture NASA published that day. Look at the two rate-limit headers, because they are the ones Session 2 named as plumbing you must not ignore and then told you not to trust on jsonplaceholder, where caching made them meaningless. Here they are real and they count down as you spend. They are not, however, personal: the demo key is limited per network address, so the number you see is what your whole address has left, not what you have left. That is why the transcript above reads 8 and not 9 after a single request, and why yours will read something else again. Session 4 is about what to do when they reach zero; today they are simply proof that a keyed request is a counted request.

If you do run out, this is what you get, and it is worth recognising on sight:

what running out looks like
> GET https://api.nasa.gov/planetary/apod?api_key=DEMO_KEY
429 Too Many Requests
Retry-After: 22797
X-Ratelimit-Limit: 10
X-Ratelimit-Remaining: 0

{
  "error": {
    "code": "OVER_RATE_LIMIT",
    "message": "You have exceeded your rate limit. Try again later..."
  }
}

Retry-After: 22797 is a number of seconds, so a little over six hours. The keyless 403 above keeps working while you are rate-limited, which is a small mercy: you can always go back and look at that one.

C. Where the key goes, and why a query string is the worst place

The key in section B rode in the query string, because that is what NASA’s own documentation shows and it is the easiest thing to type. It is also the least safe place to put a credential, and the reason is not cryptographic. HTTPS encrypts the whole request including the query string, so the key is not readable in transit. The problem is what happens at both ends, after the encryption is undone.

A URL is treated as an identifier, not as a secret, by almost every piece of software that touches it. That means a key in a query string reliably ends up written down in places nobody thought about:

  • Server access logs. Web servers log the full path and query of every request, as plain text, by default. Your key is now in a log file, and log files get shipped to third-party monitoring tools.
  • Browser history and bookmarks, if the URL is ever opened in a browser.
  • Proxy and gateway logs, on any hop between you and the server.
  • Copy and paste. A URL is the thing people paste into chat, tickets and screenshots when asking for help. A header is not.

A header avoids all of that, because headers are not logged by default and are not part of the thing people share. You can watch the difference rather than take it on trust, using postman-echo, which costs nothing and echoes your request back. Send a made-up key in the query string first:

a key in the query string · note where it turns up
> GET https://postman-echo.com/get?api_key=SECRET123
200 OK
{
  "args": { "api_key": "SECRET123" },
  "headers": { ... nothing about the key here ... },
  "url": "https://postman-echo.com/get?api_key=SECRET123"
}

The key appears twice, and the second one is the problem. It is in args, which is just echo parsing your query string. It is also inside url, and url is exactly the string that gets logged, bookmarked, and pasted. Now send the same key as a header instead:

the same key in a header · and the URL is clean
> GET https://postman-echo.com/get
> header:  X-Api-Key: SECRET123
200 OK
{
  "args": {},
  "headers": { ... "x-api-key": "SECRET123" },
  "url": "https://postman-echo.com/get"
}

args is empty and url has nothing secret in it. The key arrived, the server can read it, and the URL is now safe to paste into a ticket. That is the whole argument, and you just watched both halves of it.

Which header name? There is no standard one, which is the honest answer and a mildly annoying fact about the industry. X-Api-Key is the most common convention, but you will meet Api-Key, X-Auth-Token, and plenty of APIs that put their key in the Authorization header instead. The API’s own documentation is the only authority, so the skill is not memorising a name, it is knowing to look for one.

NASA settles that for itself, and you can see it without spending anything. Do not send these yourself, because you have one budgeted request left; this is what came back when the same call was made five times over, changing only the header name:

one request, five header names · do not run these, just read them
> GET https://api.nasa.gov/planetary/apod   (header name varied)
X-Api-Key: DEMO_KEY              429   OVER_RATE_LIMIT
Api-Key: DEMO_KEY                403   API_KEY_MISSING
X-Auth-Token: DEMO_KEY           403   API_KEY_MISSING
Authorization: DEMO_KEY          403   API_KEY_MISSING
Authorization: Bearer DEMO_KEY   403   API_KEY_MISSING

Only the first name was read at all. The other four are perfectly reasonable conventions and NASA simply does not look at them, so as far as it is concerned no key was supplied, which is exactly what API_KEY_MISSING says. The first line is the interesting one: a 429 means the key was found, recognised and counted, and the quota happened to be spent when this was captured. So the status alone tells you whether the server even read your header, which is a diagnostic worth keeping: 403 with a missing-key body when you know you sent one usually means the name is wrong, not the key.

Now spend your second and last NASA request, to prove this is not a postman-echo trick. NASA accepts the identical key either way, so you can move it out of the URL with no other change:

the same NASA call, key moved into a header · costs your last budgeted request
> GET https://api.nasa.gov/planetary/apod
> header:  X-Api-Key: DEMO_KEY
200 OK
{
  "title": "LDN 1295: The Giraffe Nebula",
  ... the same object as before, from a URL with no credential in it ...
}

Same key, same data, and the URL you could now paste anywhere. That pair of requests is one of the three ways this session’s milestone asks for, and the tradeoff you can state about it is exactly the list above.

D. Basic auth: a username and password, encoded and not encrypted

Basic auth is the oldest mechanism in HTTP and the one that shows the machinery most clearly. You send a username and password on every single request, joined by a colon, and the pair is put through base64, which is a way of rewriting arbitrary text using only safe characters so it survives being carried in a header. The whole credential goes into one header:

the shapeAuthorization: Basic <base64 of username:password>

Those angle brackets are a stand-in, not something you type. <base64 of username:password> means "the real value goes here, brackets and all replaced". You will see this convention in every API document you ever read, and the rest of this session uses it without comment.

That Authorization header is the one Session 1 named and deferred: "carries proof of who you are (Session 3)". This is it. The first word is the scheme, meaning which kind of credential follows, and Basic is one scheme. Section E is another.

postman-echo has an endpoint that genuinely checks a username and password, with a published pair anyone can use: postman and password. Ask for it with nothing first:

no credential · and this one gets the status code right
> GET https://postman-echo.com/basic-auth
401 Unauthorized
WWW-Authenticate: Basic realm="Users"

Unauthorized

Compare that with NASA’s 403 from section B, because this is the same situation answered correctly. A 401, because the server does not know who you are, plus a WWW-Authenticate header that names the scheme it wants. That header is the server telling you how to try again, which is why a well-behaved 401 is more useful than a 403: it does not just refuse, it says what would work. realm="Users" is a label for the protected area, and you can ignore it. Note the body, too, which is the bare word Unauthorized as plain text rather than JSON: not every error body is structured, and NASA’s API_KEY_MISSING object from section B is the more helpful of the two shapes.

Now build the credential. postman:password in base64 is cG9zdG1hbjpwYXNzd29yZA==, and you can send that header by hand:

the credential, sent as a header you built yourself
> GET https://postman-echo.com/basic-auth
> header:  Authorization: Basic cG9zdG1hbjpwYXNzd29yZA==
200 OK
{ "authenticated": true }

Postman will do the encoding for you, and in normal work you would let it: look for an Authorization tab alongside the Headers and Body tabs under the URL bar, pick the Basic type, and type the username and password into the two boxes. The exact wording and position of that tab have moved between Postman versions, so look for the word "Authorization" rather than a specific spot. Doing it by hand once is worth it anyway, because it shows you that the tab is a convenience and not a different mechanism: both produce the identical header, and the server cannot tell which you used.

Now the part that matters most in this whole section. Base64 is not encryption, and it is not obfuscation. It is a reversible rewriting with no key and no secret involved, so anybody who sees the header can turn it back:

the credential, read straight back out
> decode  cG9zdG1hbjpwYXNzd29yZA==
postman:password

Any online base64 decoder does that in a second, with no cleverness at all. So Basic auth sends your actual password, in effectively readable form, on every request. Two consequences follow, and they are the tradeoffs you should be able to state:

  • HTTPS is not optional with Basic auth, it is the only thing protecting the password. Over plain http:// the credential is readable by anything on the network path. This is the clearest case in the whole track for why the s in https matters.
  • The credential is long-lived and total. It is your real password, it does not expire on its own, it grants everything your account can do, and revoking it means changing your password everywhere. Bearer tokens in section E exist largely to fix exactly that.

You can watch the header arrive, too, which makes the point concrete. Send the same credential to the ordinary echo endpoint:

what the server actually receives
> GET https://postman-echo.com/get
> header:  Authorization: Basic cG9zdG1hbjpwYXNzd29yZA==
200 OK
{
  "headers": { ... "authorization": "Basic cG9zdG1hbjpwYXNzd29yZA==" },
  "url": "https://postman-echo.com/get"
}
Your turn Get a real 401, then authenticate, then decode your own credential

  2. Add a header Authorization with the value Basic cG9zdG1hbjpwYXNzd29yZA== and send again. Confirm 200 and authenticated: true.
  3. Now do it the other way: remove your header, find Postman’s Authorization tab, choose Basic, and enter postman and password. Confirm you get the same 200.
  4. Prove the encoding is not protection. Paste cG9zdG1hbjpwYXNzd29yZA== into any online base64 decoder and read the result. Then say out loud why HTTPS is mandatory here.

E. Bearer tokens, and OAuth2 in outline

A bearer token is a string that stands for a granted permission rather than for your identity. The name is the idea: whoever bears it may use it, so the server does not ask who you are, only whether the token is valid. It rides in the same Authorization header as Basic, under a different scheme:

the shapeAuthorization: Bearer <token>

Compare that with Basic and the improvements are the whole reason it exists:

Property
Basic versus Bearer
What you send
Basic sends your real password every time. Bearer sends a token that is not your password, so the password never leaves the place you typed it.
Lifetime
A password lasts until changed. A token is usually short-lived, often an hour, so a stolen one stops working on its own.
Scope
A password grants everything. A token can be issued for a narrow permission, say read-only access to one thing.
Revoking it
Killing a password affects everywhere it is used. A single token can be revoked on its own, leaving everything else working.

Where the honesty has to come in: neither of this track’s no-account services validates a bearer token, so this session cannot show you one being accepted and rejected the way section D showed Basic. What it can show you is exactly what leaves your machine, which is the part you control:

a bearer token, as the server receives it
> GET https://postman-echo.com/get
> header:  Authorization: Bearer your-token-here
200 OK
{
  "headers": { ... "authorization": "Bearer your-token-here" },
  "url": "https://postman-echo.com/get"
}

Note that echo answered 200, and would have answered 200 for any token at all, including nonsense. It is echoing, not checking. That is worth saying plainly so you do not mistake a success here for a validated credential: the only thing this proves is that your header was well formed and arrived. When you meet a real token-protected API, the same header shape is what it will want.

Where those tokens come from: OAuth2, in outline

OAuth2 is not a way of logging in. It is a way of granting an application limited access to something of yours without giving it your password. That is the entire problem it solves, and it is worth stating as a scenario: you want a scheduling app to read your calendar. You do not want to hand that app your Google password, because that would give it your email, your files and everything else, forever. OAuth2 is the arrangement that lets you say "this app, my calendar, read only" and hand over nothing else.

Three parties, and naming them makes the sequence readable:

you
The resource owner. The calendar is yours and only you can approve access to it.
the app
The client. It wants access, and it must never see your password.
the provider
The authorisation server, Google here. It already knows your password and can vouch for you.

The most common arrangement is the authorisation code flow, and it is genuinely a sequence rather than a single request, which is why it is one of Part 3’s ordering exercises:

1
The app sends you to the provider. It redirects your browser to Google, using the 3xx machinery from Session 2, saying which app is asking and for what.
2
You log in and approve, at the provider. This is the crucial step: you type your password into Google, never into the app.
3
The provider redirects you back with a short-lived code. A single-use string, not a token, and useless on its own.
4
The app exchanges the code for an access token, server to server, proving it is really that app. This is where the token is issued, and it is why the code alone is not enough for a thief.
5
The app calls the API with Authorization: Bearer <token>, which is the header you sent by hand above.

The dependency running through those five steps is what makes it safe: the code cannot be exchanged by anyone who did not register as that app, and the token cannot be obtained without your approval at step 2.

Where this track stops, stated plainly. Implementing that flow needs a registered application, a client secret and a redirect URL you control, which means an account and a server, and this session is deliberately account-free. So you will not implement OAuth2 here, today or later in this track. What you should carry away is the shape: which party holds your password (the provider, never the app), what the code is for, and that the thing you finally send is an ordinary Authorization: Bearer header, identical to the one you just sent by hand. When you meet a real OAuth2 API, Postman has a helper that walks the flow for you, and you will recognise every step of it.

F. The requests that change things: PUT, PATCH and DELETE

Session 1 named three methods and deferred them to this session, and they belong here for a reason worth stating: these are the requests auth exists to gate. A wrong GET wastes a moment. A wrong DELETE removes something.

You already know POST from Session 1, which creates something new. The other three change or remove something that already exists:

Verb
Means
What you send
PUT
Replace it
The whole new version of the thing. Anything you leave out is genuinely left out.
PATCH
Change part of it
Only the fields you want changed. Everything else is left as it was.
DELETE
Remove it
Nothing. The URL says which thing, and that is the whole request.

The PUT-versus-PATCH difference is the one that catches people, and it is not a matter of taste: sending a partial body with PUT is how fields get silently wiped. jsonplaceholder answers both faithfully enough to show it. Send only a title with PUT:

PUT with only one field · watch what is missing from the answer
> PUT https://jsonplaceholder.typicode.com/posts/1
> header:  Content-Type: application/json
> body:    { "title": "only a title" }
200 OK
{
  "title": "only a title",
  "id": 1
}

userId and body are gone. Post 1 has had four fields since Session 1, and the answer has two. That is PUT doing exactly what it promises: you said "replace it with this", this had one field, so the rest no longer exists. Now the same body with PATCH:

PATCH with the identical body · and nothing else moves
> PATCH https://jsonplaceholder.typicode.com/posts/1
> header:  Content-Type: application/json
> body:    { "title": "only a title" }
200 OK
{
  "userId": 1,
  "id": 1,
  "title": "only a title",
  "body": "quia et suscipit\nsuscipit recusandae consequuntur expedita et cum..."
}

Four fields, one of them changed. Same URL, same header, same body, different verb, and the difference is whether three fields survived. If you remember one thing from this section, make it that.

And DELETE, which needs no body at all:

DELETE · the URL is the whole request
> DELETE https://jsonplaceholder.typicode.com/posts/1
200 OK
{}

An empty object, and a 200. Real APIs very often answer 204 No Content instead, which means "done, and there is deliberately nothing to tell you". That is the same idea as Session 2’s 304: a successful response with no body, where reading only the body would make it look like nothing happened. Both are worth recognising as success.

The honest caveat, carried forward from Session 1. jsonplaceholder answers all three verbs convincingly and persists none of them. Send that PUT, then GET https://jsonplaceholder.typicode.com/posts/1 again, and you will find the original title back, exactly as Session 1 warned about its POST. That is what makes it a safe place to practise a DELETE: you cannot break anything, for anybody. It also means the response bodies above are the service telling you what would have happened, which is enough to learn the verbs and not enough to learn what a real destructive call feels like. Sessions 5 and 6 are where you design and mock an API whose writes you control. One correction while we are here: Session 1 said this session would cover a service where a write genuinely sticks. That was optimistic. Practising a real destructive call needs an API whose data is actually yours, and getting one means an account, which nothing before Session 6 asks you for.

G. Keeping the credential out of the request you share

Every credential on this page is public on purpose. The moment one is real, three habits stop being tidiness and start being the job.

First: never type a live secret into a request you might share. A Postman request holds its headers, so a shared request, an exported collection, a screenshot or a pasted URL carries the credential with it. The fix is to keep the secret in one place and refer to it by name everywhere else. Postman calls that a variable, written in double curly braces, and you would use it exactly where the literal went:

the literal, do not share thisX-Api-Key: DEMO_KEY
the same request, by referenceX-Api-Key: {{nasa_key}}

The value lives once, in what Postman calls an environment, and every request that needs it points at the name. Change the key in one place and every request follows. Share the request and the name goes, not the secret. Postman’s own no-account mode limits what you can save, which Session 1 disclosed, so treat the mechanics here as something to recognise rather than something to set up today: look for "Environment" or "Variables", and expect the exact wording to have moved between versions. The habit is the lesson, not the menu path.

Second: a key in a URL is a key you have already shared, which is section C’s whole argument. Once you are using variables, this gets easier rather than harder, because {{nasa_key}} in a header is no more effort than a literal in a query string.

Third, and the one people learn the hard way: a leaked credential is not fixed by deleting the message. If a real key ends up in a chat, a ticket, a screenshot or a commit, the only reliable response is to rotate it: issue a new one, then revoke the old one, in that order so nothing breaks in between. Deleting the message does nothing, because you cannot know who already read it, and automated scanners watch public places for exactly this.

The one that would actually cost you something. Nothing in this session uses a credential of yours, so nothing here can leak. But the first time you use a real key, you will be pasting a request into a chat to ask a colleague why it fails. Replace the credential with an obvious placeholder before you paste, every time, and get in the habit now while the stakes are zero. If you ever paste a real one by accident: rotate first, apologise second.

H. The milestone: three ways, and the tradeoffs

The milestone is to authenticate three genuinely different ways and explain what each costs you. You have already sent all three; this is doing it without the scaffolding and being able to say why each one is the way it is.

Explaining is the graded half. Anyone can copy a header. The thing worth having is being able to say, when an API hands you a choice, which one you want and what you are accepting.

> 4. the tradeoffs
api key    identifies an app or account, not a person. Lasts until
           rotated. Whoever holds it is you, with everything the
           key can do.
basic      your real username and password, base64-encoded and so
           readable. Lasts until the password changes. A thief gets
           the account itself, everywhere.
bearer     a granted permission, not your password. Usually expires
           within hours. A thief gets only what that token was
           scoped to, and only until it expires or is revoked.

> 5. query string against header
HTTPS encrypts both, so nothing changes in transit. It matters
because a URL is treated as an identifier and gets written down:
server logs, browser history, proxy logs, and whatever people
paste into chat. A header is in none of those.
