A. Timestamps: Get-Date and -Format

A script that runs while you are away has to say when it did each thing, so every line it records starts with the time. Get-Date gives the date and time now. Its -Date parameter gives it a date and time to use instead of now: this section’s examples use one, so they print the same for you as for this page.

a date, printed the computer’s way · captured live
PS C:\Users\you\ps-lab> Get-Date -Date '2026-03-04 08:05:09'

Wednesday, March 4, 2026 8:05:09 AM

That layout is the computer’s own: it follows the language settings, so another computer prints the same moment differently. This page’s Linux computer, which has no language set, printed Wednesday, 04 March 2026 08:05:09. A log needs one layout, the same every day, and -Format gives you one you choose. It takes a pattern of letters, each standing for one part of the date:

a layout you choose · captured live
PS C:\Users\you\ps-lab> Get-Date -Date '2026-03-04 08:05:09' -Format 'yyyy-MM-dd HH:mm:ss'
2026-03-04 08:05:09
PS C:\Users\you\ps-lab> Get-Date -Format 'yyyy-MM-dd HH:mm:ss'
2026-10-15 10:05:38  your time

The second one has no -Date, so it prints the moment you ran it. The year comes first on purpose: then the dates also sort in time order as plain text, character by character (Session 2), so a sorted list of log lines or dated file names is in time order too. With -Format, Get-Date gives text, a String, ready to put into a message.

Not quite every computer. With English language settings, and most others, that pattern prints exactly as above. A few language settings still change it: switching PowerShell’s language for one window on this page’s computer, Finnish and Danish printed the time as 08.05.09, Thai and Arabic printed their own calendars’ years, and the text given to -Date is read in the computer’s own calendar too, so with Thai or Persian settings even '2026-03-04 08:05:09' meant a different year, and with Arabic settings it was not understood at all. A log line is for people, so that is fine. When a program will read the time, use -Format s instead: a fixed layout, with a T between the date and the time. For the time Get-Date reads from the computer’s clock, it came out the same under every language setting tried. Section F uses it.

the time now, in the sortable layout · captured live
PS C:\Users\you\ps-lab> Get-Date -Format s
2026-10-15T13:22:20  your time

The trap: case matters in the pattern. MM is the month and mm the minutes. HH is the hour from 00 to 23, and hh the hour on a 12-hour clock, from 01 to 12, so eight in the morning and eight in the evening both print 08. Swap the case and nothing complains; you just get the wrong date:

the wrong case, and no error · captured live
PS C:\Users\you\ps-lab> Get-Date -Date '2026-03-04 08:05:09' -Format 'yyyy-mm-dd hh:MM:ss'
2026-05-04 08:03:09
PS C:\Users\you\ps-lab> Get-Date -Date '2026-03-04 20:05:09' -Format 'yyyy-MM-dd hh:mm:ss'
2026-03-04 08:05:09

In the first, the month became the minutes (05) and the minutes became the month (03). In the second, five past eight in the evening reads as the morning.

You will also see"$(Get-Date)": Get-Date with no -Format, inside double quotes. That prints the month first, as 03/04/2026 08:05:09, on every computer this page was checked on, whatever its language settings. Give -Format a pattern instead, and you choose the layout.

B. A log of your own: Write-Log

A scheduled script runs with nobody watching. What it prints goes nowhere you will see: on macOS and Linux, cron throws it away (section G shows where it says so), and on Windows, Task Scheduler’s window closes when the script ends. So the script keeps a log: a text file it adds one line to for each thing it does, each line starting with the time. Session 3’s Add-Content adds a line to the end of a file, and makes the file the first time.

To give every line the same shape, wrap that in a small function (Session 6), Write-Log. The function uses $log, a variable the script sets before it calls the function: a function can read a variable that was set before it ran. This script reads the orders and logs what it did:

~/ps-scripts/log-demo.ps1 · a script file, typed in VS Code
# log-demo.ps1: reads the orders, and logs what it did.
$ErrorActionPreference = 'Stop'
$log = "$HOME/ps-lab/out/log-demo.log"
function Write-Log {
  param([string]$Message)
  "$(Get-Date -Format 'yyyy-MM-dd HH:mm:ss') $Message" | Add-Content $log
}
Write-Log 'Started'
$orders = Import-Csv "$HOME/ps-lab/data/orders.csv"
Write-Log "Read $($orders.Count) orders"

It prints nothing: everything it has to say goes into the log. Run it twice, then read the log. Each run added its two lines below the ones before:

Logging a failure: throw on its own. A log that stops when the script stops never says why. So catch the error, log it, and let the script still fail loudly, as in Session 7. Inside catch, throw on its own, with no message, throws the same error on: the script stops, PowerShell shows the original error, and pwsh -File still ends with exit code 1. Here the file to read becomes a parameter, so a run can be pointed at a file that is not there:

~/ps-scripts/log-demo.ps1 · a script file, typed in VS Code
# log-demo.ps1: reads the orders, and logs what it did, or why it failed.
param([string]$File = "$HOME/ps-lab/data/orders.csv")
$ErrorActionPreference = 'Stop'
$log = "$HOME/ps-lab/out/log-demo.log"
function Write-Log {
  param([string]$Message)
  "$(Get-Date -Format 'yyyy-MM-dd HH:mm:ss') $Message" | Add-Content $log
}
Write-Log "Started: $File"
try {
  $orders = Import-Csv $File
} catch {
  Write-Log "FAILED: $($_.Exception.Message)"
  throw
}
Write-Log "Read $($orders.Count) orders"

C. The flight recorder: Start-Transcript

Your log says only what you told it to say. When something goes wrong that you did not expect, you want everything the script showed. Start-Transcript -Path FILE starts recording everything that appears in the window, output, warnings, errors and Write-Host text alike, into FILE, until Stop-Transcript. Like an aeroplane’s flight recorder, you seldom read it, and you are very glad of it the day something goes wrong.

~/ps-scripts/transcript-demo.ps1 · a script file, typed in VS Code

Start-Transcript -Path "$HOME/ps-lab/out/transcript.txt"

Read the recording from the top. A block of lines between the rows of stars describes the run: when it started, who ran it, on which computer, the whole command line that started PowerShell, its process number and its version. Every value in that block is your own, so it will differ from this page. Three more things to know. A transcript replaces its file each time, unless you add -Append, which adds the new run to the end; that is why a transcript is for one run you want to look at, and your own log is for every run. If the script stops on an error, the transcript still gets the error and its closing block, with a line holding TerminatingError where it stopped. And because it names your user name, your computer’s name and the command line, read a transcript before you share it.

D. Safe to run twice

A scheduled script runs every day, and some days it runs again because you started it by hand to test it. So it must do the right thing however many times it has run before. Three habits make a script safe to run twice. First, the problem, in miniature. New-Item makes a folder the first time; the second time, the folder is already there:

the second run fails · captured live
PS C:\Users\you\ps-lab> New-Item -ItemType Directory out/archive | Out-Null
PS C:\Users\you\ps-lab> New-Item -ItemType Directory out/archive | Out-Null
New-Item: An item with the specified name C:\Users\you\ps-lab\out\archive already exists.

In a script with $ErrorActionPreference = 'Stop', that error stops every run after the first. Habit 1: make sure a folder is there with -Force. On a folder, New-Item -Force makes it if it is missing, and if it is already there, keeps it, files and all, without an error. (It also prints the folder, which is why | Out-Null, from Session 4, follows it.)

-Force on a folder keeps what is in it · captured live
PS C:\Users\you\ps-lab> 'keep me' | Set-Content out/archive/note.txt
PS C:\Users\you\ps-lab> New-Item -ItemType Directory out/archive -Force | Out-Null
PS C:\Users\you\ps-lab> Get-Content out/archive/note.txt
keep me

The trap: on a file, -Force means “start it over”. New-Item on a file that is already there, with -Force, replaces it with an empty one, and says nothing. To count the file’s lines before and after, put the command in parentheses: PowerShell runs what is inside them first, and .Count after the closing parenthesis then reads the Count property of what came back, just as $tickets.Count read a variable’s in Session 5. So (Get-Content FILE).Count is how many lines FILE has, and any other property can be read the same way:

-Force on a file empties it · captured live

PS C:\Users\you\ps-lab> New-Item out/archive/note.txt -Force | Out-Null
PS C:\Users\you\ps-lab> (Get-Content out/archive/note.txt).Count
0

Habit 2: replace results, append only to the log, on purpose. A report should be the same after one run or ten, so write it with a command that replaces the file: Export-Csv and Set-Content do, as Sessions 3 and 4 showed. A log should grow by one run each time, so it uses Add-Content. Mix them up and the report doubles with every run:

Habit 3: check before you create or remove. Either way, a relative path such as data/orders.csv is looked up from there, as Session 5 showed, and fails. F. Schedule it: Task Scheduler, or cron

Now the heartbeat runs on its own. A scheduler needs to know three things: what to run (a program, and the words to hand it), when, and how (what to do on battery power, after a missed run, and so on). Windows keeps these in a scheduled task; macOS and Linux keep them in one line of a file called a crontab. Both run the same command you just tested: pwsh -NoProfile -NonInteractive -File SCRIPT.

Why -NonInteractive. Session 6 showed that a script missing a [Parameter(Mandatory)] value asks for it, and that -NonInteractive turns the question into an error instead. A scheduled script has nobody to answer. On this page’s Windows computer, a task that ran such a script without -NonInteractive was still waiting 47 seconds later, with no file written, and Task Scheduler’s own limit for a run is 72 hours by default; with -NonInteractive, the same task failed at once with exit code 1. A failure you can see beats a run that waits for days.

The full path to pwsh. A scheduler may not search the folders your prompt does for programs, so give it the program’s full path. (Get-Command pwsh).Source prints it: Get-Command from Session 1 finds the command, and its Source property is the file it runs.

The words for -Argument are one piece of text, with the script’s path in double quotes inside it, so a space in a folder name, such as a user name with a space, cannot split the path in two. The trap: a time that moves when the clocks change.
