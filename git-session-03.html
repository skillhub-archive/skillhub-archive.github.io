Branches are just pointers

A branch is not a copy of your project and it is not a folder. It is one line in one small file, holding one commit hash. This session opens that file, watches the pointer move when you commit, and then merges a branch back with a single sliding step, so that working on a branch stops feeling risky and starts feeling free.

Milestone Do work in isolation on a branch and merge it back.
git

You do not need the folders from Sessions 1 and 2. Step one below builds a brand new repository called branch-lab from scratch, in under a minute, so that every learner starts from exactly the same one-commit history. No account and no internet are needed for any of this session.

This is a workbook, not a reading. You will predict what a command does to your repository, reassemble command sequences, fill blanks, and write from scratch, and each part hands you less scaffolding than the last. The goal is the one this whole track is built on: read a Git command and know what it will do before you press enter.

A. Build a fresh lab

Session 2 left git-sandbox in a state that depends on choices you made along the way, so this session does not use it. Instead you build a small, brand new repository whose history is identical for everybody: one folder, one file, one commit. Every transcript and every drill in this session assumes that starting point.

One new flag before you paste. git init -b main is the git init you already know, plus -b, which names the first branch outright. Session 1 had you set init.defaultBranch so that new repositories start on main; -b main says it explicitly on the spot instead of relying on that setting, so this block behaves identically on any machine, including one where that setting was never made.

PowerShell (Windows default) · build branch-lab
cd ~
mkdir branch-lab
cd branch-lab
git init -b main
Set-Content notes.md "Branch lab"
Add-Content notes.md "Created while learning Git."
Add-Content notes.md "Safe to delete."
git add notes.md
git commit -m "Add notes.md"
Git Bash / macOS / Linux · build branch-lab
cd ~
mkdir branch-lab
cd branch-lab
git init -b main
echo "Branch lab" > notes.md
echo "Created while learning Git." >> notes.md
echo "Safe to delete." >> notes.md
git add notes.md
git commit -m "Add notes.md"
Already have a folder called branch-lab? Read this first

The mkdir line will fail if the folder already exists. The cd line after it will then succeed anyway and take you into the folder you already had, so the rest of the block runs against whatever is already in there instead of a clean start. The giveaway is the git init -b main line, which prints Reinitialized existing Git repository instead of Initialized empty Git repository. Two ways out.

The safe one: pick another name. Replace branch-lab with branch-lab-2 in the mkdir and cd lines and carry on. Everything else in the session is identical.

The other one: delete the old folder first. This permanently removes that folder and everything inside it, so only run it if you are certain you do not need what is in there.

PowerShellcd ~ Remove-Item -Recurse -Force branch-lab
Git Bash / macOS / Linuxcd ~ rm -rf branch-lab

The commit line prints the summary you learned to read in Session 1:

git commit · the first commit in a brand new repository
> git commit -m "Add notes.md"
[main (root-commit) eae0405] Add notes.md

Now confirm the result, and there is one more flag to name before you run it. --decorate=short asks Git for the short form of the (HEAD -> main) label you have been seeing since Session 1. That label is already on by default when you are reading output at a terminal, so adding the flag changes nothing about what you see; naming it explicitly is what keeps these transcripts correct even if you copy output somewhere else, which is the piping quirk Session 2 explained. Two commands, and the output should match this exactly apart from the hash:

confirm the starting point
> git log --oneline --decorate=short
eae0405 (HEAD -> main) Add notes.md

> git status
On branch main
nothing to commit, working tree clean

One commit, on main, nothing outstanding. That is the whole lab.

B. What a branch literally is

The old way first. Before version control, trying something risky without losing what already worked meant copying the whole project folder to project-backup-v2. That is slow, it doubles the disk space, you end up with v2, v3 and v3-final, and when the experiment works you have to merge the two folders back together by hand, file by file. Every part of that is what a branch replaces.

So here is what a branch actually is, and the fastest way to believe it is to open the files. You already know how to write a file from Session 1 (Set-Content and Add-Content). Reading one back is a single new command, and it is an ordinary file read, nothing to do with Git:

PowerShellGet-Content <file>
Git Bash / macOS / Linuxcat <file>

As in Session 1, <file> in angle brackets is a placeholder: you type a real file name there, not the word "file". Forward slashes work in both shells for the paths below. Point it at .git/HEAD, inside the hidden .git folder Session 1 introduced:

.git/HEAD · one line, naming a branch
> Get-Content .git/HEAD
ref: refs/heads/main

That is the entire file. It does not hold a commit; it holds the words ref: and then a path, refs/heads/main, which points at another file inside .git. So open that one too, and compare it against git rev-parse HEAD, a command that asks Git to resolve HEAD all the way down to the hash it eventually names:

.git/refs/heads/main · one line, and it is the commit
> Get-Content .git/refs/heads/main
eae04054a80c2a40c4572fe44eedb4138ab717dd

> git rev-parse HEAD
eae04054a80c2a40c4572fe44eedb4138ab717dd

The same 40-character hash, twice. That is the "by way of" Session 2 promised. Session 2 said HEAD is a reference to the commit you are on, reached through the current branch. Now you can see the chain as three real things on disk:

.git/HEADone line naming the current branch: ref: refs/heads/main
.git/refs/heads/mainone line holding one commit hash: eae04054a80c...
the committhe snapshot itself, stored inside .git

So, the definition this whole session rests on: a branch is a movable pointer to a commit. The branch main is not the project, and it is not a folder of your files. It is the file .git/refs/heads/main, whose entire contents are 40 hash characters plus the newline that ends the line. Forty-one bytes.

Which means creating a branch writes one more 41-byte file. Nothing is copied, nothing is duplicated, no files move. That, and not enthusiasm, is why everyone tells you branching in Git is cheap: it is cheap in the literal sense that it costs 41 bytes and no measurable time, whether your project is three files or thirty thousand.

Your turn Open the branch and see the hash
  1. In branch-lab, read .git/HEAD with Get-Content or cat. Confirm it names refs/heads/main.
  2. Read .git/refs/heads/main. Confirm it is a single 40-character line.
  3. Run git rev-parse HEAD and check the two strings are character-for-character identical.
  4. Say the chain out loud before moving on: HEAD names main, main holds a commit hash, that hash is the commit you are standing on.

C. Listing what branches exist

git branch with no arguments lists every branch in the repository and puts a * beside the one you are currently on:

git branch · list them, current one starred
> git branch
* main

Three variations are worth knowing now. Each answers a different question:

git branch --show-current · just the name, nothing else
> git branch --show-current
main

--show-current prints one bare name and no *. It is the one to reach for when you only want to answer "where am I", and because the output is a plain name it is also what scripts use.

git branch -v · add the commit each branch points at
> git branch -v
* main eae0405 Add notes.md

-v is short for verbose, and it adds two things per line: the short hash of the commit that branch points at, and that commit's subject, which is the first line of its message. Given what section B just showed you, -v is really printing the contents of each branch file in a readable form. It is the command you will use most in this session, because it is the fastest way to see which branch is pointing where.

git branch -a · all branches, including ones from a remote copy
> git branch -a
* main

-a is short for all, and it adds the branches that live on a remote copy of the repository, meaning a copy somewhere else that yours is connected to, such as one on GitHub. branch-lab is not connected to anything, so -a shows the same single line as plain git branch. Once a repository does have a remote, those extra entries appear with a remotes/ prefix, like remotes/origin/main. Remotes are Session 5, and that is where you will find out what those entries mean and how they get there. It is named here only so the flag is not a surprise.

D. Creating a branch, and switching between branches

Two jobs, and one command does both. git switch -c <name> creates a branch and moves you onto it. The -c is short for create. The new branch is created pointing at the commit you are on right now, which is the only sensible place to start from:

git switch -c feature · create it and move onto it
> git switch -c feature
Switched to a new branch 'feature'

Now look at what that did, first with the two listing commands from section C:

two branches, and the * has moved
> git branch
* feature
  main

> git branch -v
* feature eae0405 Add notes.md
  main    eae0405 Add notes.md

Read that second block twice, because it is the point of the session. Both branches show the same short hash and the same commit subject. They are two pointers aimed at one commit. Nothing was copied, no file was duplicated, and there is not a second version of notes.md anywhere. That is the cleanest possible proof of the 41-byte claim, and you can confirm it at the file level too:

the new branch file holds the same hash, and HEAD now names it
> Get-Content .git/HEAD
ref: refs/heads/feature

> Get-Content .git/refs/heads/feature
eae04054a80c2a40c4572fe44eedb4138ab717dd

Switching to a branch that already exists drops the -c, because there is nothing to create:

git switch main · move to an existing branch
> git switch main
Switched to branch 'main'

Notice the wording differs by one word, and it is a useful word: "a new branch" when you created one, "branch" when you moved to an existing one. If you ever meant to switch to an existing branch and Git tells you it made a new one, you have a typo. Get the name wrong the other way and Git simply refuses:

a name that does not exist
> git switch nope
fatal: invalid reference: nope

A fatal, so nothing happened at all, and note that Git does not offer a "did you mean" suggestion here. Run git branch and read the list.

The old way, which you will see everywhere. Before switch existed, both of these jobs were done by git checkout: git checkout -b <name> to create and move, and git checkout <name> to move to an existing branch. They still work, and they give an identical result, right down to the message. Do not run this one. It is printed here only so that you recognise it, and running it would leave you standing on a spare branch that none of the transcripts below expect:

git checkout -b · the older spelling, the same outcome
> git checkout -b legacy-style
Switched to a new branch 'legacy-style'

So why does switch exist? Because checkout does several unrelated jobs. The same command that changes branch also restores a single file over your edits, and can also put you in a state where HEAD points straight at a commit instead of a branch. One mistaken argument therefore does something quite different from what you meant, and the command tells you nothing about which job it thinks it is doing. git switch does exactly one job: change which branch you are on. Use switch in your own work, and recognise checkout when a tutorial or a colleague uses it. (That HEAD-points-straight-at-a-commit state has a name, detached HEAD, and it is Session 7.)

Your turn Create a branch and prove nothing was copied
  1. In branch-lab, run git switch -c feature.
  2. Run git branch and confirm the * is now beside feature.
  3. Run git branch -v. Confirm both branches show the same short hash and the same message. This is the one result to actually stop and look at.
  4. Read .git/refs/heads/feature and confirm it holds the same 40-character hash as .git/refs/heads/main.
  5. Run git switch nope and read the error, so you recognise it later. Then make sure you are back on feature with git branch --show-current.

E. Commit on a branch, and watch the pointer move

You are on feature. Do a small piece of work there. Create a file and commit it, exactly the way Session 1 taught:

PowerShellSet-Content feature.md "The feature notes."
Git Bash / macOS / Linuxecho "The feature notes." > feature.md
git add and git commit, on the feature branch
> git add feature.md
> git commit -m "Add feature.md"
[feature c73c51d] Add feature.md
 1 file changed, 1 insertion(+)
 create mode 100644 feature.md

Two details in that first line. The name in the brackets is feature, not main: the commit was recorded on the branch you are standing on. And the words (root-commit) are absent this time, because that label only appears on the very first commit in a repository, the one with no parent. This commit has a parent, so it is an ordinary link in the chain.

Now the question that matters. What happened to the two pointers?

git branch -v · one moved, one did not
> git branch -v
* feature c73c51d Add feature.md
  main    eae0405 Add notes.md

feature moved forward to the new commit. main did not move at all. It is still holding the same hash it held before you started. This is the whole mechanism of working in isolation, and it is not clever: committing rewrites one 41-byte file, the one for the branch you are on, and leaves every other branch file untouched. Nothing you do on feature can disturb main, because nothing you do on feature writes to main.

F. What switching actually changes, and why --all matters

Committing moves a pointer. Switching changes the files in your folder. When you switch branches, Git makes the working tree, meaning the ordinary files you can see and open, match the snapshot that branch points at. To watch that happen you need to list the folder, so here are the two shells, listing plain names one per line:

PowerShellGet-ChildItem -Name
Git Bash / macOS / Linuxls -1

Session 1 gave you Get-ChildItem -Force and ls -a for showing hidden entries. These are the same two commands without that: -Name and -1 (the digit one) both mean "just the names, one per line", so the two shells print the same thing and you can compare against the transcript.

Now predict before you press enter. This is the habit the whole track is for, and this is the first time in the track where the answer is not obvious. You are on feature. The folder holds notes.md and feature.md. You are about to run git switch main. Commit to an answer out loud: which files will be in the folder afterwards? Then run it.

the working tree changes to match the branch
> Get-ChildItem -Name
feature.md
notes.md

> git switch main
Switched to branch 'main'

> Get-ChildItem -Name
notes.md

feature.md is gone from the folder. If that looks like Git deleted your work, read this sentence carefully: it did not. The commit holding feature.md is still in the repository, and the branch feature still points straight at it. What changed is which snapshot your folder is showing. main points at a commit whose snapshot never contained feature.md, so a folder matching that snapshot does not contain it either. Run git switch feature and the file is back, instantly, because it never went anywhere.

One honest limit on that, because it is exactly where the demonstration can look broken. This applies only to work you have committed. A file you created but never committed belongs to no snapshot on any branch, so Git has nothing to swap it for and simply leaves it where it is. It follows you across the switch and git status keeps reporting it as untracked. Nothing is wrong; the file just is not part of the history yet.

Now the other thing that changed when you switched, and it catches people. You are standing on main. Ask for the history:

git log --oneline --graph --decorate=short · from main, one commit
> git log --oneline --graph --decorate=short
* eae0405 (HEAD -> main) Add notes.md

Your feature commit has vanished from the log as well. It is not lost: git log starts at the branch you are on and walks backwards along parent pointers, exactly as Session 1 described. The feature commit is not behind main, it is ahead of it on a different pointer, so the walk never reaches it.

This is where --all earns its keep. Session 2 introduced --graph and it drew a plain column of dots, because a straight line of commits on one branch has no shape to draw. That was not --graph being useless; it was --graph having only one branch to look at. --all tells git log to start from every branch, not just the current one, and the two commands together are how you see the repository rather than your corner of it:

git log --oneline --graph --all --decorate=short · every branch
> git log --oneline --graph --all --decorate=short
* c73c51d (feature) Add feature.md
* eae0405 (HEAD -> main) Add notes.md

Both commits, each labelled with the branch that points at it. Look hard at the shape, because the next section turns it into a rule: this is a straight line. There is no fork in it. main sits directly below feature, which is another way of saying main is an ancestor of feature: every commit main has, feature already has, and feature has one more on top. Nothing has happened on main since feature split off.

Memorise the long form as one unit, because you will type it constantly: git log --oneline --graph --all --decorate=short.

G. Bringing the work back: a fast-forward merge

The work on feature is finished and you want it on main. git merge <name> brings the named branch into the branch you are currently on, so the direction matters: you stand on the branch that should receive the work, and you name the branch the work is coming from. You are already on main, which is where you want to be:

git merge feature · run from main
> git merge feature
Updating eae0405..c73c51d
Fast-forward
 feature.md | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 feature.md
  • Updating eae0405..c73c51d names the two commits main moved between: from the one it was on, to the one it is on now.
  • Fast-forward is Git telling you which kind of merge it did. This is the word to look for.
  • The last three lines are the same changed-files summary a commit prints, listing what arrived in your working tree as a result.

Here is the definition, and it comes straight off the graph you just looked at. A fast-forward is possible precisely when the branch you are on has not moved since the other branch split off. That was true here: main was an ancestor of feature, so there was nothing to combine. Every commit main had, feature already had. Git did not need to work out how to reconcile two sets of changes, because there was only ever one set. So it did the only thing left to do: it slid the main pointer forward to the commit feature was already on. One 41-byte file rewritten.

Two consequences worth stating plainly, because they will not be true next session. A fast-forward creates no new commit, so the history stays a straight line and nothing new appears in your log. And because no commit is created, Git never asks you for a commit message; the command runs and returns you to your prompt.

Session 4 is the other case: both branches moved, so main is no longer an ancestor of feature, there genuinely are two sets of changes to combine, and Git has to build a real merge commit, ask you for a message, and sometimes ask you to resolve a conflict where the two sides changed the same lines. (There is also a second way to combine branches, rebase, which reshapes history rather than merging it. That is Session 8.)

Look at what the merge left behind:

after the merge · two names, one commit
> git log --oneline --graph --all --decorate=short
* c73c51d (HEAD -> main, feature) Add feature.md
* eae0405 Add notes.md

> git branch -v
  feature c73c51d Add feature.md
* main    c73c51d Add feature.md

> Get-ChildItem -Name
feature.md
notes.md

Both branch names now decorate the same commit, and git branch -v shows both holding the same hash. That is exactly the state you were in right after git switch -c feature, just one commit further along: two pointers, one commit. And feature.md is in your folder again, this time as part of main.

H. Deleting a branch you have finished with

Once the work is merged, the branch name has done its job and it is normal to remove it, so the list stays short. git branch -d <name> deletes a branch, with -d for delete:

git branch -d feature
> git branch -d feature
Deleted branch feature (was c73c51d).

> git branch
* main

> git log --oneline --graph --all --decorate=short
* c73c51d (HEAD -> main) Add feature.md
* eae0405 Add notes.md

Nothing was destroyed. Deleting a branch removes the 41-byte pointer file and that is all it removes. Commit c73c51d is still right there in the log, still holding feature.md; the only change is that one name refers to it now instead of two. Once you accept that a branch is a pointer, this stops being reassuring and starts being obvious: you deleted a pointer, so you lost a pointer.

That hash in the message is not decoration. (was c73c51d) is Git handing you the way back, and it matters in the case this example does not show: deleting a branch whose commits are not merged anywhere else really would leave those commits with no name pointing at them, and that short hash is how you would find them again. Session 8 is where you learn to use it.

Git tries hard to stop you reaching that situation by accident. -d refuses to delete a branch whose work is not already merged into the branch you are on. You have no branch called wip, so this next block is a read-only example rather than something to run, and here is what that refusal looks like:

git branch -d on a branch with unmerged work · example only
> git branch -d wip
error: the branch 'wip' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D wip'
hint: Disable this message with "git config set advice.forceDeleteBranch false"

That refusal is a safety net, and the hint names the override: -D, a capital D, deletes anyway. It is being named here so that you recognise it and know it is not a typo for -d. Do not reach for it yet. Right now it is the one command in this session that can genuinely lose work, and Session 8 covers when it is safe and how to recover if it was not.

Your turn Take feature all the way through

All in branch-lab, starting on feature. Before each step that produces output, say what you expect.

  1. Create feature.md with the line for your shell above, then git add feature.md and git commit -m "Add feature.md".
  2. Run git branch -v. Confirm feature moved to the new commit and main did not move.
  3. Predict, out loud, which files the folder will hold after you switch. Then run git switch main and Get-ChildItem -Name (or ls -1). Confirm feature.md is gone.
  4. Run git log --oneline --graph --decorate=short, then run it again with --all added. Confirm the first hides the feature commit and the second shows it, and that the graph is a straight line with no fork.
  5. Run git merge feature. Confirm the output says Fast-forward, and that feature.md is back in your folder.
  6. Run git branch -d feature, then the --all log again. Confirm the commit is still there with only main pointing at it.

I. The milestone: work in isolation, then merge it back

Section H walked you through it with every output printed. The milestone is the same shape with the scaffolding removed, a different branch name, and two commits instead of one, so that the pointer has to move twice before you bring it home.

You are in branch-lab, on main, with a clean working tree. Do the whole thing without scrolling back up. If you get stuck on a command name, use git branch and git branch -v to work out where you are first; knowing how to orient yourself is part of the milestone.

Your turn The milestone: a branch, two commits, and a merge
  1. Create a branch called drafts and move onto it in one command.
  2. Create draft-one.md with any single line in it, and commit it with the message Add draft-one.md.
  3. Create draft-two.md the same way, and commit it with the message Add draft-two.md.
  4. Confirm main has not moved, using the command that shows each branch with the commit it points at.
  5. Switch back to main, then list the folder. Confirm both draft files have vanished from it, and be able to say why in one sentence.
  6. Merge drafts into main. Confirm the output contains the word Fast-forward, and be able to say why a fast-forward was possible here.
  7. Delete drafts. Then draw the graph across every branch and confirm both draft commits are still in the history.

You have hit the milestone when you did all seven from memory, and you can explain step 5 and step 6 without looking them up.

What you should have seen (your hashes will differ)

Step 4, after both commits, with drafts two ahead and main untouched:

> git branch -v
* drafts 312f23c Add draft-two.md
  main   c73c51d Add feature.md

Step 5, back on main, both drafts gone because main points at a snapshot that never contained them:

> git switch main
Switched to branch 'main'

> Get-ChildItem -Name
feature.md
notes.md

Step 6, the merge. Two files arrive at once, and it is still a fast-forward because main never moved while you were on drafts:

> git merge drafts
Updating c73c51d..312f23c
Fast-forward
 draft-one.md | 1 +
 draft-two.md | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 draft-one.md
 create mode 100644 draft-two.md

Step 7, the delete and the final graph. Four commits, one branch, nothing lost:

> git branch -d drafts
Deleted branch drafts (was 312f23c).

> git log --oneline --graph --all --decorate=short
* 312f23c (HEAD -> main) Add draft-two.md
* b39de35 Add draft-one.md
* c73c51d Add feature.md
* eae0405 Add notes.md
