Git under the hood, and how to script it

Every command in the ten sessions was built for a person. Git has a second set built for programs, and the two have names: porcelain and plumbing. This workbook is not a tour of Git's insides for their own sake. It is the interface Git offers to scripts, which means every section ends somewhere useful: a hash you can compute, an object you can read, a question about a repository you can answer without opening it.

Milestone Read a repository's object graph by hand, then write a script that answers a question about it.
git

This one is a bonus, and it sits outside the graded ten. There is no level number, no checkbox on the Hub, and nothing here changes your 10/10. The track is finished; this is the next thing to learn if you want it, and it assumes everything the ten sessions taught.

You do not need any folder from an earlier session. Step one builds a small new repository called plumbing-lab from nothing, and it is disposable like the others. No account and no network.

This is a workbook, not a reading. You will predict what a command prints before running it, reassemble sequences, fill blanks, and write scripts from scratch. The goal is the one the whole track was built on, aimed one layer lower: read a plumbing command and know what it will tell you before you press enter.

Learn & Do

Short concept, then immediately your turn. Run each task in your own terminal before moving on, and tick the box once you have seen the result with your own eyes.

How to read the transcripts below. A line that starts with > in blue is what you type. Everything underneath it is what Git printed back. Do not type the > itself.

This session is unusual about what differs on your machine, and the difference is the lesson. Most sessions told you that hashes vary. Here, some of them genuinely do not. Blob and tree hashes are computed from content alone, so every hash below that names a blob or a tree will be identical on your machine, character for character, provided you paste the lab block as written. Commit and tag hashes will differ, because they include the time you ran the command and your name and email. Section H is about exactly that difference. Where a transcript shows a commit hash, treat it as a shape rather than a value. Dates and paths differ as always.

A. Porcelain and plumbing

These are Git's own two words for its own two command sets, and once you know them, a lot of confusing documentation stops being confusing. The metaphor is a bathroom: the porcelain is the part you are meant to touch, and the plumbing is what runs behind the wall and makes it work.

porcelainBuilt for people. git status, git log, git commit, git merge: everything from the ten sessions. Friendly output, colours, helpful hints, and a format that is allowed to change between versions because a human is reading it.
plumbingBuilt for programs. hash-object, cat-file, rev-parse, ls-tree, ls-files, for-each-ref. Terse output, no colour, no hints, and a format that is kept stable on purpose, because scripts depend on it.

That last row is the whole reason this workbook is worth two hours. Porcelain output is not a contract. Plumbing output is. If you write a script that parses git status, a future Git may reword it and quietly break you. If you write one that reads git ls-files -s, it will still work in ten years, because that is what the command is for.

You have already used plumbing once without being told. Session 9 proved an annotated tag was a real object with git cat-file -t, and Session 3 had you open .git/refs/heads/main and read the hash inside. Both were plumbing. This workbook names the set and fills it in.

Out of scope, so you know where the edges are. Packfiles and delta compression, beyond one sentence in section C. git gc, the commit-graph file, and SHA-256 repositories. And the write half of plumbing, meaning update-index, write-tree, commit-tree and update-ref, which build objects and move refs by hand. They exist, they are how porcelain is implemented, and you do not need any of them in order to read a repository, which is what this session is for.

B. Build the lab

A small repository with a subfolder, two commits and one annotated tag. It is small on purpose: you are about to read every object in it by hand, and that is only pleasant when there are ten of them rather than ten thousand.

Both blocks below produce identical blobs and identical trees, which is why every blob and tree hash in this session will match yours exactly. Paste the one for your shell. The commit and tag objects will differ, for the reason section H gives, and nothing here depends on them.

PowerShell (Windows default) · build plumbing-lab
cd ~
mkdir plumbing-lab
cd plumbing-lab
git init -b main
git config core.autocrlf true
Set-Content hello.txt "hello"
Set-Content rates.txt "rate table v1"
New-Item -ItemType Directory docs
Set-Content docs\guide.md "how to read the rates"
git add .
git commit -m "Add the first files"
Set-Content rates.txt "rate table v2"
git add rates.txt
git commit -m "Update the rate table"
git tag -a v1.0.0 -m "First release"
Git Bash / macOS / Linux · build plumbing-lab
cd ~
mkdir plumbing-lab
cd plumbing-lab
git init -b main
git config core.autocrlf true
printf 'hello\r\n' > hello.txt
printf 'rate table v1\r\n' > rates.txt
mkdir docs
printf 'how to read the rates\r\n' > docs/guide.md
git add .
git commit -m "Add the first files"
printf 'rate table v2\r\n' > rates.txt
git add rates.txt
git commit -m "Update the rate table"
git tag -a v1.0.0 -m "First release"
Two lines in there look odd, and both are deliberate.

The \r\n in the Git Bash block. PowerShell's Set-Content ends every line with a carriage return and a line feed, the pair usually written CRLF. A plain printf 'hello\n' writes only the line feed. Those two files are different sizes on disk, and section D is entirely about that difference, so the blocks are matched here to give both shells the same starting bytes.

The git config core.autocrlf true. This setting decides what Git does with those line endings on the way in, and it is the one setting every number in this session depends on. The Git for Windows installer switches it on machine-wide, so on Windows this line changes nothing and merely makes the dependency visible. On macOS and Linux it is off by default, and without this line every blob and tree hash below would differ from the ones on this page. Setting it here, in one throwaway repository, is what makes the session reproducible on any machine. Section D is about what it actually does.

Confirm the starting point:

run in plumbing-lab · two commits and a tag
> git log --oneline --decorate=short
0e0dcc4 (HEAD -> main, tag: v1.0.0) Update the rate table
8614be1 Add the first files

Those two hashes are commit hashes, so yours will be different. That is the last time this session will say so about a commit; from section C on, assume it.

C. The four object types

A Git repository is a bag of objects and a handful of names pointing into it. There are exactly four kinds of object, and every one of them is stored the same way: content in, hash out, filed under that hash. Nothing in .git is filed under a file name.

blob
Content, with no name. The bytes of one file and nothing else. No path, no permissions, no date.
tree
Names and modes. A directory listing: which name maps to which blob or which other tree.
commit
One tree, plus history. A pointer to a single tree, zero or more parents, an author, a committer and a message.
tag
A pointer with a note. An annotated tag: which object it marks, who tagged it, when and why. Session 9's -a tags.

Read that list against what Session 1 told you and something clicks. Session 1 said a commit is a snapshot of every tracked file plus a pointer to its parent. Now you can see the machinery: the snapshot is a tree, the tree names blobs, and the commit holds one tree hash and one parent hash. That is what "snapshot" was standing in for.

And it explains something Session 3 asserted. A branch is not an object at all. It is a 41-byte file under .git/refs/heads/ holding a commit hash and a newline. Objects are content; refs are names for objects. Two different things, which is why git branch -d deletes 41 bytes and no commits.

The chain runs one way, and it is worth saying out loud before you start reading it, because every command in the rest of this session walks some part of it:

the chain, from a name down to file content
a ref  ->  a commit  ->  a tree  ->  a blob
main       "Update"      the root    the bytes of
                         directory   hello.txt

Count what is actually in there. git count-objects is plumbing, and -v makes it verbose:

run in plumbing-lab · how many objects
> git count-objects -v
count: 10
size: 0
in-pack: 0
packs: 0
size-pack: 0
prune-packable: 0
garbage: 0
size-garbage: 0

Ten objects for two commits and three files, and the arithmetic is worth doing once: three blobs, plus the docs tree, plus a root tree, is five objects for the first commit. The second commit changes rates.txt, so it needs a new blob and a new root tree, and the docs tree and the two unchanged blobs are reused, not copied. That is two more. Then two commit objects and one tag object. Five, plus two, plus three, is ten.

Your count may be higher and that is fine, because the number grows every time you stage something. size: 0 is a total in kilobytes, rounded down, so ten tiny objects come to zero. in-pack: 0 means nothing has been compressed into a packfile yet. Git eventually bundles loose objects into packfiles and stores similar ones as deltas against each other, which is how a repository with a long history stays small. That is the one sentence this session spends on packfiles.

D. hash-object, and what a hash is actually computed from

Git names an object by hashing it, and the formula is short enough to do by hand. For a blob it is:

the formula, for a blob
sha1( "blob " + <length in bytes> + <a zero byte> + <the content> )

That is the whole thing. The word blob, a space, how many bytes of content there are, a single zero byte as a separator, then the content. Hash all of that and you have the name Git files it under. This is what "content addressed" means: the name is derived from the content, so identical content anywhere in the world produces an identical name, and changed content produces a different one. There is no counter and no registry.

git hash-object computes it for you:

run in plumbing-lab · the hash of hello.txt
> git hash-object hello.txt
ce013625030ba8dba906f756967f9e9ca394464a

Now the surprise, and it is the best thing in this session. Ask your shell how big that file is, and then ask Git how big the object it stored is. They disagree.

PowerShell(Get-Item hello.txt).Length
Git Bash / macOS / Linuxwc -c < hello.txt
run in plumbing-lab · seven bytes on disk, six bytes stored
> (Get-Item hello.txt).Length
7

> git cat-file -s ce013625030ba8dba906f756967f9e9ca394464a
6

The file is seven bytes and the blob is six. The word hello is five characters, so the file on disk ends with a carriage return and a line feed, two bytes, and the stored object ends with a line feed, one byte. Git changed the content on the way in.

This is core.autocrlf, and Session 1 warned you about it without explaining it. On Git for Windows the installer turns it on machine-wide. It converts CRLF to LF when content goes into the repository and back again when files come out, so that a repository shared between Windows and everywhere else stays consistent. Session 1 showed you the warning it prints; this is the mechanism underneath.

--no-filters skips the conversion, and hashing the same file both ways is the cleanest possible demonstration:

run in plumbing-lab · the same file, two different hashes
> git hash-object hello.txt
ce013625030ba8dba906f756967f9e9ca394464a

> git hash-object --no-filters hello.txt
ef0493b275aa2080237f676d2ef6559246f56636

Two hashes for one file, and the first one is the one Git actually uses. Confirm that rather than taking it on trust, by asking the index what it recorded:

run in plumbing-lab · which of the two Git stored
> git ls-files -s hello.txt
100644 ce013625030ba8dba906f756967f9e9ca394464a 0	hello.txt

So the rule is: hash-object given a PATH applies the same filters a real git add would, which is what makes it agree with Git. --no-filters and --stdin do not, because there is no path for Git to look up a filter rule against. That is a genuinely useful distinction the moment you script anything: if your script compares a hash it computed against a hash Git stored, and the two disagree on a Windows machine, this is why.

Now do the arithmetic by hand and watch it match. The stored content is six bytes, so the formula says hash the string blob 6, a zero byte, then hello and a line feed:

Git Bash / Linux · the formula, by hand
> printf 'blob 6\0hello\n' | sha1sum
ce013625030ba8dba906f756967f9e9ca394464a *-

Character for character, the hash Git gave you. No Git involved in that command at all: just a string and a standard hashing tool. The * before the - is sha1sum noting that it read standard input in binary mode, and is not part of the hash. On macOS the tool is named shasum rather than sha1sum, and everything else is the same. That is the point at which content addressing stops being a phrase and becomes something you have done.

Two honest notes on that last command. One: it needs printf and sha1sum, which Git Bash has and PowerShell does not, so it is shown in one shell only. PowerShell can do it, but the code is long enough to obscure the idea. Two: outside this lab, on a macOS or Linux machine, you would normally write hello.txt with a line feed alone and leave core.autocrlf off. Then the file would be six bytes on disk, --no-filters would agree with the plain form, and the two-hash demonstration above would show one hash twice. Nothing would be wrong. The gap between the file and the object is not a universal fact about Git: it is what happens when a filter is switched on, which is exactly why the lab block switched one on and wrote CRLF, so that every reader can watch it happen.

E. cat-file, the object reader

Objects are stored compressed, so you cannot read them with an ordinary text tool. Prove it once, then never try again. A loose object lives under .git/objects/, in a folder named after the first two characters of its hash, in a file named after the other thirty-eight:

a loose object on disk
.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a

That file is zlib-compressed and read-only, and opening it shows binary. git cat-file is the command that decompresses and prints, and it has three flags worth knowing:

-tType. Prints one word: blob, tree, commit or tag. Session 9 used this to prove an annotated tag is its own object.
-sSize in bytes, of the content Git stored.
-pPretty print the content, formatted for the object's type.

Point it at a commit and read what a commit is really made of:

run in plumbing-lab · a commit, raw
> git cat-file -t HEAD
commit

> git cat-file -p HEAD
tree a4b0f5cc388f3552c72c8ab4dd8ddf0299cf0794
parent 8614be1bb23151ed06a5ed561a84e10ee5d88305
author Patrick Burdette <patrick@example.com> 1788109131 -0500
committer Patrick Burdette <patrick@example.com> 1788109131 -0500

Update the rate table

Six lines, and every one of them was promised by an earlier session. One tree, which is the snapshot. One parent, which is Session 1's pointer backwards. An author and a committer. A blank line, then the message. There is nothing else in a commit. No file contents, no diff, no branch name: a commit does not know which branch it is on, which is why moving a branch pointer never touches the commits.

Those long numbers are timestamps, not corruption. 1788109131 is Unix epoch seconds, the count since the start of 1970, and -0500 is the timezone offset the commit was made in. Git stores time this way because it is unambiguous and sorts correctly. Every porcelain command you have used was reformatting this for you. The tree hash on your machine will match the one above; the two timestamps and the parent hash will not.

Now the root commit, which is missing a line. Session 1 called the first commit in a repository the root commit and said it has no parent. Here is that, as stored:

run in plumbing-lab · the root commit has no parent line at all
> git cat-file -p HEAD~1
tree bfe40343cf529a54663a9b712ce92cf8ce3d03bf
author Patrick Burdette <patrick@example.com> 1788109131 -0500
committer Patrick Burdette <patrick@example.com> 1788109131 -0500

Add the first files

The parent line is not empty, it is absent. That matters for scripting: code that assumes every commit has a parent line breaks on the one commit in every repository that does not.

And there is a batch form built for scripts, which is the clearest signal that plumbing has a different audience. --batch-check reads names on standard input and prints hash, type and size for each, one line each:

run in plumbing-lab · cat-file --batch-check
> "HEAD`nHEAD^{tree}`ndeadbeefdeadbeefdeadbeefdeadbeefdeadbeef" | git cat-file --batch-check
0e0dcc4b7fe2d14b5b69b9fcf1f9af18aaf5a026 commit 246
a4b0f5cc388f3552c72c8ab4dd8ddf0299cf0794 tree 105
deadbeefdeadbeefdeadbeefdeadbeefdeadbeef missing

Three inputs, three lines, and an unknown object reports missing rather than failing. That is deliberate: a script feeding a thousand names wants a thousand answers, not an error on the first bad one. In Git Bash the same command uses printf to make the three lines rather than PowerShell's backtick-n.

The tree size of 105 is reproducible; the commit size of 246 is not. A tree's size depends only on the names, modes and hashes inside it, all of which the lab block fixes. A commit's size includes your name and your email address, so yours will differ by however many characters your name differs by. That is a small thing, and it is exactly the distinction this session keeps making.

F. rev-parse, the command that makes everything else scriptable

Every command so far needed a hash, and typing hashes is not a workflow. git rev-parse turns a name into a hash. That is its whole job, and it is the piece that makes the rest scriptable: you write the name a person would use, and the script gets the hash Git needs.

run in plumbing-lab · the five forms worth knowing
> git rev-parse HEAD
0e0dcc4b7fe2d14b5b69b9fcf1f9af18aaf5a026

> git rev-parse --short HEAD
0e0dcc4

> git rev-parse HEAD^{tree}
a4b0f5cc388f3552c72c8ab4dd8ddf0299cf0794

> git rev-parse HEAD:hello.txt
ce013625030ba8dba906f756967f9e9ca394464a

> git rev-parse v1.0.0^{}
0e0dcc4b7fe2d14b5b69b9fcf1f9af18aaf5a026
HEADThe commit you are standing on, in full. The form you will use most.
--shortThe abbreviated form, which is what git log --oneline has been showing you since Session 1. Git also accepts an abbreviation anywhere it wants a hash, provided it is long enough to be unambiguous in that repository, so a short hash you read off one command can be pasted straight into the next one.
HEAD^{tree}The tree of that commit, rather than the commit. The braces mean "the thing of this type that this resolves to".
HEAD:pathThe blob at that path, in that commit. Note it is the blob as committed, which is not necessarily what is on your disk right now.
v1.0.0^{}The commit an annotated tag points at, rather than the tag object itself. The empty braces mean "follow this until it is not a tag any more".

That last one has a trap in it worth meeting now, because it costs an afternoon when you meet it in a script instead. An annotated tag is its own object, so a tag name resolves to two different hashes depending on how you ask:

run in plumbing-lab · a tag name resolves two ways
> git rev-parse v1.0.0
1592c31ac94c7e42f4cda8a7b5ae3b539b5ca83b

> git rev-parse v1.0.0^{}
0e0dcc4b7fe2d14b5b69b9fcf1f9af18aaf5a026

> git rev-parse HEAD
0e0dcc4b7fe2d14b5b69b9fcf1f9af18aaf5a026

Without the braces you get the tag object. With them you get the commit, which is the same hash as HEAD. A script that checks "is the current commit the tagged release" and forgets the braces compares a tag hash against a commit hash, finds they differ, and reports that you are not on the release when you are. Section G has the same trap in a second syntax.

Two more small ones, both useful and both plumbing:

run in plumbing-lab · which branch, and how many commits
> git symbolic-ref HEAD
refs/heads/main

> git rev-list --count HEAD
2

symbolic-ref prints the ref name HEAD points at, in full, which is the machine-readable version of "which branch am I on". It is what Session 10's deploy hook was comparing against. rev-list --count counts commits reachable from a starting point, which is how a build number gets generated in about a hundred thousand projects.

G. Three commands that list things, and the difference that matters

These three look interchangeable and are not. The distinction is not about output format, it is about which of Git's three areas each one reads, which makes this section the plumbing payoff for Session 1:

git ls-tree
Reads a commit. What the repository looked like at that point in history.
git ls-files
Reads the index, the staging area. What would go into your next commit.
git for-each-ref
Reads the refs. Branches and tags: the names, not the content.
run in plumbing-lab · ls-tree, one level and then recursive
> git ls-tree HEAD
040000 tree 61f703bb18f9514de9813103865f6fc37d03d3a3	docs
100644 blob ce013625030ba8dba906f756967f9e9ca394464a	hello.txt
100644 blob 2435b81334b7684dea1b11ba7972774595b35f1c	rates.txt

> git ls-tree -r HEAD
100644 blob ae3118094cf377e37babdf3201f6dbca903b2e84	docs/guide.md
100644 blob ce013625030ba8dba906f756967f9e9ca394464a	hello.txt
100644 blob 2435b81334b7684dea1b11ba7972774595b35f1c	rates.txt

Read the plain form first, because it shows you the shape. Three entries: docs is a tree, and the other two are blobs. That is a directory listing, exactly as section C described, and it is one level deep. -r recurses, so the docs tree is replaced by what is inside it and every line is a blob with a full path.

The numbers on the left are modes, and three of them cover almost everything you will see: 100644 for an ordinary file, 100755 for an executable one, and 040000 for a tree. That is the entire permission model: Git records whether a file is executable and nothing else. Two more exist and are worth knowing before you point a script at somebody else's repository, because a parser that assumes three modes will eventually meet them: 120000 is a symbolic link, and 160000 is a submodule, meaning a pointer to a commit in another repository entirely.

Now the good part. Stage a change and watch two of these three commands disagree about the same file:

PowerShellSet-Content rates.txt "rate table v3" git add rates.txt
Git Bash / macOS / Linuxprintf 'rate table v3\r\n' > rates.txt git add rates.txt
run in plumbing-lab · the index and the commit, disagreeing
> git ls-files -s rates.txt
100644 f8ee2c9240de6919d833159590cce66c5d62182b 0	rates.txt

> git ls-tree HEAD rates.txt
100644 blob 2435b81334b7684dea1b11ba7972774595b35f1c	rates.txt

Same path, two different blob hashes. The index holds the version you just staged and the commit holds the version you committed earlier, and they are genuinely different objects, both stored, both real. This is Session 1's three areas, made concrete. Session 1 drew them as boxes and asked you to trust the picture; here the difference between two of them is two hashes you can read.

The 0 in the ls-files -s output is the stage number, and it is zero for every file that is not in conflict. During Session 4's merge conflict it would have been 1, 2 and 3 on the same path, for the merge base, your side and their side. That is where "unmerged path" is actually stored.

Put the lab back before moving on, because section H assumes a clean tree:

PowerShellgit restore --staged rates.txt Set-Content rates.txt "rate table v2"
Git Bash / macOS / Linuxgit restore --staged rates.txt printf 'rate table v2\r\n' > rates.txt

Finally, for-each-ref, which is the scripting form of git branch and git tag. Its whole point is --format: you say which fields you want and it prints exactly those, so nothing has to be parsed out of prose.

run in plumbing-lab · for-each-ref, and the star that matters
> git for-each-ref refs/tags --format="%(refname:short) %(objecttype) %(objectname:short) %(*objectname:short) %(*objecttype)"
v1.0.0 tag 1592c31 0e0dcc4 commit

> git rev-parse --short main
0e0dcc4

Read the five fields across. The ref is v1.0.0. Its object type is tag, because an annotated tag is its own object. %(objectname) is that tag object's hash. And %(*objectname), with a star, is the object the tag points at, which is the commit, and which matches main exactly.

This is the same trap as v1.0.0^{}, in a second syntax, and it is the one thing in this session most likely to bite you in a real script. A release check that reads %(objectname) for an annotated tag and compares it against a commit hash will never match, and it will fail silently rather than erroring, because both values are perfectly valid hashes. The star is the dereference. Learn the pair together: ^{} in rev-parse, and * in a for-each-ref format.

H. Why a commit hash changes, finally answered

Session 8 told you that amending a commit produces a different hash and that a commit cannot be edited. It gave the reason as "the hash is computed from everything the commit contains". That was true and it was not specific enough to act on. Now you can watch it happen, field by field.

Amend the message and nothing else, then compare the commit hash and the tree hash across the change:

run in plumbing-lab · before and after an amend
> git rev-parse HEAD
0e0dcc4b7fe2d14b5b69b9fcf1f9af18aaf5a026

> git rev-parse HEAD^{tree}
a4b0f5cc388f3552c72c8ab4dd8ddf0299cf0794

> git commit --amend -m "Update the published rate table"
[main 8a2a3cc] Update the published rate table
 Date: Sat Aug 30 19:45:27 2026 -0500
 1 file changed, 1 insertion(+), 1 deletion(-)

> git rev-parse HEAD
8a2a3cc1f4fabaf4ad7421c1dc074568d64830a1

> git rev-parse HEAD^{tree}
a4b0f5cc388f3552c72c8ab4dd8ddf0299cf0794

The commit hash changed and the tree hash did not. Not a similar tree: the identical tree, character for character. No file changed, so no blob changed, so no tree changed, and the new commit points at exactly the same snapshot the old one did. What Git built was a second commit object naming the same tree.

Read the new object and you can see which fields moved:

run in plumbing-lab · the amended commit
> git cat-file -p HEAD

Update the published rate table

Three things are the same and two are different. Same tree, same parent, same author line including its timestamp. The message changed, which you asked for. And the committer timestamp moved, from ...131 to ...141, ten seconds later, which you did not ask for and could not have prevented.

Author and committer are two different people, and Git has always tracked both. The author is whoever wrote the change; the committer is whoever put it into the repository. They differ when somebody applies a patch on your behalf, and the --author flag you have seen in earlier lab blocks sets the first without touching the second. An amend keeps the original author date, because you did not rewrite the work, and updates the committer date, because the commit object was created just now.

This corrects an intuition Session 8 could have left you with. Session 8 explained a cherry-picked commit getting a new hash by saying the parent changed, which is the usual reason and is true. But it is not the only reason, and it is not even necessary: the amend above kept the same parent and still produced a new hash, because the committer timestamp is part of the object. Two commits made a second apart with identical content, message, author and parent are still different objects.

So the rule, stated precisely enough to script against:

The top two rows are why this session could grade you on a blob hash and why ce013625... appeared on your screen and on this page. The bottom two are why no session on this track has ever graded a commit hash, and why it never will.

Put the lab back before moving on, because that amend left main pointing at a commit your tag does not. A second --amend will not undo it, since that would only build a third object. Move the branch back to the commit the tag names, which is a use for the dereferencing syntax section F just taught you:

I. The milestone: read the graph, then script a question about it

Two halves. Read the object graph by hand first, walking a ref all the way down to file content with no porcelain at any step, then write a script that answers a question you cannot answer by eye.

The script below is the shape to aim for. It lists every file in the current commit with the number of bytes Git stored for it, largest first, which is the plumbing answer to "what is big in this repository":

PowerShell · every file in HEAD, by stored size
git ls-tree -r HEAD | ForEach-Object {
  $mode, $type, $sha, $path = $_ -split '\s+', 4
  [pscustomobject]@{ Bytes = [int](git cat-file -s $sha); Path = $path }
} | Sort-Object Bytes -Descending | ForEach-Object { "{0,8}  {1}" -f $_.Bytes, $_.Path }
Git Bash / macOS / Linux · the same thing
git ls-tree -r HEAD | while read mode type sha path; do
  printf '%8s  %s\n' "$(git cat-file -s $sha)" "$path"
done | sort -rn
run in plumbing-lab · what it prints
      22  docs/guide.md
      14  rates.txt
       6  hello.txt

Read what that script is doing, because the shape generalises. ls-tree -r HEAD produces four fields per line: mode, type, hash, path. The loop splits them, hands the hash to cat-file -s to get a size, and prints the size next to the path. Every plumbing script you ever write is some version of this: one command lists object names, another command asks something about each name.

Those three sizes are reproducible and worth checking against yours. They are stored blob sizes, so they follow the top row of the table in section H. hello.txt is six bytes for the reason section D spent a page on, not five, and not the seven your file manager reports.
