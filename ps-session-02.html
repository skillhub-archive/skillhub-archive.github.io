A. The pipe: joining two commands

So far each command has worked alone: you typed it, it printed something, done. The character |, called the pipe, joins two commands: whatever the command on its left produces is handed to the command on its right, instead of being printed. On US and UK keyboards it is Shift plus the \ key. Commands joined by pipes make a pipeline, and each command in it is a stage. Only the last stage’s output reaches your screen.

Your first stage-two command is Select-Object, which picks things out of whatever it is handed. Its -First parameter takes a whole number and keeps only that many things from the start, and -Last keeps that many from the end. Here Get-Content hands over the lines of the orders file, one at a time, and Select-Object keeps the first three:

a two-stage pipeline · captured live
PS C:\Users\you\ps-lab> Get-Content data/orders.csv | Select-Object -First 3
OrderId,Date,Customer,Product,Qty,Total,Status
5001,2026-03-01,Ana Ruiz,Cast iron pan,1,34.00,shipped
5002,2026-03-01,Ben Okafor,Chef knife,2,58.00,shipped

Session 1’s Get-Content data/orders.csv -TotalCount 2 did a similar job with a parameter of Get-Content itself. The difference is that Select-Object -First works on the output of any command, which is the whole idea of a pipeline: small commands that each do one job, joined in a row. Spaces around | are optional; this workbook always puts them in, because they make a pipeline easier to read.

In BashBash has the same pipe character, for the same job: joining commands. The head command, which you run from Bash, keeps the first lines of what it is given, so this does the same job as the pipeline above, either straight from the file or through a pipe from cat: 
$ head -3 data/orders.csv
OrderId,Date,Customer,Product,Qty,Total,Status
5001,2026-03-01,Ana Ruiz,Cast iron pan,1,34.00,shipped
5002,2026-03-01,Ben Okafor,Chef knife,2,58.00,shipped
$ cat data/orders.csv | head -3
OrderId,Date,Customer,Product,Qty,Total,Status
5001,2026-03-01,Ana Ruiz,Cast iron pan,1,34.00,shipped
5002,2026-03-01,Ben Okafor,Chef knife,2,58.00,shipped
The output looks identical. What travels down the pipe is not: section B shows the difference.

B. What travels: objects, not text

In Bash, what goes down a pipe is text: characters, the same ones you would see on screen. In PowerShell, what goes down a pipe is objects. An object is one thing, such as one file, packaged with named facts about it. Each named fact is a property, and each property holds a value. A file object has more than a dozen properties; the four you use most today are:

Property
Holds
Value for notes.txt
Name
the file’s name
notes.txt
Length
its size, in bytes
40
Extension
the end of its name, from the last dot
.txt
LastWriteTime
when it was last changed
4 March 2026, 7:05 in the morning

The table that Get-ChildItem printed in Session 1, with its Mode, LastWriteTime, Length and Name columns, was not what Get-ChildItem produced. It produced file objects, and because nothing came after it, PowerShell displayed them, choosing a few properties to show as columns. Put another stage after it and that stage receives the objects themselves, with every property, whether or not it was ever shown.

Select-Object can also pick properties: give it property names, separated by commas, and it keeps only those, so the table shows just those columns:

That looks like Session 1’s -Name switch, and for names it is the same result. The difference is that -ExpandProperty works for any property, on objects from any command.

A longer name, such as System.IO.DirectoryInfo for Directory, means the value is itself another object. {get;} means you can read the property; {get;set;} means it could also be changed. Today you only read.

Objects come from every command, not just Get-ChildItem. Each line that Get-Content hands down the pipe is an object too, of the kind called System.String: a string, a piece of text. A string has one property of its own, its Length, which is the number of characters in it:

what a line of text holds · captured live
PS C:\Users\you\ps-lab> Get-Content README.txt | Get-Member -MemberType Property

----   ---------- ----------

When a pipe carries objects of more than one kind, Get-Member prints one block for each. Get-ChildItem logs hands over a folder as well as files, so piping it to Get-Member prints a block headed TypeName: System.IO.DirectoryInfo, for the archive folder, then one headed System.IO.FileInfo, for the four logs.

PowerShell adds a few properties of its own. -MemberType Property lists the properties that come with that kind of object. As objects travel, PowerShell attaches some extra ones, and Get-Member without -MemberType lists those too, under other MemberType names such as NoteProperty, CodeProperty and ScriptProperty. On a file, Mode, the column of flags in every listing, and BaseName, the name without its extension, are two of them. On a line from Get-Content, there are six NoteProperties recording where the line came from, such as PSPath, the file, and ReadCount, the line’s number in it. They work like any other property:

two added properties · captured live

Mode  BaseName Extension
----  -------- ---------
-a--- notes    .txt

Every property this session uses is in both. The full list with methods is a different length in each version too, which is why you read the names you need rather than counting the rows.

D. Sorting, then picking

Sort-Object puts the objects it receives in order by the property you name, smallest first. Add the switch -Descending to reverse it, largest first. It sorts by the property’s value whether or not that property is on screen:

sorted by size · captured live
PS C:\Users\you\ps-lab> Get-ChildItem exports -File | Sort-Object Length

    Directory: C:\Users\you\ps-lab\exports

Mode                 LastWriteTime         Length Name
----                 -------------         ------ ----
-a---            3/4/2026  7:06 AM              0 empty.tmp
-a---            3/2/2026  7:00 AM             38 report-final.csv
-a---            3/4/2026  7:05 AM             40 notes.txt
-a---            3/3/2026  7:00 AM             57 report-final-v2.csv
-a---            3/4/2026  7:00 AM             77 report-FINAL-really.csv
-a---            3/4/2026  7:10 AM           8198 inventory-dump.csv

The output is still file objects, so PowerShell displayed them the usual way. Sort first, then pick. To get the three biggest files, sort largest first and then keep the first three. Select-Object’s parameters can be used together, so -First 3 -ExpandProperty Name keeps three objects and prints just their names:

the three biggest · captured live
PS C:\Users\you\ps-lab> Get-ChildItem exports -File | Sort-Object Length -Descending |
  Select-Object -First 3 -ExpandProperty Name                                 one line, wrapped here
inventory-dump.csv
report-FINAL-really.csv
report-final-v2.csv

The order of the stages matters here. Each stage only sees what the stage before it handed over, so if Select-Object -First 3 came before the sort, it would keep whichever three files happened to arrive first, and the sort would then order just those three. In the same way, -First 1 with a list of properties, such as Select-Object -First 1 Name, Length, keeps one object and shows two of its properties.

A long pipeline can go over several lines. End a line with | and press Enter: PowerShell knows the pipeline is not finished, shows >> instead of the prompt, and waits for the next stage. Type the last stage without a | after it and press Enter. If >> is still showing after that, press Enter once more on the empty line to run it.

Numbers sort as numbers, text sorts as text. To see why that matters you need two small things. Text typed inside single quotes, such as '96', is a string, even when it looks like a number; a number typed without quotes, such as 96, is a number. And several values separated by commas go down the pipe one after another, the way Get-Alias took several names in Session 1. Given no property, Sort-Object sorts the values themselves:

the same three values, as text and as numbers · captured live
PS C:\Users\you\ps-lab> '96', '366', '147' | Sort-Object
147
366
96
PS C:\Users\you\ps-lab> 96, 366, 147 | Sort-Object
96
147
366

Text is compared one character at a time, from the left, the way a dictionary is ordered: 1 comes before 3, which comes before 9, so '96' lands last. Numbers are compared by size. Get-Member said Length is a long, a whole number, so Sort-Object Length sorts sizes as numbers without being told to. That is the first thing objects save you: every value keeps its kind.

In BashThe sort command receives text, so it compares text unless you tell it the lines are numbers with -n. (printf here just prints each number on its own line.) 
$ printf '96\n366\n147\n' | sort
147
366
96
$ printf '96\n366\n147\n' | sort -n
96
147
366
In Bash, remembering -n is your job, every time.

E. Filtering with Where-Object

Where-Object keeps the objects that pass a test and drops the rest. Its simplest form is three words after the cmdlet: a property name, a comparison operator, and a value. A comparison operator compares two values and answers True or False; PowerShell’s are written with a hyphen, like parameters:

Operator
True when the property is
Example test
-eq
equal to the value
Extension -eq '.csv'
-ne
not equal to it
Extension -ne '.csv'
-gt
greater than it
Length -gt 50
-lt
less than it
Length -lt 50
-like
a match for a wildcard pattern
Name -like 'report*'

Put text values inside single quotes, as in section D; numbers need none. -like uses the same * wildcard as Session 1’s -Filter: 'report*' means “starts with report”, and '*report*' means “has report anywhere in it”. Here are the files in exports bigger than 50 bytes:

a filter on a number · captured live
PS C:\Users\you\ps-lab> Get-ChildItem exports -File | Where-Object Length -gt 50 |
  Select-Object Name, Length                                                  one line, wrapped here

Name                    Length
----                    ------
inventory-dump.csv        8198
report-FINAL-really.csv     77
report-final-v2.csv         57

Each file object arrives at Where-Object, which asks “is your Length greater than 50?”; the three that answer True go on to the next stage. You can type a comparison on its own to see its answer. That also shows something worth knowing: PowerShell’s comparisons ignore capital letters unless you ask otherwise, by adding a c, for “case-sensitive”, to the operator:

comparisons on their own · captured live
PS C:\Users\you\ps-lab> 5 -gt 3
True
PS C:\Users\you\ps-lab> 'ERROR' -eq 'error'
True
PS C:\Users\you\ps-lab> 'ERROR' -ceq 'error'
False

So -eq treats ERROR and error as equal, and -ceq does not; -clike is the case-sensitive -like. Today you use only the plain operators. Bash works the other way round, with case-sensitive comparison as the normal kind, and so does Python, so this is worth remembering when you switch between them.

A misspelt property is not an error. If you type a property name that the objects do not have, Where-Object finds no value at all on any of them. Every object then gets the same answer to the test, so either none passes or every one does:

Length, misspelt, twice · captured live

  Select-Object -ExpandProperty Name                                          one line, wrapped here
PS C:\Users\you\ps-lab> Get-ChildItem exports -File | Where-Object Lenght -lt 50 |
  Select-Object -ExpandProperty Name                                          one line, wrapped here
empty.tmp
inventory-dump.csv
notes.txt
report-FINAL-really.csv
report-final-v2.csv
report-final.csv

No red text and no warning, either time. The first looks like “no file is that big”. The second looks like a filter that worked, until you notice an 8198-byte file in a list of files smaller than 50 bytes. When a filter returns nothing, or everything, check the property’s spelling with Get-Member before you trust the result.

F. When the object itself is the test: { $_ }

The form you just used names a property. But a line from Get-Content is a string, and the thing you want to test is the text itself, not its Length. For that, Where-Object takes a script block instead: a small piece of PowerShell inside curly braces, { }, which it runs once for every object that arrives, keeping the objects where the answer is True.

Inside the braces, $_ means “the object being tested right now”. Session 1 said that $ marks a variable, a named value PowerShell keeps; $_ is one that PowerShell fills in itself, with each object in turn. So this keeps the lines of the log that contain ERROR:

testing the text itself · captured live
PS C:\Users\you\ps-lab> Get-Content logs/web-2026-03-01.log | Where-Object { $_ -like '*ERROR*' }
2026-03-01 09:06:03 ERROR POST /checkout 500 payment timeout

Six lines went in, and $_ held each one in turn; one matched. To test a property inside a script block, put a dot and its name after $_: the dot reads a property, as .PSVersion did on $PSVersionTable in Session 1. So these two do exactly the same thing:

two spellings of one filter · both captured live
PS C:\Users\you\ps-lab> Get-ChildItem exports -File | Where-Object Length -gt 1000 |
  Select-Object -ExpandProperty Name                                          one line, wrapped here
inventory-dump.csv
PS C:\Users\you\ps-lab> Get-ChildItem exports -File | Where-Object { $_.Length -gt 1000 } |
  Select-Object -ExpandProperty Name                                          one line, wrapped here
inventory-dump.csv

Use the short form when you test one property; you will need the script block whenever the test is about the object itself, and you will see it in almost every example online, so it pays to read both.

G. Objects versus text, and why display comes last

Here is one question answered both ways: which files in exports are bigger than 50 bytes? In PowerShell you ask for the property by name. In Bash you start from ls -l, which prints one line of text per file, and pull the size out by its position: in Git Bash, where this was checked, the size is the fifth column of that text and the name the ninth. awk, a separate tool you run from Bash, picks columns out of text, where $5 means the fifth column:

the same question, two shells · both captured live
PS C:\Users\you\ps-lab> Get-ChildItem exports -File | Where-Object Length -gt 50 |
  Select-Object -ExpandProperty Name                                          one line, wrapped here
inventory-dump.csv
report-FINAL-really.csv
report-final-v2.csv
$ ls -l exports | awk '$5 > 50 {print $9}'
inventory-dump.csv
report-FINAL-really.csv
report-final-v2.csv

Same answer. What the objects save you shows up when the text stops cooperating:

  • Names, not positions. Length means the size on every system. $5 means the size only for as long as the text is laid out the way you counted.
  • Spaces in names. awk splits a line into columns wherever there are spaces. In a test folder holding a file called my report.csv, ls -l | awk '{print $9}' printed just my for it: the space had split the name into two columns. A file object’s Name is one value, spaces and all.
  • Kinds of value. As section D showed, a size stays a number and a date stays a date, so sorting and comparing work without flags you have to remember.

Bash has its own answers to each of these, and learning them is what the Linux & the Shell track, the one after this, is for. The difference is where the work goes: in Bash you take text apart, in PowerShell you ask an object for what you want.
