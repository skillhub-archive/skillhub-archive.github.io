A. How HTTP works: the request/response round trip

Every time you load a web page or an app fetches data, the same thing happens under the hood: a client (your browser, or your Python script) sends a request to a server, and the server sends back a response. That conversation runs over HTTP (HyperText Transfer Protocol), the shared language of the web. You point the request at a URL, and when a URL is specifically an address that hands back data for programs to use, we call it an endpoint.

Each request carries a method, a single word naming what you want to do. There are four you will meet constantly, and the verb tells you the intent:

  • GET, read data (fetch a user, a list of jobs). This is the one you will use most, and the default when you just want to look at something.
  • POST, create or send new data (submit a form, add a record).
  • PUT, update or replace something that already exists.
  • DELETE, remove something.

The server's reply always begins with a status code, a three-digit number that says how it went. You do not memorize all of them, you learn the families by their first digit: 2xx means success (200 OK is the classic), 4xx means your request was wrong, a client error (404 Not Found is the famous one), and 5xx means the server had a problem, not you (500 Internal Server Error). Reading the family first tells you instantly whose fault a failure is: a 4xx means fix your request, a 5xx means the server is broken and retrying later might help. (There is also 3xx for redirects, "the thing you want moved, go here instead", which you will meet less often because requests usually follows them for you.)

B. Making the call: the requests library

Doing that round trip from Python is the job of requests, the third-party package you pip installed in Session 6. You hand it a URL, it does the network call, and it hands you back a response object: one variable that bundles up everything the server said. You send a GET with requests.get(url):

import requests            # the HTTP library from Session 6

response = requests.get("https://api.github.com/users/torvalds")   # send a GET, store the reply
print(response.status_code)   # the status number -> 200
print(response.text[:40])     # the raw body as TEXT, first 40 chars: {"login":"torvalds","id":1024025,...

That response object has a few parts you will reach for every time. It helps to name each one now, because the rest of the session leans on them:

  • response.status_code, the status number itself (e.g. 200, 404).
  • response.ok, a handy boolean: True for any 2xx success, False otherwise.
  • response.raise_for_status(), a method that does nothing on success but raises an exception (Session 6) if the status was a 4xx or 5xx. A quick way to make a bad status crash loudly instead of slipping past.
  • response.text, the raw response body as a string.
  • response.json(), the body already parsed into a Python dict or list (more on this in Concept C).

The numbers in a real response (a follower count, a repo count) change over time, so do not expect an exact match: what stays constant is the shape, the set of keys, and that is what you learn to grab.

C. JSON is text until you parse it

JSON (JavaScript Object Notation) is the format almost every API speaks. It is just text arranged in a shape that maps cleanly onto Python: { } becomes a dict, [ ] becomes a list, and strings, numbers, true/false sit inside. It looks so much like a Python dict that it is easy to forget the crucial thing: what comes back from a server is a string, not a dict.

Turning that text into a real Python object is called parsing, and the json module (built into Python) does it. json.loads(text) parses a string into a dict/list ("loads" = load-from-string), and its mirror json.dumps(data) goes the other way, turning a dict or list back into a JSON string. Watch the spacing json.dumps produces, it puts a space after each colon and each comma:

import json

text = '{"city": "Reno", "temp": 72}'   # a plain STRING that happens to hold JSON
data = json.loads(text)                  # parse it into a real dict
print(data["city"])                      # now you can index by key -> Reno

back = json.dumps({"city": "Reno", "temp": 72})   # dict -> JSON string
print(back)                              # note the spaces after : and , -> {"city": "Reno", "temp": 72}

Here is the trap that catches everyone once. If you try to index the raw text by key, as if it were already a dict, Python refuses:

body = '{"temp": 72}'    # this is a STRING (exactly what response.text hands you)
print(body["temp"])      # TypeError: string indices must be integers, not 'str'

That error message is worth decoding, because it tells you exactly what went wrong: indices is just the plural of index, the position number from Session 3, so Python is saying a string can only be reached into by a number (body[0] gives the first character), never by a key like "temp". Only a dict can be indexed by a key. The fix is to parse first, then index the result: json.loads(body)["temp"] gives you 72. This is the same lesson as Session 5 ("every cell from a CSV is text, int() it before doing math") and Session 6's convert-before-use: the data shows up in one form and you have to convert it before you can use it. With requests, the shortcut response.json() does the json.loads step for you in one call, so you rarely type json.loads by hand, but knowing it is what is happening is the point.

D. Digging into nested JSON

Real responses are rarely flat. A server hands you dicts inside lists inside dicts, several layers deep. The good news: you already know how to navigate it. Drilling in is just the dict and list access from Session 3, done one step at a time, left to right. Use [key] to step into a dict and [index] to step into a list, and chain them:

data = {"results": [{"name": "Ada"}, {"name": "Linus"}]}
print(data["results"])           # the value under "results" is a LIST -> [{'name': 'Ada'}, {'name': 'Linus'}]
print(data["results"][0])        # [0] takes the first item, a dict -> {'name': 'Ada'}
print(data["results"][0]["name"]) # then ["name"] reads its field -> Ada

Read data["results"][0]["name"] as a path: into results, take the first item, read its name. Two more tools from Session 3 carry over. When a key might be missing, .get(key, default) returns the value if present or a fallback if not, instead of raising an error: data.get("count", 0). And a value keeps whatever type the JSON gave it, so a JSON string like "42" is still a string when you pull it out, and you must int() it before doing math, exactly the string trap from Session 5.

E. Query parameters, checking status first, then your milestone

Often you need to tell the endpoint what you want: search terms, a page number, a filter. Those ride along as query parameters, the ?key=value&key=value part you have seen on the end of URLs. You could glue that string together yourself, but requests does it cleanly if you pass a params= dict, and it builds the ?... for you:

import requests
# these two are equivalent; the second is easier to read and safer
response = requests.get("https://api.github.com/search/repositories?q=python")
response = requests.get("https://api.github.com/search/repositories", params={"q": "python"})

Now the habit that separates working integrations from flaky ones: getting a response object is not the same as a successful request. A 404 or a 500 still hands you a full response, but its body is an error message, not your data. So you check the status before you trust the body. Compare the naive version with the careful one:

# NAIVE: assumes it worked. On a 404 this parses an ERROR body as if it were your data
data = response.json()
print(data["places"])          # may explode or give nonsense if the request actually failed

# CAREFUL: confirm success first (2xx), then read the body
if response.ok:                # True only for a 2xx status
    data = response.json()     # safe to parse now
else:
    print("request failed:", response.status_code)   # e.g. a 4xx or 5xx

You have three ways to guard the body, use whichever fits: test response.ok, compare response.status_code == 200, or call response.raise_for_status() to turn a bad status into an exception you can try/except. And because the network itself can fail (no wifi, server down), a real call also belongs inside a try/except: requests raises requests.RequestException (the base type for all its network errors) when it cannot complete the round trip, so catching that keeps a dropped connection from crashing your script.

Your turn The milestone: call a live API and pull fields out

This is your Session 7 milestone, run for real in VS Code against a live, no-login endpoint. Write a script that: (1) imports requests; (2) GETs https://api.zippopotam.us/us/90210 inside a try/except requests.RequestException so a network error fails gracefully; (3) calls response.raise_for_status() so a bad status is caught too; (4) parses the body with response.json(); and (5) drills into the nested result to print the ZIP's place name and state (the shape you practiced in Concept D). Build it before peeking. When it runs you will have done the full round trip: request, status check, parse, navigate.

Show reference solution 
import requests             # the HTTP library you pip-installed in Session 6

url = "https://api.zippopotam.us/us/90210"   # keyless public API: a US ZIP -> place info
try:
    response = requests.get(url)             # send the GET over the network
    response.raise_for_status()              # a 4xx/5xx becomes an exception here
except requests.RequestException as e:       # network failure or bad status lands here
    print("could not reach the API:", e)
else:
    data = response.json()                   # parse the JSON body into a dict
    place = data["places"][0]                # "places" is a list; take the first entry
    print("ZIP:", data["post code"])         # -> ZIP: 90210
    print("City:", place["place name"])      # -> City: Beverly Hills
    print("State:", place["state"])          # -> State: California
