Real programs meet bad data, missing files, and the unexpected, and by default Python answers by crashing. This is the session where your scripts stop being fragile.

A. When it crashes: reading a traceback

When Python hits a problem it cannot handle, it stops the program and prints a traceback: a report of what went wrong and where. The word "traceback" is literal, it traces the chain of calls backward from the point of failure. An exception is Python's name for one of these errors (a "ValueError", a "FileNotFoundError", and so on), and an uncaught exception, one you did nothing to handle, crashes the whole program on the spot. Here is what that looks like when a script prices.py tries to turn some bad text into a number:

# prices.py
total = int("12x")         # "12x" is not a whole number, so int() cannot parse it
print(total)               # this line never runs; the program already crashed above

Run it and Python prints (your exact file path and line number will differ, that part is machine-specific):

Traceback (most recent call last):
  File "prices.py", line 2, in <module>
    total = int("12x")
ValueError: invalid literal for int() with base 10: '12x'

The trick is to read a traceback bottom-up. Beginners stare at the top and freeze, but the top lines are just the trail of where Python was. The last line is the one that matters: it names the ExceptionType (here ValueError) and a message explaining it (invalid literal for int()...). The lines just above it show the exact file and line where it blew up. So your habit becomes: jump to the bottom, read the error type and message, then look one or two lines up for the location.

You will keep meeting the same handful of built-in exception types, so it pays to recognize each by the operation that triggers it:

  • ValueError, a value is the wrong kind, e.g. int("12x") on text that is not a number.
  • ZeroDivisionError, dividing by zero, e.g. 1 / 0.
  • KeyError, asking a dict for a key it does not have, e.g. {}["k"] (dicts were Session 3).
  • IndexError, asking a list for a position past its end, e.g. [1, 2, 3][99] (only indexes 0, 1, 2 exist).
  • FileNotFoundError, opening a file that is not there, e.g. open("missing.txt").
Your turn Cause a crash on purpose

In a new file, write a single line that you know will fail, for example int("hello") or 1 / 0. Run it, then read the traceback from the bottom. Say out loud the exception type and the message. Getting comfortable reading these now means they stop being scary later.

B. Catching it: try / except

You do not have to let an exception crash the program. The try / except statement lets you attempt risky code and catch the error if it happens, so the script keeps running. Put the line that might fail inside the try block; put your response inside the except block. When the risky line raises an exception, Python abandons the rest of the try and jumps straight to except. Here is the exact same int("12x") from Concept A, first uncaught, then caught, so you can feel the difference:

# UNCAUGHT: this crashes and prints the full traceback, nothing after it runs
total = int("12x")
print("done")              # never reached

# CAUGHT: the error is handled, so the program survives and continues
try:
    total = int("12x")     # the risky line goes in the try block
except ValueError:
    print("that was not a number")   # this runs instead of crashing -> that was not a number
print("done")              # now this DOES run -> done

That is the whole idea: an uncaught exception ends the program; the same exception wrapped in try / except becomes a fork in the road you control. The program does not crash, it does the sensible thing you told it to and carries on.

Your turn Turn a crash into a message

Take a line you know can fail, int("oops") is perfect, and wrap it in try / except ValueError. In the except block, print a friendly message instead of crashing. Add a print("still running") after the whole thing and confirm it prints, that line proves your program survived.

Show reference solution 
try:
    number = int("oops")            # this raises ValueError
except ValueError:
    print("could not read a number") # handled, so no crash
print("still running")               # proof the program kept going

C. Catch the RIGHT error, plus else and finally

It is tempting to catch everything with a bare except: (or the barely-narrower except Exception:). Resist it. A catch-all swallows not just the error you expected but also bugs you did not, like a misspelled variable name, and hides them behind your friendly message so you never learn they exist. Watch how the clunky broad version quietly buries a real typo:

# BROAD and dangerous: this hides a genuine bug
try:
    total = int("50")
    print(totl)            # TYPO: "totl" does not exist, this is a real bug (NameError)
except:                    # catches EVERYTHING, including the typo
    print("something went wrong")   # you get this and never see the typo -> something went wrong

The fix is to name the specific exception you actually expect. Then an error you did not anticipate is left uncaught, and it surfaces loudly with a traceback, exactly what you want while developing:

# SPECIFIC and honest: only the expected error is caught
try:
    total = int("50x")     # the only failure we anticipate here is a bad number
except ValueError:         # catch ONLY that; a typo would still crash and show itself
    print("that is not a valid number")

Two more optional blocks round out the statement, and it helps to name what each is for. else runs only if the try block raised no exception (the "all clear" path). finally runs no matter what, error or not, which makes it the place for cleanup that must always happen. The full shape, in the order the blocks run:

try:
    n = int("5")           # this succeeds
except ValueError:
    print("bad number")    # skipped, because there was no error
else:
    print("parsed", n)     # runs because try succeeded -> parsed 5
finally:
    print("all done")      # always runs, error or not -> all done
Your turn Specific catch with a finally

Run it and note which blocks fire. Then change "42" to "42x" and run again, watch the except replace the else while finally prints both times.

finally:
    print("finished")          # runs every time

D. Raising your own errors, and a word on logging

Sometimes you are the one who should stop things, because the data is wrong in a way only your program understands (a negative price, an empty name). The raise statement lets you throw an exception yourself, on purpose, with a message that explains the problem. You pick an exception type that fits, ValueError is the usual choice for a bad value, and pass it a message:

def set_price(amount):
    if amount < 0:
        raise ValueError("price cannot be negative")   # stop here with a clear reason
    return amount

set_price(-5)              # raises the error; the caller can try/except it, or it crashes with your message

Raising is the flip side of catching: raise creates an exception, except handles one. Code that calls set_price can wrap it in try / except ValueError and read your message off the caught exception. To do that you grab the object itself with except ValueError as e (the as e part names the caught exception e). That object carries two useful things: print(e) shows its message (the text after the colon on a traceback's last line), and type(e).__name__ gives its type name as a string, e.g. "ValueError". The type name is handy when you have caught broadly with except Exception as e and want to see which exception you actually got.

Finally, a light touch of logging. When you want to note that something odd happened without stopping, the beginner reflex is print(). That works, but the standard library's logging module is better for real scripts: messages carry a severity level (INFO, WARNING, ERROR) and can be silenced or redirected to a file without deleting the lines. The easiest entry point is logging.warning() and logging.error(), drop-in upgrades from print for anything that is a problem rather than normal output:

import logging               # the logging module ships with Python
logging.warning("could not parse row 3")   # prints a WARNING line to the screen -> WARNING:root:could not parse row 3

You do not need to configure anything to start: logging.warning(...) works out of the box, and the WARNING:root: prefix tells you the severity and where it came from. Reach for it instead of print when you are recording that something went wrong.

Your turn Raise, then catch your own error

Write a function charge(amount) that raises a ValueError("amount cannot be negative") when amount is below zero, and otherwise returns amount. Then call charge(-10) inside a try / except ValueError as e and print the message with print("Error:", e).

Show reference solution 
def charge(amount):
    if amount < 0:
        raise ValueError("amount cannot be negative")   # you decide it is invalid
    return amount

try:
    print(charge(-10))
except ValueError as e:        # "as e" names the caught exception
    print("Error:", e)         # read your message off it -> Error: amount cannot be negative

E. Virtual environments & pip, then your milestone

Everything so far was Python code. This last piece is different: venv and pip are commands you type in your terminal (the shell), not inside a .py file. They are how you use third-party packages: the huge library of code other people wrote and published on PyPI (the Python Package Index) for you to install rather than write yourself. And pip itself is Python's package installer, the tool that fetches a package from PyPI and drops it into your project (the name is a self-referential joke, "pip installs packages"). It ships with Python, so you already have it.

The problem they solve: if you pip install everything into one system-wide Python, two projects that need different versions of the same package collide. A virtual environment (venv) fixes this by giving each project its own private folder of packages. A mental model that keeps the two straight: venv is the isolated room, and pip is the tool that puts packages into that room. The workflow, shown as an honest terminal transcript (what you type, and what you see back):

# 1. create a virtual environment named venv, in your project folder
python -m venv venv         # -m runs the built-in venv module; the 2nd venv is the folder name

# 2. activate it. On Windows PowerShell (Patrick's setup):
venv\Scripts\Activate.ps1
#    (on Mac/Linux it is instead:  source venv/bin/activate)
#    once active, your prompt shows the env name in front:
(venv) PS C:\projects\myapp>

# 3. install a package from PyPI into THIS environment
pip install requests
Successfully installed requests-2.32.3

# 4. record your exact versions so anyone can rebuild the setup
pip freeze > requirements.txt      # writes a list of installed packages+versions to a file

# later, on another machine, recreate everything with:
pip install -r requirements.txt

A few pieces in that transcript are worth naming, because they are new. In python -m venv venv, the -m flag means "run a module": it tells Python to find a module that ships inside it (here the built-in venv) and run that, instead of looking for a file. The word right after -m is the module's name; the last word is just the folder name you are creating, conventionally also called venv. (You will see the same -m pattern again, e.g. python -m pip ....) Step 2's Activate.ps1 is not something you write: it lives inside the folder you just made (under venv\Scripts\ on Windows, venv/bin/ on Mac/Linux), generated for you by that first command.

In step 4, pip freeze prints your installed packages with their exact version numbers, and the > beside it is a shell redirect that saves that printout into the file instead of showing it on screen ("freeze" is the metaphor: it locks the exact versions in place so the setup is reproducible). The mirror command pip install -r requirements.txt uses the -r flag, short for "read from this requirements file", to reinstall everything the file lists. So one command writes the list of versions down, the other reads it back, and like -m, both -r and > are just short options that change what the command does.

Three habits worth locking in: make a venv per project and activate it before you work; pip install the packages you need into it; and pip freeze into a requirements.txt so the setup is reproducible. Your version number after requests- may differ, and that is fine.

Your turn The milestone: fail gracefully + install and use a package

This is your Session 6 milestone, done in two halves. First, in your terminal: create a venv, activate it, and run pip install requests (the HTTP package you will use for real in Session 7). Then write a script that: (1) imports requests; (2) loops over the cells ["300", "N/A", "120"], trying to int() each into a running total but catching ValueError so a bad cell prints a friendly "skipping" note instead of crashing (this is the S5 string trap: a CSV-style cell like "N/A" is text and int() refuses it); (3) prints the total; and (4) prints requests.__version__ to prove the package really imported. Build it before peeking, this is graceful failure and the package ecosystem in one script.

Show reference solution 
import requests             # the third-party package you just pip-installed

cells = ["300", "N/A", "120"]
total = 0
for cell in cells:
    try:
        total += int(cell)                  # "N/A" is text, so int() raises ValueError
    except ValueError:
        print(f"skipping bad cell: {cell}")  # fail gracefully, keep looping -> skipping bad cell: N/A

print("Total:", total)                       # the good cells only -> Total: 420
print("requests version:", requests.__version__)  # proof the import worked (version varies)
